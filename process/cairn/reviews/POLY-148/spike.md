## 1. Check lines (command `node spikes/POLY-148/checks/run.mjs <id>`, ids handle, service, cookie, second-factor, pages)

**H, hashed handle (option 1): 14 of 14 PASS.** Predicate for each: the path's response sets `__Host-poly_handle`; `sha256(value)` is the only form in `app.session_handle`; it maps to the new session; web's `/spike/whoami` with the handle alone answers 200 for that user and session. Paths: email, magic-link, oauth-callback, second-factor-totp, totp-first-verify-rotation, refresh, and [beyond] sign-up, backup-code, two-factor-disable, change-password, passkey-sign-in, passkey-register-session; plus sign-out (the cascade kills the handle in the same transaction) and forgery (BetterAuth's cookie, `sha256` hex or base64url of a handle, or a random value is refused by web; a data-only `pg_dump` holds no plain handle, and does hold the plain BetterAuth token, which needs the auth secret to present). Rotations (first TOTP verify, disable, change-password) issue a new handle and kill the old one (seceng #14). Held sign-ins (TOTP hold, passkey hold) set no handle cookie.
Handle cookie, as set: `__Host-poly_handle=<43 chars base64url, 256 bits>; Max-Age=604800; Path=/; HttpOnly; Secure; SameSite=Lax`.
How it is built (`service/handle-plugin.ts`, 41 lines): a plugin after-hook, **last in `plugins[]`**. `dispatch.mjs` runs `options.hooks.after` first and plugin hooks after, in array order, so a hook in `options.hooks.after` runs before twoFactor's hold deletes the session and would issue a handle for a deleted session. As the last plugin it sees the final `ctx.context.newSession`. It writes through the routing pool, so inside a request transaction the row commits with the session. Every session-creating route calls `setSessionCookie`, which sets `newSession`, which is why one hook reaches all of them. **Refresh also sets `newSession`** (same session), so the hook skips a session that already has a handle row.
Findings on H:
- Refresh does not slide the handle cookie. `handleAuthRequest` calls `auth.api.getSession` itself, which extends the session row but discards its headers. The handle keeps the Max-Age from sign-in (7 d), so a session refreshed on day 6 outlives its handle cookie by 6 days. The sign-in cookie has the same shape today (the refreshing response re-issues no session cookie). Stage 2 decides: a fixed 7-day cookie, or the service re-issues the handle on refresh (a few lines in the handler, unmeasured).
- Sign-out clears the handle cookie (measured, `note`).

**S, same-origin service.** PASS: pinned-version (resolves 1.7.18), auth-source-unchanged (imports `packages/auth/src` in place), routed-as-poly_auth (the write log shows `poly_auth` inserting the session), web-serves-no-auth, service-serves-only-auth, allowlist (9 spellings 404 through Caddy, `/ok` 200), sign-up-invited (user, Person, claim all by `poly_auth` in one context-free transaction), sign-up-refused (403 `invitation_required`, no user row), two-factor-hold, web-role-reach, secret-placement.
**FAIL S.poly_auth-grants** (a measured result): `public.entity INSERT`. `provisionPerson` runs in the sign-up transaction and inserts the Person entity as the invoker, so the service needs that tenancy write grant and the `entity_insert` policy `TO poly_auth`. Plain reading: stage 2 as priced (block S, "`packages/auth` unchanged in substance") re-opens on this point. Two ways out, neither measured: (1) a definer `app.provision_person()` that `userCreateAfter` calls instead of the insert, owned by `poly_authz`, EXECUTE to `poly_auth` only; the tenancy grant then stays with the definers. (2) accept the grant, which is the one INSERT column list `(type_id, name, tax_classification, self_user_id)` plus policies.

**C, cookie scope.** PASS path-scoped: all six cookies BetterAuth set (`session_token`, `session_data`, `state`, `two_factor`, `better-auth-passkey`, `dont_remember`) carry `Path=/api/auth`, `__Secure-`, Secure, HttpOnly, SameSite=Lax. Configuration, two lines in the service: `advanced.cookiePrefix = '__Secure-better-auth'` and `advanced.defaultCookieAttributes.path = '/api/auth'` (`createCookie` honours both for every cookie, and `advanced.cookies.<name>.attributes` per cookie). PASS flows-finish: OAuth (state cookie), second-factor verify (two_factor cookie), passkey (challenge cookie), sign-out all finish when the browser sends each cookie only to `/api/auth`. In Chromium (browser item d): after a real sign-in, Chromium stored `__Secure-better-auth.session_token Path=/api/auth` and `__Host-poly_handle Path=/`; a request to web carried only `__Host-poly_handle`.
**FAIL C.capped-out-clear:** `handler.ts` builds the 30-day-cap clearing cookie by hand with `Path=/`, so a path-scoped session cookie stays in the browser (server-side the row is deleted, so the cookie is dead, but it is not cleared). One-line fix in `handler.ts` (use `c.attributes.path`); unmeasured.
**REPORT host-vs-secure (trade-off, measured and read):** `__Host-` forces `Path=/` and no Domain, so BetterAuth's session cookie would go to web too (the problem being solved). `__Secure-` allows `Path=/api/auth`, but unlike `__Host-` it does not stop a Domain attribute, so a sibling-subdomain (or `Set-Cookie` injection) cookie of the same name can shadow it; the cost is that `__Secure-` has no host-only guarantee, and the cookie is not the web-visible secret any more, because it is httpOnly and path-scoped. The handle, which web must receive, keeps `__Host-`. Net: BetterAuth's cookie moves to `__Secure-` + `Path=/api/auth`, the handle stays `__Host-` + `Path=/`.

**M, magic link and the second factor: 3 of 3 PASS** (email, magic-link, oauth-callback, for a TOTP user and a passkey-only user, with a no-second-step control that gets a session). An enrolled user signing in by magic link **is held**: no session row, no session cookie, no handle; a `two_factor` cookie for the TOTP user, a redirect to `/sign-in/second-step` for the passkey-only user. The hold works because `packages/auth` widens twoFactor's matcher to `SIGN_IN_PATHS`. This closes the open item in `comparison.md` §6; **no gap for POLY-89** from this item. Caveat: `second_step_at` and `recent_auth_at` were set by SQL.

**P, pages: REPORT.** Through Caddy `/sign-in` and `/sign-up` are served by the service stub with `default-src 'none'; style-src 'self'; script-src 'self'; img-src 'self'; connect-src 'self'; form-action 'self'; base-uri 'none'; frame-ancestors 'none'` and no `Set-Cookie`.

## 2. Browser measurements (Chromium via the repo's Playwright; `spikes/POLY-148/browser/measure.mjs`; `document.cookie` is never read)
Web's script is `page.evaluate` in web's page at `/` (same origin, under web's CSP).
- **(a) `window.open('/sign-in')`: holds.** Web's script got the sign-in page's DOM, attached an `input` listener to its password field and read the value typed by the user ("typed-secret-1"). The service's `frame-ancestors 'none'` does not apply (not framing).
- **(b) `<iframe src="/sign-in">`:** with `frame-ancestors 'none'` on the service's page the iframe is **not** reachable (stopped); control without that directive, reachable.
- **(c) service worker:** web registered `/spike/sw.js` with scope `/` (it answers its own script path with `Service-Worker-Allowed: /`) and the worker served an altered `/sign-in` to a fresh navigation: **holds.** With Caddy refusing `Service-Worker: script` (a second Caddy on 58490, `caddy/Caddyfile.sw`): registration failed (`TypeError: Failed to register a ServiceWorker`), nothing altered: **stopped.** The rule refuses every worker script on the origin; the app has none.
- **Reading:** (a) holds, so moving `/sign-in` and `/sign-up` to the service **on the same origin does not stop a persistent web compromise from capturing the passwords typed there.** Only a separate origin (for example `auth.<domain>`) does, and that changes the cookie design: `__Host-` would then be the right prefix for BetterAuth's cookie (host-only, `Path=/`), the handle would need a cookie web can read (a different host, so a handoff the spike did not build), and CORS/redirect handoffs appear. Not measured here.

## 3. Sizing: the pages (Principal decides)
1. **Pages that take a secret.** Built today: `/sign-in` (42 lines) and `/sign-up` (64 + 6 lines server). Not built yet and each takes a secret: `/sign-in/second-step` (TOTP, backup code; the hold already redirects to it), password reset (POLY-137), change password, TOTP enrolment and the step-up prompts in Settings (POLY-89, POLY-139). If only `/sign-in` and `/sign-up` move, the others stay in web and a persistent web compromise captures those secrets. Moving all of them means every secret page lives in the service.
2. **Size, moving the two built pages:** 2 pages, 106 lines of Svelte, plus the shared shell they use. The service serves static HTML and an external script, or bundles Svelte with a second Vite build (the spike's stub is 279 bytes, no Svelte). Needed from `packages/ui`: tokens and the form components the DESIGN login and sign-up screens use. About 1–2 loop-days (guess), as the architect's estimate; adding the second-step page and password reset later adds to it.
3. **DESIGN** (`docs/DESIGN/index.html`, `styled-screens/login.html` 109 lines, `sign-up.html` 123): the page shell and navigation back to the app become the service's own (no web layout, no sidebar state), the `poly-theme` cookie must be readable at the service's path (it is set by web at `Path=/`, so it is), and the "Home box on a `.local` name" rule moves with the pages. Links between the app and the sign-in pages are same-origin, so none changes.
4. **CSP and Caddy.** Web today: `kit.csp` `default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; … frame-ancestors 'none'`. The service's pages ran under `default-src 'none'; style-src 'self'; script-src 'self'; …; frame-ancestors 'none'` with **no `unsafe-inline`**: a static page, an external CSS file and an external script fit it (the stub measured the headers and the render; a script executing under `script-src 'self'` is standard CSP and not separately run). Caddy before: one upstream per host. After: `@auth path /api/auth /api/auth/* /sign-in /sign-in/* /sign-up /sign-up/*` to the service, the rest to web, and optionally `@sw header Service-Worker script` refused (`caddy/Caddyfile`, `Caddyfile.sw`). The routes are 8 lines per host.

## 4. Sizing: dev and e2e with two servers
- **Vite dev proxy.** `apps/web/vite.config.ts` has no `server.proxy`. Add `server: { proxy: { '/api/auth': service, '/sign-in': service, '/sign-up': service } }` and the same under `preview.proxy`; the service runs as `node --watch` (Node 26 strips types). About 10 lines.
- **Playwright `serve.ts`** (today: one disposable Postgres, in-process seeding through `createAuth`, `vite build` then one `vite preview`). Two servers: spawn the service (own env: `poly_auth`, the secret) before `vite preview`, with `preview.proxy` standing in for Caddy, one origin (`E2E_PORT`) so `baseURL` and `storageState` are unchanged. `webServer` can stay one command (serve.ts starts both) or become an array. Readiness: poll `/api/auth/ok` on the service and `/healthz` on web before answering. Seeding changes: the in-process `signInEmail` bypasses the service, so the seeded `storageState` must also carry the handle cookie and insert its `app.session_handle` row; the BetterAuth cookie moves to `__Secure-…` with `Path=/api/auth`. About 60–90 changed lines in `serve.ts` and the config (guess), 0.5–1 loop-day (guess); no harness change lands in POLY-148.
- **Cookies on `http://localhost`.** Measured on `http://127.0.0.1` in Chromium: `__Secure-` (Path=/api/auth) and `__Host-` cookies are stored and sent, since Chromium treats loopback as secure. Firefox and WebKit were not run (the repo's Playwright runs only Chromium); WebKit is known to refuse Secure cookies over plain HTTP on localhost (unmeasured), so a WebKit project would need `https` or a non-prefixed cookie name in dev only.

## 5. Harness deviations from production (each does not change a result)
- **Plain HTTP** on the app origin, Caddy in a container (`polycarpic-caddy:ci`, `auto_https off`), upstreams reached at `host.docker.internal`. Caddy only routes and forwards `Host` and `X-Forwarded-For`; TLS and the container boundary add nothing to cookie, hook or grant behaviour. `Secure` cookies are accepted over loopback HTTP by Chromium (item d), and the jar in the checks applies the prefix rules.
- **Rate limiting off**, `requireClientIp` false: the limiter is memory-only and independent of every item here.
- **Google's four hosts redirected** inside the service (`globalThis.fetch` rewrite) to the check-owned fake; the callback code path is BetterAuth's own.
- **`second_step_at`, `recent_auth_at`, and the grants in §1 (a)–(c)** set or added by SQL: POLY-89's definers are not built; (a) and (b) are things stage 2 must settle; (c) is the migration pricing S already names.
- **`/spike/whoami` and `app.spike_session_of_handle`** stand in for web's `enter_session` (block E); a real `enter_session` also writes the marker and returns the shell projection, which the spike does not build.
- **The service's cookie config** (the two lines in §1 C) and **the handle plugin** are the only additions to `@poly/auth`'s options; `S.auth-source-unchanged` confirms the source is the shipped one.
