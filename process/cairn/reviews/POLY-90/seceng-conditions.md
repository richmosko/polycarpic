# POLY-90 — seceng conditions (written before the ruling)

Inputs read: POLY-90 and its comments; ARCH §3.1 (entity, invitation rows), §3.1b, §3.1c; SECURITY C-01, C-03, C-05, C-28, R-22, R-23; POLY-62 ruling and verdict (O1, N3, the poly_govern standing condition); migrations 0003, 0006–0008, 0013 (seat_claimed_invitations, sync_second_step, require_second_step_for_role); packages/auth user-hooks.ts and route-policy.ts; definers.json. POLY-62's F1 is quoted in POLY-90's last criterion; no separate F3 record is in the tree, so nothing here depends on it.

Each condition: **what must be true**, **attack stopped**, **test that proves it**, **wrong build that still passes a weaker test**.

## 0. Facts of the current tree that the design must answer

- **K1. A second owner can already arrive through a path the gate does not see.** `app.seat_claimed_invitations()` (poly_govern, called from `sync_second_step` at first enrolment) INSERTs an owner or manager membership. `gate_owner_changes` exempts poly_govern and is not on membership INSERT; nothing locks the entity or counts owners there. Today a sole owner can issue direct owner invitations, add a co-owner, and the pre-issued invitees still seat as owners at enrolment: the A-24 hole is live, not future.
- **K2. seat_claimed_invitations locks invitation rows before any entity row.** Every other membership guard locks the entity first. Two orders on the same pair of rows is a deadlock waiting for the revocation to add the second lock.
- **K3. `app.owner_count` is caller-relative** (null to a non-member). Fine for the gate, wrong for any check that must hold whoever commits.
- **K4. No held raise exists yet** (POLY-91): a raise for an unenrolled member is refused (`second_step_required`), so today role = 'owner' is the only owner. **No user tombstone write exists yet** (POLY-114/115).
- **K5. `invitation_govern_update` is `WITH CHECK (claimed_user_id = app.current_user_id())`** and poly_govern has no UPDATE on `revoked_at`. A revocation run by a poly_govern definer will hit this; the tempting fix (`WITH CHECK (true)`) widens every poly_govern definer's write.

## 1. Founder column and its deferred constraint trigger

- **F-1 Written once, by the database.** `founding_owner_user_id` is set from `app.current_user_id()` by the insert path (trigger overwrites whatever is supplied), FK `user(id)` ON DELETE NO ACTION. No login role (poly_app, poly_auth, poly_worker, poly_operator) holds INSERT or UPDATE on the column; poly_app's column-exact INSERT grant on entity is unchanged. *Stops:* a creator naming someone else (or a victim) founder, or an owner rewriting it to take force_change. *Test:* catalog — `has_column_privilege` false for INSERT and UPDATE for every login role; behaviour — poly_app INSERT naming the column → 42501; UPDATE → 42501; stored value equals the creator. *Wrong build passing a weak test:* grants the column and relies on the trigger overwrite; "stored value = creator" alone passes, the catalog assertion does not.
- **F-2 A Person's founder is its user.** CHECK `self_user_id IS NULL OR founding_owner_user_id = self_user_id`. *Stops:* any future transfer path or the operator `set-founder` CLI moving a Person's founder away from its user (which would let a co-owner of a shared Person become founder and force-remove the user). *Test:* superuser UPDATE of a Person's founder to another owner → 23514 with the constraint name.
- **F-3 Backfill before NOT NULL.** Existing entities take the user of their earliest `membership.created` audit row (falling back to the earliest owner row, then `self_user_id`); the migration refuses (raises) if any live entity resolves to none, rather than picking arbitrarily. *Test:* migration test on a seeded pre-0022 database: each entity's founder is the seated creator.
- **F-4 The deferred check reads state, not the triggering row, and is caller-independent.** Constraint trigger `DEFERRABLE INITIALLY DEFERRED`, AFTER INSERT OR UPDATE OF founding_owner_user_id ON entity and AFTER UPDATE OF role OR DELETE ON membership. At commit it re-reads the entity's current founder and whether that user holds a membership with role = 'owner'. It is a SECURITY DEFINER owned by a NOLOGIN role (poly_authz: read-only is enough), `search_path = ''`, EXECUTE to no role, on definers.json — never an invoker function (it would run as whatever role commits and read membership through that role's RLS: false refusals for poly_auth/operator, false passes if a policy ever hides the row) and never `app.owner_count` (K3: a founder who just deleted their own row is a non-member at commit, count null). No row for the entity → refuse, never pass. *Stops:* the founder dropping owner without a transfer; a check that silently passes for some committing role. *Tests:* (a) two owners A (founder), B: A lowers own role → the statement succeeds, COMMIT fails with the trigger's SQLSTATE and message; (b) A demotes then re-promotes in one transaction → commits (state, not row); (c) same as (a) committed as poly_auth-context and as superuser → refused. *Wrong build:* checks `NEW.role` immediately in a plain trigger — passes (a) but fails (b); invoker version passes (a) as poly_app, fails (c).
- **F-5 No role exemption.** Not poly_govern, not poly_purge, not superuser. Purged entities are skipped by state (`purged_at IS NOT NULL`), never by role. *Stops:* the later tombstone/purge or apply_change path (both poly_govern/poly_purge, exempt from the gate) removing a founder silently. *Test:* superuser deletes the founder's owner row on a two-owner entity → refused at commit. *Wrong build:* copies the gate's exemption list; every poly_app test passes.
- **F-6 Tombstone shape (for the architect to rule).** The entity tombstone is id-only (`entity_tombstone_check`). Either the founder column joins it (`(purged_at IS NULL) = (founding_owner_user_id IS NOT NULL)`), or the ruling says why the user link survives the purge. ARCH's bare "NOT NULL" contradicts the id-only tombstone; I prefer the first.
- **F-7 No transfer path unless it ships whole.** If `app.transfer_founder` is not in this loop, nothing can change the founder (F-1 holds). If it is: caller is the founder, target holds role = 'owner' now, entity row FOR UPDATE first, step-up within 5 minutes checked in the database, refused on a Person (F-2), audit + notice to every owner, EXECUTE to poly_app only.

## 2. `invitation.issued_via` not updatable; revoked tokens refused at acceptance

- **I-1 Not updatable by any role, owner included.** Column grants already deny it to login roles; add a BEFORE UPDATE refusal (or extend `invitation_set_once`) so even poly_owner/superuser cannot change it, and extend the `tenancy_column_updatable` battery to name the column. poly_app's INSERT column list stays without `issued_via` (default 'owner'). *Stops:* an owner relabelling a direct row as 'operator' (or, later, attaching a `change_request_id`) to dodge the 1 → 2 revocation. *Tests:* poly_app UPDATE → 42501 (privilege); superuser UPDATE → the trigger's SQLSTATE and message; poly_app INSERT naming `issued_via` → 42501. *Wrong build:* grants only — the poly_app test passes, the superuser case does not.
- **I-2 If `change_request_id` arrives in this loop**, no login role may write it (FK to change_request, written only by apply_change). Otherwise a sole owner stamps pre-issued invitations with any request id and they survive the transition. If it does not arrive, POLY-112 carries this condition.
- **I-3 Every acceptance step refuses a revoked row, by re-reading under its lock.** Three readers: `claim_invitations`, `accept_invitations`, `seat_claimed_invitations`. All filter `revoked_at IS NULL` in the `FOR UPDATE` query today; the condition is that it stays in the locked query (READ COMMITTED re-checks it on the new row version), never in an earlier unlocked read. *Tests:* (a) revoke, then sign up with the token → `invitation_required`; (b) claim at sign-up, revoke, then enrol → no membership, `accepted_at` stays null; (c) concurrency: revoke in T1 (held open), enrol in T2 blocks, T1 commits, T2 commits with no seat. *Wrong build:* checks revocation in TypeScript before calling the definer — (a) passes through the route, (b) and (c) fail.

## 3. The 1 → 2 revocation (A-24, C-28)

- **V-1 One trigger, every writer.** AFTER INSERT OR UPDATE OF role ON membership, FOR EACH ROW, not deferred, firing for every role (poly_app raise, poly_govern seat, later apply_change and the POLY-91 promotion, superuser). Never a call the paths must remember. *Stops:* K1 — the seat path today, and each future path that makes an owner. *Test:* the seat case: sole owner A issues a direct owner invitation X to I and a direct one Y to J; I claims; A raises enrolled member M to owner → X and Y revoked; I enrols → no owner seat. *Wrong build:* revocation called from the raise path only — the raise test passes, the "second owner arrives by enrolment" test (below) fails.
- **V-2 Fires on "an owner was added and the entity now has ≥ 2 owners"**, not "= 2". Count read after the write (AFTER ROW sees it), with role = 'owner' only. *Stops:* a one-statement 1 → 3 (multi-row insert) and a 2 → 1 → 2 cycle skipping it. *Tests:* superuser seats two owners in one INSERT on a sole-owner entity with a direct invitation outstanding → revoked; drop back to one owner, issue a new direct invitation, add an owner → revoked (ARCH's case). *Wrong build:* `= 2` passes the ARCH cases, fails the multi-row one.
- **V-3 Lock, then count, with a count nobody can null.** The trigger itself takes `entity FOR UPDATE` (no row → 42501) before counting; it does not rely on the gate's lock (the gate is not on INSERT and exempts poly_govern). The count is a poly_authz definer that is not caller-relative (K3) or treats null as "revoke"; never `IF app.owner_count(e) >= 2` where null skips. *Stops:* a revocation skipped because the writer is a definer or operator context with no membership. *Test:* the superuser seat case above (no user in context) revokes.
- **V-4 One lock order: entity row before invitation rows, everywhere.** `seat_claimed_invitations` takes each target entity FOR UPDATE, in entity-id order, before its invitation `FOR UPDATE` (K2). No `SKIP LOCKED` or `NOWAIT` in the revocation. *Stops:* (a) a deadlock that aborts a legitimate enrolment (the passkey or TOTP registration fails); (b) the "fix" for that deadlock, SKIP LOCKED, which ends with three owners. *Test (ARCH's concurrency case, sharpened):* sole owner A; direct owner invitations X→I, Y→J, both claimed; I and J enrol concurrently with a barrier holding T1 after its insert. Assert: both transactions COMMIT (no 40P01, no 40001 under the default READ COMMITTED), exactly two owners, one of X/Y accepted and the other revoked, the loser enrolled with no seat. *Wrong build:* lock in the trigger only — ends with two owners via a deadlock abort, so "exactly two owners" passes; the "both commit" assertion fails. SKIP LOCKED — passes "both commit", fails "two owners".
- **V-5 Scope of the UPDATE.** Same entity; `issued_via = 'owner'`; `revoked_at IS NULL AND accepted_at IS NULL`, **claimed or not, expired or not** (seat ignores expiry, so an expired claimed row still seats); excluding the invitation the current write is consuming. *Tests:* claimed-and-expired direct owner row is revoked and does not seat; an accepted row, another entity's row and an operator row are untouched. *Wrong build:* `claimed_at IS NULL` or `expires_at > now()` — the ARCH "outstanding invitation" case passes, the claimed or expired case fails.
- **V-6 Narrow privilege (K5 and the POLY-62 standing condition).** The revocation is a poly_govern SECURITY DEFINER, `search_path = ''`, EXECUTE to no role (trigger only), on definers.json. poly_govern gains UPDATE (`revoked_at`) only, through a new policy whose WITH CHECK requires `revoked_at IS NOT NULL` and `issued_via = 'owner'`; `invitation_govern_update` is not loosened. It writes one `invitation.revoked` audit row per row and the inviter's notification (payload: invitation id and entity id, no email). *Test:* poly_app/poly_auth/poly_worker EXECUTE → 42501; catalog test that `invitation_govern_update`'s WITH CHECK is unchanged; audit row count equals revoked count.
- **V-7 Effective owners only.** Counting role = 'owner' satisfies it today (K4). Carried as conditions: **POLY-91** — the promotion is a membership UPDATE of role, so it fires V-1; tests: a held owner raise does not revoke, its promotion does. **POLY-166** — if "effective owner" comes to exclude an unenrolled owner, the gate's count and V-2's count are one function and move together.

## 4. User tombstone check

- **T-1 The guard sits on the tombstone write, in the database.** No tombstone write exists in this loop (K4). An uncalled `app.can_tombstone(uuid)` is not a control and its test proves nothing about the path. My position: the founder trigger (F-4, F-5) is the structural check — a tombstone that deletes the founder's owner row on an entity with another owner fails at commit — and this loop proves it with F-5's test. The explicit early refusal ("you found X, transfer first", all entities locked in id order before the check) is a condition on **POLY-115**, along with: memberships are removed through the ordinary triggers, no exemption from the founder check, no `session_replication_role`. If the architect instead adds the tombstone marker column now, it must be writable by no login role and carry this guard as a BEFORE UPDATE trigger, tested on that write.

## 5. Self-Person owner row (F1)

- **P-1 Immediate refusal with its own message.** BEFORE UPDATE OR DELETE ON membership: when `OLD.role = 'owner'` and the entity's `self_user_id = OLD.user_id` and (DELETE or `NEW.role <> 'owner'`) → 23514, own message. Reads `self_user_id` through a definer or a grant every firing role holds; no row → refuse. No role exemption in this loop (POLY-114/115 add the narrowest one with their purge path). *Stops:* share Person → demote self → removed → `provisionPerson` fails on every request (a self-inflicted or co-owner-driven lockout). *Tests:* A's Person with owners A and B (B seated by superuser): A demotes self → 23514 **with P-1's message, at the statement**; A deletes own row → same; superuser does either → same; positives: B lowers own role → succeeds; A removes a viewer → succeeds. *Wrong builds:* (1) no P-1 at all, tested on a sole-owner Person — `keep_an_owner` raises 23514 too, so a SQLSTATE-only assertion passes; hence two owners and the message. (2) relying on the founder trigger (F-2 makes the user founder) — fails only at COMMIT; hence "at the statement".

## 7. R-22 and R-23

- **R-22 (leaked link):** nothing more in this loop beyond I-3. Existing-user acceptance (the POLY-87 follow-up placed here) is not in POLY-90's criteria and has no route yet; it belongs to **POLY-129** (its criterion "an owner invites an existing user as viewer; once accepted"). Condition there: the signed-in session's user accepts with the token and an explicit consent action; never an email match alone; the acceptance definer locks the entity first and inherits V-1 by being a membership write.
- **R-23 (IdP-minted address): the row's mitigation is weaker than written.** "A manager or owner invitation seats only after a second step is enrolled" does not stop the attacker R-23 names: whoever controls the address enrols their own second step and is seated as owner. Exposure today is nil (the only shipped issuer is the operator CLI, viewer-only, entity-less), and it opens when POLY-129 ships owner-issued manager/owner invitations. Condition on **POLY-129**: a token-less claim (`/callback/:id`, `/magic-link/verify`) claims viewer rows only; a manager or owner row needs the token on every path. Cost: an invited manager/owner signs up through the emailed link (password, or OAuth once the callback carries the token). This is a **for-the-lead** item (it changes an approved risk's text); I write no risk row until the lead answers.
