1. Targets & Topology

Ruled order (Principal, 2026-11-06): a Hetzner VPS, then a local-network box, then Vercel + Neon. ARCH §7 says what each is; SECURITY C-70 to C-77 say why it is built this way; this document says how to stand it up and run it. The three are deployment targets of one application, not three architectures.

1.1 Reading this document as the operator

  • You are one person running one instance for your own household (PRD §3). Nothing here is written for hosting other people, and nothing here makes that safe (SECURITY R-6).
  • If you only read two sections, read §7 (to stand it up) and §8 (to keep it alive). Everything else is the reasoning behind them.
  • Terms: the box is the machine running the containers; the operator is you; a digest is the exact fingerprint of one build of the app image (sha256:…); compose is the tool that starts the containers listed in compose.yml.

Who may reach itBrowsers on the LAN only (C-76). No inbound path from the internet exists: the router forwards nothing, UPnP and NAT-PMP are off, the host drops inbound IPv6, and nftables allows 443 (80 redirects) and SSH from the LAN CIDR only. Away from home there is no access in v1.
Outbound allowlistDNS, NTP and TCP 443 only (C-76). Consequence found here: an SFTP upload to a Hetzner Storage Box uses port 22 or 23 and is blocked, which is one reason §9 rules the backup destination to an S3-compatible bucket over 443 on every target.
DNSReal-domain mode (default): the name is polycarpic.home.<domain>, defined only on the LAN (router DNS override, or one hosts-file line per device). There is no public A or AAAA record for it. The public zone holds only short-lived _acme-challenge TXT records written by Caddy. .local mode: the name is polycarpic.local, answered by mDNS or the same LAN DNS override.
TLSTwo modes selected by TLS_MODE (§3.4): real-domain (DNS-01 wildcard from a public ACME issuer) or private-ca (name-constrained operator CA). The app refuses to start on a mismatch (ARCH §7.8, SECURITY C-76).
Third partiesSame as §1.2 minus nothing; all are outbound over 443. OAuth sign-in works in real-domain mode and is disabled server-side in private-CA mode. A verification email link only opens from the LAN.
HardwareAny x86-64 mini PC or small server with a TPM 2.0, UEFI Secure Boot, 8 GB RAM or more, a 256 GB or larger SSD, and wired Ethernet. Put it on a small UPS. Buying advice is in §7.2 step 1.

Compose mounts each file as a secrets: entry at /run/secrets/<name> into only the containers listed in §2.2. 3.3 SSH, GitHub token, signing

  • Operator SSH. One ed25519 key per laptop, listed in ~/.ssh/authorized_keys of a non-root sudo user polyops. Root login and password auth are off. Adding or removing a laptop is §8.8. Hetzner's console is the break-glass path if you lose every key.
  • The box's GitHub credential (ARCH §8.1). A fine-grained personal access token, this repository only, contents:read and packages:read, expiry 90 days, stored as github_read_token and used only by the deploy script. If the package and repository become public, delete it. Renewal is §8.4. A reminder is set 14 days before expiry by the same outside monitor (§6.5).
  • Release signing. The prod tag is accepted only if its SSH signature verifies against /etc/polycarpic/allowed_signers. That file is installed at bootstrap from your own machine, not fetched from the repository: a copy pulled from the repo would be forgeable by whoever can push to it (ruling D-5, re-fold R-3).
  • Image trust. gh attestation verify pins the repository and the signer workflow .github/workflows/build.yml (§4.4).

3.5 Home-box disk unlock (TPM)

LUKS2 with two key slots: a TPM2 slot sealed to Secure Boot state (PCR 7), and a long recovery passphrase kept offline. Use PCR 7 only by default. Adding PCR 11 (the kernel image) makes every kernel update change the measurement and leave the box locked after the automatic reboot, unless the distribution ships signed PCR policies; whether Ubuntu 24.04 does is unmeasured and is a first-deploy measurement (SECURITY C-72 already marks PCR 11 per-distro). Firmware checklist, console hardening and verification are in §7.3 step 4.

3.6 The recovery sheet

One printed page, kept somewhere that survives a house fire, listing: where the password manager's emergency kit is; the age private key (as the AGE-SECRET-KEY-… line); the credential keyring offline copy; the LUKS recovery passphrase; the private CA root key (private-CA mode). The age key and the keyring are written on separate lines of separate sheets and never in the same file; a lost keyring costs a relink (RB-4), a lost age key costs every backup (§6.1). Nothing on the sheet is stored on the box or in a backup.

4.3 Which jobs run on which paths

Workflows follow the pattern already proven in .github/workflows/ci.yml: no workflow-level paths: filter on anything that is a required check (a required check whose workflow never starts blocks the merge forever); the filter is a changes step inside the job and every later step is gated on it, failing closed. Inside the app, Turborepo's affected graph narrows the work to touched packages.

4.4 Build, scan, attest, deploy (pull-based)

  1. Build once. build.yml runs on every push to main: pnpm install --frozen-lockfile with lifecycle scripts blocked (C-80), build the one adapter-node image, push to GHCR tagged with the git sha, record the digest.
  2. Scan and attest. Trivy on the image (fail on fixable critical or high and on embedded secrets, C-82); CycloneDX SBOM; actions/attest-build-provenance for the digest. The same step builds and attests the custom Caddy image and the tools image.
  3. Release. When /merge-pr pushes a signed v1.* tag, release.yml looks up the digest already built for that commit (never rebuilds), checks that its attestation exists, and publishes a GitHub Release whose body is one line, digest: sha256:…. If no image exists for the tagged commit the workflow fails and nothing deploys.
  4. The box polls. A systemd timer runs polycarpic-deploy every 5 minutes (with 60 s jitter) under flock, so two runs never overlap. Staging: newest main digest from GHCR. Prod: newest v1.* release from the Releases API.
  5. Verify, then act. If the digest equals current-digest, exit. Otherwise: pull by digest; gh attestation verify --repo richmosko/polycarpic --signer-workflow .github/workflows/build.yml; for prod also git verify-tag against /etc/polycarpic/allowed_signers and a check that the tag's commit is the one the digest was built from (the image carries its commit as a label, also covered by the attestation). Any failure: log, alert, stop. The box never runs an unverified image.
  6. Extract the ops bundle (compose files, Caddyfile, scripts) from the verified image into /opt/polycarpic/releases/<digest>/, so the compose definitions are covered by the same attestation as the code.
  7. Pre-migration check, then the migration (§4.5), docker compose up -d for the project, then poll /api/v1/health for up to 120 seconds.
  8. Result. Healthy: write current-digest, log the deploy, ping the monitor. Unhealthy: automatic rollback (§4.6) and an alert.

Not changing during a deploy: secrets (placed by you, never by CI), the deploy script itself and the timer unit. Those change by an operator step (polycarpic-ops self-update, §8.7) that runs the same verification on a newer release, because a script that rewrites itself from the network is the supply-chain path this design exists to close.

4.5 Migration deployment mechanism

The tool is the one the POLY-76 spike ratifies (Drizzle Kit recommended, ARCH §6.2). Whichever tool wins, the mechanism below is fixed because it follows from the spike's constraints.

  • One-off container, not app startup. The migrate service (same image, migrate entrypoint) connects as poly_migrator, the only login that may run DDL, and runs each file as set role poly_owner … reset role so objects are owned by the NOLOGIN owner and FORCE RLS holds. web and worker never get the migrator password and refuse to start if the schema version is behind the image.
  • Definers and policies. SECURITY DEFINER functions are created owned by their role (poly_authz, poly_purge, and so on) and policies target roles with to:; the DB battery proves both through the same runner on every PR, so a migration that works only for a superuser cannot reach the box.
  • Order. check-config (secrets present, TLS_MODE, PLAID_ENV) → migrate --plan (lists pending files, exits) → if any are pending, a pre-migration backup (a pg_dump encrypted to the age public key, uploaded like any backup, plus kept in the local spool for 7 days) → migrate under an advisory lock → up -d.
  • Failure. Each file runs in a transaction, so a failed file leaves the schema as it was. The deploy stops, the old containers keep running on the old digest, and an alert is sent. Nothing is rolled forward by hand.
  • Expand and contract. A release only ever adds (columns, tables, nullable fields, new functions). A removal ships at least one release after the code that used the thing is gone. Therefore the previous release's code always runs on the new schema, which is what makes rollback a one-file change.
  • Vercel and Neon. The same migrate entrypoint runs in the Vercel build step against Neon's direct endpoint; the runtime uses the pooled one (§1.4, D-6).

4.6 Rollback

  • Automatic. If health does not pass in 120 seconds after up -d, the script points desired-digest back at current-digest, restarts that release's containers from its own ops bundle, writes the failure to deploy.log and alerts. The failed digest is recorded in /opt/polycarpic/quarantine and skipped by the poll until a newer one appears.
  • Manual, one command. polycarpic-ops rollback reverts to the previous digest recorded in deploy.log without contacting GitHub, then keeps the poll from re-deploying the newer release by quarantining it. §8.6 has the steps.
  • Schema. A code rollback never needs a schema rollback (expand-contract). A schema-level undo is the restore path (§6.8), starting from the pre-migration backup.
  • Brief interruption. up -d recreates web, so for a few seconds Caddy has no healthy upstream; Caddy retries for 10 seconds (lb_try_duration) which hides it for most requests. ARCH §8.1's "keeps routing to the last healthy containers" is not literally achievable with a plain recreate on one box; v1 accepts the few seconds (re-fold R-4).

4.7 Vercel path

Vercel builds on the signed tag through its Git integration, with the topology checks of ARCH §7.6 run first in GitHub Actions on every PR touching routes or project config. The Vercel environment-variable names check uses a read-scoped Vercel token held as a GitHub environment secret with required reviewers; it reads names, never values. No deployment credential for Vercel lives in GitHub. A failed migration step fails the build and Vercel keeps serving the previous deployment.

6. Disaster Recovery & Monitoring

Resolves ARCH OQ-9 detail and OQ-26; ruled in §9 (D-1 to D-4). In plain terms: backups are locked with a key that never lives on the server, stored where the server cannot delete them, and proven by restoring them somewhere else once a month.

6.1 What is backed up and how

flowchart LR
  pg[("Postgres prod")] --> base["Nightly: pg_basebackup plus pg_dump plus globals"]
  pg --> wal["Continuous: WAL segments, archive_timeout 5 min"]
  base --> enc["age encrypt to public key"]
  wal --> enc
  enc --> spool["Local spool, LUKS volume"]
  spool --> up["rclone put-only, HTTPS 443"]
  up --> bucket[("Object-lock bucket, 35 days")]
  bucket -.->|"read credential, operator laptop"| drill["Monthly restore drill"]
  priv["age PRIVATE key: password manager and printed sheet"] -.-> drill
  • Nightly (02:15). Three artifacts, each encrypted on the box to the age recipient before it leaves: (1) a pg_basebackup tar of the cluster, the base for point-in-time recovery; (2) a pg_dump --format=custom of the database, the portable fallback that restores onto any Postgres of the same or a newer major; (3) pg_dumpall --globals-only, which carries the roles (poly_owner, poly_app and the rest) that a per-database dump omits. A restore without (3) comes up without its RLS roles, so the drill checks for it.
  • Continuous. Postgres archive_command copies each WAL segment to the spool; a one-minute timer encrypts and uploads it; archive_timeout = 300 forces a segment at least every 5 minutes, so the worst case loss is about 5 minutes plus upload delay, inside the 15-minute RPO.
  • Correction to ARCH §7.2. WAL replay needs a physical base backup; a pg_dump alone cannot be the base for WAL. The nightly set above adds pg_basebackup (re-fold R-5). Physical restore needs the same Postgres major, so the image's major is pinned and recorded in each backup's name.
  • Not backed up, by design: the credential keyring (SECURITY §6.4: losing it means relinking), the secrets directory, staging's database, the age private key. Anything in the secrets directory is recreated from the password manager and provider consoles (§8.9).
  • Where. An S3-compatible bucket with Object Lock in compliance mode and a 35-day default retention, written by a put-only credential over HTTPS 443 (works on every target, including the home box's outbound allowlist). The store, not the box, enforces that nothing can be deleted or overwritten before 35 days. The box credential cannot shorten retention or delete versions. This replaces the Storage Box default (ruling D-3): a Storage Box "append-only" mode is unmeasured and its SFTP port is blocked on the home box. A Storage Box remains a documented fallback on the Hetzner target once its cannot-delete drill passes. Provider: Principal question Q3.

6.2 Naming and integrity

Objects are named <instance>/<pgmajor>/<yyyy>/<mm>/<dd>/<kind>-<utc-timestamp>.age with a .sha256 sibling written after the upload. The backup job fails, and alerts, if a listed object does not match its recorded checksum after upload. The age private key never appears in any path or log.

6.3 Retention (SECURITY R-5)

Everything in the bucket expires 35 days after it is written and the store allows nothing earlier. So a purged entity's data can remain in backups for at most 35 days after the purge; the purge confirmation screen should say "up to 35 days" (re-fold S-3). There is no long-term archive tier in v1: if you need a yearly keepsake, export from the app (the export carries the hash-chain head) and keep it yourself. Lifecycle expiry is a bucket rule, so no deletion credential exists anywhere.

6.5 Monitoring, heartbeat and alert routing

  • Two independent alert paths, so one failure never silences both. Path A: the app and host scripts email you through Resend (SECURITY §9 list, plus backup, deploy and certificate events). Path B: an outside monitor that does not depend on the box or Resend: a free-tier dead-man's-switch service (Principal question Q4; recommendation: Healthchecks.io). The box pings it, and silence past the grace period emails you.
  • What pings Path B. (1) Every 5 minutes, only if local /api/v1/health is OK and the served certificate's issuer matches TLS_MODE (C-76); (2) after each successful backup upload; (3) after each successful deploy poll. Grace: 15 minutes, 26 hours and 20 minutes respectively. The ping carries no data. On the Hetzner target the same service also checks the public URL from outside.
  • Health endpoint exposure (re-fold R-6). Public /api/v1/health returns only ok or not. The detailed fields ARCH §7.4 lists (last migration, last backup time) are served on the loopback-only admin listener and read by the host scripts, so a stranger learns nothing about backup cadence.
  • Alerts that need no new service: spool older than 2 hours; backup older than 26 hours; certificate under 14 days; disk over 80 percent; deploy failed or rolled back; unattended-upgrades pending reboot for more than 3 days; GitHub token under 14 days; ledger hash-chain break (SEV1) or a verifier silent for 8 days. All thresholds are provisional and tuned after POLY-M1.
  • Logs. JSON to stdout, Docker json-file rotation, 30 days on the box (SECURITY §9). The operator's query surface is docker compose logs and journalctl. No log service in v1.
  • The dashboard the lead can point to: the monitor's check list (green or red per box) plus polycarpic-ops status, which prints the running digest, last deploy, last backup, certificate days left and disk use on one screen.

6.6 Vercel + Neon backups (answers OQ-26)

  • A cron function cannot run pg_dump or ship WAL, so the Compose mechanism does not apply.
  • Default (v1.0, no new trust): rely on Neon's point-in-time restore for the plan in use (window unmeasured; read it on the plan page at deploy time and record it here), and run polycarpic-ops neon-export from the operator's laptop weekly: pg_dump through a read-only role, age-encrypted to the same public key, uploaded with the put-only credential to the same bucket. RPO is then up to 7 days beyond Neon's window, stated honestly.
  • Recommended before real data lands on this target: a nightly GitHub Actions export. It needs a database role that can read every ledger row to live in a GitHub environment secret, which makes GitHub a holder of a ledger-read credential (TB-12). That is a SecEng ruling and a Principal acceptance, not a devops default. Until then the default stands. Recorded as OQ-INFRA-1.
  • Restore: create a Neon project, run polycarpic-ops restore --dump from the laptop (§8.10), repoint the Vercel variables, redeploy.

6.7 The restore drill (a GA gate)

Monthly, scripted, and run off the box: your laptop or a throwaway server, never the VPS, because the age private key must never reach it (ARCH §7.2). The first passing drill against real backup objects is a gate for v1.0 (DECISIONS 2026-11-06); a drill that has not run in 45 days raises an issue and an email.

  1. List the bucket with the read credential; take the newest base backup and WAL.
  2. Decrypt with the age private key from the password manager.
  3. Start a scratch Postgres at the recorded major; restore the globals, then recover to the latest WAL; separately restore the pg_dump into a second scratch instance.
  4. Assert: the trial balance of every entity sums to zero; the per-entity hash-chain verifier passes (C-24); the roles from the globals file exist; the latest journal entry is within 20 minutes of the drill's start for the WAL path.
  5. Assert, using the box credential file copied for the drill, that deleting an existing object fails and so does shortening its retention (C-73's second test).
  6. Record date, backup names, timings and pass or fail in process/cairn/reviews/restore-drill-<date>.md via the lead (not edited by hand on the box). Destroy the scratch instances.
