1. Targets & Topology

Order: a Hetzner VPS, then a local-network box, then Vercel + Neon. ARCH §7 says what each is; SECURITY C-70 to C-77 say why it is built this way; this document says how to stand it up and run it. The three are deployment targets of one application, not three architectures.

1.1 Reading this document as the operator

  • You are one person running one instance for your own household (PRD §3). Nothing here is written for hosting other people, and nothing here makes that safe (SECURITY R-6).
  • If you only read two sections, read §7 (to stand it up) and §8 (to keep it alive). Everything else is the reasoning behind them.
  • Terms: the box is the machine running the containers; the operator is you; a digest is the exact fingerprint of one build of the app image (sha256:…); compose is the tool that starts the containers listed in compose.yml.

HardwareAny x86-64 mini PC or small server with a TPM 2.0, UEFI Secure Boot, 8 GB RAM or more, a 256 GB or larger SSD, and wired Ethernet. Put it on a small UPS. Buying advice is in §7.2 step 1.

How the two halves hand over. backup writes each artifact into spool/dump/.inflight/ (or spool/premigration/.inflight/) through age, so plaintext never reaches disk, and publishes all or nothing: only after the base, the dump and the globals file have all succeeded does it ln the three into spool/dump/, and on any failure it removes its own temporaries and publishes nothing. Postgres's archive_command does the same for WAL into spool/wal/. The uploader mounts the spool read-only and can read a file but not change, create or delete one; it uploads each file and its .sha256 sibling and prints verified <dir> <name> <sha256>. Root acts on that report (polycarpic-ops upload): it accepts a line only for a known directory and a name that matches the spool grammar, opens the file without following a link, recomputes the sha256, and only when it equals the reported value (and, for dump/ and premigration/, the record root wrote after the backup) deletes the file or, in premigration/, writes the .sha256 sibling that marks it uploaded. Neither container can do the other's job: backup has no route out and no bucket key; uploader has no database credential, no route to Postgres and no write to the spool. Nothing outside these two containers reads or writes the spool except root on the host.

Planned total caps are about 7.85 GB (including the 128 MB uploader and the two auth services at 256 MB and 192 MB) for a prod+staging host that is never fully busy at once; the host keeps the remainder. Unmeasured. If docker stats after POLY-M1 shows the caps are hit, raise the plan size before raising a cap.

  • Only caddy has a ports: mapping. Caddy listens on 8080 and 8443 inside the container (no NET_BIND_SERVICE under cap_drop: [ALL]); ports: maps ${POLY_BIND_ADDR:?}:80:8080 and ${POLY_BIND_ADDR:?}:443:8443. POLY_BIND_ADDR has no default, so a missing value fails the render instead of binding 0.0.0.0; on the local box it is the LAN address.
  • Caddy reads three operator values from its environment, all required: POLY_DOMAIN (sites app.<domain> and staging.<domain>), POLY_STAGING_ALLOW (the staging remote_ip allowlist) and POLY_TLS (the ACME account email on a real host; internal only in tests). A missing value fails the render rather than starting Caddy with an unparsable Caddyfile.
  • backup-net's gateway, the host, lies inside the /29 that pg_hba.conf admits for poly_backup. Host root is already trusted, so this is accepted.
  • The one-off services (migrate, backup, uploader) sit behind compose profiles and use restart: "no"; every long-running service uses unless-stopped.
  • Every container: non-root user, read_only: true with named tmpfs for writable paths, cap_drop: [ALL], security_opt: [no-new-privileges:true], restart: unless-stopped, a healthcheck. No Docker socket is mounted anywhere.
  • The compose-policy lint (C-70) is a CI job that parses the rendered config (docker compose config) and fails on any violation of the list above, any secret in environment:, any ports: outside caddy, or any service on both project networks. C-79 adds: only backup and postgres are on backup-net; backup-net is internal: true with a fixed subnet equal to the one in pg_hba.conf; only backup mounts db_password_backup; only uploader mounts backup_store_credential; uploader is on no network that postgres is on.
  • The compose-policy lint also enforces, for the backup path: every prod and staging service sets ulimits: {core: 0} (rule core-dump); backup and uploader have a /tmp tmpfs of at most 1 MiB (tmp-size); no service mounts /var/lib/polycarpic/state or a parent of it (state-mount) or anything under secrets/host/ (host-secrets); the uploader mounts the spool read-only and nothing else writable (uploader-spool-ro).
  • Postgres runs with the C-75 settings from a mounted postgresql.conf fragment: log_parameter_max_length = 0, log_parameter_max_length_on_error = 0, log_statement = 'ddl', plus archive_mode = on, archive_timeout = 300 and an archive_command that encrypts each segment with age straight into spool/wal/ (§6.1). C-79 adds: max_replication_slots = 2, max_wal_senders = 3, max_slot_wal_keep_size = 2GB (unmeasured, tuned with OQ-INFRA-5) so a slot can never fill the disk, log_connections = on, and password_encryption = scram-sha-256. The image job starts the real postgres service of prod.yml (same mounts and command, no -c flags) and runs SHOW on each, checks pg_settings.sourcefile is the mounted fragment, and checks ALTER SYSTEM is refused; provision-check runs SHOW on the deployed server.

3.5 Home-box disk unlock (TPM)

The home box has one LUKS2 container holding an LVM volume group; / and /srv/polycarpic are logical volumes in it (SECURITY C-72, T-85). One container means one unlock, one TPM binding and one recovery passphrase, so the box still restarts unattended. The container has two key slots: a TPM2 slot sealed to the Secure Boot state (PCR 7), and a long recovery passphrase kept offline. Use PCR 7 only by default. Adding PCR 11 (the kernel image) makes every kernel update change the measurement and leave the box locked after the automatic reboot, unless the distribution ships signed PCR policies; whether Ubuntu 24.04 does is unmeasured (OQ-INFRA-2).

  • Method (unmeasured, OQ-INFRA-10). Ubuntu's default initramfs cannot unlock from a TPM by itself. Two candidates, tried in this order at the first home-box deploy: (A) the installer's encrypted LVM layout plus clevis-luks with the tpm2 pin on PCR 7 and clevis-initramfs; (B) dracut in place of initramfs-tools, with systemd-cryptenroll --tpm2-pcrs=7. The first method that passes every check in §7.2 steps 6 and 7 is recorded here. If neither passes, stop and return to SecEng and the Principal; no fallback is chosen here.
  • What stays unencrypted: the EFI partition and /boot (kernel and initramfs). Someone with an hour and the box can rebuild an unsigned initramfs there; that residual is accepted (T-85) unless OQ-INFRA-2 finds a way to measure it.
  • Consequence you must know: with root encrypted the box has no network until it is unlocked, so a failed unlock waits at a console prompt and SSH cannot reach it. Recovery is a keyboard, a monitor and the recovery passphrase (§8.9). Until the unattended-reboot checks of §7.2 step 6 pass, automatic reboots stay off on this box and you reboot it yourself in the monthly window (§8.2).

Firmware checklist, console hardening and verification are in §7.2.

3.6 The recovery sheet

One printed page, kept somewhere that survives a house fire, listing: where your secret store's emergency kit is; the age private key (as the AGE-SECRET-KEY-… line); the credential keyring offline copy; the LUKS recovery passphrase; the private CA root key (private-CA mode). The age key and the keyring are written on separate lines of separate sheets and never in the same file; a lost keyring costs a relink (RB-4), a lost age key costs every backup (§6.1). Nothing on the sheet is stored on the box or in a backup.

4.4 Build, scan, attest, deploy (pull-based)

  1. Build once. build.yml runs on every push to main and on the weekly schedule, on main only. A siblings job builds, pushes, scans with Trivy and attests the Postgres, tools and Caddy images, each carrying the commit as org.opencontainers.image.revision. A read-only release-lint job writes its own images.env from the sibling digests, installs from the frozen lockfile with lifecycle scripts blocked (C-80) and runs the compose-policy lint, because the lint needs npm packages and no job that can push or attest installs any. The app job needs both, writes its own infra/release/images.env from the sibling job outputs, builds the one adapter-node image with infra/release/images.env inside it, pushes it, and records the digest. The app's attestation therefore covers the three sibling digests.
  2. Scan and attest. Trivy on each image (fail on fixable critical or high and on embedded secrets, C-82), a CycloneDX SBOM of the app, and actions/attest-build-provenance for every digest. The weekly release-scan scans the newest v1.* Release's app digest and the three siblings frozen with it.
  3. The runtime image carries no package manager. npm, npx, corepack, pnpm and yarn do not resolve on PATH, /usr/local/lib/node_modules is absent, and the image runs as node (non-root; apt and dpkg remain in the slim base and are acceptable only because of that). infra/ci/image.sh check asserts it on the built image in the PR image job and in build.yml, before the scan.
  4. Release. When /merge-pr pushes a signed v1.* tag, release.yml looks up the digest already built for that commit (never rebuilds), checks that its attestation exists, and publishes a GitHub Release whose body is one line, digest: sha256:…. If no image exists for the tagged commit the workflow fails and nothing deploys. The lookup finds a digest only while that commit's image-<commit> artifact exists, which is 90 days after its main build. A re-run of an old workflow run keeps the original commit; to release an older commit, merge a new commit and tag that.
  5. The box polls. polycarpic-deploy@<project>.timer fires every 5 minutes (60 s jitter) and runs polycarpic-ops deploy <project> under one flock shared by both projects, because both can touch the shared edge. A busy run exits 0 and logs busy. Staging takes the latest successful build.yml run on main (event push or schedule) and its image-<commit> artifact. Prod takes the highest semver among the non-draft, non-prerelease v1.* Releases whose body is exactly one digest: line, never the newest by date. Every value from GitHub is matched against a fixed pattern first.
  6. Verify, then act. A digest equal to current ends the run; a quarantined one ends it quietly. For prod the tag is fetched into a bare repository and its SSH signature checked against allowed_signers; its direct target must be a commit, and the tag object's name, the ref and the Release must agree. The tag's commit, or the staging run's head_sha, is C. Then, in this order and each a named refusal: gh attestation verify with --repo richmosko/polycarpic --signer-workflow richmosko/polycarpic/.github/workflows/build.yml --source-ref refs/heads/main --deny-self-hosted-runners --source-digest C --predicate-type https://slsa.dev/provenance/v1 before any pull (the source digest comes from the certificate GitHub issues, not from anything the build writes); docker pull by digest; the revision label equals C; the bundle; each sibling image through the same attestation, pull and label checks at the same C; the Postgres major equals current's; and the compose guard. Prod must also be newer than current; staging's C must be current's commit or descend from it, so an old run replayed is refused not-newer. A downgrade happens only through rollback. Nothing with a candidate digest is created, run or composed before all of this passes. A refusal is logged, raises the alert and (for the signature, name, label, bundle, sibling-label, Postgres-major and guard refusals) quarantines the digest. A GitHub or network failure, or a failed pull, is logged as transient, raises no alert, quarantines nothing and is retried at the next poll; a lasting outage shows in status as last-poll older than an hour.
  7. The bundle is data. docker create (never started), docker cp of /release/infra, docker rm. The image build assembles /release/infra from the same fixed manifest the host accepts (a missing file fails the build), copies it root-owned and read-only into the runtime stage, and writes an all-zero images.env only where no real one exists (a pull request or local build; the host refuses an all-zero digest). The tar is read at most 64 MiB plus one byte while streaming and refused above 64 MiB, above 512 members, with a name over 200 characters, with pax headers, links, devices, FIFOs, set-id bits, absolute or .. paths, or any path outside the fixed manifest. The files are extracted, and the sibling images checked, into a private .incoming-* directory under releases/; only when every member is accepted is it renamed to releases/sha256-<digest>/ (root 0755 or 0644), and a tree hash is recorded. An existing sha256-<digest> is used only if it is root-owned, not group- or world-writable and its tree hash equals the incoming one, else the refusal release-tree (alert, no quarantine); it is never rewritten. A run removes only a directory it renamed itself, and only when no current or previous of prod, staging or edge names it; an unreadable pointer counts as naming every release, so nothing is removed. A leftover .incoming-* is removed at the start of the next run. Pruning a release removes its saved render and no other. The host executes nothing from a release: a release path appears in a command only as config's -f, --env-file or --project-directory. Every compose up carries --pull never --no-build; compose run carries --pull never (it has no --no-build) and the guard refuses any build key.
  8. The guard. The installed code and policy (infra/deploy/compose-allow.json, shipped by install.sh, never read from a release) judge the rendered configuration of the release before any of it runs, and again on current's before it is touched and on previous's before a rollback. It reads a raw and a plain render. Every render runs with no network and no privilege: unshare --net -- setpriv --reuid 10020 --regid 10020 --clear-groups --no-new-privs -- docker compose … config, as polycarpic-render (uid and gid 10020, no shell, no home, no other group, used by nothing else; provision.sh --stage host creates it and provision-check.sh check H23 asserts uid, gid, shell, groups and that every process of that uid is a docker or docker-compose executable whose arguments hold compose and config), with HOME and XDG_CACHE_HOME an empty root-owned directory and both COMPOSE_EXPERIMENTAL_*_REMOTE flags 0. A remote include therefore cannot be fetched and fails as guard-render; a missing or altered render user is the refusal render-user (exit 4, nothing touched). Compose's JSON drops a zero ulimits.core to {}; the guard writes it back as 0 only where the policy pins it at zero, and any other empty object where a number belongs is guard-render. The corrected plain JSON is what is judged, and it is saved as state/deploy/<project>/render-<12 hex of the digest>.json (root 0600, written to a temp file and renamed, no link followed, mounted by nothing, never logged or sent), the render is judged and rendered once more from the corrected bytes on stdin under the same isolation, and the two must be equal (guard-render), all in memory; only then is it saved, beside render-<12 hex>.sha256. up and run compare the file's sha256 with the guard's in-memory record, and a miss is unjudged; backup, upload, cli and a rollback's reuse of the saved file compare it with the sidecar, and a miss is state (in a rollback, the rule below). A rollback needs no disk write: it renders and judges in memory, and when the corrected bytes equal the saved file and its hash, up names the saved file and nothing is written. Only when they differ is it saved; if that save fails, the saved pair is used when its hash holds and its bytes, read back through the isolated stdin render, pass the guard now, else rollback-unhealthy. The guard returns a record of project, digest, saved file and its sha256 that only it can construct. Every up, run, exec and ps with files, the rollbacks, the edge and backup, upload and cli name only that file with -f, after its sha256 is re-read, and the edge's up takes that record and the digest it is about to start; a mismatch is the refusal unjudged (alert, no quarantine, Caddy untouched). With a current and no saved render, backup, upload and cli refuse state and never fall back to a bundle's compose file. A service's plain environment holds no key beyond its raw one plus the keys of its listed env_files (guard-env), and a bind mount carrying any option block on the plain render is refused (guard-mount). The caller's directory decides nothing: every child of the tool runs with its working directory at /, and every compose call it builds (config, up, run, exec, ps, restart, including backup, upload, cli and status) names --project-directory (the render home for stdin, a saved render and calls with no file; a bundle file's own directory for a render or the no-release fallback) and an explicit --env-file (/dev/null where none is ruled), because Compose otherwise reads a .env in the caller's directory, takes values from it and turns profiles on. A .env in the render home is the refusal render-path. provision.sh, provision-check.sh and gate-check.sh change to / and name both options too. web, auth, worker and migrate each name their command (command: ["<service>"]); for every service of the three files the command and the entrypoint are the exact value the policy and the compose lint name or absent (missing or null in Compose's JSON), since the image's own default is web, which the worker would otherwise have run. With no current, right after Postgres is healthy and before any backup or one-off, the tool asks the container's local socket whether the login poly_migrator exists: 0 is roles-missing (the provision command, exit 4, no quarantine, nothing started), 1 goes on, anything else is roles-read (alert, no quarantine); a missing role looks exactly like a wrong password to migrate --plan, so the answer is never inferred from it. provision.sh --stage database first creates the database polycarpic (TEMPLATE template0) when pg_database does not list it (both statements fixed text over the local socket on database postgres; a failed read stops), then runs roles.sql. One Compose version is used for every render, judgement and start: the exact N.N.N in infra/deploy/compose-version of the installed ops bundle. provision.sh --stage host installs docker-compose-plugin at exactly that version from Docker's repository and holds that package alone (engine, containerd and runc stay free to take fixes); a newer or held plugin is brought to the version, a version the repository does not list stops, and a newer one is never taken. provision-check.sh H25 fails unless docker compose version --short equals the file both as root and as the render user with its own HOME, the package comes from download.docker.com and is held, and nothing sits in /root/.docker/cli-plugins. deploy, first-deploy and edge-deploy compare both answers before any network call; a difference, an unreadable file or a failing command is the refusal render-env (alert, no quarantine, exit 1), with both versions on stderr and the fix named. A rollback warns and goes on, because the guard still judges what it renders and refusing would take the way back away. CI installs the same version from the same file. When a render fails, guard-render says why: one line on stderr and in deploy.log under the event render-error, giving the stage (raw, plain or stdin), the exit code or timeout, and then text from the release, not an instruction: and Compose's last stderr line, cleaned and cut to 300 bytes (never stdout); the alert, status and POLY-103 carry the name only, and no install command is printed, since a wider policy is not its fix. The installed bundle's own compose file of the project is then rendered the same way with fixed placeholder image values (never the candidate's images.env): if that fails too, or either render timed out, the refusal is render-env (alert, no quarantine, tried again at the next poll), else guard-render quarantines. A service, key, mount, network, secret file, env_file or published port that the policy does not name is refused (guard-service, -key, -pinned, -image, -name, -mount, -file, -env, -network, -ports), and logging, ulimits, mem_limit and tmpfs must equal the policy's pinned values. Every image must be one of the four just verified. When current's own render is refused, the name is current-guard-<rule> (alert, no quarantine of the candidate). Changing the policy needs an operator install.sh; a release that needs a new mount, service or network is refused until then. When the guard refuses a candidate, the alert, deploy.log and status carry one fixed text and nothing from the bundle: the refusal name, a review command chain for the laptop (ending in echo 'review: on main' and, for prod, echo 'review: tag signed'), and infra/ops/install.sh <target> --ssh-key <file> --commit <C>. Go on to the install only if each review command printed its review: line, and compare the command with this runbook first: root on the box can print any text. --commit ships C's files with no checkout, because a checkout would run C's tracked git hooks on the laptop; it refuses a C that is not an ancestor of origin/main, before any ssh. The CI lint stays the full check on every pull request; the guard is narrower and is the trust boundary, because staging has no human gate.
  9. Order of a run. (prod only: current's Postgres is started from current's bundle if it is down; then polycarpic-ops backup premigration, whose premigration-set line goes into deploy.log verbatim, before any candidate container holds a credential; then the backup lock, held to the end.) check-config for migrate, web, auth and worker; migrate --plan (0: nothing to apply; 3: apply; 2: plan-diverged); migrate (exit 1 or 2 quarantines and leaves the running containers untouched; 4 does not quarantine); up -d; then up to 120 seconds of health polling. first-deploy skips the backup, which a first deploy has nothing to back up, and refuses with existing-data (exit 4) when the project's Postgres directory is not empty. Two ways through: the project's own earlier attempt (with an empty directory and no current, first-deploy writes first-attempt before it starts Postgres and removes it when healthy, so a rerun after roles-missing proceeds; it skips the backup only while there is no current and the project's database, read over the container's local socket, holds no table outside the system schemas, and a table or a failed read makes the backup required), and --existing-data, which makes the backup required. With no release yet, the backup renders the ops bundle's prod.yml with an all-zero placeholder digest for the app and tools images, which only satisfies ${…:?} and cannot be pulled. The timer's deploy refuses with not-first-deployed while the project has no current.
  10. Healthy. Every long-running service of the project is running, healthy and on the image the release names, and web answers HTTP 200 on its health route (the status code only; a compromised container can still answer 200, so this is liveness, not security). Healthy: current becomes previous, the new release is current, the <project>-current link and (prod) /opt/polycarpic/images.env follow, older bundles are pruned and the alert clears. On prod in real-domain mode, except on the first deploy, https://app.<domain>/api/v1/health is also asked through Caddy (at POLY_BIND_ADDR, that name as SNI, full certificate verification, no redirect followed, 10 s), once as a baseline before the project's up. A baseline of 200 makes 200 required in the health poll and after a rollback; any other baseline logs and alerts edge-probe-baseline, even when healthy, and the probe is not required, so an unrelated certificate or network fault never quarantines a good release. Unhealthy: §4.6.
  11. The shared edge. Caddy, edge.yml and the Caddyfile come from a signed prod release and are rendered and brought up only by a prod run, as the compose project polycarpic-edge; both renders are judged before either up, and rollback restores edge. Before any prod release exists, polycarpic-ops edge-deploy edge-<n> brings Caddy up alone from a signed edge-<n> tag (prod still accepts only v1.*, and edge-deploy only edge-<n>): the ownership checks (prod has no current, a damaged one counting as present, and no polycarpic-prod container is listed, a failed listing counting as one) are read after the deploy lock is held; n must rise; the tag, signature, attestation, bundle and siblings are verified as for prod; only the edge render is guarded; only Caddy is started, and an unhealthy Caddy is quarantined and edge's previous release comes back after its guard. State is under state/deploy/edge/, shown by status as edge until prod has a current. Prod takes over once: its first deploy must be at edge's commit or descend from it (edge-older otherwise), and if that first deploy fails after upping Caddy, Caddy goes back to edge's current. A staging run renders no edge.yml and issues no argument naming the edge project, edge.yml or caddy, on any host. The two edge networks, polycarpic-edge-prod (10.201.30.0/28) and polycarpic-edge-staging (10.202.30.0/28, driver bridge), are created by provision.sh --stage host and declared external in all three compose files; the lint keeps both subnets outside every pg_hba allow range and the 10.200.0.0/16 pool.

Not changing during a deploy: secrets (placed by you, never by CI), the operator tool, the guard and its policy, and the units. Those change only by infra/ops/install.sh from a reviewed checkout (§7.1 step 6), because code that rewrites itself from the network is the supply-chain path this design exists to close.

Failure handling. Every shared directory (/opt/polycarpic, releases, state/deploy, the project's state directory and the render home) is made and kept exactly root 0755 by one helper that sets the mode with chmod, whatever the umask; a root-owned directory that is too tight (0700, 0750) is repaired, opened without following a link; one with any bit beyond 0755, a link, another owner or a non-directory is the refusal render-path (rollback-unhealthy inside a rollback), left as found, and the bad path is named on stderr and in deploy.log. provision.sh stops on those too, where it would otherwise change an owner, and provision-check.sh H24 names the path. Before any render, every path the render names (the bundle's compose file, images.env, the env files) must be root-owned, the file o+r and every parent o+x; a miss is render-path (alert, no quarantine, tried again at the next poll). provision.sh --stage host creates /opt/polycarpic, releases and state/deploy and provision-check.sh H24 asserts them. From the candidate's first up (the shared edge's included) every exit that is not healthy, refusals included, goes through one unwind: the old release is restored first; then the quarantine, the log line, the alert and the removal of in-progress are each written in their own try, in that order, none able to stop the next; the alert is also written to stderr and the exit is never 0. in-progress is removed only after the quarantine line is on disk, so a failed write leaves the next run to treat the digest as interrupted. A manual rollback restores before it quarantines and writes its pointers after the restore; a failed pointer write is reported with exit 1 and the old release up. A refusal alerts first, then logs, then quarantines, each in its own try. A run takes one compose ps and carries its answer; a failed or unparsable one stops it with ps (alert, no quarantine), and with a current Postgres starts only from current's judged render. A one-off is gone only when docker inspect exits non-zero and says No such object or No such container; anything else is re-checked every 5 seconds for 60 seconds with the locks held, then oneoff-stuck. Each health child's timeout is worked out just before it starts, so six slow children cannot push the rollback past the window. A health child that times out, dies or prints non-UTF-8 counts as not healthy (each child's timeout is the lesser of 30 seconds and what is left of the 120). One handler wraps deploy, edge-deploy and rollback: any other exception before the candidate's first up is the refusal internal (alert, exit 1, no quarantine); after it, the automatic rollback runs with internal logged; inside a rollback it is rollback-unhealthy. A run that finds in-progress left behind alerts interrupted and tries that digest again once; the same digest interrupted twice is quarantined with reason interrupted, and interrupted is removed when another digest is tried or becomes healthy. A transient outage run by hand (first-deploy, edge-deploy) exits 1 with the cause on stderr and no alert; the timer keeps exit 0. transient-since holds the first of an unbroken run of transient outcomes and is removed by any run that gets past verification or finds nothing new; older than an hour, the alert is transient-stale. Every deploy, first-deploy, edge-deploy and rollback first requires /srv/polycarpic to be a mount point of its own device: otherwise data-mount (exit 4, nothing touched, first-attempt not written). Before any network call, a prod run and edge-deploy read edge.env: unreadable or missing a key is edge-env. Rollback of any kind, automatic, manual or edge, first checks that the release directory is root-owned and not group- or world-writable, parents included. A one-off container (check-config, migrate) is named polycarpic-<project>-<service>; a stale one is removed first; on a timeout it is removed with docker rm -f and docker inspect must show it gone before any lock is released, else oneoff-stuck (alert, quarantine, exit 1; a later run refuses while it exists). migrate's client timeout is 30 minutes, above the runner's 10-minute lock wait; a timeout is migrate-timeout and quarantines.

The record. /var/lib/polycarpic/state/deploy/<project>/ holds current and previous (one line: digest, tag or -, commit, tree hash, time), quarantine (digest, time, reason; a guard-<rule> or current-guard-<rule> line adds the installed ops bundle id), first-attempt (while a first deploy is unfinished), in-progress (the candidate's digest from before its first up to the end of the run), interrupted (a digest whose run did not finish), transient-since, the saved render-*.json files, deploy.log (time, event, fields; a closed set of events), alert (one line, present from any stop or rollback until the next healthy run), last-poll and token-expiry. All are written by root, none is mounted by a container. Only a missing file is absent: any other read error on current, previous, quarantine, first-attempt, in-progress or interrupted, and any malformed content, stops the run with state (exit 1, no quarantine, the file never rewritten from a partial read). A pointer has five fields, all validated for its project: digest, tag (v1.* for prod, edge-<n> for edge, - for staging), commit, a 64-hex tree hash and a UTC time YYYY-MM-DDTHH:MM:SSZ; a tree that cannot be hashed is release-tree. A guard-<rule> quarantine lifts only when the stored and the installed bundle ids are both well-formed and differ and the digest has no other reason: after install.sh installs another bundle the next poll judges the digest again in full. Every other reason holds for good; there is no clear command, and the fix is a new digest. The CI lint refuses any Caddyfile line outside a fixed per-block allowlist (caddy-allow), so a Caddyfile change always carries a lint change. status shows deploy per project (red while alert exists, warning when GitHub was not read for an hour) and token.

4.5 Migration deployment mechanism

The tool is the one the POLY-76 spike ratifies (Drizzle Kit recommended, ARCH §6.2). Whichever tool wins, the mechanism below is fixed because it follows from the spike's constraints.

  • One-off container, not app startup. The migrate service (same image, migrate entrypoint) connects as poly_migrator, the only login that may run DDL, and runs each file as set role poly_owner … reset role so objects are owned by the NOLOGIN owner and FORCE RLS holds. The migrate module is the one place a session-level SET ROLE is allowed (a dedicated connection, closed after the run, never pooled; ARCH §2.1); a custom file that switches to another definer owner ends on SET ROLE poly_owner. Drizzle Kit is the runner (POLY-76, ARCH §6.2). web and worker never get the migrator password and refuse to start if the schema version is behind the image.
  • Who owns what in the database (POLY-76, ARCH §6.2). provision.sh makes poly_owner the owner of the database; poly_owner creates the drizzle tracking schema and drizzle.__drizzle_migrations (it is the active role when the first file runs). poly_owner is NOLOGIN NOBYPASSRLS and poly_migrator is its only member, granted WITH INHERIT FALSE, SET TRUE so it holds none of poly_owner's privileges until it runs SET ROLE (the run is proven to end as poly_owner because only poly_owner may insert tracking rows; with inherited privileges a RESET ROLE would pass as poly_migrator; SECURITY C-85). The grant carries no ADMIN option, and no role other than poly_owner holds INSERT, UPDATE, DELETE or TRUNCATE on the tracking table. poly_migrator owns no object (SECURITY C-85; a catalog test over pg_class, pg_proc, pg_namespace, pg_type is POLY-83's). poly_migrator is proposed to hold no database CREATE of its own: target, unmeasured, because the spike granted both; POLY-83 measures it, and until then provisioning must not be written to depend on either answer. poly_app and poly_worker get USAGE on drizzle and SELECT on the tracking table, nothing more; that is all the "schema behind image" start check needs. Neon gets the same grants from the first migration. provision.sh runs packages/db/sql/roles.sql as the superuser, per database; that file also revokes plpgsql from PUBLIC and grants it back to the definer owners only, and revokes EXECUTE from PUBLIC on the 17 built-ins that run a SQL string they are given (query_to_xml and its family, ts_stat, ts_rewrite(tsquery,text)). It is idempotent, and the same file is re-run after every restore and every major Postgres upgrade (§8.10, §5).
  • Definers and policies. SECURITY DEFINER functions are created owned by their role (poly_authz, poly_purge, and so on) and policies target roles with to:; the DB battery proves both through the same runner on every PR, so a migration that works only for a superuser cannot reach the box.
  • Order. On prod, first a pre-migration backup taken before any candidate container holds a credential (§4.4). Then check-config (secrets present, TLS_MODE, PLAID_ENV) → migrate --plan (lists pending files, exits) → if any are pending, the pre-migration backup described here (the backup container runs pg_dump --format=custom as poly_backup through the same age pipe as the nightly set into spool/premigration/; the uploader ships it like any backup; it stays in the spool 7 days; no other dump path exists, C-79) → migrate (takes pg_advisory_lock on its connection before running, so a second concurrent run waits and applies nothing; and refuses, as does migrate --plan, when the applied rows in drizzle.__drizzle_migrations are not a hash-for-hash prefix of the journal, or when poly_backup holds anything beyond what roles.sql grants it: exit 2, backup-acl) → up -d.
  • Failure. All pending migrations run in one transaction (drizzle-orm 0.45.4 behaviour, read from source), so a failing file leaves the tracking table and the schema as they were. Consequence: no CREATE INDEX CONCURRENTLY in a migration (a CI check refuses it). CI also refuses a journal whose when values are not strictly increasing, because the runner would silently skip a migration older than one already applied (ARCH §6.2, POLY-83). Unmeasured until POLY-83 and POLY-100 run it. The deploy stops, the old containers keep running on the old digest, and an alert is sent. Nothing is rolled forward by hand.
  • Expand and contract. A release only ever adds (columns, tables, nullable fields, new functions). A removal ships at least one release after the code that used the thing is gone. Therefore the previous release's code always runs on the new schema, which is what makes rollback a one-file change.
  • Vercel and Neon. The same migrate entrypoint runs in the Vercel build step against Neon's direct endpoint; the runtime uses the pooled one (§1.4, D-6).

4.6 Rollback

  • Automatic. If health does not pass within 120 seconds after up -d, the digest is quarantined and current's release is brought back up from its own bundle, after its tree hash is re-checked and the guard has judged its render, and health is polled again. When the run's project owns the edge (§4.4), the same is done for Caddy: the edge render is judged first and Caddy comes back on that release's image; both renders are judged before either up. A Caddy that starts and routes wrongly passes its caddy version health check and needs the manual rollback. Healthy: rolled-back and an alert. Unhealthy, or no previous release (a first deploy): rollback-unhealthy and an alert, and nothing else is changed. A rollback never migrates. The poll skips a quarantined digest without alerting again.
  • Manual, one command. polycarpic-ops rollback <project> makes no GitHub call: it quarantines current, re-checks previous's tree hash, runs the guard on its render and brings it up from releases/. §8.6 has the steps.
  • Schema. A code rollback never needs a schema rollback (expand-contract). A schema-level undo is the restore path (§6.8), starting from the pre-migration backup, restored off the box (§6.4).
  • Brief interruption. up -d recreates web, so for a few seconds Caddy has no healthy upstream; Caddy retries for 10 seconds (lb_try_duration) which hides it for most requests. ARCH §8.1's "keeps routing to the last healthy containers" is not literally achievable with a plain recreate on one box; v1 accepts the few seconds.

4.7 Vercel path

The operator deploys a verified signed tag with infra/vercel/deploy.sh (D-11), after the topology checks of ARCH §7.6 which run in GitHub Actions on every PR touching routes or project config. The Vercel environment-variable names check uses a read-scoped Vercel token held as a GitHub environment secret with required reviewers; it reads names, never values. No deployment credential for Vercel lives in GitHub. A failed migration step fails the build and Vercel keeps serving the previous deployment.

It then writes three artifacts as poly_backup (SECURITY C-79) into spool/dump/.inflight/, each ending in age to the recipient public key, so plaintext never reaches the spool: (1) base: pg_basebackup -Ft -X none -c fast -D - | gzip -1 | age, a tar of the cluster, the base for point-in-time recovery (-X none because pg_basebackup cannot stream WAL in tar mode to stdout; the archived WAL covers the backup window, and no replication slot is left behind: measured on the scratch stack, where the base recovered with the archived WAL and the row inserted after the base was present after recovery); (2) dump: pg_dump -Fc | age, the portable fallback that restores onto any Postgres of the same or a newer major (the custom format is already compressed); (3) globals: pg_dumpall --globals-only --no-role-passwords -l polycarpic | gzip -1 | age, which carries the roles (poly_owner, poly_app and the rest) that a per-database dump omits, without password hashes (restored logins get new passwords from your secret store). A restore without (3) comes up without its RLS roles, so the drill checks for it. Names are <kind>-<major>-<system id>-<UTC timestamp>.age; the system id comes from IDENTIFY_SYSTEM over the replication connection, so a cluster re-created by a fresh initdb never collides with the old one's names (§6.2). The last stdout line on success is published dump <TS> <sys> <base> <dump> <globals>. Postgres's archive_command (archive-wal.sh) compresses each WAL segment with gzip -1 and encrypts it with age (public key from the mounted config; exactly one recipient, as for the nightly set) into spool/wal/.inflight/, syncs, links it to spool/wal/wal-<major>-<system id>-<segment>.age and removes the temporary, returning failure if the target already exists. The system id is read with pg_controldata from the data directory the command runs in. The history forms Postgres hands the command are archived the same way (…<segment>.<offset>.backup, ….partial, <timeline>.history). Compression is what keeps the bucket inside its 10 GB cap: every segment is 16 MiB, and lightly used ones compress to about 81 KB. The uploader runs every minute and ships what it finds. archive_timeout = 300 forces a segment at least every 5 minutes while the database is active, so the worst case loss is about 5 minutes plus upload delay, inside the 15-minute RPO. If the spool volume fills, archiving fails and Postgres keeps WAL: the 2-hour spool alert and the disk alert (§6.5) are what catch it. A crash after the link but before Postgres records the segment makes the retry fail on the existing target until root has removed the shipped file; the retry then uploads a second version of that name, which restore and the drill treat as an alert (§6.7).

And a WAL segment must be encrypted before it reaches the spool, which needs age in the Postgres image. Physical restore needs the same Postgres major, so the image's major is pinned and recorded in each backup's name.

The bucket's lock mode, period and lifecycle are read back through the API, not the dialog. The account's master key is never put on the box, used for backups or stored: each setup regenerates it before and after. Upload step. Only the uploader talks to the bucket, one object per call and the same for the .sha256 sibling: rclone --config /tmp/rclone.conf copyto <file> b2:<bucket>/<object> --no-check-dest --s3-no-head --s3-upload-cutoff 5G --retries 1 --low-level-retries 1. The config (type = s3, provider = Other, the endpoint from ops.conf, no_check_bucket = true, the two keys) is written to /tmp/rclone.conf at 0600; no key reaches an argv or an environment. --no-check-dest and --s3-no-head together make the whole run a PUT per object with no HEAD and no list (measured: without either, rclone sends a HEAD the box key cannot make), and a single part (a file over 5 GiB is refused, exit 1) means Content-MD5 covers the whole object and rclone compares the response ETag with it. On a mismatch rclone sends one DELETE of the object, which the key cannot make and Object Lock would refuse (measured against a fake bucket; the refusal on B2 itself is measured in POLY-105). A refused or mismatched upload stops the run, exit 1, and the file stays in the spool. For wal/, then dump/, then premigration/, each regular file in name order is checked first: a name outside the spool grammar, a file that does not begin with the age header, a symlink, anything in .inflight/ is never uploaded (a stray file is reported as upload.sh: stray file <dir>/<name> and the run exits 2 after the loop). The objects are named <instance>/<major>/<dir>/<name> (§6.2). The uploader prints only verified <dir> <name> <sha256> lines. Root (polycarpic-ops upload) then recomputes each hash, and on a match deletes the spool copy; a complete nightly set (the globals file confirmed in this run and no base or dump of the same system id and time left in dump/) rewrites last-upload and pings the monitor, and a WAL upload does neither. Any mismatch, a refused upload, a stray file or a line that fails validation keeps the file, pings /fail and exits 1; a failed ping never changes the exit code.

6.1a The Postgres image and minor

ARCH fixes the major (17, in infra/postgres-major); the image and minor are INFRA's. Image: the official postgres image, tag 17.12. Prod and staging run the age derivative (§2.2) whose single FROM postgres:17.12@sha256:… line is the only place the minor and digest are written. CI starts its Postgres service from the same tag and digest (read from that line, not retyped), and the backup container uses the same image so pg_basebackup, pg_dump and a restore drill run the server's own minor. Neon is created on Postgres 17; Neon applies its own minors and they are not ours to pin. The digest is filled in at the first build (unmeasured until then).

The server minor is held. The derivative and the DB test image run apt-mark hold on postgresql-$PG_MAJOR and postgresql-client-$PG_MAJOR before apt-get upgrade, so the server runs the minor its tag names and the upgrade still applies the OS fixes (libc, openssl, zlib). A server security minor therefore reaches the image only through a bump of the FROM line. When pgdg ships the next minor the held pgtap install in the DB job fails until that line is bumped: the drift is loud.

Who bumps a minor. renovate.json at the repository root covers the two derivative Dockerfiles only (the Postgres tag and digest, age, the Caddy version in the xcaddy build line, with Postgres limited to majors below 18, a 3-day release age and no auto-merge). The weekly workflow .github/workflows/renovate-check.yml (Monday 05:47 UTC and on demand) runs renovate --platform=local --dry-run=lookup from the digest-pinned renovate/renovate image with permissions: contents: read, no secret and no token, so it opens nothing and the repository gains no new write access. It fails when any watched dependency has an update, and the red run is the notification; the bump is a one-to-three line edit by hand. CI runs the DB battery against the bumped line first; the devops-engineer reviews and merges. Minors stay inside 17 and need no restore drill, because a physical restore needs only the same major. A major is never a bump (§5, §6.7). Drift check: a lint job in the infra lint (POLY-95) fails when the major on the FROM line differs from infra/postgres-major, so the file and the image cannot disagree (ARCH §6).

6.2 Naming and integrity

Spool names follow one grammar, shared by the backup, the archive command, the uploader and the restore: ^(base|dump|globals)-<major, 2 digits>-<system id, 1 to 20 digits>-<YYYYMMDDTHHMMSSZ>\.age$ in dump/ (premigration/ admits dump and globals only) and ^wal-<major>-<system id>-<24 hex>(\.<8 hex>\.backup|\.partial)?\.age$ or wal-<major>-<system id>-<8 hex>\.history\.age in wal/. Bucket objects are named <instance>/<major>/<dir>/<spool name>, where <dir> is the spool subdirectory and the major is the one in the name, with a .sha256 sibling holding <sha256 hex> <spool name> written after the object. The system id keeps a re-initialised cluster's segments apart from the old one's, so a restore chosen by upload time can never take a segment of another cluster. A name carries no path: restore refuses any bucket key that is not exactly <instance>/<major>/<dir>/<name>, and names its local files by the bucket's fileId. The upload is checked against the checksum B2 returns (§6.1) and the drill checks every download against its sibling (§6.7). The age private key never appears in any path or log.

6.3 Retention (SECURITY R-5)

Everything in the bucket expires 35 days after it is written and the store allows nothing earlier. So a purged entity's data can remain in backups for at most 35 days after the purge; the purge confirmation screen should say "up to 35 days". There is no long-term archive tier in v1: if you need a yearly keepsake, export from the app (the export carries the hash-chain head) and keep it yourself. Lifecycle expiry is a bucket rule, so no deletion credential exists anywhere.

6.5 Monitoring, heartbeat and alert routing

  • Two independent alert paths, so one failure never silences both. Path A: the app and host scripts email you through Resend (SECURITY §9 list, plus backup, deploy and certificate events). Path B: an outside monitor that does not depend on the box or Resend: Healthchecks.io, free tier, a dead-man's-switch service. Each box pings it, and silence past a check's grace period emails you. It holds no data: a ping carries no body, only the fact that it arrived.
  • What pings Path B. (1) Every 5 minutes, only if local /api/v1/health is OK and the served certificate's issuer matches TLS_MODE (C-76); (2) after each complete nightly set that root has verified (the base, the dump and the globals file all uploaded and compared; root sends the ping from heartbeat_url, a WAL upload alone sends none, so WAL cannot keep the backup check green while the nightly set fails); (3) after each successful deploy poll. Grace: 15 minutes, 26 hours and 20 minutes respectively. The ping carries no data. Healthchecks.io only listens; it does not probe your URL. So before the 5-minute ping the host script makes the same request a browser would (the Hetzner box requests its public name through public DNS, the home box its LAN name) and skips the ping if that fails, which covers Caddy and DNS faults a local health check would miss. A script that detects a failure on its own (a failed backup, a rolled-back deploy) sends the ping to the check's /fail address so the alert arrives at once instead of at the grace deadline.
  • Healthchecks.io setup (once). Create the account with two-step sign-in and your own address as the alert email. In one project create six checks: polycarpic-hetzner-alive, -backup, -deploy and, for the home box, polycarpic-home-alive, -backup, -deploy, each with the period and grace given above and a name that tells you which box it is. Copy the project's ping key; the secret heartbeat_url on each box is the full ping URL of that box's backup check, https://hc-ping.com/<ping-key>/polycarpic-<box>-backup; root sends the success ping to it and appends /fail for a failure. The alive and deploy checks are pinged by their own scripts with their own URLs. Leave auto-creation of checks off. The monthly drill and the 90-day GitHub token get a check each too (period 35 days and 90 days, pinged by you at the end of the task, §8.2 and §8.4). Free-tier check count and grace limits are unmeasured (OQ-INFRA-9).
  • Health endpoint exposure (ARCH §7.4). Public /api/v1/health returns only ok or not. The detail ARCH §7.4 lists (database connectivity, applied schema version against the image's, last job runs) is served by the status listener inside web, bound to 127.0.0.1 in the container, never published and never routed by Caddy, and read by the host scripts with docker compose exec web until POLY-81 moves it into an admin service. Backup age is not app state: root writes /var/lib/polycarpic/state/last-upload (a timestamp and the object names of the last complete nightly set) only after it has compared every hash itself, no container mounts the state directory, and polycarpic-ops status, the 26-hour alert and the backup heartbeat read that file. A stranger learns nothing about backup cadence, and a dead web does not hide a healthy backup.
  • Not configured is not passed. While heartbeat_url is absent, provision-check prints WARN H13 heartbeat not configured: alert path B does not exist; a box going quiet or a full bucket goes unnoticed and ends PASSED WITH 1 WARNINGS: H13. When a prod cluster exists, or with --prod, the warning is a failure: real data does not sit behind a single alert path.
  • Alerts that need no new service: spool older than 2 hours; backup older than 26 hours (from last-upload); any non-temporary row in pg_replication_slots (the 5-minute ping is also skipped, C-79); WAL kept on disk by a slot over half of the 2 GB cap; a poly_backup connection in the last 24 hours that no jobs.log line accounts for (status lists them); B2 storage at 75 percent of its cap; certificate under 14 days; disk over 80 percent; deploy failed or rolled back; a reboot pending (/var/run/reboot-required older than 3 days on Hetzner; older than 7 days on the home box, where automatic reboot stays off until the kernel-update reboot test passes, §3.5, SECURITY C-72), checked daily by a timer and sent through both alert paths; GitHub token under 14 days; ledger hash-chain break (SEV1) or a verifier silent for 8 days. 6.7 The restore drill (a GA gate)

Monthly, scripted, and run off the box: your laptop or a throwaway server, never the VPS, because the age private key must never reach it (ARCH §7.2). The first passing drill against real backup objects is a gate for v1.0; a drill that has not run in 45 days raises an issue and an email.

  1. infra/drill.sh --identity <age key file> --read-credential <file> --bucket <name> --box-credential <file> [--instance <i>] [--before <UTC>] [--report <path>] runs restore.sh's selection and restore code (infra/backup/restore-lib.sh), both --base and --dump, into two throwaway containers. It lists the bucket with the read credential and takes the newest complete nightly set by upload time, then every WAL version of the same system id from the base's start. It refuses (exit 3, each reason listed) a set whose timestamp is in the future, an object uploaded before its timestamp or more than 4 hours after it (a late upload fails the drill's selection, which is DR1: the drill has no --set, and restore.sh --set <TS> is what accepts a late set, printing WARN late upload), and two complete nightly sets in one UTC day.
  2. Each check prints one line, PASS|FAIL|SKIP <id> <text>, for example PASS DR1 every chosen object has one version and no hide marker (set <TS>, <n> versions listed). The checks: DR1 every chosen object has one version and no hide marker (else the versions are listed; a hide marker after a checksum mismatch is the usual cause; the listing reads version <fileId> <time> <object> sibling yes|no, and to restore from such a name restore.sh --accept-version <fileId> takes the version whose sibling is yes, because --before alone cannot pass a name that has two versions before the cutoff); DR2 every download matches its .sha256 sibling; DR3 the globals file contains no PASSWORD and no SCRAM-SHA-256$; DR4 the base recovers through the WAL and promotes, and the newest WAL chosen is the newest listed; DR5 after packages/db/sql/roles.sql is re-run as the superuser on each restored instance, DO $$BEGIN END$$ as poly_app fails with permission denied for language plpgsql and SELECT query_to_xml('SELECT 1', true, false, '') fails with permission denied for function (SQLSTATE 42501); DR6 every role in roles.sql exists in both instances (on the dump instance the check runs before roles.sql is re-run, on what the globals file and the dump restored by themselves; on the base instance after); DR7 the row count of every FORCE ROW LEVEL SECURITY table restored from the pg_dump equals the count in the base-backup restore (proof that BYPASSRLS dumped it whole, C-79); DR8 no public.session row lacks an app.session_handle row (the dump is never restored data-only, so the handle table comes with session); it is a FAIL that names the missing tables when either table is absent, because a check with nothing to check must not pass; DR9 the trial balance of every entity sums to zero, the per-entity hash-chain verifier passes (C-24) and the newest journal entry is within 20 minutes of the drill's start, SKIP while the schema has no ledger; DR10 with the box credential file copied for the drill, against a probe object <instance>/drill/probe-<TS> that the drill uploads itself (never a backup object), deleting it fails, shortening its retention fails, changing the bucket's default retention fails, and a plain upload over its name leaves the first version intact with its original sha256 (C-73's second test); DR11 the time inside each archive (the dump's Archive created at, the base's backup_label START TIME) lies within 1 minute before and 3 hours (nightly) or 10 minutes (base) after its name's timestamp, so an old file under a fresh name is caught.
  3. The last line is DRILL PASSED (exit 0), DRILL INCOMPLETE: not checked: <ids> (exit 3, listing DR9 while the schema has no ledger) or DRILL FAILED: <ids> (exit 1); usage errors exit 2. The first drill gate (POLY-116) accepts exit 0 only. A fault in one object is a FAIL line and the drill goes on with the newest upload version, so every check still runs. The drill's stdout carries only the check lines and the verdict; version listings and refusal reasons go to stderr. A stray bucket key is a DR1 FAIL with its count. A check with no result line (DR5 and DR6 need one per instance) is a FAIL reading <id> did not run, so a stage that never ran cannot pass. Scratch containers are removed on exit.
  4. --report <path> writes the filed form as markdown: the date, the set's timestamp, per object its kind, timestamp, upload time and the sha256 from its sibling, and every check line. It carries no bucket name, fileId, system id or object key, because the repository is public; the fileIds an operator needs to act on stay on the terminal, on stderr. The lead files it as process/cairn/reviews/restore-drill-<date>.md (not edited by hand on the box).

7. Deployment Runbook

Written for someone who has not run a server before. Every step has the command, what you should see, and what to do if you do not. Do the steps in order and do not skip the checks. Commands marked laptop$ run on your own computer, box$ on the server. polycarpic-ops is the operator tool on the box. infra/ops/install.sh installs it into /opt/polycarpic/ops/current (step 11) and you run it as sudo polycarpic-ops; polycarpic-ops help lists the subcommands the installed bundle has. A subcommand this document names that help does not list is not in the installed bundle.

Before you start. No real books exist before v1.0. Until then, do §7.1 with staging only to learn the process with fake data; the prod steps are marked (from v1.0). If any step fails twice, stop and ask. Do not improvise on a box that will hold real data.

7.1 Primary target: Hetzner VPS

  1. Install the tools on your laptop. 
    laptop$ brew install age hcloud gh git rclone nmap
laptop$ age --version && hcloud version && gh --version | head -1

    Expect: a version line from each of the three. If command not found, the install failed: read the error from brew; on Linux use your package manager for the same names.

  2. Create your SSH key (your proof of identity to the server). 
    laptop$ ssh-keygen -t ed25519 -C "polycarpic-operator" -f ~/.ssh/polycarpic_ed25519
laptop$ cat ~/.ssh/polycarpic_ed25519.pub

    Expect: it asks for a passphrase: set one, and store it in your secret store. The second command prints one line starting ssh-ed25519. Never share the file without .pub.

  3. Create the backup key (this is the most important key you will ever make). 
    laptop$ age-keygen -o polycarpic-backup.key
Public key: age1...

    Expect: it prints Public key: age1…. Copy the public key line into a note called backup-public-key. Open polycarpic-backup.key, copy the whole file into your secret store as a secure note, and print one copy for the recovery sheet (§3.6). Then rm polycarpic-backup.key. If you lose this key, no backup can ever be opened; if someone else gets it, they can read every backup. Keep it off the server forever.

  4. Create the backup bucket and its keys at Backblaze B2. Sign up at backblaze.com, choose the EU Central region (it cannot be changed later), turn on two-step sign-in and save the codes in your secret store, and add a payment method (Caps & Alerts need one). In B2 Cloud Storage → Buckets → Create a Bucket: name polycarpic-<yourname>-backups, Private, and Object Lock: Enable, which can only be done at creation. Open the bucket's Object Lock settings: default retention Compliance mode, 35 days. Add a lifecycle rule: hide 36 days after upload, delete 1 day after hiding. Note the bucket's S3 endpoint (shown on the bucket page, like s3.eu-central-003.backblazeb2.com). Under Caps & Alerts set a storage cap (start 10 GB) with an email alert at 75 percent; leave downloads uncapped so a restore is never blocked (C-73). Then make the keys with the tool, not the web form: the form's "Write Only" key also carries delete and settings permissions. 
    laptop$ python3 infra/operator/b2-setup.py --bucket polycarpic-<yourname>-backups

    Expect: it says In Backblaze, App Keys → Generate New Master Application Key; do that and type the two parts at the hidden prompts. It reads the bucket back and prints PASS or FAIL for private, Object Lock in compliance mode, 35 days, and lifecycle 36 / 1 (encryption is reported, not required). It lists the two keys it will make (polycarpic-put-only and polycarpic-read, both restricted to the bucket) and waits for a typed yes. Each new key is shown once. It then reads every key back and checks its capabilities exactly (§6.1), asks you to generate the master key again, and checks that the old one is now refused. It ends B2 SETUP PASSED. Store both new key pairs in your secret store, labelled b2-put-only (goes on the server) and b2-read (laptop only), together with the endpoint; never store the master key. Check: rclone lsd or rclone ls with the read key lists the empty bucket without error. If the tool says Object Lock is not enabled, the bucket was created without it and cannot be fixed: delete the empty bucket and create it again. A FAIL line names what to change; run the tool again. Once, before the first backup, b2-setup.py --probe measures the box key's minimum (§6.1). When the probe says PROBE: INCONCLUSIVE, run it again as b2-setup.py --probe --show-rclone-output: after the temporary key is deleted it prints --- rclone output (temporary key already deleted) ---, rclone's output with every key value replaced by <redacted> and cut to 4096 bytes, then --- end ---. The option is valid only with --probe (otherwise exit 2).

  5. Hetzner project and API token. In the Hetzner Cloud console create a project named polycarpic, then Security → API tokens → Generate (Read & Write). Copy the token once. 
    laptop$ hcloud context create polycarpic
(paste the token when asked)
laptop$ hcloud server list

    Expect: an empty table, no error. If it says unauthorized, the token was copied wrong: generate a new one.

  6. Get the repository and read the plan. 
    laptop$ git clone git@github.com:richmosko/polycarpic.git && cd polycarpic
laptop$ git tag -v v1.0.0     # from v1.0; before then use main

    Expect (from v1.0): Good "git" signature for …. If it says BAD or shows no signature, do not continue.

  7. Create the server, firewall and volume. 
    laptop$ infra/hetzner/create.sh --name polycarpic --location fsn1 --type <type> \
          --ssh-key ~/.ssh/polycarpic_ed25519.pub

    Expect: without --type it prints the 4 vCPU / 8 GB shared x86 plans and exits 2 (Hetzner renames its plans, §2.1); pick one and run it again. It refuses to run while HCLOUD_TOKEN is set: use the context of step 5. It prints IPv4: <address> and IPv6: <prefix>::1 (network <prefix>/64): Hetzner reports the /64 network, and the server's own address is <prefix>::1, which is the one every --ipv6 and AAAA record below uses. The server gets one firewall with three rules; each rule lists IPv4 and IPv6 sources together, so three rules cover both families. It ends with created: server, firewall (22,80,443 in), volume 20 GB. It is safe to run again; it skips what exists. If it says the location has no stock, use nbg1 (Nuremberg): same country, same prices, and the backup bucket is unaffected. If it prints anything about opening ports other than 22, 80, 443, stop.

    Then remove the token (SECURITY C-78). It can rebuild the server, move the volume or open the rescue console, so it does not stay on your laptop:

    laptop$ hcloud context delete polycarpic
laptop$ ls ~/.config/hcloud

    Expect: the context is deleted and the directory holds no token. Then, in the Hetzner console, Security → API tokens, delete the token. The next run of create.sh (or §8.10) starts with a freshly generated one.

  8. Point your DNS at it. If the domain's name servers are not yet Cloudflare's: add the domain to a free Cloudflare account, copy the two name servers it gives you into the registrar's "name servers" setting (the registrar stays the registrar), and wait until Cloudflare shows the zone Active (minutes to a day). Then, with a Cloudflare token limited to this zone (DNS edit), write the records from the repository, using the two addresses of step 7 (--ipv6 takes the <prefix>::1 address, never the /64): 
    laptop$ python3 infra/operator/dns-records.py --ipv4 <address> --ipv6 <address>
laptop$ python3 infra/operator/dns-check.py --ipv4 <address> --ipv6 <address>
laptop$ dig +short app.example.com A
laptop$ dig +short app.example.com AAAA

    Expect: dns-records.py lists what it will create and waits for a typed yes. It creates SPF -all, the null MX, CAA for Let's Encrypt and Sectigo only (no wildcard issuance), the _dmarc record (p=reject, no report address: DMARC reports stay off), Resend's two CNAMEs and DKIM key for mail, and A and AAAA for app and staging (TTL 300, DNS only: an orange cloud would put Cloudflare in front of the server and break the design). It never deletes or overwrites: if a record of the same name and type already holds another value it prints CONFLICT with both values and exits 1 without writing. An existing hand-made _dmarc (the older v=DMARC1; p=reject) is such a conflict: in Cloudflare, edit that TXT record to the value the tool printed (v=DMARC1; p=reject; sp=reject; adkim=s; aspf=r), then run the tool again. Delete that token afterwards. dns-check.py takes a second token, read-only (Zone:DNS:Read), and ends DNS CHECK PASSED. The domain rule it enforces: only app and staging are web names; no wildcard; no CNAME to a name outside the zone except the two pinned mail aliases (send.mail, rsend.mail), and neither alias target may answer with an address; no delegation; nothing proxied. Anything else in the zone is a FAIL. Then the dig lines show the server's addresses within a few minutes; if empty after 30 minutes, the records are on the wrong zone or have a typo.

  9. First login. 
    laptop$ ssh-add -t 1h ~/.ssh/polycarpic_ed25519
laptop$ ssh -i ~/.ssh/polycarpic_ed25519 polyops@app.example.com
box$ cloud-init status --wait

    Expect: ssh-add loads the key for one hour and asks for its passphrase once; never add --apple-use-keychain, which keeps the key unlocked for good. The first time, a question about the host fingerprint: compare it with the one in the Hetzner console (server → Console shows it in the boot log) before typing yes. Then status: done. If status: error, run sudo cat /var/log/cloud-init-output.log | tail -50 and ask; do not continue. If login is refused, the key in step 7 was not the one in step 2.

  10. Hand the box its three public facts (nothing secret yet). 
    laptop$ ssh polyops@app.example.com "echo 'age1...yourpublickey' | sudo tee /etc/polycarpic/age-recipients.txt"

    Expect: the recipient line is echoed back. The release-signing public keys are installed after the tool is (step 11): ssh -t polyops@app.example.com 'sudo polycarpic-ops allowed-signers install' < ~/.config/polycarpic/allowed_signers. The file is your own copy of the keys (make it from the key /merge-pr signs with, once; keep it in your secret store) and must not come from the repository (§3.3). Expect one fingerprint line per key, then 1 key(s) installed; provision-check shows WAIT H18 until then.

  11. Provision the box. Install the operator tool from your verified checkout of step 6, then run it on the box. 
    laptop$ infra/ops/install.sh polyops@app.example.com --ssh-key ~/.ssh/polycarpic_ed25519
box$ sudo polycarpic-ops provision --stage host --target hetzner --domain example.com --b2-bucket polycarpic-<yourname>-backups
box$ sudo polycarpic-ops provision-check

    Expect: install.sh prints installed polycarpic-ops git-<12 hex> at /opt/polycarpic/ops/current (previous: none); run again on the same commit it prints polycarpic-ops git-<12 hex> already installed and changes nothing. It ships the committed files only (git archive of HEAD, never your working tree) and refuses with exit 2 when a file it ships has an uncommitted change. The tool and the scripts stay on the box across reboots. --b2-bucket is written once to /etc/polycarpic/ops.conf (change: ops.conf B2_BUCKET=<name>), and provision-check reads the bucket from there (or from its own --b2-bucket; with neither it prints no bucket: run provision --b2-bucket <name> once, or pass --b2-bucket and exits 2). Both pass the scripts' output and exit code through. provision prints a change: line for everything it does and ends host stage: <n> changes; run again, it ends host stage: no changes. provision-check.sh prints one line per check (PASS, FAIL with its fix, WAIT, WARN, INFO) and, before the first deploy, ends HOST CHECKS PASSED; <n> checks wait for the first deploy (exit 3): the waiting ones need a running Postgres (D1 to D6) or the secrets of step 12. On a staging-only box (steps 12 to 13 done, prod not yet deployed) the expected WAIT lines are exactly: H12 (while no uploader credential exists), D3 (prod only), and the prod part of D1, D2, D4, D5 and D6. Any other WAIT, or a WAIT naming staging, is a finding: stop and ask. After the first deploy it ends ALL CHECKS PASSED. It covers: key-only SSH with no root login and a single allowed user, read from the running sshd -T (not the config file); unattended upgrades on; Docker's effective settings; the data volume LUKS2, mounted at /srv/polycarpic from its mapper device, with a root-only key file; swap off; the secrets layout and modes, no world-readable file and no two secrets alike; the data directories, spool ACLs and spool contents; no host account holding a service group; host.env with MAIL_FROM under mail.<domain> and no secret in it; one age recipient; the box's B2 key exactly as §6.1 (H12; it waits until step 12 sets it); the clock synchronised; the sudoers file exactly one line; and, with Postgres running, the Postgres settings, only the plpgsql extension, the C-79 reach (from web and uploader the poly_backup login is refused, from backup it works), no leftover replication slot, a SCRAM verifier on every login role, and the fixed network subnets. The first deploy runs provision.sh --stage database --project staging|prod: it applies roles.sql and sets each login password from its file; the verifier is computed on the box, so Postgres never receives a plaintext password. Until step 12 sets heartbeat_url the check prints WARN H13 heartbeat not configured and ends PASSED WITH 1 WARNINGS: H13, never ALL CHECKS PASSED; once a prod cluster exists (or with --prod) that warning is a FAIL, because without alert path B a full bucket or a silent box goes unnoticed (§6.5). Any FAIL line names the fix; apply it and run the check again. Do not continue past a FAIL.

  12. Enter the provider secrets. For each secret in the list below, run the command and paste the value when prompted (nothing is shown as you type). The command reads from a terminal only. 
    box$ sudo polycarpic-ops set-secret resend_api_key
box$ sudo polycarpic-ops set-secret backup_store_credential   # the PUT-ONLY pair (the uploader mounts it); prod only
box$ sudo polycarpic-ops set-secret heartbeat_url             # prod only
box$ sudo polycarpic-ops set-secret plaid_secret              # and any other secret a service mounts
box$ sudo polycarpic-ops list-secrets

    Expect: the prompt resend_api_key (input hidden): ; backup_store_credential asks twice, key id (input hidden): then application key (input hidden): . A value that is empty, holds a space or a control character, or (for heartbeat_url) does not start https:// exits 2 and writes nothing. It writes each mounting service's file and prints one line per file, written: /etc/polycarpic/secrets/auth/resend_api_key (<n> bytes, 0440 root:10007), then set-secret: resend_api_key written for auth, worker; run: sudo polycarpic-ops restart auth worker (for the two names only a one-shot service mounts, the last line ends ; the next uploader run reads it). If the file exists it first asks resend_api_key exists for: auth, worker; type yes to replace: ; anything but yes exits 1 with not replaced. It refuses a name no service mounts (no compose file mounts oauth_google_secret into a service) with set-secret: no service in prod.yml, edge.yml mounts <name>; names you can set: … and exit 2, and the names a tool writes (§3.2). list-secrets prints names, sizes and permissions, never values, and never opens a file:

    SERVICE   NAME                      STATE    MODE OWNER         BYTES
auth      auth_secret               set      0440 root:10007       45
auth      db_password_auth          missing
auth      resend_api_key            set      0440 root:10007       36
...
15 files: 2 set, 13 missing

    A file that is not 0440 root:<gid> (0400 root:root for a host-only secret) shows WRONG with its real mode, the last line adds ; <k> wrong: run provision-check, and the exit is 1; missing files do not fail it. For staging add --staging to each command and use sandbox values only; staging has no uploader, so backup_store_credential and heartbeat_url are prod only. Missing a required one is not a problem now: the first start tells you which. You do not enter any db_password_*: provision generated them, db_password_backup included. Never paste a secret into a chat, an issue or a file in the repository.

  13. First deploy of staging. 
    box$ sudo polycarpic-ops first-deploy staging
box$ sudo polycarpic-ops init-keyring --staging

    Expect: it takes the latest successful main build, verifies it (§4.4), runs the config check and the migration, starts the containers and, when healthy, enables polycarpic-deploy@staging.timer. A host with no prod release also gets the shared Caddy from this run. If the Postgres roles do not exist yet it prints run: sudo polycarpic-ops provision --stage database --project staging and exits 4; run that and repeat. init-keyring prints the staging keyring once; staging's keyring may be lost freely (relink sandbox items), so do not worry about saving it. Staging holds test data only, always, so it does not wait on the gate in step 16. The order of a first staging box: provision --stage host (the edge networks and edge.env) and the database stage; the secrets, including github_read_token and staging-auth; allowed-signers install; first-deploy staging (again after the database stage if it asks); then edge-deploy edge-1, which needs a signed edge-1 tag and its Release; then the outside scans. Staging needs no Caddy to be deployed; it is served once Caddy is up. If it ends deploy: refused attestation: stop; do not override; check that the read token is set (polycarpic-ops set-secret github_read_token, polycarpic-ops status shows token) and that the image really came from this repository. deploy.log under /var/lib/polycarpic/state/deploy/staging/ names every refusal.

  14. Prod (from v1.0): the keyring, then the first deploy, with the door closed. 
    box$ sudo polycarpic-ops first-deploy prod
box$ sudo polycarpic-ops init-keyring

    The maintenance page this step relies on is not built (the Caddyfile has none); this step does not run before it exists. Expect then: first-deploy prod requires the signed tag check to pass, enables the prod deploy timer and, because images.env now exists, the two backup timers,. Caddy shows a static "not open yet" page for the prod name until you open it in step 17. init-keyring prints the prod keyring once: copy the whole block into your secret store (as a secure note separate from the age key) and the recovery sheet, then confirm with polycarpic-ops keyring-fingerprint that what you saved has the same fingerprint it prints. The keyring is not in any backup (SECURITY §6.4).

  15. Prove the outside world sees only what it should. From a machine not on the box's network (your laptop at home is fine for the Hetzner target): 
    laptop$ nmap -Pn -p- app.example.com
laptop$ nmap -Pn -6 -p- app.example.com
laptop$ curl -sI https://app.example.com | head -5
laptop$ ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no polyops@app.example.com

    Expect: exactly three open ports, 22, 80 and 443, in both scans (a full scan can take 10 to 20 minutes). The curl shows HTTP/2 200 (staging) or the maintenance response (prod) over a valid certificate. The last command ends Permission denied (publickey). Any other open port, especially 5432, 2375 or 3000, means a containment failure: close it (polycarpic-ops lockdown stops all containers except Caddy), and tell the team-lead before doing anything else.

  16. Make the bootstrap user (SECURITY C-01, §4.1: an invitation on an empty instance, so the first sign-up cannot be won by a stranger).

    Gate: the first real account and its data start here, so this step does not run on prod until the deploy-gate check passes. The check is on the instance, after it has migrated. It reads the catalog and changes nothing. A closed, empty prod holds nothing, so steps 5 to 15 run first. The gate also needs, from the laptop, python3 infra/operator/dns-check.py --ipv4 <address> --ipv6 <address> to end DNS CHECK PASSED and python3 infra/operator/laptop-check.py to end LAPTOP CHECK PASSED (it fails on any hcloud context, an HCLOUD_TOKEN in the environment, or a token in hcloud's config file).

    box$ sudo polycarpic-ops gate-check

    Without the helper: /opt/polycarpic/ops/current/infra/postgres/gate-check.sh docker compose -p polycarpic-prod exec -T postgres psql -U postgres -d polycarpic (the helper prints gate: error (polycarpic-prod postgres is not running) and exits 1 when prod has no running Postgres). The gate passes only when the command exits 0 and prints exactly one line, gate: pass. Any other output, a non-zero exit, or an error is a fail: stop and do not make the user. Every failing control prints its own FAIL line naming the object. The check requires, on the migrated schema: app.second_step_streak and app.sign_in_record exist with row-level security enabled and forced; the six triggers (two_factor_15_lock, two_factor_16_lock_delete, session_80_sign_in_record, sign_in_record_05_refuse, sign_in_record_10_immutable, sign_in_record_no_truncate) exist and are enabled; app.guard_second_step_lock() and app.record_session_sign_in() are owned by poly_govern, are SECURITY DEFINER and are executable by no login role; app.purge_sign_in_record() is owned by poly_purge, is SECURITY DEFINER and is executable by poly_worker only; no login role holds a write privilege on either table; no login role other than poly_backup can read the sign-in record (the backup role reads every table); app.enter_asserted_user does not exist; poly_app holds no privilege on BetterAuth's six tables, app.session_handle, the sign-in record or the streak table, and executes exactly the eleven app functions web needs; every second-step method added or removed is audited by the database: the triggers two_factor_80_sync and passkey_80_sync exist, are enabled and run app.sync_second_step(), which is owned by poly_govern, is SECURITY DEFINER, is executable by no login role and whose body writes both second_step.method_added and second_step.method_removed to audit_event; app.complete_step_up(text, uuid, bigint) is owned by poly_govern, is SECURITY DEFINER and is executable by poly_auth only, and no login role can update public.session.recent_auth_at itself (that function is the only writer of the "confirm it's you" stamp); the triggers two_factor_no_truncate, passkey_no_truncate (a TRUNCATE of the method tables is refused, since it would leave no audit row), two_factor_85_step_up_spent, step_up_totp_10_forward and step_up_pending_resolved exist and are enabled, the last as a deferred constraint trigger; no login role can delete from public."user"; and role membership is exactly this set: poly_migrator holds poly_owner and the seven definer-owner roles (no inherit, set, no admin) and poly_backup holds pg_read_all_data, so no login role can SET ROLE to a role that owns the record or its triggers. Each line is refused by a planted fault in tests/db/gate-check.test.ts. A method added after the first waits 24 hours before it counts, and the database writes an email for every method change, so a found backup code plus the password is not a full takeover. The check also requires: app.method_hold and app.mail_outbox exist with row-level security enabled and forced, and no login role holds a privilege on either (poly_backup reads them through pg_read_all_data); the triggers two_factor_12_method_hold (BEFORE UPDATE OF failed_verification_count, backup_codes) and passkey_12_method_hold (BEFORE UPDATE OF counter) run app.guard_method_hold(), and user_21_email_fixed, two_factor_84_codes_replaced and account_80_password_changed exist and run their functions; the bodies of app.sync_second_step(), app.complete_step_up(text, uuid, bigint) and app.check_factor_removal(uuid, text, uuid) name the hold and the outbox (a tripwire: the proof is the behavioural tests); the nine mail and hold definers are owned by poly_govern (the purge by poly_purge), are SECURITY DEFINER, and are executable by exactly the one login role that needs each; no outbox row has been unsent for over an hour (a notice that cannot be delivered keeps its method off: fix the key or the address, or ask the operator to reset the user's second step); poly_auth carries idle_in_transaction_session_timeout = 15s; and no purge has been missed: no app.tx_identity marker older than 6 hours, no app.sign_in_record row older than 401 days, no sent app.mail_outbox row older than 31 days. A staging or production auth or worker without RESEND_API_KEY_FILE and MAIL_FROM refuses to start (check-config), so the notices cannot be missing at deploy. The command and the service name are unmeasured; the first prod run confirms them. The same check and the same rule apply to the home box and the Vercel path. Staging is not gated.

    box$ sudo polycarpic-ops cli user invite you@example.com --bootstrap

    Expect: the sign-up link on one line, then invitation recorded (bootstrap), expires <time>. Nothing is emailed. Copy the link into your browser; it is stored nowhere (not in Docker's log, not in a file), and it works only for that address. When you have used it, clear the terminal screen and its scrollback: the link also sits in your terminal's or tmux's history. The one-shot container runs the release that is deployed, never a newly pulled image. If prod is not running it prints polycarpic-prod is not running: deploy it first (exit 1); if the running image is not pinned by digest it prints running web image is not pinned by digest (exit 1) and runs nothing.

  17. Open the door, sign up, and set the second step. 
    box$ sudo polycarpic-ops open prod

    Expect: prod is open. Open the link step 16 printed, create a password, confirm the emailed code, and set up an authenticator app as your second step. Save the backup codes in your secret store. If you are asked to sign in before an invitation exists, step 16 did not complete: run polycarpic-ops close prod and repeat from 16.

  18. First backup, on demand. 
    box$ sudo systemctl start polycarpic-backup.service   # runs backup, then starts the uploader
box$ sudo systemctl status polycarpic-upload.service
box$ sudo polycarpic-ops status

    Expect: the service ends Finished; status shows OK backup prod last upload <date>Z (<n> m) and OK backupdb prod <n> poly_backup connections in 24 h, all accounted, and ends STATUS GREEN. status does not read Healthchecks.io: your monitor shows the heartbeat check green. If the upload fails with an access error, the put-only key was pasted wrong; if it fails with a lock error, the bucket's Object Lock is not enabled (step 4).

  19. First restore drill, from your laptop (this is a v1.0 gate; do it now while it holds nothing, and monthly after). 
    laptop$ infra/drill.sh --bucket polycarpic-<yourname>-backups

    Expect: it asks for the read key and the age private key file (paste it from your secret store into a temporary file it deletes afterwards), restores into a scratch Postgres on your laptop, and ends DRILL PASSED with the checks of §6.7, including delete attempt: DENIED, overwrite: DENIED, shorten retention: DENIED and bucket retention change: DENIED. A FAILED line names the check. Do not go live with real data until this passes.

7.2 Secondary target: the local-network box

Do §7.1 steps 1 to 4, 12, 14 and 16 to 19 unchanged (names and addresses differ). This section covers what is different: the hardware, the encrypted disk (root and data), the network lockdown and TLS. Do all of it before any real data touches the box. One thing to know first: with root encrypted, a box that fails to unlock waits at a console prompt and is unreachable over the network, so have a keyboard and monitor to hand for steps 2, 6 and 7.

  1. Hardware and firmware. A small x86-64 PC with a working TPM 2.0 (listed as fTPM, PTT or "Security Device" in the firmware; see the pre-purchase checks under Troubleshooting step 6 below), wired Ethernet, an SSD, and a UPS. In the firmware setup (usually Delete or F2 at power-on), do the whole checklist:
    • Update the firmware to the manufacturer's latest.
    • Set a setup (administrator) password; store it in your secret store.
    • Secure Boot on, in user or deployed mode with the factory keys (not "setup mode").
    • TPM enabled.
    • Boot from USB and from network (PXE): disabled (the unattended unlock depends on this and on Secure Boot, §3.5). Boot order: the internal SSD only. (Temporarily enable USB for the install in step 2, then disable it again in step 8.)
    • "After power loss": power on.

    Expect: the settings stick after a save and reboot. If the machine has no setup-password option, it is not suitable for this role (the firmware password is the control, C-72): choose different hardware.

  2. Install Ubuntu Server 24.04 LTS from a USB stick (download from ubuntu.com; verify its checksum there). First generate the recovery passphrase in your secret store (six or more random words) and write it on the recovery sheet: the installer asks for it now and it becomes the permanent recovery slot. In the installer: language, keyboard, wired network (static address later), "Ubuntu Server (minimized)" is fine; storage: custom, with this layout (unmeasured on 24.04, OQ-INFRA-10; if the installer cannot make it, stop and ask):
    • 1 GB EFI system partition (unencrypted, required by the firmware).
    • 1 GB ext4 mounted at /boot (unencrypted: kernel and initramfs; the accepted residual, §3.5).
    • The rest of the disk as one encrypted volume (LUKS2, passphrase = the recovery passphrase) holding one LVM volume group polycarpic with two logical volumes: root, 80 GB ext4 at /, and data, all the remaining space, ext4 at /srv/polycarpic.
    • No swap.
    Name the server polycarpic; create user polyops with a long password you keep in your secret store; tick "Install OpenSSH server" and import your SSH key from GitHub; no extra snaps.

    Expect: it reboots to a passphrase prompt on the console (type the recovery passphrase; the TPM is not bound yet), then to a login prompt. lsblk shows / and /srv/polycarpic on crypt/lvm devices and only /boot and /boot/efi on plain partitions. If it does not boot, re-check that the SSD is first in the boot order.

  3. Give it a fixed address. In your router, reserve the box's current address for its network card (DHCP reservation). Write the address down.

    Expect: after a reboot of the box, it has the same address. Check from the laptop: ssh -i ~/.ssh/polycarpic_ed25519 polyops@<address> works.

  4. Router settings. Log in to the router. Confirm: no port forwarding rules; UPnP and NAT-PMP off; no "DMZ host"; IPv6 either off or its firewall set to block inbound. Screenshot the pages to your secret store's note for this box.

    Expect: all four true. If your router cannot turn UPnP off, replace the router before continuing: it can open the box to the internet without asking.

  5. Provision the host. 
    laptop$ ssh -t -i ~/.ssh/polycarpic_ed25519 polyops@<address> 'sudo polycarpic-ops allowed-signers install' < ~/.config/polycarpic/allowed_signers
box$ sudo polycarpic-ops provision --target home --lan-cidr 192.168.1.0/24
box$ sudo polycarpic-ops provision-check

    Expect: provision-check ends ALL CHECKS PASSED, covering: nftables default-deny with inbound 443 (80 redirects) and SSH from the LAN only; the DOCKER-USER drop rule for non-LAN sources; Caddy's publish address equals the LAN address; IPv6 disabled; outbound limited to DNS, NTP and 443 (the check tries port 25 and 8080 and expects failure); sshd key-only without root login; swap off; and, that / and /srv/polycarpic sit on dm-crypt devices (findmnt), that lsblk shows one crypt container under the one partition, with / and /srv/polycarpic as logical volumes in it and only the EFI partition and /boot outside it (SECURITY C-72, S-9), that the LUKS header shows the passphrase slot (the TPM slot is added in the next step, so this check runs again after it), and that the Docker address pool and the fixed subnets of §2.2 do not overlap. The script takes no device argument: it formats nothing.

  6. Bind the encrypted disk to the TPM (one binding unlocks root and data). The script wraps the method; the candidates are shown so you know what happens. 
    box$ sudo polycarpic-ops disk-bind
   # candidate A (try first): clevis-luks-bind with the tpm2 pin, pcr_ids 7,
   #   + clevis-initramfs, then update-initramfs -u
   # candidate B (if A fails): dracut in place of initramfs-tools,
   #   + systemd-cryptenroll --tpm2-device=auto --tpm2-pcrs=7
box$ sudo reboot

    Expect: disk-bind asks for the recovery passphrase once, binds the TPM, rebuilds the initramfs and prints the slots (passphrase and tpm2, nothing else). Then these checks, all of which must pass (together they are "root unlocks after reboot without a prompt"; checks 1 and 3, a plain reboot and a reboot after a kernel update, are the two reboot tests SECURITY S-9 names):

    1. Reboot: with your hands off the keyboard, the box answers SSH within 3 minutes and findmnt / shows a /dev/mapper/… device.
    2. Cold start: shut down, unplug the power for 10 seconds, plug in. Same result.
    3. Kernel update: install a newer kernel (the next available one; apt list --upgradable | grep linux-image) and reboot. Same result. If no newer kernel exists yet, repeat this check after the first one that does, before real data. Until it passes, leave unattended-upgrades automatic reboot off on this box (§3.5).
    4. polycarpic-ops provision-check --disk ends ALL CHECKS PASSED: TPM slot and passphrase slot both present on the one container, PCR list is exactly 7.

    If any of these waits for a passphrase, the binding did not take: type the recovery passphrase to continue, then see Troubleshooting step 6 below. PCR 11 is deliberately not used (§3.5). The method that passes is recorded here once OQ-INFRA-10 is measured.

  7. Prove the disk stays locked when the machine is tampered with. Enter the firmware setup, turn Secure Boot off, save, and let it boot, with a keyboard and monitor attached.

    Expect: it stops at the root unlock prompt on the console and never reaches the network (so SSH does not answer), instead of unlocking silently. That proves the key is tied to the Secure Boot state, and because root is encrypted too, nothing on the box ran. Type the recovery passphrase only to continue. Then go back into the firmware, turn Secure Boot on, save, reboot, and confirm it unlocks by itself again (check 1 of step 6). If it unlocked silently with Secure Boot off, the TPM binding is not what it claims: do not store real data; run polycarpic-ops disk-bind again with PCR 7 only and repeat.

  8. Harden the console. The script sets these and the check verifies them; in plain terms: no automatic console login; the emergency and single-user shells ask for a root password (set with sudo passwd root: long, random, saved in your secret store); the bootloader has a password and no editable or recovery entries. Now disable USB boot again in the firmware (the install is finished). 
    box$ sudo polycarpic-ops harden-console
box$ sudo polycarpic-ops provision-check --console

    Expect: ALL CHECKS PASSED. As a hands-on test, power-cycle the box and at the boot menu press e: it must ask for the bootloader password.

  9. DNS and TLS: choose one mode and set it before first deploy. The mode is set by TLS_MODE in /etc/polycarpic/host.env and the app refuses to start on a mismatch. See 7.3 for each mode, then return here.
  10. Secrets, first deploy, keyring, outside-in check. Do §7.1 steps 12 and 14 (secrets; first deploy and keyring for prod) with --target home; the bootstrap, open, backup and drill steps (16 to 19) follow once the checks in steps 11 and 12 below pass. There is no staging on this box: run the process in staging on the Hetzner server first. The gate in §7.1 step 16 applies here: do not run the bootstrap or open the box until the gate passes: the command exits 0 and prints exactly one line, gate: pass. Any other output, a non-zero exit or an error is a fail: stop.

    Expect the same results, except the first-deploy check also prints served certificate issuer matches TLS_MODE.

  11. Outside-in scan of your home from outside. Use your phone on mobile data as a hotspot for the laptop (or a cloud shell). Find your home's public IPv4 address (visit any "what is my IP" page from home) and the box's IPv6 global address if it has one (ip -6 addr on the box; disabled means none). 
    laptop-off-LAN$ nmap -Pn -p- <home-public-ipv4>
laptop-off-LAN$ nmap -Pn -6 -p- <box-ipv6-if-any>

    Expect: all ports filtered or closed, none open. Also try browsing to the box's name from mobile data: it must not resolve (real-domain mode) or not be found. Anything open: unplug the box's network cable, then fix the router or firewall (C-76).

  12. Outbound test. 
    box$ curl -sS --max-time 5 https://github.com -o /dev/null -w "%{http_code}\n"
box$ curl -sS --max-time 5 http://example.com:8080 || echo blocked

    Expect: 200 (or a 3xx) for the first; blocked (a timeout) for the second.

Troubleshooting step 6. If the TPM slot will not bind: check systemd-cryptenroll --tpm2-device=list (or clevis luks list) shows a device; confirm the firmware's TPM is enabled and in TPM 2.0 mode; confirm Secure Boot shows "enabled" in mokutil --sb-state. If it still fails with both candidate methods, stop: either this machine will not do (use hardware with a working TPM2 and Secure Boot) or the method does not work on 24.04 (OQ-INFRA-10). There is no passphrase-at-every-boot fallback (P8 stands), so do not put real data on a box whose disk cannot be bound to the TPM. If the hardware is fine and neither method in step 6 gives an unattended root unlock on Ubuntu 24.04, stop and return to SecEng and the Principal: the remaining options (a different distribution, a measured unified kernel image, a PIN) change a ruling and are not mine to choose. Do not buy hardware before checking, on the model's own spec sheet or by booting a live USB on it: (1) a TPM 2.0 (fTPM, Intel PTT or discrete) is listed and can be enabled in the firmware; (2) Secure Boot can be turned on and off, with factory keys; (3) the firmware has a setup (administrator) password; (4) USB and network boot can be disabled; (5) it has an "After power loss: power on" option; (6) a live Ubuntu 24.04 USB shows the TPM, ls /dev/tpmrm0 exists and systemd-cryptenroll --tpm2-device=list lists a device. Unmeasured per model; buy from a seller with a return window until steps 6 and 7, including the kernel-update reboot, have passed.

7.3 Home-box TLS, step by step

Mode A (default): real domain, DNS-01 wildcard

  1. In Cloudflare create an API token that can edit DNS records in this one zone only (My Profile → API Tokens → Create → "Edit zone DNS" template, Zone Resources → Include → Specific zone → your domain). Name it polycarpic-home-caddy.
  2. box$ sudo polycarpic-ops set-secret dns_api_token and paste it. Set TLS_MODE=real-domain, PUBLIC_ORIGIN=https://polycarpic.home.example.com in /etc/polycarpic/host.env.

    Expect: list-secrets shows the token, mounted only into caddy (the SERVICE column of list-secrets names the mounting service).

  3. Make the name resolve on your LAN only. Preferred: in the router's DNS settings add a local record polycarpic.home.example.com → <box address>. If your router cannot, add the line 192.168.1.20 polycarpic.home.example.com to /etc/hosts (macOS/Linux) or C:\Windows\System32\drivers\etc\hosts on each device. 
    laptop-on-LAN$ dig +short polycarpic.home.example.com
laptop-off-LAN$ dig +short polycarpic.home.example.com @1.1.1.1

    Expect: the first shows the box's address (or use ping if you used a hosts file); the second shows nothing. If the second shows an address, you published the box's name: delete that record in Cloudflare.

  4. First deploy requests the wildcard. Expect in polycarpic-ops logs caddy: certificate obtained successfully within about two minutes. Browse to the name from a LAN device: a normal padlock, issuer a public CA. If the order fails with DNS problem, the token's zone or permission is wrong; if with rate limit, wait an hour and do not retry in a loop.
  5. Register your sign-in apps with Google and GitHub using the callback URL https://polycarpic.home.example.com/api/auth/callback/<provider>, then set-secret each client secret. GitHub asks for read:user and user:email only.

Mode B (fallback): .local with a private CA

  1. Make the CA on your laptop, not the box. 
    laptop$ infra/ca/ca.sh init --name polycarpic.local
laptop$ infra/ca/ca.sh intermediate --out ./box-intermediate

    Expect: root.crt (public: this goes on devices), root.key (private: it must go into your secret store as a secure note, then be deleted from the laptop) and a folder with the intermediate cert and key. Running ca.sh show root.crt must print Name Constraints: permitted DNS polycarpic.local. If it does not, the CA is unconstrained: delete it and do not continue.

  2. Copy only the intermediate to the box: scp box-intermediate/* polyops@<address>:/tmp/, then box$ sudo polycarpic-ops install-intermediate /tmp/…. Set TLS_MODE=private-ca, PUBLIC_ORIGIN=https://polycarpic.local. The root key never leaves your secret store.
  3. Install the root certificate on every device that will sign in:
    • macOS: sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain root.crt (also needed in Firefox: Settings → Privacy & Security → Certificates → Import, tick "trust to identify websites").
    • iPhone/iPad: AirDrop root.crt, open it, install in Settings → Profile Downloaded; then Settings → General → About → Certificate Trust Settings → enable full trust.
    • Windows: double-click, Install Certificate → Local Machine → "Trusted Root Certification Authorities".
    • Android: Settings → Security → Encryption & credentials → Install a certificate → CA certificate.
    • Linux: copy to /usr/local/share/ca-certificates/ and run sudo update-ca-certificates.
  4. Gate item, once per browser and OS you use (R-20). 
    laptop$ infra/ca/ca.sh test-constraint
   # issues a certificate for evil.example.com signed under the intermediate and serves it on https://127.0.0.1:8443 with a hosts-file line you add as it prints

    Expect: in each installed browser the page shows a certificate error (name constraint violated). If any browser loads it as trusted, that browser ignores the constraint: remove the root from that device and do not use that browser for this box, or move the box to Mode A. Record the result per browser in the ledger via the team-lead.

  5. Make polycarpic.local resolve: most devices find it by themselves (mDNS). If not, add a router DNS record or a hosts-file line as in Mode A step 3. Open https://polycarpic.local: padlock, no warning. OAuth buttons are absent and OAuth routes return 404 by design; sign in with email, password and the second step. Passkeys on a .local name are unmeasured: use an authenticator app.

Moving a .local box to a real domain

  1. Everyone who is an owner or manager must already have an authenticator app or backup codes (passkeys will not survive, because they are tied to the old name; every session ends). Check each member: box$ polycarpic-ops cli user mfa-methods --all-owners must show TOTP or backup codes for each. Anyone without: ask them to add one, or use polycarpic-ops cli user reset-mfa <email> on their behalf afterwards.
  2. Tell the household first: everyone will be signed out once.
  3. Do Mode A steps 1 to 4. Change TLS_MODE and PUBLIC_ORIGIN; polycarpic-ops redeploy home.

    Expect: the app starts and the served certificate chains to a public CA. If the app refuses to start with a mode message, the settings disagree: fix host.env.

  4. Each person signs in with email, password and an authenticator code, then adds Google/GitHub from Settings while signed in. It is never linked automatically by matching email.
  5. Remove the old root from every device (reverse of the install steps), then delete the intermediate from the box (polycarpic-ops remove-intermediate). Keep the root key in your secret store for the record, or destroy it.

8. Operations Runbook

Day-2. Same format: command, what you should see, what to do otherwise. After any step that changes the box, run polycarpic-ops status and confirm green before you close the laptop.

Two facts for any user-support case: only a database superuser can correct a user's email address (no role the app or the operator CLI uses can); and a notice that cannot be delivered keeps its second-step method held, so fix the sending key or the address, or reset the user's second step with cli user reset-mfa.

8.1 Rotate a secret

  • Provider key or token (Resend, price, BLS, OAuth client secret, Plaid secret, bucket put-key): create the new one at the provider, then sudo polycarpic-ops set-secret <name>, then restart the services set-secret names in its last line (sudo polycarpic-ops restart auth worker for resend_api_key), then revoke the old one at the provider. Expect <service>: healthy for each, and status green. The bucket key is held by the one-shot uploader alone, so nothing restarts: the next uploader run reads it, and you expect a successful upload within 5 minutes after systemctl start polycarpic-upload. Order matters: revoke last.
  • Database role password: sudo polycarpic-ops rotate-db-password app|worker|migrator|backup. It changes the role in Postgres and the file in one step and restarts the matching container. Expect healthy.
  • BetterAuth secret (planned rotation, SECURITY A-33): sudo polycarpic-ops auth-secret add adds a new version that encrypts new data while older versions still decrypt; restart; run polycarpic-ops cli auth rewrite-secrets (re-encrypts TOTP seeds, backup codes and OAuth tokens under the newest version); when it reports 0 rows on old versions, run polycarpic-ops auth-secret retire <version>. Expect that nobody is signed out. Never replace the secret outright outside an incident: it ends every session and makes every enrolled second step undecryptable (everyone would need reset-mfa).
  • Annual review: list every secret with list-secrets and rotate any that you cannot account for.

8.2 The monthly window (first Sunday, about 45 minutes)

  1. Run the restore drill from the laptop (§6.7). Expect DRILL PASSED; a failure is SEV2 (RB-5).
  2. box$ sudo apt update && sudo apt full-upgrade, then sudo reboot if it says so (the reboot can wait about a minute behind apt-daily: wait, and do not issue it twice). Expect: after about two minutes polycarpic-ops status is green. The home box must come back without asking for a passphrase, root and data both (§7.2 step 6 check 1); on the home box this is also where you reboot after a kernel update until the unattended-reboot check has passed (§3.5). Check ls /var/run/reboot-required before closing the window: with automatic reboot off, a file older than 7 days raises the pending-reboot alert (§6.5), so a missed window is noticed.
  3. Docker: if apt held back Docker packages, upgrade them now; containers restart.
  4. Check polycarpic-ops status: disk under 80 percent, certificate more than 14 days left, GitHub token more than 14 days left.
  5. Read the month's alerts and any rolled-back deploys in /opt/polycarpic/deploy.log.
  6. Check that the last renovate-check run is green; if it is red, bump the lines it names (§6.1a).
  7. Re-read the operator-account checklist of §7.0 (C-78): two-step sign-in, own password and recovery address on every account, the registrar transfer lock, and no Hetzner API token left on the laptop (ls ~/.config/hcloud is empty). provision-check cannot see these.
  8. From the laptop run python3 infra/operator/dns-check.py --ipv4 <address> --ipv6 <address> (ends DNS CHECK PASSED), python3 infra/operator/laptop-check.py (ends LAPTOP CHECK PASSED), and python3 infra/operator/b2-setup.py: type anything but yes at its plan prompt and read its bucket checks and key read-back, which must show no FAIL. It asks for a fresh master key and regenerates it afterwards.
  9. Tell Healthchecks.io the drill happened: laptop$ curl -fsS -m 10 --retry 3 "$(polycarpic-ops heartbeat-url drill)" (the helper prints the check's address from the ping key kept in your secret store). Expect: the polycarpic-drill check turns green; if it is not pinged for 35 days you get an email.

  2. Force a renewal test: sudo polycarpic-ops caddy-renew-test. Expect: staging ACME order succeeded (it uses the issuer's test environment).

8.10 Restore from backup and replace a box

  1. Get the keys in front of you: age private key, the keyring offline copy, the provider secrets from their consoles, the recovery sheet.
  2. Build the replacement by repeating §7.1 steps 6 to 11 (Hetzner) or §7.2 (home) with a new, empty data volume, but do not yet point DNS at it and do not run first-deploy.
  3. Restore the data on your laptop first (it needs the age private key, which must not touch the new box): laptop$ infra/restore.sh --identity <age key file> --read-credential <file> --bucket <name> --base decrypts the newest complete nightly set's base and every WAL version of the same system id from the bucket, and recovers them in a throwaway Postgres in a container (no network, no capabilities, no bind mount); --dump restores the dump and the globals file instead (the whole dump, never data-only, so app.session_handle comes with session). It refuses to run unless the identity file is mode 0600 or tighter and, on macOS, fdesetup isactive succeeds (otherwise pass --plaintext-disk-is-encrypted if you know the disk is encrypted). Expect the last three lines this scratch removes itself at <UTC time> (--hours 8); remove it and any other now with: restore.sh --cleanup, scratch container: <name> and connect: docker exec -it <name> psql -U postgres: the container runs docker run -d --rm … sleep <hours> with --hours 1 to 24 (default 8, anything else exits 2), so a forgotten restore does not leave a decrypted ledger in Docker's disk. restore.sh --cleanup removes every container labelled polycarpic.restore=scratch and prints how many; every run warns about ones that still exist. A name with a second version or a hide marker (a retry after a checksum mismatch makes one) exits 3 and lists every version on stderr as version <fileId> <time> <object> sibling yes|no (whether that version's bytes match the name's sibling); --before <UTC> picks the time to restore as of and prints a WARN, and --accept-version <fileId> (repeatable) takes that version and prints WARN accepting version <fileId> of <name>; an id that belongs to no chosen object exits 2, and a version whose bytes do not match the sibling exits 4. A bucket key outside the naming grammar (the put-only key can write any name) is left out and counted: the run prints WARN <n> stray objects in the bucket and goes on. Compare the scratch cluster with what you expect; the decrypted files sit in a temporary directory that is removed on exit unless you pass --keep. Sending the recovered data to the new box and applying it is not part of this tooling: do it only by streaming it, with no plaintext file on the box, into a separate throwaway cluster, never a database inside prod.

    The plain data exists on your laptop only. If the laptop is shared or unencrypted, use a throwaway server for the decrypt step instead.

  4. Re-run roles.sql as the superuser against the restored database: box$ sudo polycarpic-ops provision --stage database --project prod (the same step provision.sh runs, §4.5). Then sudo polycarpic-ops status shows OK revokes prod plpgsql and 17 built-ins closed to PUBLIC. A physical or logical restore can bring back the old language and function privileges, and the file re-applies the plpgsql revoke and the revoke of the 17 SQL-string built-ins. The restore drill (§6.7) runs it too and checks that DO $$BEGIN END$$ as poly_app fails with permission denied for language plpgsql.
  5. Re-enter the secrets (§7.1 step 12), restore the keyring file from the offline copy (polycarpic-ops restore-keyring; keyring-fingerprint must match what you wrote down), or generate a new keyring and relink every connection (RB-4).
  6. Deploy the last release (polycarpic-ops first-deploy prod), open it, switch DNS to the new address, and confirm in the outside-in scan (§7.1 step 15).
  7. Run a backup and the monitor check; run the restore drill once more within the week.
  8. Time yourself. RTO is 4 hours on Hetzner; if you took longer, write down the slow step and tell the team-lead so §7 improves.

Temporary landing on Hetzner for a lost home box: do the same on a Hetzner server with --target hetzner, using a temporary DNS name. Household members use that name until the home box is rebuilt. Real-domain mode on the home box is unaffected by this.

Neon: create a new Neon project, restore with polycarpic-ops neon-restore from the latest weekly export (decrypt on the laptop), update the Vercel variables, redeploy with infra/vercel/deploy.sh.

8.11 Suspected compromise (commands for SECURITY RB-1, RB-2)

  1. Stop the bleeding. box$ sudo polycarpic-ops lockdown: Caddy serves the maintenance page and every other container stops. Expect: the outside scan shows only Caddy. If you cannot log in, disable the server's network in the provider console (Hetzner) or unplug the cable (home).
  2. Keep the evidence. Hetzner: take a server snapshot in the console. Home box: do not power off if you can avoid it; copy deploy.log and docker logs output to the laptop.
  3. If the worker or keyring may be exposed (RB-1): revoke every bank token at its provider (Plaid /item/remove, SimpleFIN, broker OAuth), then after the replacement is up, generate a new keyring and relink. If only the keyring leaked, polycarpic-ops cli secrets rotate (§8.12) is enough; if the database and the keyring may both have been exposed, rotation is not enough.
  4. Rotate every operator secret (§8.1), the BetterAuth secret by replacement this time (sessions all end), the bucket keys and the DNS token. Remove the SSH keys you cannot account for (§8.8).
  5. Rebuild from a clean attested image on a fresh host (§8.10), restoring the last backup taken before the compromise, and verify it against the hash chain and against the head of the last export an owner holds off the box (RB-2 step 6).
  6. Postmortem within 5 business days (SECURITY §10).

8.12 Rotate the credential keyring

box$ sudo polycarpic-ops cli secrets rotate. Expect: it adds key n+1, re-seals every connection under it, and ends rows remaining under old key: 0; removed key n; audit_event written. Save the new keyring offline immediately: polycarpic-ops keyring-show prints it once; replace the password-manager note and the printed sheet, and confirm with keyring-fingerprint. If it stops midway it is safe to run again.

8.13 Decommission

  1. Export everything each household member wants to keep (app export carries the hash-chain head); run a final backup; wait for it to appear in the bucket.
  2. Revoke every bank connection from the app (Settings → Connections → Unlink) and confirm each at its provider.
  3. Hetzner: delete the server, the volume, the firewall, the SSH key and the project. Home box: remove the intermediate/DNS token, then securely erase the disk (sudo cryptsetup erase /dev/… then blkdiscard, or physically destroy it).
  4. Delete the DNS records and the DNS token; remove the private CA root from every device; delete the Resend domain, OAuth apps, monitors and the GitHub token.
  5. Backups: nothing to delete; they expire in 35 days and cannot be removed earlier. Destroy the age private key only after you are certain you will never restore (or after the last backup expires).
