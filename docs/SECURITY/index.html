1. Compliance Posture

Source of truth is PRD §6 (Non-Functional Requirements) and the Principal's audience decision of 2026-09-27.

Polycarpic is software a person installs and runs for their own household. The Principal will never operate it as a service for others. That is a standing non-goal (PRD §3), not a v1 deferral. Nobody is anybody's "customer", so no formal compliance regime attaches.

That does not lower the bar. The Principal made the PRD §6 security items hard requirements, and this document treats them that way. Every control here answers a threat in §3, not an auditor. The yardstick is OWASP ASVS 4.0 Level 2, used as a checklist, not as a certification target.

3. Threat Model (STRIDE)

One table per component group. Only threats with non-trivial likelihood × impact are listed. L = likelihood, I = impact (H/M/L). Control IDs refer to §7.

Attacker model.

  • (a) An internet attacker who can reach Caddy.
  • (b) A curious or malicious household member with a legitimate viewer or manager grant.
  • (c) A counterparty who controls text that lands in our data. Anyone who sends the user money writes a payee or memo string.
  • (d) A compromised dependency or CI path.
  • (e) A thief with a backup or a disk.
  • (f) An attacker with code execution in web. This one is in scope, and the design limits what they get.

The operator's own superuser is not modelled as an attacker (R-1).

4. Authentication & Authorization

§4.3–§4.5 are the rulings on ARCH OQ-2, OQ-3 and OQ-4. OQ-1 is ruled in §6.3. §12 has the summary and the changes against 8963efb.

4.1 Authentication

  • Provider. BetterAuth in our own Postgres, via the Drizzle adapter. Sign-in methods:
    • Email + password, hashed with scrypt (the BetterAuth default).
    • OAuth 2.0 with PKCE and a verified state, via Google, Apple or GitHub.
    • Passkeys.
    • Optional magic links sent through Resend.
  • Invite-only registration (C-01). The first user on an empty instance is the bootstrap user. After that:
    • Self-signup is off. New users arrive only through a membership invitation from an entity owner.
    • OAuth sign-in for an unknown email with no pending invite is rejected.
    • No switch reopens public sign-up (Principal, 2026-11-07, P6). No configuration flag or environment variable enables self-signup, so there is nothing to flip by mistake or through a configuration compromise.
    • An invitation that shares no entity: polycarpic user invite <email>.
      • Runs on the box only, by the operator, and writes an audit_event.
      • Creates a single-use invitation with the same expiry as an entity invitation.
      • The invitee gets only their own Person entity.
      • No entity is involved, so neither the co-owner approval (§4.2.2) nor the ancestor-invite notice applies.
  • MFA (C-03). TOTP and passkeys, with single-use backup codes. BetterAuth stores the codes encrypted (XChaCha20-Poly1305 under the auth secret), not hashed. It checks a code by decrypting the list, so hashing them is not an option.
    • Ruled (Principal, 2026-11-07, P1): a second step (TOTP or a passkey) is required for any user holding owner or manager on any entity, with the one exemption below. It is optional for viewers (R-7). OAuth-only users must enrol a passkey or TOTP to hold those roles, because we cannot verify the IdP's MFA.
    • The own Person is exempt until the first real action (Principal, 2026-11-08, OQ-34). Every user owns their own Person from sign-up, so without an exemption the rule above would bind everyone, viewers included. The owner row on a user's own Person (entity.self_user_id) is exempt while that Person is unshared: it has no other member, and it is not rolled up into a parent entity (A-28). Enrolment is forced, and the action is not performed, before any of these:
      • creating a Trust, Business, Household or Holding (the creator's owner row is refused);
      • sharing the own Person: the first invitation on it, or linking it under a parent, whose members would then see it (C-25);

      • any step-up action on the own Person (export, purge, granting access, linking a bank), because step-up needs a second factor.
      Viewing shared entities never triggers it. Unenrolled, the user can read and keep their own unshared books by hand, and nothing more. The refusals are in the database (BEFORE INSERT triggers on membership and invitation, ARCH §3.1c), not only in the UI.
    • The first factor is anchored on the account email (Principal, 2026-11-08; T-82). A gate that asks for the password and then accepts the first factor offered stops only someone at an unlocked laptop. A password thief can do the same steps on their own device. So a user with no factor enrols their first one only after confirming a code sent to the account's email address, as well as the password. This applies at every OQ-34 gate, at the sign-in gate after an operator reset-mfa, and to an OAuth-only user, whose fresh IdP round trip stands in for the password.
      • Order. Password (or the fresh round trip), then the emailed code, then the factor. The code is asked for before any TOTP secret is shown or any passkey ceremony begins, so a thief learns nothing and stores nothing.
      • The code. Six digits from a CSPRNG, also offered as a link. It lasts 10 minutes and is used once. It is stored hashed as a T1 verification token and never logged. Five wrong entries void it. Sends are limited to 3 per 15 minutes per user (C-04). The response is the same whether or not a send was suppressed.
      • Bound to the session. The code, and the enrolment grant it opens, are keyed to the session that started the set-up. A code entered in another session, or after a new sign-in, is refused. The grant lasts 10 minutes and is consumed by the first factor write.

The gate is in the app, which wraps BetterAuth's enrolment endpoints, and in the database (A-29), so a forgotten route fails closed.
      • Email is not a factor. BetterAuth's otp two-factor method is not configured. An emailed code anchors the first enrolment, and never stands in for the second step.
      • Once a factor exists, nothing changes. Adding a second method, and every step-up, uses the existing factor. The email anchor is for the first factor only.
      • Residual. A thief with both the password and the email account can enrol. Email is already the recovery root (magic-link sign-in, invitations, the new-device notice in §9), so this adds no root. The user is emailed when a factor is enrolled (§9).
      • BetterAuth, measured (better-auth 1.7.18 and @better-auth/passkey 1.7.18, 2026-11-08, POLY-62 spike). Where the docs and the code differ, the code was taken as correct. Paths are under node_modules/better-auth/dist/.

4.2 Authorization model

RBAC over the membership join (user, entity, role), enforced by Postgres RLS. A user's rights come only from membership rows. They never come from a user_id column on a data table, and never from entity structure. Access is a grant; the hierarchy grants nothing.

can(role, action) in packages/tenancy exists to render a correct UI and to return a clean 403 early. It is not an enforcement point.

The design test: delete every can() call, and the system must still be safe. Any control that fails this test is app-layer-only authorization, and the security gate rejects it.

There are two exceptions, and both are enforced in database functions rather than can(): step-up recency (checked by the route, and required as an argument by the purge function) and sole-owner status.

4.2.2 Co-owner approval on multi-owner entities (Principal, 2026-11-07, P5b)

Co-trustees and partners govern as a group. Without this rule, any one owner, including a 0-unit bookkeeper owner, could admit anyone, raise a role or rewrite ownership alone (T-26). On an entity with more than one owner, these changes need the approval of every other current owner:

  • (a) inviting a member, or raising a role (viewer → manager → owner);
  • (b) removing or demoting a co-owner;
  • (c) any cap-table edit (equity_total, equity_holding).

Removing a viewer or manager, and lowering or giving up one's own role, stay single-owner actions. Sole-owner entities are unaffected.

  • A pending state, enforced in the database.
    • The request. A change_request row holds entity, kind, payload, requester, created time, expiry and status (pending | applied | declined | expired | withdrawn). One change_approval row is written per approving owner, and both tables are append-only apart from the status.
    • Direct writes. poly_app's direct INSERT and UPDATE on membership, invitation and equity_*, for the actions above, pass only while app.owner_count(entity_id) = 1.
    • Multi-owner path. Otherwise the only write path is app.apply_change(change_id). It is an allowlisted definer owned by a new NOLOGIN, NOBYPASSRLS poly_govern role, holding role-targeted INSERT and UPDATE on exactly those tables. A can()-only gate fails the §4.2 design test.
  • Who approves. The approvers are every current owner other than the requester, recomputed when the change is applied, never fixed when it is requested.
    • For a co-owner's removal or demotion, the target is one of the approvers, so no owner can be removed by the others alone. A deadlock is broken by the founding owner (below).
    • An approval counts only if its approver is still an owner at apply time.
    • One decline ends the request.
    • The requester may withdraw it.
  • Applying. When the last approval lands, apply_change runs in that approver's transaction and re-validates the payload against current state:
    • the role still exists;
    • the cap-table Σ invariant holds;
    • the entity version the request was made against is unchanged, or there is no conflicting applied change since.
    If validation fails, the request is declined as stale and nothing applies. Only on apply does the invitation become live and its email go out.
  • Step-up. Requesting, approving and declining each need a re-authentication within 5 minutes, with the second factor required for owners (C-03, P1).
  • Audit and notice. Each step writes an audit_event: change.requested, .approved, .declined, .withdrawn, .expired and .applied. Every owner is notified on request and on outcome. Pending requests, including an invitee's email address, are visible to owners only.
  • The founding owner (Principal, 2026-11-07, R-19 ruling). Each entity records one founding owner, entity.founding_owner_user_id, set to its creator. For a Person entity that is its own user.
    • Always an owner. A trigger refuses any state where the founder does not hold owner.
    • Breaking a removal deadlock. Once a request to remove or demote a co-owner is declined or expired, the founder may force it through app.force_change(change_id), a poly_govern definer.
      • It requires that the caller is the founder, that the kind is a co-owner removal or demotion, and that the status is declined or expired.
      • It requires a step-up within 5 minutes, with the second factor.
      • It writes a change.forced audit_event and notifies every owner, the target included.
      • The founder may raise the request themselves. The force still needs the decline or the 14-day expiry first, so the target always has warning.
    • No other extra power. The founder has none over invites, role raises or cap-table edits, which still need every other owner. The founder is never a target of force_change.
    • Leaving the role. The founder can only step down or transfer it in-app, as a founder-only action, with step-up and a notice to every owner.
      • Stepping down names a successor among the current owners.
      • A founder who would give up their own owner role must transfer the founder role first, if another owner exists.
    • Account deletion.
      • In the in-flow deletion (§4.6), a founder of an entity with other owners must name a successor among them. The tombstone transaction refuses while any entity still names them as founder.
      • On a sole-owned entity, the transfer target becomes founder. On a purge, the question does not arise.
    • A founder who vanishes without deleting. The backstop is the operator CLI (polycarpic entity set-founder, polycarpic membership …), which is audited and notifies every owner.
  • Edges (SecEng rulings):
    • An owner who never responds.
      • A request expires 14 days after it is made, and expired counts as declined. Silence never approves.
      • Owners are reminded at day 7.
      • The requester may ask again. One open request per kind and target, and an expired request can be re-raised at most once per 7 days.
    • An approver in the middle of account deletion.
      • While their deletion flow runs they are still an owner and may approve or decline.
      • At their tombstone they stop being an owner, so their approvals stop counting and they stop being required.
      • Each pending request on their entities is re-evaluated. If it is now fully approved, it is not auto-applied: the requester is notified to confirm, with step-up.
      • Leaving an entity is giving up one's own role, so it needs no approval.
    • The owner set changes while a request is pending.
      • A new owner becomes a required approver.
      • A departed owner drops out, and the requester-confirm rule above applies.
    • Bootstrap, when the second owner is added.
      • A sole owner adds the first co-owner, by invite or by raising a member's role, as a single-owner action. There is nobody to approve.
      • The invitee's acceptance is their own consent, and they do not approve their own admission.
      • From the moment two owners exist, every further change in (a) to (c) needs approval.
      • Invitations sent while sole owner (OQ-31, confirmed). When the effective owner count goes from 1 to 2, every outstanding invitation the sole owner issued on the direct path is revoked, at every role, and its inviter is notified to re-raise it as a request. Otherwise an owner invitation issued alone could land after the approval rule applies.
        • An invitation records how it was issued (direct, or the change_request that applied it), and that column is not updatable. Approved invitations are not revoked.
        • The revocation runs in the same transaction as the membership write that makes the second owner, not in a later job. That write locks the entity row before counting owners, so two direct owner invitations accepted at once serialize: the first makes two owners and revokes the second.
        • A revoked token is refused at acceptance with the same response as an expired one.
        • The rule fires on every 1 → 2 transition, including after an entity drops back to one owner. A raised owner still waiting for enrolment (§4.1) does not count until the role is effective. The transition, and the revocation, happen at enrolment.
      • The entity-creation default cap table, and transfer in account deletion, are sole-owner cases.
    • Pending changes and the purge. A purge needs a sole owner, so §4.2.2 never meets it. Pending requests on a purged entity are deleted with it, and their audit events survive.

pgTAP for the sidebar-IA rows (qa-engineer, C-17). Each row gets an allow test and a deny test, run as poly_app with the app layer bypassed:

  • A viewer cannot run any of the actions: every INSERT or UPDATE is rejected by policy.
  • A manager cannot relink or unlink another user's connection.
  • A mapping to another entity's account fails the composite FK.
  • An auto-post whose opting-in user has been demoted to viewer writes 0 rows, and its rule ends with auto_post = false.
  • A "Correct entry" never UPDATEs the original; it leaves one reversal plus one new entry.
  • Sync and schedule below the minimum interval are rejected.

Revocation semantics. Revoking a membership takes effect on the next transaction; there is no cached authorization. The user's sessions stay valid for their other entities. Data a client has already fetched cannot be recalled (R-11). The native milestone must purge its cache on any 401, 403 or empty scope.

4.3 RLS mechanism — ruling on ARCH §3.3 (OQ-2)

Ruling: confirmed, with amendments. These stand as designed: transaction-local GUC, STABLE SECURITY DEFINER visibility functions, ENABLE + FORCE on every tenant table, and default-deny.

Additions (a)–(d) are already in ARCH (from 8963efb) and remain in force:

  • (a) The coverage probe is derived from the catalog.
  • (b) No CREATE on public.
  • (c) Per-command policies with WITH CHECK on every write; FOR ALL is banned.
  • (d) The inversion canary stays.

Review found defects that (a)–(d) do not cover. Amendments (e)–(l) are new:

  1. FORCE RLS vs. the definer functions (latent defect, T-20).
    • The problem. Under FORCE, the table owner is also subject to policies. ARCH has visible_entities() and has_role() owned by poly_owner, and they read membership, which is itself FORCEd.
    • Why it breaks. Once membership's own SELECT policy calls has_role() (so that managers can list members), the chain function → membership policy → function makes Postgres raise "infinite recursion detected in policy". If the policy does not call it, the functions silently see only the rows the policy allows.
    • Fix. A poly_authz role (NOLOGIN, NOBYPASSRLS) with SELECT on membership and entity_type only, plus a role-targeted policy CREATE POLICY authz_read ON membership FOR SELECT TO poly_authz USING (true). Both functions are owned by poly_authz. FORCE stays uniform and nothing gets BYPASSRLS. poly_app cannot use the policy, because it is not a member of poly_authz.
  2. The empty-string GUC (defect).
    • The problem. 8963efb and ARCH say current_setting('app.user_id', true) returns NULL when unset. That is only true until the GUC is first touched in a session. After any transaction-local set, the placeholder reads back as '', and ''::uuid raises. That is fail-closed, but noisy and fragile.
    • Fix. Every policy reads app.current_user_id(), which is nullif(current_setting('app.user_id', true), '')::uuid. The pool-reuse test runs its no-context probe on a connection that has already carried a context.
  3. TRUNCATE (defect). It ignores RLS and fires no row-level DELETE triggers. Fix: a statement-level BEFORE TRUNCATE trigger that raises on every append-only table, and no login role holds TRUNCATE.
  4. Pinned search_path.
    • Definer functions use SET search_path = '', and every name is schema-qualified.
    • EXECUTE is revoked from PUBLIC and granted explicitly.
    • Policies call these functions as (select app.fn()), so each is evaluated once per statement as an initplan.
    • A catalog allowlist names every SECURITY DEFINER function, and any function not on it fails the battery.
  5. Immutable tenancy columns. entity_id, actor_kind and actor_id are left out of poly_app's column-level UPDATE grants, so no row can change tenant or author. UPDATE policies carry both USING and WITH CHECK.
  6. Views. Every view over tenant tables is created WITH (security_invoker = true). Materialized views over tenant data are banned, because RLS cannot apply to them. The battery asserts both rules.
  7. Role hygiene. poly_app and poly_worker are NOSUPERUSER, NOBYPASSRLS and NOCREATEROLE. They have no TRUNCATE, REFERENCES or TRIGGER grants and are members of no other role. The battery checks this with pg_has_role and has_table_privilege.
  8. Non-enumerable identifiers. Primary keys for tenant-visible rows are UUIDs (v7 is acceptable). FK checks bypass RLS, so sequential IDs would make an existence oracle. ARCH §4.1's /entities/42 becomes a UUID.

Pool safety. set_config(…, true) is safe under the in-process node-postgres pool and under transaction-mode pgbouncer, including Neon's pooler. The rules that keep it safe:

  • Statement-mode pooling is banned, because it breaks transactions.
  • The deploy checklist asserts the pooler mode on both targets (DevOps).
  • withTenant() refuses to nest (AsyncLocalStorage guard).
  • withTenant() accepts only a branded SessionUserId, which only packages/auth can construct.
  • The raw pool is not exported, and the layer lint enforces that.
  • Session-level SET is banned by lint.

What RLS buys, and what it does not.

  • It buys: authorization bugs become empty results instead of leaks. That covers a missing WHERE, an IDOR, a forgotten table.
  • It does not buy: any defence against SQL injection or code execution inside poly_app. The GUC is app-asserted, so anyone who can run SQL as poly_app can set it to anyone (R-2).
  • For that case: prevention is C-44. The blast radius is capped by C-30 (web cannot open credentials) and C-10 (no DDL, no TRUNCATE).

4.4 System jobs — ruling on OQ-3

Ruling: confirmed as folded into ARCH. A job's tenant writes run under the linking user's membership. No tenant policy has a system bypass clause. The requirements already on POLY-64 stand:

  • provider_connection.linked_by_user_id is NOT NULL.
  • withSystem(job, connection, fn) sets app.user_id to that user and app.actor = system:<job>. Authority and attribution stay separate.
  • If that user's membership drops below manager, or their account is deleted, the connection flips to principal_invalid. That state surfaces on the dashboard, writes an audit_event and notifies the owners. It never fails silently.
  • A job never falls back to running context-free. If no principal resolves, it errors.

Additions:

  • Entity-bound jobs with no connection (the tax-period freeze) run under a current owner of the entity, chosen deterministically as the earliest owner membership, with actor = system:<job>. Every tenant write therefore has a human principal.
  • Scheduling needs a cross-tenant list of targets. That list comes from one allowlisted SECURITY DEFINER function, app.job_targets(job), which returns only (entity_id, principal_user_id, connection_id). Only poly_worker can execute it.
  • Reference-data writes (prices, CPI, tax tables) go through role-targeted policies (TO poly_worker). poly_app gets SELECT only. A role-targeted policy cannot be unlocked by any GUC that poly_app sets.
  • Cash-in-Transit aging is computed on read by the exceptions report, not stored by a job. That removes a job that would need cross-tenant reads.
  • poly_worker tenant DML is limited to the import path:
    • import_batch, raw_transaction, reported_balance
    • draft, transfer_match
    • status columns of provider_connection
    • journal_entry / journal_line, for auto_post only
    • tax_period_freeze, audit_event

4.5 The purge path — ruling on OQ-4 (revised)

Ruling: the purge function is owned by a dedicated NOLOGIN poly_purge role, with role-targeted DELETE policies. This reverses 8963efb, which had the function owned by poly_owner and rejected a separate role. The guard order ARCH folded in is kept, with two guards added.

  • Why 8963efb's shape fails (T-51).
    • A definer function owned by poly_owner runs as the table owner, and under FORCE ROW LEVEL SECURITY the owner is subject to policies.
    • Append-only tables deliberately have no DELETE policy. So the function would delete zero rows and report success.
    • Adding a poly_owner DELETE policy would instead hand the purge capability to the migration owner.
  • Why the separate-role objection does not hold. 8963efb said "a role needs a credential". A NOLOGIN role has no credential; it is only the owner identity for the definer function. The entry point is just as narrow: one function, with EXECUTE granted to poly_app. The only change is which role's privileges the function runs with.
  • Shape.
    • poly_purge is NOLOGIN and NOBYPASSRLS, with DELETE on the purgeable tables only.
    • Each purgeable table gets CREATE POLICY purge ON <t> FOR DELETE TO poly_purge USING (entity_id = nullif(current_setting('app.purge_entity', true), '')::uuid).
    • The append-only triggers allow DELETE only when current_user = 'poly_purge' and OLD.entity_id matches the GUC. poly_app can set the GUC but can never become poly_purge.
    • app.purge_entity(entity_id, export_id, reauth_at) is SECURITY DEFINER, owned by poly_purge, with search_path = ''.
  • Guards, in order, in one transaction:
    1. Re-authentication within 5 minutes. The route checks it, and the function requires the timestamp as an argument.
    2. Sole-owner check against app.current_user_id().
    3. An export.completed audit event for this entity, by this user, within 24 hours, carrying a SHA-256.
    4. (New.) No tenant write to the entity since the export's snapshot marker, so a manager's later postings cannot slip past the export. The entity row is locked FOR UPDATE.
    5. An entity.purged audit_event is written before the first delete. It records the actor, entity id and name, the export event, per-table row counts and timestamps. audit_event has no FK to entity and no purge policy.
    6. Every connection is revoked at the provider. The worker revoke job must have succeeded; a failed revocation blocks the purge and is never skipped.
    7. Set app.purge_entity transaction-locally and delete in dependency order.
    8. (New.) Assert zero rows remain for the entity in every purgeable table before commit. This is the fail-loud guard against T-51.
  • Not permitted:
    • purge by a job;
    • purge through the API without interactive, typed confirmation of the entity name;
    • purge of a partial date range (that is an edit, and edits are reversals);
    • purge while a second owner exists.
  • Backups: purged data persists until the backup retention window rolls (R-5). The purge warning says so.
  • Rejected alternatives:
    • ALTER TABLE … DISABLE TRIGGER is DDL. It needs an ACCESS EXCLUSIVE lock and the table owner, and it affects every tenant.
    • Tombstoning is not a purge, so it breaks the PRD §5 promise.
    • BYPASSRLS is broader than needed.
  • No execution delay (Principal, 2026-11-06, OQ-23). SecEng had recommended a cancellable 24-hour delay against a hijacked session. The Principal ruled it out, after hearing that rationale and the architect's objections.
    • The purge runs as soon as the guards pass.
    • Every member is emailed immediately, before the entity's rows go.
    • Recorded as R-16.
  • Roll-up junction. The entity_rollup purge policy matches either column, so purging an entity removes it from every parent and the parents' owners are notified (ARCH §3.4). The cap-table rows on other entities that name the purged entity as a holder are open: see A-19.

4.6 Account deletion in-flow — who invokes the purge (OQ-25)

Ruling: the account being deleted is the only invoker of every step. This follows ARCH §3.4a, on the Principal's ruling of 2026-11-06, which replaced the refusal for a sole owner.

  • Who. Only the user who is deleting their account, signed in, with a fresh step-up:
    • password plus their second factor, or a passkey;
    • an OAuth-only user does a forced fresh round trip (prompt=login, max_age=0), plus their second factor (required for an owner, P1);
    • a user with no second step (Principal, 2026-11-08): the password, or the fresh round trip, plus a code sent to the account's email, with the same lifetime, attempt cap, send limit and session binding as the first-enrolment code (§4.1). No factor is set up. A departing user gains nothing from a factor they would use once, and a password thief without the mailbox can neither delete nor enrol (T-84, T-82). The confirmation authorises this deletion run only, including the own Person's export it produces, and no other step-up action.
    An enrolled user's deletion is unchanged. An unenrolled user can hold no manager or owner role outside their unshared own Person, so their run is that Person's purge (with its export), their viewer memberships ended, and any held raise cancelled. The plan, transfer-or-purge choices, exports and typed name are otherwise unchanged. Never a job, never another member, never the operator CLI. The user still holds owner when each purge runs, so the §4.5 sole-owner guard passes on its own terms, and no guard is relaxed for this flow.
  • The plan is bound to the session. The per-entity choices (transfer to whom, purge with which export) are held server-side, keyed to the session that made them.
    • Another session, or a new sign-in, starts again from the list.
    • If the 5-minute step-up lapses mid-run, the user is prompted again. The run never continues silently.
  • Founder succession. For each entity where the user is the founding owner and other owners remain, the flow requires a successor named among them (§4.2.2). A sole-owned entity's transfer target becomes founder.
  • Exports. Every purge choice carries its own export.completed event, by this user, within 24 hours (guard 3). The flow produces these exports before the final confirmation.
  • Order. Transfers first, then purges, then the tombstone.
    • A transfer names a current member who is not mid-deletion themselves. The recipient is notified, and the transfer writes an audit_event.
    • A failed provider revocation stops the run at that entity (§4.5 guard 6). Nothing later is applied.
  • Audit. One account.deleted audit_event records every choice: the transfer targets, and each purged entity's id with its export SHA-256. It sits alongside the per-entity entity.purged events. All of them keep the tombstoned user id.
  • Email. Every member of a purged entity is emailed as each purge begins (OQ-23). The departing user gets a confirmation at their address before the tombstone removes it. Every remaining member of a shared entity they leave is notified (ARCH §3.4a).
  • Tests (C-52):
    • another member cannot drive a deletion's purge step;
    • a plan made in session A cannot be confirmed from session B;
    • a lapsed step-up blocks the next purge;
    • an unenrolled user's deletion needs the password and the emailed code, offers no factor set-up, and is refused with the password alone;
    • the unenrolled deletion confirmation does not pass step-up for any other action;
    • a failed revoke leaves the account undeleted and the remaining entities untouched;
    • the tombstone transaction refuses if a sole-owned entity appeared during the flow.

6.2 Operator secret handling

  • Files, not environment variables.
    • Secrets live on the host in /etc/polycarpic/secrets/ (root:root, files 0400, directory 0700).
    • They are mounted as compose secrets: at /run/secrets/, and apps read them through the *_FILE convention.
    • Why: environment variables leak through docker inspect, /proc/<pid>/environ, child processes and error reporters that dump process.env.
    • Revised: 8963efb and ARCH §9 specify a root-only env file.
  • Per-container scoping. Each container gets only the secrets it needs. web never gets the credential private key or the backup key. Staging gets its own values, and its own keyring, which seals only Plaid Sandbox and SimpleFIN demo tokens. It never gets prod's keyring or the production Plaid secret (C-77). Revised in v1.1: staging had no keyring while it used only the fake provider.
  • Nothing in images. No secret is ever baked into an image or passed as a build arg. .env.example lists names with a comment each, never values.
  • Fail closed at startup. Outside development, the app refuses to start if a required secret is missing, or if a secret-looking env var is set in production.
  • Read once. Secrets are read at startup. There is no runtime secret-fetch path and no admin endpoint that reveals configuration.
  • Vercel. The tertiary target uses Vercel's encrypted env vars (R-3). The hosting order is Hetzner, then the local box, then Vercel + Neon (Principal, 2026-11-06).
  • Local box. Same file layout as the Hetzner path. In real-domain mode (P7) the DNS-API token is a file secret mounted into Caddy only, scoped to one zone (C-76).

6.3 Credential sealing — ruling on OQ-1 (revised)

Ruling: app-layer asymmetric sealing in packages/secrets. web holds only public keys; the private keyring is mounted into worker only.

This replaces 8963efb's symmetric envelope scheme, which ARCH §3.1 and TB-4 folded in: an AES-256-GCM DEK wrapped by a master key mounted into the app. The seam is unchanged: seal() / open() with a key_id. Rejecting pgcrypto and external KMS still stands (§6.5).

  • Why revise.
    • With a symmetric master key, whoever seals can also open. The sealing process is web, because it receives the SimpleFIN setup token or the Plaid public token.
    • web is also the internet-facing process, and the most likely place for RCE or SSRF. So one web compromise would yield every bank token (T-31).
    • Asymmetric sealing removes that path at about the same implementation cost.
  • Algorithm. HPKE (RFC 9180) base mode: DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, AES-256-GCM. The library (e.g. @hpke/core, or an equivalent over node:crypto) is pinned in the packages/secrets design file, with SecEng sign-off. No home-rolled construction.
  • Binding. The HPKE aad is the canonical encoding of (connection_id, entity_id, provider, key_id, alg_version). A blob copied to another row fails to open (T-32).
  • Stored columns. enc (the encapsulated key), ciphertext, key_id, alg_version. These replace ARCH §3.1's "ciphertext + nonce + wrapped DEK + key_id".
  • Flows.
    • Link (in web): receive the setup or public token, exchange it with the provider, seal() the result under the active public key, insert the row, drop the plaintext.
    • Poll (in worker): open() inside one call frame, for one provider call. The plaintext is never cached and never held in a module-level variable.
    • Unlink: web enqueues a revoke job. worker opens the credential, calls adapter.revoke(), then deletes (C-32).
  • Database enforcement. poly_app has column INSERT and UPDATE on the sealed columns, but no SELECT. poly_worker has SELECT. The columns never appear in DTOs or openapi.json (C-31).
  • Errors. Provider errors are re-thrown with the credential stripped. A raw provider exception never reaches a response or a log without passing through the scrubber.
  • Import boundary. A lint boundary rule forbids any package except packages/secrets from importing the crypto module. Only apps/worker may import open().

6.4 Key rotation for an operator with no KMS

  1. Run polycarpic secrets rotate in worker. It generates key n+1, adds it to the keyring, and publishes its public key as the active sealing key.
  2. It re-seals every row with key_id = n: open with n, seal with n+1. The step is idempotent and resumable.
  3. It asserts that zero rows remain under key n, removes n, and writes an audit_event.
  4. When to rotate: on any suspicion that the worker, the box, the operator's SSH key, or a backup together with the keyring was compromised, and whenever the operator changes. Annual rotation is optional hygiene. If the keyring and the database may both be exposed, rotation alone is not enough: revoke every token at the provider and relink (RB-1).

A lost keyring means relinking, not data loss. Every connection shows "relink required". The ledger is not encrypted under this key. The runbook says this plainly, so that nobody stores the key next to the backup "to be safe". The keyring is never part of the backup set.

6.5 Why not pgcrypto, and why not a secrets manager

  • pgcrypto (rejected). The key and the plaintext would pass through SQL. That puts them in pg_stat_activity, potentially in statement logs, and in the same process as the data. A stolen dump must yield inert ciphertext. With the key co-located, it does not.
  • Vault or a cloud KMS (rejected for v1). On a single VPS, a vault's unseal material sits on the same box. So it adds a service for a novice operator to run without adding real separation. It would also break the near-zero-spend guardrail and add an availability dependency. The key_id seam leaves room for a KMS-backed keyring later; revisit if R-6 ever triggers.
  • The credential-free path stays the recommended default. The CSV/OFX adapter stores no credential. An instance that never links an aggregator holds zero T2 data. The operator runbook presents linking as a convenience trade-off.

6.6 Backup key custody — owned by DevOps (ARCH OQ-9)

Requirements on INFRA:

  • Backups are encrypted on the box before they leave it.
  • The key can be recovered without the VPS.
  • The key is distinct from the credential keyring, and the two are never stored together.

Recommended shape:

  • An asymmetric recipient (age-style), so the box holds only the public half.
  • A write-only or append-only store credential, or immutable snapshots.

With that shape, a fully compromised box can neither read nor delete its own historical backups. The acceptance test is a restore onto a clean machine. RPO and RTO numbers are DevOps's call.

C-24Per-entity ledger hash chain (Principal, 2026-11-07, P4):
  • Hash. entry_hash = sha256(prev_hash ‖ canonical(entry, its lines)), in journal_number order per entity. The canonical encoding is pinned and versioned: field order, numeric text form and UTF-8 NFC.

9. Logging, Monitoring & Detection

  • Logged: request ID, user UUID, entity UUID, route, action, outcome, latency, job name and run ID.
  • Never logged: T1 or T2 values, request or response bodies, memo or payee text, amounts, emails, cookies, Authorization, SQL parameters. The C-33 canary test enforces this.
  • Storage and retention. JSON logs stay on the box, rotated, for 30 days. Postgres logging is set per C-75. An optional OTel export must pass through the same serializers.
  • Operator alerts, sent by email through Resend:
    • more than 20 sign-in failures in 10 minutes;
    • MFA disabled, or a new passkey added;
    • a membership grant;
    • a provider link or unlink;
    • an export or a purge;
    • 3 failures of a revoke job;
    • a connection going principal_invalid;
    • a backup failure, or no successful backup within the RPO;
    • an RLS battery failure on deploy (this also blocks the deploy);
    • more than 50 authz denials or empty scopes per user in 10 minutes.
    The thresholds are provisional and unmeasured; tune them after POLY-M1. Revised: 8963efb accepted no alerting at all (its R-2). Email on these events costs almost nothing.
  • User-facing notices. Users get an email for a sign-in from a new device, a password or MFA change (including a first factor enrolled), and being granted or removed from an entity.
  • Audit. audit_event (C-53) survives purge. The journal actor columns (C-23) are the ledger's own audit trail. C-24, the per-entity hash chain, makes ledger edits detectable. A weekly verifier checks it, and every export carries the chain head.

10. Incident Response

  • On call: each instance's operator. For the Principal's instance, that is the Principal. Alerts arrive by email (§9).
  • Severity:
    • SEV1: suspected T1 or T2 exposure, or keyring exposure; a confirmed cross-tenant read or write; code execution on the box; ledger tampering detected.
    • SEV2: T3 exposure limited to one user; no backup within the RPO; a revoke that cannot complete; a critical CVE with a known exploit in a deployed dependency.
    • SEV3: a vulnerability with no evidence of exploitation; a threshold breach that turns out benign.
  • Runbooks. These cover the security content only; exact commands live in the INFRA runbook.
    • RB-1: keyring or worker compromise (SEV1).
      1. Stop worker.
      2. Revoke every token at its provider: Plaid /item/remove, SimpleFIN bridge revocation, broker OAuth revoke. If the database and the keyring may both have been exposed, treat every token as burned.
      3. Generate a new keyring.
      4. Relink every connection.
      5. Rotate the provider API secrets.
      6. Review audit_event and the logs for credential opens that happened outside import runs.
    • RB-2: web or box compromise (SEV1).
      1. Put Caddy into maintenance mode.
      2. Snapshot the volume for forensics.
      3. Rotate every operator secret, including the BetterAuth secret. This invalidates all sessions.
      4. If the worker or the keyring was reachable, run RB-1.
      5. Rebuild from a clean, attested image on a fresh host.
      6. Restore the last backup taken before the compromise, and verify it against the C-24 chain and against the head of the last export the owner holds off the box.
    • RB-3: cross-tenant leak bug (SEV1).
      1. Disable the affected route.
      2. Add the failing case to the RLS battery or the authz matrix before fixing it.
      3. Identify affected users from request logs, by route and user ID.
      4. Notify the affected members.
    • RB-4: lost keyring (SEV3). Generate a new keyring. Every connection then shows "relink required". The ledger is unaffected.
    • RB-5: backup failure or restore (SEV2). Follow INFRA. Restore to staging first, and run the balance and hash verifier before promoting.
    • RB-6: compromised dependency (SEV1 or SEV2).
      1. Pin to the last known-good version.
      2. Rebuild and redeploy.
      3. Diff the SBOMs to check whether the bad version shipped in a release image.
      4. If it did, run RB-2.
  • Post-incident: a blameless postmortem within 5 business days as a cairn issue comment or review file (location per process/WORKFLOW.md). Record decisions in process/DECISIONS.md. The regression test lands with the fix.
