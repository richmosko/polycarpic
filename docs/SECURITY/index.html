1. Compliance Posture

Source of truth is PRD §6 — Non-Functional Requirements → Security / Regulatory, decided with the Principal 2026-09-27.

The posture in one sentence: a self-hosted personal tool, operated by the person whose books it holds, has no customer and therefore no third-party compliance obligation — so no regime attaches, and the security work here is justified by the threat model, not by an auditor.

What the absence of a regime does not buy us. 3. Threat Model (STRIDE)

One subsection per trust boundary from §2, plus two data-integrity surfaces that matter more here than any network threat. Not exhaustive — only threats with non-trivial likelihood × impact. Controls are catalogued in §7; the C-n references point there.

Adversary model. Three adversaries are in scope: (A) an unauthenticated internet attacker with no prior access; (B) an authenticated user of the instance who holds some membership and wants data or writes outside it — the household member with a viewer grant is the realistic case, and it is the adversary the whole tenancy design exists to stop; (C) a compromised or hostile upstream dependency (an aggregator returning malicious payloads, a poisoned npm package). Explicitly out of scope: the box's own root/superuser (R-1) and an attacker with physical access to a powered-on VPS.

4. Authentication & Authorization

Resolves ARCH OQ-2 (RLS shape + permission matrix) and OQ-3 (system-job principal). §4.3–§4.5 are the SecEng rulings the architect asked for; the summary table is §12.

4.1 Authentication

  • User authn. BetterAuth against our own Postgres (no external identity store). Email+password with a modern memory-hard hash (BetterAuth default, Argon2id/scrypt class — not a fast hash), OAuth 2.0 + PKCE via Google / Apple / GitHub, TOTP MFA available with single-use recovery codes. Email verification and recovery flows go through Resend.
  • MFA policy. Available and encouraged, not mandatory in v1 — a self-hoster locking themselves out of their own books with no support desk is a worse outcome than the marginal risk, given the box is single-tenant and the login surface is rate-limited. Recovery codes are shown once and stored hashed. Re-evaluate if a household ever exceeds ~5 members (R-7).
  • Session model (web). Server-side session record in Postgres, referenced by an HttpOnly / Secure / SameSite=Lax cookie. Server-side means revocation is real: logout, password change, and MFA reset invalidate sessions immediately.
  • Token model (native / MCP). Named, listable, individually revocable bearer tokens stored hashed, scoped to a user — never to an entity, because entity access must stay a live membership lookup. A token grants exactly what its user can do at the moment of the request, not at the moment of issue.
  • Service authn. There is no service mesh: one Node process pair (web, worker) and one database. The worker authenticates to Postgres as poly_worker; on the Vercel target, Vercel Cron calls an internal route authenticated by a dedicated shared-secret header compared in constant time — that route is otherwise indistinguishable from an unauthenticated public endpoint and must be treated as a first-class auth surface.

4.2 Authorization model

RBAC over the membership join, enforced in the database. A user's rights come from rows in membership (user_id, entity_id, role) — never from a user_id column on a data table, and never from entity structure. Access is a grant; the hierarchy grants nothing.

Enforcement point: Postgres RLS. Single source of truth. The can(role, action) helper in packages/tenancy exists to render a correct UI and to return a clean 403 early. It is not an enforcement point, and no control in §7 depends on it. The design test is blunt: if every can() call were deleted, the system would still be safe — slower and uglier, but safe. Any control that fails that test is app-layer-only authz and gets rejected at the security gate.

Entity type affects tax routing and reporting, never authorization; adding a type must never require touching a policy. Revocation semantics. Revoking a membership takes effect on the next transaction — there is no cached authorization anywhere, because visibility is recomputed per transaction from membership. Two consequences must be handled explicitly: (a) the revoked user's active sessions and bearer tokens remain valid for their own entities and simply stop seeing the revoked one (correct, and free); (b) a native client's local cache is outside our control — the iOS/macOS milestone must purge cached entity data on a 403/empty-scope response, and SECURITY reviews that milestone specifically. Server-side we cannot un-see what was already read; the honest statement to the user is that revocation stops future access, not past knowledge.

4.3 RLS mechanism — SecEng ruling on ARCH §3.3 (OQ-2)

Ruling: ARCH §3.3 is confirmed as specified, with four additions (a)–(d) below. Transaction-local GUC, STABLE SECURITY DEFINER visibility functions, FORCE RLS everywhere, default-deny. The pgbouncer/pooling risk I flagged in Research is answered by set_config(..., is_local => true): the setting is scoped to the transaction and discarded at COMMIT or ROLLBACK, so it is safe under both the in-process node-postgres pool and a transaction-mode external pooler.

Non-negotiable corollary: the whole guarantee rests on transaction-mode pooling. If an external pooler is ever introduced in session mode, or if any code opens a connection outside withTenant()/withSystem(), the guarantee is void. Hence: SET (session-level) is banned by lint; direct pool.query() outside packages/db is banned by lint; and a pooler-mode assertion belongs in the deploy checklist (DevOps, INFRA).

Additions to the ARCH shape:

  1. (a) Coverage must be derived, not listed. The CI probe enumerates tables from pg_catalog and fails on any table carrying a tenant column without ENABLE + FORCE RLS and at least one policy. A hand-maintained list of "tables to check" will drift the first time someone adds a staging table in a hurry. Tables intentionally global (price_observation, cpi_observation, tax_table, system report_definition) sit on an explicit, commented allow-list — and adding to that list is a security-gate decision, not a build fix.
  2. (b) poly_app must not own tables and must not hold CREATE on public. ARCH says the first part; I am adding the second, because CREATE on a schema in the search_path is the standard way to defeat a SECURITY DEFINER function. Every definer function also pins its own search_path (C-14).
  3. (c) Write policies must be split per command. A single FOR ALL policy with a USING clause and no WITH CHECK lets a manager insert a row attributed to an entity they cannot see. Every tenant table gets separate SELECT / INSERT / UPDATE / DELETE policies, and every write policy carries an explicit WITH CHECK. A pgTAP test asserts the WITH CHECK path directly (insert with a forged entity_id must fail).
  4. (d) The probe needs a negative control. Keep ARCH's inversion self-test (an unprotected canary table must leak). A green RLS suite that would also be green against a database with RLS switched off is worthless, and that failure mode is common enough to be worth one canary table.

Default-deny check. current_setting('app.user_id', true) returns NULL when unset, and entity_id = any (app.visible_entities()) with a NULL-derived empty array matches nothing. The battery asserts a context-free query returns zero rows on every tenant table — this is what makes "a route forgot its auth check" a bug rather than a breach (C-6).

4.4 System jobs — SecEng ruling (OQ-3)

Ruling: adopt ARCH's proposal — a job's tenant writes run under the linking user's membership, with actor_kind = 'system' and actor_id = <job>. Reject a dedicated system policy clause.

Why. A "system may write anything" clause is a permanent RLS bypass sitting in every policy, reachable by any code path that can set the system flag, and it is exactly the kind of clause that gets copied into a new policy without thought. Binding the job to the linking user's membership means the job's write scope is bounded by construction — it can never write more than the human who created the connection could, and that bound is re-checked every transaction rather than at link time.

Consequences that must be built, not assumed:

  • provider_connection.linked_by_user_id is NOT NULL and is the principal for that connection's jobs. withSystem(job, connection, fn) sets app.user_id to that user and app.actor = 'system:<job>'. Actor and principal are deliberately different things — the entries say "the import job did this", while the permission check says "under Alice's grant".
  • Fail closed on revocation. If the linking user's membership is revoked or their account is deleted, the job's writes stop returning rows to write — correct, and automatic. But silent failure is unacceptable: the connection must flip to principal_invalid, surface on the entity's dashboard, and an audit_event is written. Re-linking by a current manager is the remedy. This is a new requirement on the import milestone and needs a QA test.
  • Reference-data jobs (prices, CPI, tax tables) touch no tenant table and run as poly_worker with no user context — those policies grant poly_worker directly. That is the only place a role-based grant substitutes for a membership check, and it is safe precisely because those tables have no tenant column.
  • A job must never run with an absent context as a fallback. If no principal resolves, the job errors — it does not proceed context-free (which, given default-deny, would silently write nothing and look like success).

4.5 The purge path — SecEng ruling (OQ-4)

Ruling: adopt ARCH §3.4's SECURITY DEFINER function. Reject a separate purge role; reject tombstoning.

  • Why not a separate role. A purge role needs a credential; a credential needs to live somewhere the app can reach; anything the app can reach is reachable by an attacker who has the app. It converts a narrow code path into a standing credential — strictly worse.
  • Why not tombstoning. Tombstoning is soft-delete with better branding. PRD §5 promises the owner that the books are gone, after an explicit warning about their own retention obligations; leaving the rows in place and hiding them behind a flag makes that promise false, and adds a permanent "show tombstoned rows" bypass to every query. Deletion must actually delete.
  • Why the definer function is acceptable. It is one auditable code path, owned by poly_owner, with its escalation bounded to a single entity_id for the duration of one transaction. The append-only triggers honour app.purge_entity only inside that definer context — so poly_app setting the same GUC is inert, and C-34 tests exactly that.

Required guards, in order, inside the function:

  1. Re-authentication within the last 5 minutes (checked at the app layer and recorded; the function receives the assertion and requires it present).
  2. Sole-owner check — refuse if any other owner membership exists on the entity.
  3. Fresh-export check — an audit_event of kind export.completed for this entity, by this user, within the last 24 hours. Stale exports do not count; an export that failed mid-stream does not count. The window exists so the exported file actually reflects what is about to be destroyed.
  4. Write the audit_event of kind entity.purged — actor, timestamp, entity name and id, the export event it relies on, and row counts per table. Written before the first delete, outside the purge cascade, with a nullable entity_id so the FK does not drag it down.
  5. Set app.purge_entity transaction-locally, delete in dependency order, reset.
  6. Revoke every provider credential for that entity at the provider before deleting the connection rows (a purge that leaves live bank tokens behind is the worst possible outcome).

Not permitted: purge by a background job, purge by API without an interactive confirmation, purge of a partial date range (that is an edit, and edits are reversals), and purge while any other owner exists.

The inference rule that makes T3 real: which securities someone holds, where they shop, who they pay, and what they earn is a complete personal profile. The system therefore holds no analytics, no telemetry containing tenant data, and makes no outbound call carrying user data except a provider call the user initiated or an owner-initiated export. Nothing about a user's books leaves the box otherwise — that sentence from ARCH §1 is a control, and any future feature that breaks it (crash reporting with payloads, hosted error tracking, an LLM call carrying transaction text) requires an explicit security review and a PRD-level decision, not a library import.

A note on the log/store asymmetry. T3 is stored in the clear and redacted in logs. That is deliberate: the database is access-controlled, backed up encrypted, and RLS-filtered; log files are none of those things — they get tailed over SSH, pasted into bug reports, and shipped to whatever aggregator someone adds later. Logs are the most likely place for financial PII to escape, which is why the redaction list carries a unit test (C-20) rather than a convention.

6.2 Operator secret handling

  • One root-only env file on the VPS (0600, outside the repo and outside any build context), referenced by compose. On the Vercel target, Vercel environment variables.
  • No secret is ever baked into a container image — an image layer is effectively public once pushed to any registry.
  • .env.example carries variable names and a comment each; never a value, never a placeholder that looks like a value.
  • The app fails to start when a required secret is missing outside development. A system that silently degrades to "no encryption" because a variable was unset is worse than one that refuses to boot (C-26).
  • Secrets are read once at startup into process memory; there is no runtime secret-fetch path and no admin endpoint that reveals configuration.

6.3 Credential sealing — the ruling (OQ-1)

Ruling: application-layer envelope encryption in packages/secrets, AES-256-GCM, per-record DEK wrapped by an operator-held master key. Reject pgcrypto; reject an external secrets manager for v1.

Scheme. On seal(plaintext): generate a random 256-bit DEK and a random 96-bit nonce; encrypt the credential with AES-256-GCM under the DEK, binding the record id and provider as additional authenticated data (so a ciphertext cannot be moved between connection rows); wrap the DEK with the current master key (also AES-256-GCM, its own nonce); store {ciphertext, nonce, wrapped_dek, dek_nonce, key_id, alg}. On open(sealed): unwrap with the master key version named by key_id, decrypt, return the plaintext inside the call frame only. AEAD is required, not optional — it makes ciphertext substitution a decryption failure rather than a silent success.

PropertyRule
Plaintext lifetimeExists only within a secrets.open() caller frame, for the duration of one provider call. Never assigned to a module-level variable, never cached, never returned up more than one layer.
LoggingThe sealed column and every known credential key name are in the pino redaction list. A unit test seals a known canary string and asserts it never appears in serialized log output (C-20).
API exposureThe column is absent from every DTO and from openapi.json. An OpenAPI-freshness diff in CI means adding it would show up in review as a visible spec change (C-16).
ErrorsProvider errors are re-thrown with the credential stripped; a raw provider exception is never propagated to a response or a log line without passing through the scrubber.
Who can decryptOnly packages/secrets. A lint boundary rule forbids any other package importing the low-level crypto module.

6.4 Key rotation for an operator with no KMS

Envelope encryption exists here for exactly one reason: rotation without re-encrypting the data. Rotating the master key rewraps a few dozen small DEK blobs rather than decrypting and re-encrypting every credential, which keeps the operation short, interruptible, and safe to retry.

  1. Operator generates a new master key and adds it as version n+1, keeping n present. Both are loaded; n+1 becomes the write key.
  2. pnpm secrets:rewrap — for each sealed record with key_id = n: unwrap the DEK with n, rewrap with n+1, update key_id. Idempotent and resumable; the credential ciphertext itself is untouched.
  3. The job asserts zero rows remain at key_id = n, then the operator removes key n. An audit_event records the rotation.
  4. Cadence: annually as hygiene; immediately on any suspicion that the box, the operator's SSH key, or a backup was compromised. In that case rotation alone is insufficient — see §10: assume the old key is known and revoke every provider credential.

Lost master key = unrecoverable credentials, by design. The remedy is re-linking each provider connection, which is inconvenient but not data loss — the ledger itself is not encrypted under this key. The runbook must say so plainly so a panicked operator does not go looking for a backdoor that must not exist.

6.5 Why not pgcrypto, and why not a secrets manager

  • pgcrypto (rejected). To encrypt or decrypt in SQL, the key must be reachable by the Postgres process — passed as a query parameter (landing in pg_stat_activity and potentially the statement log) or held in a GUC/config file next to the data. That collapses the distinction between "database compromised" and "bank credentials compromised", which is the entire value of sealing. A stolen dump or a leaked backup must yield inert ciphertext; with pgcrypto and a co-located key, it does not.
  • External secrets manager — Vault, AWS/GCP KMS (rejected for v1). The deploy audience is a competent stranger on one VPS (PRD §6). Requiring them to run or subscribe to a KMS contradicts the self-host goal and the near-zero-spend guardrail (PRD §2 goal 4), and it adds an availability dependency: a KMS outage would stop imports. The seam is preserved — seal()/open() with a key_id is exactly the interface a KMS-backed implementation would present, so swapping the implementation later touches one package. Revisit if the hosted-offering Non-Goal is ever reversed (R-6).
  • The credential-free path stays the recommended default. CSV/OFX file import implements the same ImportAdapter interface with no stored credential at all (ARCH §2.3). An instance that never links an aggregator holds zero T2 data and removes this entire threat class. That should be the documented default for a cautious self-hoster, with aggregator linking presented as a convenience trade-off — stated in the operator runbook, not buried here.

6.6 Backup key custody — open, DevOps owns

Backups must be encrypted on the box before egress (C-38), so the off-box store never holds plaintext. The key custody question is the hard half and it is genuinely open: a key stored only on the VPS is useless in the exact scenario backups exist for. SecEng's requirement on DevOps (ARCH OQ-9, INFRA v1): the encryption key must be recoverable independently of the VPS — an asymmetric scheme where the box holds only a public key and the private key lives with the operator (age/gpg-style) satisfies this cleanly and is the recommended shape, since a write-only backup credential plus a public encryption key means a fully compromised box cannot read its own historical backups. A tested restore from a clean machine (C-40) is the acceptance criterion; RPO/RTO numbers are DevOps's to state.

8. CI/CD Security

Shape agreed with devops-engineer; INFRA holds the runner-level detail. Maps to ARCH §8's "Security scan" stage, which this section expands.

  • Branch protection (implemented). main requires a PR, includes admins, forbids force-push, and requires the strict cairn status check. No direct pushes — the workflow rule is enforced by GitHub, not by etiquette (C-48).
  • Signed commits / tags. Commit signing is not required — the repo has one human author and per-agent worktree identities, so signature verification would prove little and break the agent workflow. Release tags cut by /merge-pr should be signed, since a tag is what triggers a prod deploy and is the one artifact worth binding to the operator. Recommended, not yet implemented — tracked as R-8.
  • Secret scanning. Pre-commit hook plus a CI job (gitleaks-class), plus GitHub push protection. Pre-commit alone is insufficient (hooks are skippable); CI alone is too late (the secret is already pushed to a public repo) — both, deliberately (C-25).
  • Dependency scanning. Committed lockfile, --frozen-lockfile installs, automated update PRs (Dependabot or Renovate), and a pnpm audit gate failing on high severity. Given adversary (C), the supply chain is the most probable route to the master key (C-44).
  • Image scanning. The built adapter-node image is scanned before it is pushed or deployed; high-severity OS/library findings block the deploy (C-49).
  • SAST. tsc strict, ESLint including the layer-boundary rules (which are themselves a security control — they are what keeps the crypto module and the connection path un-importable from elsewhere) and a security-rules plugin. No commercial SAST; it would not pay for itself at this size.
  • DAST / penetration testing. None in v1 (R-3). The exposed surface is one Caddy-fronted app on one box, and the highest-value assertions — cross-tenant isolation, immutability, credential non-exposure — are covered far more precisely by the pgTAP battery than by a scanner.
  • SBOM. CycloneDX generated at release build, stored with the release artifact, so "are we affected by CVE-X?" is answerable without reconstructing a historical dependency tree (C-45).
  • The DB battery is a security gate. ARCH §8 lists it under correctness; it is also the primary tenancy control. When packages/db or any schema changes, the RLS + trigger battery must pass — a red battery blocks the merge regardless of what else is green.
  • Deploy credentials. Scoped to a GitHub environment with required reviewers on prod; the deploy key is distinct from the operator's SSH key so it can be revoked without locking the operator out (C-47).

9. Logging, Monitoring & Detection

Detection capability here is deliberately modest — one operator, one box, no SIEM. What exists must therefore be high-signal and trustworthy.

  • What is logged. Structured JSON (pino): request id, user id (or system:<job>), route, action, outcome, duration, and the entity id where relevant. Authentication outcomes (success, failure, MFA challenge, lockout) are logged at a dedicated level so they can be grepped without wading through request noise.
  • What is never logged. T1 and T2 values, in any form. T3 free text — payee and memo strings are redacted in logs even though they are stored in the clear (§5). Full account numbers, provider payloads, request bodies on mutating routes. The redaction list is code with a canary unit test, not a convention (C-20).
  • Storage and retention. Container stdout → host files, rotated (logrotate, size- and age-bounded). Local only; no log shipping in v1, which means no third party ever holds even redacted financial traffic. If log shipping is ever added, it is a §5-boundary change requiring security review.
  • The audit log is the real detection surface. audit_event (append-only, owner-readable, outside the purge cascade) records: membership grant / revoke / role change, provider connection link / unlink / revocation attempt and outcome, full-entity export, entity purge, master-key rotation, and principal-invalidation of a connection. These are the actions that matter after the fact — the ones an attacker would need, and the ones a user would dispute. It lives in the database rather than in log files precisely because it must survive log rotation and be queryable years later.
  • Alerts. v1 has uptime pinging only (DevOps). There is no automated alerting on authentication-failure spikes, authz denials, or anomalous egress — accepted as R-2, with the compensating control that the audit log makes after-the-fact reconstruction possible. The first alert worth adding, when one is added, is repeated auth failure followed by a success.
  • Postgres logging. Slow-query log on. Statement logging stays off in prod: log_statement = 'all' would write payee and memo text — T3 data — into a plaintext file with different handling than the database it came from.

10. Incident Response

Written for the realistic case: one person, their own data, no pager. The value here is a pre-written decision order for a moment when nobody thinks clearly.

10.1 Roles and declaration

On call: the instance operator — for the primary instance, the Principal. There is no rotation and no escalation path; the runbook must therefore be executable by one person from a laptop. Any self-hoster inherits this role for their own instance, which is why the runbook ships with the app rather than living only here.

SeverityCriteriaFirst action
SEV-1Suspected disclosure of T1 or T2 data (master key, box compromise, leaked backup, credential in a public log); or a cross-tenant read/write (RLS bypass); or a ledger-integrity violation (a posted row changed, an unbalanced entry landed).Contain first, diagnose second. §10.2.
SEV-2Availability loss (box down, database down, TLS expired); backups failing; imports failing silently for more than a day.Restore service; then root cause. No credential rotation needed unless SEV-1 is also suspected.
SEV-3A single provider connection broken, a stale price series, a failed job with a clean retry, a low-severity dependency CVE.Normal backlog issue in cairn.

10.2 SEV-1 runbook — containment → eradication → recovery

  1. Contain. Take the app off the internet (stop the web container or drop 443 in the firewall) — the database keeps running so evidence and books survive. Do not rebuild or docker compose down -v: destroying state destroys the answer to "what happened".
  2. Preserve. Snapshot the volume and copy current logs off the box before any remediation. This is the step that is always skipped and always wanted later.
  3. Assess exposure. Which tier? T2 exposure (credential/master key/backup) is the gravest because it reaches the user's actual bank accounts, which are outside this system's control and cannot be restored by restoring a backup.
  4. Eradicate — credentials. On any suspicion that the box, an SSH key, or a backup was exposed: revoke every aggregator credential at the provider (Plaid /item/remove, SimpleFIN access revocation, broker token revoke) — do not merely delete local rows. Then rotate the master key (§6.4), every Postgres role password, every provider API key, the Resend key, OAuth client secrets, the backup-store credential, and the CI deploy key. Assume anything readable on the box is known to the attacker.
  5. Eradicate — sessions. Invalidate all sessions and bearer tokens; force re-authentication; reset MFA if T1 exposure is plausible.
  6. Eradicate — access. Rotate operator SSH keys; review authorized_keys, system users, cron, and the compose files for anything added.
  7. Recover. Rebuild the host from a known-good image and restore data from the last backup taken before the suspected compromise window; re-link provider connections by hand (the deliberate consequence of key rotation, §6.4). Verify integrity before reopening: RLS battery green, balance invariants green, audit_event reviewed for the window.
  8. Special case — RLS bypass or ledger-integrity violation. Do not reopen on a patch alone. Write the failing pgTAP test first, watch it fail, fix, watch it pass, and add it permanently to the battery (C-9). An integrity bug that leaves no regression test behind will return.
  9. Notify. No regulator requires notification (§1). Every person holding a membership on an affected entity is told what was exposed and what they should do (e.g. watch the linked accounts) — honestly, even when it is the operator's own fault, and especially when the operator is also the only user.

10.3 Post-incident

  • Blameless postmortem within 5 business days: timeline, what the threat model got wrong, which control was missing or mis-sized.
  • A decision entry in process/DECISIONS.md; every SEV-1 also amends this document — a new §3 threat row and a new §7 control, or an explicit §11 acceptance. An incident that changes no artifact was not learned from.
  • File the regression test as a cairn issue if it cannot ship with the fix.

R-1 The operator's superuser bypasses RLS entirely. Anyone with root on the VPS or a Postgres superuser session reads and writes every entity's books regardless of membership, and can read the master key file. Structural, not a defect: the person running the box owns the hardware, the volume and the keys. Pretending RLS defends against the box's own administrator would be theater. R-2 No automated security alerting. No detection of auth-failure spikes, authz-denial patterns, or anomalous egress; discovery of a live intrusion depends on the operator noticing. One operator, one box, near-zero-spend guardrail (PRD §2 goal 4). A SIEM for a single-household instance costs more attention than it returns, and a noisy alert nobody reads is worse than none. audit_event gives after-the-fact reconstruction of every consequential action (§9); auth outcomes logged at a dedicated level; uptime ping. Small, single-purpose surface behind Caddy; no compliance regime requires it (§1); the highest-value properties (tenant isolation, immutability, credential non-exposure) are asserted far more precisely by pgTAP than by any scanner. Before any hosted offering; otherwise at GA pending — SecEng recommendation
R-4 Staging co-located with prod on one VPS — shared kernel, so a container escape from staging reaches prod. Saves a second box (ARCH §10). Staging holds only fake data, so a staging compromise discloses no real books; the value at risk is the pivot, not the data. Separate compose project, database and credentials (C-43); staging never holds real provider credentials; ARCH already flags a later split. INFRA v1 (DevOps, ARCH OQ-9) pending — inherited from ARCH §10
R-5 Master-key rotation is a manual operator runbook step, not automated or scheduled, and a lost key makes sealed credentials unrecoverable. The target operator has no KMS (§6.5). Automation would require storing the new key somewhere the automation can reach — reintroducing the problem. Unrecoverability is the correct failure mode; the recovery is re-linking providers, not a backdoor. Rewrap job is idempotent and resumable (C-27); the runbook states plainly that a lost key means re-linking; the ledger itself is not encrypted under this key. Annually, with the rotation pending — SecEng recommendation
R-6 Multi-tenant design leaves the hosted-offering door open. If the standing Non-Goal is ever reversed, GLBA Safeguards Rule, state financial-privacy law, and possibly PCI DSS attach — and R-1, R-2, R-3 all become unacceptable at once. Hosting for others is a standing Non-Goal (PRD §3 #10), not a deferral. The architecture is tenant-safe by construction, so the reversal would be a compliance programme, not a rewrite. This row exists so the reversal is a deliberate, costed decision. Any such decision re-opens §1 and invalidates R-1/R-2/R-3. Only on a deliberate decision to host Rich Mosko (PRD §3, 2026-09-27)
R-7 MFA is optional, not mandatory. A password-only account with a granted membership is a viable path to another person's financial data. Self-hosted with no support desk: a forced-MFA lockout has no recovery path and destroys access to the user's own books. Login is rate-limited and OAuth (which carries the IdP's own MFA) is the encouraged path. C-1 rate limiting + lockout; OAuth-first onboarding; hashed single-use recovery codes when MFA is enabled; auth outcomes logged. When a household exceeds ~5 members, or at GA pending — SecEng recommendation
R-8 Commits and release tags are unsigned. A repo-write compromise could introduce a commit indistinguishable from an authored one. One human author plus per-agent worktree identities; signature verification would prove little about agent commits and complicates the workflow. Branch protection already prevents unreviewed merges (C-48). Branch protection with admins included, no force-push, strict status check. Signing release tags is recommended before the first prod deploy, since a tag triggers deployment. Before the first prod deploy (M1 infra) pending — SecEng recommendation
R-9 User-defined entity types are readable across tenants. A type created by one user is visible to anyone holding a membership on any entity of that type — a deliberate cross-tenant metadata read (kickoff §2.4). Necessary: a viewer must read the type name to render the entity. The exposure is a type label and its owner id — no financial data, no membership list, no entity names. An explicit, narrow RLS policy on entity_type rather than a blanket read grant; a pgTAP test asserts it exposes label-level fields only. Users are told a custom type name is visible to anyone sharing that type. If entity types ever carry more than a label pending — inherited from kickoff §2.4
R-10 Cross-root read access (PT-3, tooling): cairn serve reads directories named in a committed roots: config (or --repos), i.e. outside the repo. A malicious roots: entry in a PR could point a reviewer's local board at a sibling directory (e.g. ../../.ssh). Read-only and localhost-only — no write path to a secondary root, and the /api/board payload carries only parsed cairn frontmatter, so there is no exfiltration channel. A directory without a config.yml is skipped before anything is read. Whoever can commit a roots: entry already has a stronger vector (editing cairn.py/board.js directly), so a runtime path-jail would be theater against the real threat. Startup stderr banner logs each resolved absolute root path when >1 root loads (human tripwire against a stale/fat-fingered roots: silently serving the wrong tracker). Re-evaluate if cairn ever gains a write path to non-primary roots. 2027-02-21 Rich Mosko

12. Rulings on ARCH Open Questions

The four questions ARCH §12 assigns to seceng, answered. Each links to the section carrying the reasoning; the architect can close OQ-1–OQ-4 against this table.

OQQuestionRulingDetail
OQ-1 Credential sealing mechanism and key rotation for a self-hoster with no KMS. App-layer envelope encryption in packages/secrets: AES-256-GCM, per-record DEK wrapped by an operator-held master key, AAD-bound to the record, stored as ciphertext + nonce + wrapped DEK + key_id. pgcrypto rejected (co-locates key with data, so a DB dump yields plaintext). External KMS rejected for v1 (contradicts self-host + near-zero-spend; adds an availability dependency) — the seal/open/key_id seam ARCH already fixed is exactly what a KMS implementation would slot into. Rotation is an operator-run rewrap job over wrapped DEKs, annually or on compromise. §6.3, §6.4, §6.5; controls C-15, C-17, C-26, C-27
OQ-2 Confirm the RLS shape in ARCH §3.3, and the permission matrix per role × action × entity type. ARCH §3.3 confirmed (transaction-local GUC, STABLE SECURITY DEFINER visibility functions, FORCE RLS, default-deny) with four additions: (a) coverage probe derived from pg_catalog, not a hand-maintained list; (b) poly_app also loses CREATE on public; (c) per-command policies with an explicit WITH CHECK on every write — no FOR ALL; (d) keep the inversion canary. Matrix: roles are uniform across entity types — type affects tax routing and reporting, never authorization. Managers post, confirm, reverse, link and export; only owners manage memberships, entity metadata and audit reads; viewers are read-only and see account numbers masked to last-4, with no access to raw provider payloads; purge is sole-owner only. §4.2.1 (matrix), §4.3 (mechanism); controls C-6 … C-14
OQ-3 System-job principal: the linking user's membership, or a dedicated system policy clause? Linking user's membership — ARCH's proposal adopted; a system policy clause is rejected as a permanent RLS bypass reachable by any path that can set the flag. provider_connection.linked_by_user_id is NOT NULL and is the principal; actor stays system:<job>, so attribution and authority are deliberately separate. New requirement on the import milestone: when that user's membership is revoked or their account deleted, the connection flips to principal_invalid, surfaces on the dashboard, and writes an audit_event — it must not fail silently. Reference-data jobs (no tenant column) are the only role-granted exception. §4.4; control C-30, audit entries §9
OQ-4 Purge path coexistence with the append-only triggers, and how the purge is audited. ARCH §3.4's SECURITY DEFINER function adopted. Separate purge role rejected (converts a code path into a standing credential); tombstoning rejected (makes PRD §5's promise false and adds a permanent query bypass). Required guards, in order: re-auth ≤ 5 min → sole-owner check → completed export within 24 h → audit_event written before the first delete (append-only, nullable entity_id, outside the cascade) → transaction-local app.purge_entity honoured only inside the definer context → provider-side credential revocation before deleting connection rows. No purge by job, by API without interactive confirmation, of a partial range, or while a second owner exists. §4.5; controls C-33 … C-37
