1. System Context

The system and the actors around it. C4 context level.

Polycarpic is a single self-hosted web application backed by one PostgreSQL database. Users (the Principal, household members holding a membership grant, later native iOS/macOS clients and a user-scoped MCP server) reach it over HTTPS. Inside, a genuine double-entry general ledger lives in Postgres under row-level security keyed on the membership join. Outbound, the system pulls transactions from bank/brokerage aggregators through a provider-agnostic adapter interface (a deterministic fake first, then CSV/OFX files, direct broker APIs, Plaid and SimpleFIN), end-of-day prices and the CPI-U series as reference data, and sends transactional email through Resend. Identity is local (BetterAuth in our own Postgres) with sign-in through outside identity providers (IdPs): Google and GitHub confirm who a user is, so the user has no separate password with us, and BetterAuth then starts a session of our own. Sign in with Apple arrives with the native iOS clients (POLY-122). Nothing about a user's books leaves the box except through a provider call the user initiated or an owner-initiated export.

2. Components & Layer Model

Each package imports only what the layer map allows, and never upward. Each layer is one or more workspace packages, each with tests that run alone. The boundary is enforced by lint and by package resolution, not by convention.

2.1 Layer model

Kickoff §3 asks for layers defined before details, depending only downward, with narrow interfaces. The model below is the contract.

Rule (Principal, 2026-11-09). A package or app imports another workspace package only if its allow-list in the layer map lists it.

  • The file is the authority. The layer map is layers.json at the repo root. For every package and app, it records the layer, the public subpaths, and the allow-list. Every subpath is restricted: an allow-list entry naming the package (db) grants its index only, and a subpath is importable only by a package whose allow-list names it (db/auth). The allow-lists are the Consumes column of §2.2, which carries each as a data-consumes attribute; CI fails if the two disagree. The architect owns the file. A change to what a package may import is an architecture change and needs the architect's sign-off in review; that sign-off is review, not a machine check.
  • Never up, never round. No allow-list entry points at a higher layer. The allow-lists contain no cycle. Same-layer imports exist only where listed: auth → tenancy, securities → ledger, reports → portfolio, tax, web → ui. Type-only imports count the same as value imports.
  • Standing restrictions, in the same file:
    • Nothing under packages/ imports SvelteKit (@sveltejs/kit, $app/*, $env/*); packages/ui may import svelte.
    • Only packages/db imports a Postgres driver, and it opens connections only through withTenant() / withSystem() (§3.3). The restriction names every specifier that yields a connection: pg, pg-pool, postgres, @neondatabase/serverless, the drizzle-orm Postgres driver subpaths and Kysely's PostgresDialect, however imported: outside db, kysely allows named imports only. A driver type another package needs is re-exported by db. BetterAuth's plain poly_app pool and withContextFreeTx are on the db/auth subpath, which only packages/auth imports; the routing pool takes its pool and Kysely dialect from there (§3.1c, POLY-76). Session-level SET is refused everywhere except the migrate module in db: SET, SET SESSION, RESET, set_config(…, false), and any role switch, SET LOCAL ROLE included. Other SET LOCAL statements and set_config(…, true) are transaction-scoped and pass. layers.json names that one file by its path, not a glob. Its client is a dedicated connection closed after the run, never pooled (§6.2). The exemption is on the A-39 list that an inline or blanket eslint-disable cannot bypass, and web and worker never import the module (SECURITY C-85, A-40).
    • Only apps/worker imports secrets/open. Only packages/secrets imports the HPKE library or calls createCipheriv, createDecipheriv, publicEncrypt or privateDecrypt. Elsewhere, crypto and node:crypto allow named imports only, with subtle and webcrypto refused. The global crypto.subtle may digest, sign and verify, but not encrypt, decrypt, wrapKey or unwrapKey (SECURITY §6.3, A-39).
    • Only packages/auth imports db/session, the constructor of the branded SessionUserId that withTenant() accepts. A cast to SessionUserId is refused outside db/session and test files, so the brand cannot be skipped.

Enforced three ways (built by POLY-82; run in CI's lint job by POLY-96):

  1. Lint. eslint-plugin-boundaries, with its element and allow rules generated from layers.json, never hand-copied. It runs in the editor and in CI. dependency-cruiser is a fallback only for a rule the plugin proves unable to express.
  2. Resolution.
    • Each package.json has an exports map listing only . and its declared subpaths. TypeScript resolves with moduleResolution: "bundler", which honours exports, so a deep import past the index fails in tsc, Vite and Vitest alike. This is also what keeps the raw pool unreachable (§3.3).
    • Each cross-package import is a declared workspace: dependency. Under pnpm's strict linking, an undeclared one does not resolve; import-x/no-extraneous-dependencies turns that into a readable lint error.
    • Resolution does not guard a restricted subpath. web declares secrets, and every db consumer declares db, so secrets/open and db/session resolve for them. Lint is the only source-side guard there. An inline eslint-disable of a boundaries, restricted-import, brand-cast or session-SET rule therefore fails lint, and so does a blanket eslint-disable that names no rule. Lint sees no import inside one package, so a module-graph check shows the secrets index reaches neither the open module nor the keyring reader (SECURITY A-39). The real boundary is the keyring mount, not these rules (SECURITY §6.3).
  3. Checks on the file (CI):
    • Every directory under packages/ and apps/ is in the file, and every entry in the file exists.
    • The allow-lists are acyclic and never point up a layer.
    • Each package's declared workspace: dependencies are on its allow-list.
    • The file matches §2.2's data-consumes lists.

Why the cycle check runs on the file, not in lint. Every cross-package import must be on an allow-list, so the real import graph is a subgraph of the allow-list graph, and a subgraph of an acyclic graph is acyclic. That holds only if lint sees every edge. Re-exports and import() with a literal specifier count as edges, and a cross-package import() with a computed specifier is refused. The layer order alone already rules out cycles across layers, so the file check matters only within a layer. Cycles between modules inside one package are not a boundary question and are not checked.

3.1a The cap table: equity, separate from access

Principal, 2026-11-07: every entity carries a cap table; equity is independent of the access roles; it replaces tax_allocation_share.

Membership answers "who may do what"; the cap table answers "who owns how much". A 0-unit owner is a bookkeeper; a 25% holder may have no access at all. The two never derive from each other.

  • Shape. Two append-only tables, both effective-dated. equity_total(entity_id, total_units, effective_from) holds the unit count; equity_holding(entity_id, holder_entity_id, units, effective_from) holds each holder's count. Units are numeric, units ≥ 0, total_units > 0. The total is dated, not a column on entity, because a past allocation must use the total in force on its date: issuing units in June must not rewrite January's split.
  • The split on date d. The latest equity_total row with effective_from ≤ d, and for each holder its latest equity_holding row with effective_from ≤ d; a holder at 0 units has left. Stake = units / total. The remainder, total − Σ units, is outside owners: real holders the system does not track, whose share allocates to no one.
  • Corrections are new rows. Nothing is updated or deleted. A change is a set of rows sharing one effective_from; each row carries recorded_at, and for one holder and one date the latest recorded row wins. A change entered from the wrong date is undone by a row at that date restoring the earlier units, plus the row at the right date.
  • A Person's table is implicit: itself at all units. No rows are stored for a Person entity, and a trigger refuses any. A parent (Household, Holding) carries a cap table like any entity, and a parent is never a holder.
  • Defaults. A new non-Person entity is created with 100 units and the creating user's own Person holding all 100, from the creation date; the creation form shows the table so the user can change it before saving. Every user's own Person is marked by entity.self_user_id (unique, nullable, set by provisionPerson; §3.1).
  • Invariant. Σ units ≤ total units at every date. A DEFERRABLE INITIALLY DEFERRED constraint trigger checks it at commit, at every change point from the earliest effective_from written in the transaction onward, so a new total and new holder rows commit together.
  • Who writes: owner of entity_id only (it is entity metadata). While the entity has one owner the write is direct; with more than one, every edit, the entity-creation default excepted, is a cap_table change_request that applies once every other owner approves, re-validated against the Σ invariant at apply (§3.1b). Who may be a holder: a Person, Trust or Business that is either visible to the editing user (any membership) or the own Person of a user holding a membership on this entity. The editor lists owner-access members first, then the other members, then "add holder" over the editing user's other entities. Anyone else is reached by inviting them as a member first, or left in the outside-owners remainder. "Invite as viewer" appears in both places (settled for ux-designer, PR #78): in the save that adds a Person holder whose user has no access, and afterwards on any saved row whose Person holder's user still has none, so a declined or skipped offer can be taken up later. The invite is its own action, never bundled into the cap-table write: on a sole-owner entity it is an ordinary invitation insert in the same transaction; on a multi-owner entity it is a separate invite request raised beside the cap_table request, and either may apply or fail without the other. An entity holder gets no offer, since membership belongs to users.
  • Who reads: any member of the entity, by ordinary RLS on entity_id. The equity_* SELECT policies are not widened for anyone else. Everything beyond that goes through definers owned by the NOLOGIN, NOBYPASSRLS role poly_stake, all on the allowlist (SECURITY A-18, C-27):
    • app.my_stakes() is a holder's owners' read path. It returns entity id, display name, units, total units and effective-from for every entity in which the caller's own Person, or an entity the caller owns, holds units. Never another holder's row.
    • app.cap_table_candidates(entity_id), for an owner of entity_id only: id and display name of members' own Persons and of Person, Trust and Business entities visible to the caller.
    • app.allocated_income (§4.5).
    poly_stake's role-targeted SELECT policies are confined to app.held_entities(): entities in which the caller's own Person, or an entity the caller owns, has ever held units, plus one link onward; candidates also read members' own Persons.
  • Notice. Adding or changing a holder writes a notification in the same transaction: to the user whose own Person it is, or, for a Trust or Business holder, to each of its owners. The editor may not see those owners, so the write is done by the definer trigger app.check_equity_holding(), owned by poly_graph (§3.3b).
  • Cycles refused. The holder graph (entity → holder) must stay acyclic: an entity never holds itself through any chain. app.check_equity_holding() runs BEFORE INSERT, SECURITY DEFINER owned by poly_graph (graph-wide read; SECURITY A-16), search_path = '', under pg_advisory_xact_lock on its own fixed key, the same mechanism as the parent-link trigger. It also refuses a new row naming a tombstoned holder (§3.4b). An edge is any pair that has ever had a row with units > 0, whatever the date, so the check needs no reasoning about date ranges. It is stricter than needed, and the cost is that a long-exited holding still blocks the reverse one.
  • Depth: one entity link in v1, deeper chains refused. An entity may be held by an entity whose own holders are Persons (an LLC held by a trust held by its beneficiaries), never by an entity that is itself held by an entity. The same trigger refuses a row that would make an entity-to-entity chain two links long, from either end. Refusal, rather than treating the deeper share as outside, means no income ever silently drops out of tax (§4.5). The cost is that a holding company inside a trust cannot be modelled in v1 (unmeasured; no structure described so far needs it). Raising it is one migration and a composition change in §3.3c and §4.5. Errors name no hidden entity, as in §3.3b.
  • A holder that is purged becomes a former holder: its rows stay, shown as "Former holder (purged <date>)" with an optional label the entity's owners type themselves (a cap-table edit), and its units count as outside owners from the purge date (§3.4b, OQ-33).
  • Tests (pgTAP): Σ over total refused at a later change point; a Person row refused; a direct and an indirect cycle refused, including through an entity the editor cannot see; a two-link chain refused; a non-owner write refused; app.my_stakes returns only the caller's holder rows, and a holder's owner reads 0 rows from equity_holding directly; a non-owner gets 0 candidates; a notification lands for an owner invisible to the editor; with two owners, a direct equity_holding INSERT is refused.

3.1c A raised role waits for the second step

Principal, 2026-11-07, P1 (SECURITY §4.1, C-03); PRD v1.4 §5 ("a viewer promoted to manager or owner enrols before the new role takes effect"); DESIGN v0.16 second-step flow (the member keeps viewer access, a Waiting for second step badge, the "Role raise waiting" notice). Chosen over refusing the raise at apply. Meets SECURITY v1.2 A-25 / C-03 / T-81: the stored value every check reads stays at the previous role until enrolment.

Choice: a pending role on membership. membership.role is always the role in force; a raise the member cannot yet hold is parked in a separate column and promoted by a trigger when they enrol. Refusal at apply was rejected because it throws away an approval the co-owners already gave and makes the owner chase the member before asking.

3.2 Invariants the database enforces (not the app)

  1. Balanced entries. A DEFERRABLE INITIALLY DEFERRED constraint trigger on journal_line checks Σ base_amount = 0 per entry at commit, and at least two lines. The app computes balance too, for good error messages; the trigger is the backstop.
  2. Append-only posted rows. BEFORE UPDATE OR DELETE triggers on journal_entry, journal_line, journal_chain, change_approval, lot, lot_match, tax_period_freeze, tax_close and on raw_transaction where status = 'posted' raise, and so do BEFORE TRUNCATE statement triggers on the same tables. No login role holds TRUNCATE. The one exception is DELETE by current_user = 'poly_purge' for the entity named in app.purge_entity (§3.4). Corrections go through correctEntry(original, newLines). In one transaction it writes a reversal (a mirror entry with reverses_entry_id set) and a replacement entry with replaces_entry_id set. The UI calls this action "Correct entry". The UI never offers "edit" or "reverse" on a posted row; it badges the replacement and shows the struck-through reversal on click-through (DESIGN). reverseEntry() on its own stays internal, for a correction whose replacement is empty.
  3. Two-way link. Confirming one or more drafts inserts the entry and, in the same transaction, sets each draft's entry_id and flips each raw row to posted. The link is held on the draft side (many drafts → one entry). The entry's source_ref only marks it as import-sourced; it doesn't point back to a single row. A check ensures a posted raw row always has an entry (gate G4, §3.2a).
  4. Single posting date. One date column per entry; a posting_date_allowed(entity, date) function hook (always true in v1) is the seam where period locking plugs in later without a schema change.
  5. Same-entity legs. Every line's account belongs to the entry's entity (composite FK (entity_id, account_id)). Cross-entity transfers are two entries, one per entity's books (§4.3).
  6. Actor recorded. actor_kind + actor_id are NOT NULL on entries and drafts, and are forced by a BEFORE INSERT trigger from the transaction's context rather than merely defaulted. actor_kind = 'user' requires actor_id = app.current_user_id(), so a caller cannot attribute an entry to someone else (SECURITY A-5).
  7. Gapless Journal ID. Every entry carries journal_number, unique on (entity_id, journal_number) and shown as JE-000214; the UUID stays the key. A BEFORE INSERT trigger assigns it, so a caller cannot supply one: UPDATE entity_journal_counter SET last_number = last_number + 1 … RETURNING. Since poly_app has no write grant on the counter, the trigger function is SECURITY DEFINER, owned by the NOLOGIN, NOBYPASSRLS role poly_journal, which also owns the chain trigger below (SECURITY A-23). A plain sequence would burn a number on rollback. The counter row is locked until commit, so a rolled-back posting, including one failing the deferred balance check, returns its number, and postings in one entity serialize. Different entities never contend. The append-only trigger is unaffected, because the number is set before the row exists and the counter is a separate table. A correction takes two numbers, reversal then replacement, in its one transaction. A transaction touching several entities takes the counters in entity_id order, which rules out deadlock. Auto-post batches commit per entry or in short groups, so a batch never holds the lock against a user posting by hand. The cost is one row lock per posting (unmeasured; household write rates make contention unlikely).
  8. Lots tie to the ledger. For each custodial account and securities nature class, the ledger balance equals the summed adjusted basis of open lots there (§3.6). Lot write and entry commit in one transaction; a periodic assert job is the tripwire, and a mismatch alerts rather than repairs.
  9. Hash-chained ledger (Principal, 2026-11-07, P4; SECURITY C-24; POLY-M2). Each entity's posted entries form a SHA-256 chain in journal_number order: entry_hash = sha256(prev_hash ‖ canonical(entry, its lines)), the first entry chaining from a fixed per-entity seed. The canonical encoding is pinned and versioned (alg_version): field order, numeric text form, UTF-8 NFC.
    • Written at commit. The hash covers the lines, which do not exist when the entry is inserted, so it is computed by a DEFERRABLE INITIALLY DEFERRED constraint trigger on journal_entry, app.chain_entry(). It reads the entry's lines, reads the head from entity_journal_counter, inserts the journal_chain row and moves the head. The ruling says "after the balance check"; deferred triggers on two tables fire in queue order, so the order is not guaranteed, and it does not need to be: a failed balance check aborts the transaction, chain row included, so no chain row ever commits for an unbalanced entry.
    • No new lock. The counter row is already locked by the numbering trigger until commit, so the head moves under the same serialisation as the gapless number, and a rolled-back posting leaves neither a number nor a chain row. Two entries in one transaction (a correction) chain in number order, which is their queue order.
    • The trigger is the only writer (SECURITY A-23, C-24; OQ-30 closed). poly_app and poly_worker hold no write grant on journal_chain or the counter, and read both through ordinary tenant RLS, viewer and up, for the export head and the verifier. poly_journal's grants, each through a role-targeted policy TO poly_journal: SELECT, plus UPDATE of last_number, head_number and head_hash only, on the counter; INSERT on the counter, used only by the AFTER INSERT trigger on entity; INSERT on journal_chain, never UPDATE or DELETE (append-only under C-21, the purge excepted); SELECT on journal_entry, journal_line and journal_chain. The wide read is acceptable for the reason SecEng gives for poly_graph: a function returning trigger cannot be called to return data. Posted entries are never UPDATEd to hold their hash.
    • No line after the chain row. SET CONSTRAINTS … IMMEDIATE is open to any role, so poly_app could fire the deferred chain trigger before an entry's lines exist. A poly_journal BEFORE INSERT trigger on journal_line refuses a line whose entry already has a journal_chain row, so the chain always covers every line and an early fire fails the posting instead of raising a false SEV1 at the verifier.
    • Verifier. A weekly job unit per entity, running under the entity's earliest owner through app.job_targets (§3.3), recomputes the chain from the entity's lines and compares every link and the head. A break is SEV1 ledger tampering: an audit_event, a notification and an email to every owner, and an email to the operator (§7.4).
    • Head leaves the box. Every export carries the head (journal_number, entry_hash), recorded in its export.completed event, and the ExportReceipt DTO (§2.4) carries both, with alg_version: the receipt shows JE-000214 and a shortened hash, the full hash behind Copy. An entity with no posted entry has no head; the receipt says so and the field is null. A purge deletes the chain and records the final head in entity.purged (§3.4).
    • Limit. The operator's superuser can disable the triggers and recompute the whole chain. Detection then rests on a head held off the box, an export the owner kept (R-1, re-confirmed 2026-11-07).
    • Cost. One SHA-256 over an entry of a few lines and one row insert per posting, inside a lock already held (unmeasured; expected negligible against the 2 s dashboard NFR, which is a read path).
    • Tests (C-24): a superuser edit (triggers disabled) to an entry, a line, or the order is caught by the verifier; a rolled-back posting leaves no chain row and no gap; poly_app cannot insert into or update journal_chain, or insert or update a counter row; a new entity gets its counter at number 0 with the seed, and a caller-supplied journal_number is overwritten; under SET CONSTRAINTS ALL IMMEDIATE, an entry then its lines is refused and no chain row commits; catalog: each poly_journal function is attached as a trigger only to its intended table (pg_trigger.tgfoid to tgrelid), and a direct call fails; a correction's two entries take two links in number order; the export's head equals the verifier's.

3.3 RLS mechanism and connection-pooling safety

Confirmed by SecEng in SECURITY §4.3 / §12 (OQ-2), with the four additions listed last. The permission matrix is SECURITY §4.2.1: roles are uniform across entity types.

  • Roles. poly_owner (NOLOGIN; owns every object); poly_migrator (LOGIN; used only by the migrate step; runs migrations as set role poly_owner … reset role, which mosko-fintech measured as the working shape); poly_app (LOGIN; DML grants only; NOBYPASSRLS; not the table owner, so RLS applies); poly_worker (LOGIN; NOBYPASSRLS; reference-data writes plus tenant DML limited to the import path, SECURITY §4.4); poly_authz (NOLOGIN; owns the authorization functions and nothing else); poly_purge (NOLOGIN; NOBYPASSRLS; owns the purge function; DELETE on purgeable tables only, plus the tombstone UPDATE on entity, §3.4b); poly_backup (LOGIN, REPLICATION, BYPASSRLS, member of pg_read_all_data, no write grants; NOSUPERUSER NOCREATEDB NOCREATEROLE, CONNECTION LIMIT 3, default_transaction_read_only = on; used only by the backup job, from the backup network, §7.2; confirmed by SecEng under C-79, SECURITY v1.3 A-36). BetterAuth's own statements run as poly_app too, through the routing pool; its grants on BetterAuth's tables are listed in §3.1c (SECURITY A-31).

The setting dies at COMMIT/ROLLBACK, so a pooled connection cannot carry a previous request's identity. withTenant, withSystem and withContextFreeTx (§3.1) refuse to nest inside one another, and the context-free one asserts with its first statement that app.user_id is empty (SECURITY C-84). This works with the in-process node-postgres pool on the VPS and with Neon's transaction-mode pooler. Session-level SET is banned by lint.
  • Default deny. Policies read context only through app.current_user_id() = nullif(current_setting('app.user_id', true), '')::uuid. The nullif matters: once a backend has set the GUC and the transaction has ended, current_setting returns '', not NULL. Without nullif, a reused backend would compare against an empty string instead of denying cleanly (SECURITY A-3). Every tenant table has RLS ENABLEd and FORCEd, including drafts, raw rows, lots and staging tables.

Tenant writes by a job (import polling) run under the linking user's membership (provider_connection.linked_by_user_id) with actor = system:<job>, so authority and attribution stay separate. 3.3a Parent roll-up under RLS: totals, not rows

Access stays membership-only and is never inherited (PRD §5): membership on a parent grants nothing on its children, and the reverse. Yet a parent member must see the parent's consolidated figures, including children they hold no membership on, and drilling into such a child stops at the boundary panel (DESIGN §5.7). Plain RLS cannot serve that: under poly_app the child's lines are invisible, and §3.3(j) bans materialized views over tenant data.

Mechanism: one allowlisted definer function computed on read. app.rollup_totals(parent_entity_id, as_of, period_from, period_to) is STABLE SECURITY DEFINER, search_path = '', owned by a new NOLOGIN, NOBYPASSRLS role poly_rollup, with EXECUTE granted to poly_app. It sits on the definer allowlist.

  1. It returns nothing unless app.has_role(parent_entity_id, 'viewer') holds for app.current_user_id().
  2. poly_rollup owns no tables. It reads entity_rollup, entity (name and type only), account, journal_line, lot and the reference prices through role-targeted FOR SELECT TO poly_rollup policies whose predicate is entity_id = any (app.rollup_descendants()), the recursive walk of §3.3b from the parents the current user belongs to. Even a bug in the function body can read only entities beneath those parents.
  3. It returns aggregates only: one row per (entity, report line, currency) for the parent's own accounts and each entity beneath it, each entity once however many paths reach it (§3.3b), carrying the entity's display name and a viewer_has_membership flag, which tells the UI whether a click opens the register or the boundary panel. Report lines are account class as of as_of: assets, of which each of the four nature classes (§3.6; cash at its balance, the three securities classes at market) and other assets (real estate, prepaid tax and the like, at book); liabilities; net worth; plus income and expense by top-level category for the period. Never an account, entry, line, payee, memo, lot or position. This grain is the Principal's ruling of 2026-11-06 (OQ-18). The period is any range, by ruling (Principal, 2026-11-07, P2): the function takes whatever period_from / period_to it is given, with no snapping to whole months and no period guard. For a small entity, one-day ranges effectively reveal individual amounts and their dates; that exposure is consented, and the consent wording on the inclusion step and on the placement and ancestor-invite notices is a security requirement (SECURITY C-25, T-72, R-17), changed only through a security-gate review.
  4. A companion, app.rollup_tree(parent_entity_id), returns the edges beneath the parent with display names and no figures. The UI uses it to draw subtotals for nested parents, including ones the viewer holds no membership on, from the rows above.
  5. The function's result shape is fixed by its RETURNS TABLE. A pgTAP test asserts that a parent viewer without child membership gets totals equal to the child owner's own figures, and zero rows from every tenant table for that child.

Alternative rejected: worker-materialized per-child aggregates in a tenant table keyed by the parent. A job must run under a principal holding membership (§3.3), and the child's principal is the wrong one to write the parent's rows. The cache goes stale on every posting and needs invalidation triggers. And it buys no extra isolation: the function above already confines its reads by role and by policy. Revisit only if the dashboard's <2 s NFR fails measured at parent scale (unmeasured; a household has a handful of children).

Holdings popover on a parent (DESIGN, 2026-11-06). The popover lists positions, which this function never returns. So on a parent it lists the parent's own accounts and those of entities the viewer holds a membership on, read through the ordinary RLS path, and any other included entity shows its total and the boundary panel. It belongs to the roll-up milestone; SecEng confirmed the gating (SECURITY C-25): no definer returns a position.

Scope: the junction and its trigger (§3.3b) ship in M1 with tenancy. The consolidated view, app.rollup_totals, its economic sibling (§3.3c) and the popover land in POLY-1.1, the quick follow-up right after GA (§11). SecEng signed off the function and poly_rollup (SECURITY C-19 amended, C-25; OQ-19 closed), with one change folded in §3.3b: the graph triggers belong to poly_graph, not poly_rollup.

3.3b Nesting: an acyclic graph, each base entity counted once

A parent may include base entities and other parents to any depth, and a base entity may sit in several parents (PRD §5, 2026-11-06). So the structure is a directed acyclic graph, not a tree, and two paths can reach one entity:

flowchart TD
  h["Holding"] --> a["Household A"]
  h --> b["Household B"]
  a --> p["Person"]
  b --> p
  a --> t["Trust"]

Person is reached twice from Holding and is summed once.

  • Traversal: a recursive CTE on read, no closure table. WITH RECURSIVE over entity_rollup, using UNION rather than UNION ALL, yields each descendant once, which is the count-once rule, and it would terminate even on bad data. A closure table would read faster, but it is a second copy of the structure, and on a graph with shared entities a delete needs path counting to avoid removing a pair another path still justifies. Structures here are small (unmeasured; a household has a handful of entities) and the only reader is the roll-up, so that cost buys nothing. Revisit only if the dashboard's <2 s NFR fails measured at parent scale.
  • Membership and RLS do not depend on depth. Access stays per entity: tenant policies call app.visible_entities(), which reads membership alone and never walks the graph. The only traversal is app.rollup_descendants() and the two functions above, all on the definer allowlist. Depth therefore adds no cost and no risk to any ordinary read.
  • Cycle prevention: a trigger, under a lock. app.check_rollup_edge() runs BEFORE INSERT and rejects a child that is the parent or any ancestor of it. It must be SECURITY DEFINER, because a cycle can pass through entities the inserting user cannot see under RLS. It is owned by poly_graph, with search_path = '' and a graph-wide read of entity_rollup: poly_rollup's reads are confined to the caller's descendants, so a check run as poly_rollup would miss a cycle outside them (SECURITY A-16, T-77). Two concurrent inserts could each pass while blind to the other, so the trigger first takes pg_advisory_xact_lock on one fixed key. That serializes every parent-link insert on the instance; these are rare, so the cost is nil. A delete cannot create a cycle and takes no lock. UPDATE is already refused.
  • Sanity limit: 8 levels. The same trigger rejects an insert that would make the longest path from any top parent to any entity beneath it exceed 8 links. The product sets no cap. This one is a judgement, not a measurement (unmeasured): it bounds the work of a definer function, and it sits well above the deepest structure anyone has described (Holding over Household over base entity, 2 links). It is a constant in the function; raising it is one migration.
  • Validation errors name no hidden entity. The user sees "this would make an entity its own ancestor" or "this structure is too deep (limit 8 levels)". The refusal does disclose that some link exists, one bit about structure the user may not see; SecEng accepted it (R-15).
  • Consent travels upward, with notice (Principal, 2026-11-06). Agreeing to a parent accepts that parent's later placement under another parent. So linking Household into a Holding shows every entity beneath Household to the Holding's members as totals. In the same transaction, app.check_rollup_edge() writes a notification to every owner beneath, which a definer must do because the inserter may not see them. Each can see the parents above (app.parents_of) and remove their own entity's link. That link is the direct one: a Person's owner leaves a Holding by leaving the Household inside it. The notice names the new top parent and states what becomes visible, in the consent wording (C-25), with an audit_event.
  • Notice when a parent gains a member (Principal, 2026-11-07, P5; SECURITY A-21). A second poly_graph trigger, app.notify_ancestor_invite(), runs AFTER INSERT on invitation on a parent-kind entity, and AFTER INSERT on membership on a parent-kind entity when no invitation produced the row (the operator CLI). An invitation row exists only once it is live, after any §3.1b approval, so the trigger fires at exactly the moment the audience grows. In the same transaction it walks every descendant at any depth and writes one notification per owner per person, deduplicated across paths and entities, naming the parent and the new member, with the consent wording and the pull-out link. Any role triggers it, since viewers see totals too; a later role raise (an UPDATE) does not; an accepted invitation's membership does not fire again. Nothing waits on the recipients.
  • Tests (pgTAP): a diamond sums once; a direct and an indirect cycle are refused, including one through an entity invisible to the inserter, and one through an entity invisible to poly_rollup's predicate; two concurrent opposing inserts leave at most one row; a ninth link is refused with the validation error; a parent viewer gets totals and zero rows from every tenant table at every depth; an invitation going live on a Holding notifies the owners of a Person two levels down whom the inviter cannot see, once each, and a role raise does not; calling a poly_graph function directly fails.

3.3c The economic view: the gross roll-up, weighted by the viewer's stake

Principal, 2026-11-07: ships with POLY-1.1 beside the gross roll-up, and reveals nothing the gross view does not.

The gross roll-up answers "what does this Household hold"; the economic view answers "what of it is mine". In a marriage with separate property, a trust one partner inherited counts fully in the gross view and not at all in the other partner's economic view.

  • Mechanism: a sibling definer, same grain. app.rollup_economic(parent_entity_id, as_of, period_from, period_to), owned by poly_rollup, on the allowlist, with the same guard and the same RETURNS TABLE as app.rollup_totals plus a stake column. It takes no Person argument: the viewer's Person is the entity whose self_user_id = app.current_user_id(), so nobody can request another member's economic view. The gross function, its rows and the OQ-18 grain are unchanged.
  • Same set, never wider. It weights exactly the rows app.rollup_totals returns for that parent and adds none, so an entity the viewer holds units in but which sits outside this parent contributes nothing here (Principal, 2026-11-07, OQ-29). A cross-parent "my net worth" is a later option that needs SecEng.
  • Weight of a row of entity H, for the viewer's Person P:
    • H = P: 1. Another Person: 0, since a Person's table is implicit (§3.1a).
    • Otherwise P's stake in H, plus, for each entity holder B of H, B's stake in H × P's stake in B. One link only, which §3.1a guarantees is the deepest chain there is. B's cap table is read whether or not B is beneath the parent.
    • Balances use the split in force on as_of. Period income and expense use the split in force on each entry's posting date, the same rule as tax allocation (§4.5), so a mid-year change splits the year.
  • Economic net worth = Σ over the selected parent's roll-up set (the returned rows) of net worth × weight, each entity once (§3.3b). It is not the sum over every entity the Person holds units in. It is a figure of the economic view only; the gross view's net worth is unchanged.
  • Disclosure. Dividing an economic figure by its gross figure gives the viewer's own stake in that entity, which the cap-table notice already tells them. It gives nothing about any other holder. SecEng confirmed (SECURITY C-25). Like the gross view, it takes any date range, with no period guard (P2).
  • Former holders. A purged holder's units weight as outside owners from the purge date, and nothing looks through it on any date, since its own cap table is gone (§3.4b).
  • Tests (pgTAP): on every row, Σ over all holders' economic figures + the outside-owners share = the gross figure; a spouse's separate trust weights 0 for the other spouse; a stake changed mid-period splits the period's income at the change date; a viewer gets no economic row for an entity absent from the gross rows.

3.4 The privileged purge path

A sole owner's whole-entity purge (PRD §5) runs through one SECURITY DEFINER function, app.purge_entity(entity_id, export_id, reauth_at). The function is owned by the dedicated NOLOGIN, NOBYPASSRLS role poly_purge, with search_path = '', and EXECUTE is granted to poly_app (SECURITY §4.5, OQ-4).

Why not poly_owner: under FORCE RLS the owner is itself subject to policies. Append-only tables have no DELETE policy, so an owner-run purge would delete zero rows and still report success (T-51).

How the deletes are allowed: each purgeable table carries CREATE POLICY purge … FOR DELETE TO poly_purge USING (entity_id = nullif(current_setting('app.purge_entity', true), '')::uuid). The append-only triggers allow DELETE only when current_user = 'poly_purge' and the row's entity matches. poly_app can set the GUC but can never become poly_purge.

The roll-up junction has two entity columns, so its purge policy matches either: parent_entity_id = … or child_entity_id = …. Purging a base entity removes it from every parent it sat in, and each parent's owners get a notification. Purging a parent removes its own books and its junction rows, upward and downward; everything beneath it stays intact, and a nested parent simply loses that link. The cap table is the opposite case: equity_*'s purge policy matches entity_id only, never holder_entity_id, because the rows naming the purged entity as a holder are the other entity's history. Those rows stay, and the purged entity's row stays as a tombstone so they resolve (§3.4b). Pending change_requests on the entity are deleted with it (a purge needs a sole owner, so none can be awaiting another owner); their audit events survive.

The guards run in this order, in one transaction:

  1. Re-authentication within 5 minutes. The route checks it, and the function requires the timestamp as an argument.
  2. Sole-owner check against app.current_user_id().
  3. An export.completed audit event for this entity, by this user, within 24 hours, carrying a SHA-256.
  4. No tenant write to the entity since the export's snapshot marker. The entity row is locked FOR UPDATE.
  5. An entity.purged audit_event is written before the first delete. It records the actor, entity id and name, the export event, per-table row counts, the final chain head (§3.2.9) and the ids of the entities on whose cap tables it was a holder (§3.4b). audit_event has no FK to entity and no purge policy.
  6. Every connection has been revoked at the provider by the worker revoke job. A failed revocation blocks the purge.
  7. Set app.purge_entity transaction-locally and delete in dependency order, attachments, journal_chain and the counter included. Then reduce the entity row to its tombstone (§3.4b).
  8. Assert zero rows remain for the entity in every purgeable table before commit, and that the entity row is in tombstone shape (fail loud). entity is not a purgeable table: it has no purge DELETE policy, so the catalog-derived list of purgeable tables never contains it, and the tombstone assert covers it instead.

Not permitted: purge by a job; purge through the API without typed confirmation of the entity name; purge of a partial range; purge while a second owner exists. What the confirmation says about backups (SECURITY A-35, R-5): purged data stays "up to 35 days in backups", the bucket's fixed retention (§7.2); the store cannot delete it sooner, and there is no long-term archive tier in v1. The same words appear on each purge choice in account deletion (§3.4a). Rejected: DISABLE TRIGGER (DDL, affects every tenant), tombstoning the entity's data in place of deleting it (breaks PRD §5; the id-only tombstone of §3.4b holds no data), BYPASSRLS (broader than needed). No execution delay (Principal, 2026-11-06, OQ-23): the guards above stand, operator backups remain, and every member is emailed immediately, before the entity's own rows go. SecEng had recommended a cancellable 24-hour delay (SECURITY §12.3 Q2).

An account with no second step (Principal, 2026-11-08; SECURITY v1.2.2 A-30, §4.6). A departing user gains nothing from a factor they would use once, so the flow does not make them set one up. The tombstone transaction refuses an unenrolled user unless the plan carries a live stamp. Everything else in the flow is unchanged, and enrolled users use their factor as before. Such a user holds owner only on an unshared own Person (§3.1c), so the transfer and founder steps do not arise; a user the operator reset who still holds owner elsewhere meets the sign-in gate first.

Who invokes: the account being deleted, and only it, for every step: signed in, with a fresh step-up including the second factor for an owner (password or IdP plus the emailed code for an unenrolled user, above); never a job, another member or the operator CLI. The plan is held server-side and bound to the session that made it; another session starts again from the list (SECURITY §4.6, C-52; OQ-25 closed).

3.4b Purging an entity that holds units on other cap tables

SECURITY A-19, SecEng's proposal, designed here; before POLY-1.0. What the other entity's owners see in place of the name was ruled by the Principal on 2026-11-07 (OQ-33, option c).

Entity X holds units in E: E's equity_holding rows name holder_entity_id = X. Those rows are keyed to E, append-only, and part of E's history, so purging X must not touch them. It must not leave them dangling either, and X's share must go somewhere.

  • A tombstone, always. Every purge reduces X's entity row to id and purged_at, every other column null (name, type, self_user_id, founder, tax attributes), instead of deleting it; a CHECK admits that shape only when purged_at is set. Always, not only when X is referenced: one code path, one deterministic assert, and a referencing row written concurrently cannot slip between a "referenced?" check and the delete. The cost is one id-only row per purged entity, which says only that some entity existed and when it was purged. The PRD §5 promise holds: every row of X's data is gone. It is the same move as the user tombstone (§3.1).
  • How the tombstone is written. poly_purge gains one role-targeted policy, FOR UPDATE TO poly_purge USING (id = purge GUC), with UPDATE granted only on the columns it nulls and purged_at. No DELETE policy exists on entity. holder_entity_id FKs entity ON DELETE NO ACTION, so a bug that tried to delete the row instead fails loudly.
  • The append-only trigger is untouched. E's rows are neither updated nor deleted, and E gains no rows. So no exception is added to the equity_* trigger, the Σ invariant still holds as written, and no cap_table request on E is needed: X's owner purging their own entity is not an edit of E's cap table.
  • The share moves by a read rule, not a write. The split on date d (§3.1a) adds one clause: a holder whose entity has purged_at::date ≤ d contributes 0, so its units fall into outside owners = total − Σ live units. One SQL function computes the split, and the economic view (§3.3c), allocated income and tax allocation (§4.5) all call it. Before the purge date the rows stand as recorded and the share remains the former holder's, so E's past closes and reports still agree with themselves. Closes are never reopened, so a close already posted is unchanged.
  • Look-through ends on every date. If X was an entity holder with its own holders, X's cap table is purged with it, so nobody's economic weight in E through X can be computed for any date, even before the purge. The economic view therefore shows X's units as outside owners for a past as_of too. That is a deliberate inconsistency with E's direct split, bounded to the look-through path, and the view says so when it applies. Keeping X's cap table past the purge would break the PRD §5 promise.
  • No new rows naming a former holder. app.check_equity_holding() refuses any new row whose holder is tombstoned. E's owners reassign the units by an ordinary edit, a new row for another holder (through a cap_table request if E has several owners); a correction of X's units before the purge date is not possible after it. A pending cap_table request on E whose payload names X fails re-validation at apply and is declined as stale.
  • The cycle and depth checks keep treating the former edges as edges, which is harmless: a tombstoned entity can never hold or be held again.
  • Notice. The tombstone UPDATE fires a poly_graph trigger, app.notify_former_holder(), AFTER UPDATE OF purged_at, which writes one notification to each owner of each entity whose cap table named X, in the purge's transaction. poly_graph already holds the graph-wide equity_holding read, owner membership SELECT and notification INSERT this needs, so poly_purge gains no read of other entities' rows. X's own members are emailed as every purge begins (OQ-23); E's owners are the other side.
  • What E's owners see in place of the name (Principal, 2026-11-07, OQ-33). The system shows "Former holder (purged <date>)" and copies nothing of X: the tombstone holds no name, and no snapshot is taken at purge. E's owners may add an optional label they type themselves, recording what they already know. The label is E's own data:
    • Shape. equity_holder_label(entity_id, holder_entity_id, label, recorded_at), keyed to E, append-only like the rest of the cap table; the latest row recorded for a holder wins, and clearing writes an empty label. A trigger admits a row only for a tombstoned holder, so a live holder's name always comes from its entity.
    • Who writes. It is a cap-table edit: owner of E only, direct while E has one owner, a cap_table change_request otherwise (§3.1b). The multi-owner gate covers equity_holder_label along with equity_*, and poly_govern gets INSERT on it.
    • Who reads. Members of E, by ordinary RLS, like E's other cap-table rows.
    • Purge. Purged only with E: its purge policy matches entity_id, never holder_entity_id, so purging X never touches it.
  • Tests (pgTAP): purging X leaves E's equity_holding rows unchanged and resolvable; the zero-rows assert passes with the tombstone present and fails if any other column is non-null; E's split on the day before the purge includes X and on the purge date counts its units as outside; Σ economic + outside = gross still holds for E after the purge; a new row naming X is refused; a pending cap_table request naming X is declined as stale; each owner of E, including one the purging user cannot see, gets one notification; deleting the tombstone row fails; the row shows "Former holder (purged <date>)" with no trace of X's name; a label for a live holder is refused; with two owners, a direct label INSERT is refused; purging X leaves E's labels intact.

3.5 Attachments

PRD §5 includes attachments (statements, receipts, closing documents) in export and purge, but v1 had no storage design (SECURITY A-14). The design:

  • Location: Postgres bytea in an entity-scoped attachment table. It is RLS-covered like every other tenant table, and it automatically falls inside backup, export and purge. It works unchanged on every hosting target, including Vercel + Neon.
    • Rejected for v1: a filesystem or S3-compatible object store. That would be a second access-control system to keep in lockstep with RLS, and a second thing to back up, export and purge.
    • Cost: database size. At household scale, a few hundred MB per year is expected (unmeasured).
    • Revisit if the attachment table exceeds a size set in INFRA.
  • Limits: 10 MB per file. Type allowlist: PDF, PNG, JPEG, and CSV/OFX (kept as import evidence). The type is sniffed server-side, and the client-declared type is never trusted. A SHA-256 is stored for de-dup and for the export manifest.
  • Serving: only through an app route inside withTenant, with Content-Disposition: attachment, X-Content-Type-Options: nosniff, the sniffed Content-Type, and a restrictive CSP. Nothing is rendered inline.
  • Linking: entry_attachment links an attachment to a journal entry, draft or account. A link doesn't change the entry, so attaching to a posted entry is allowed. Unlinking is manager+ and writes an audit_event. Attachment bytes themselves are insert-only.
  • Boundary: uploads cross TB-11 (untrusted file ↔ parser). Attachments are stored, never parsed. CSV/OFX import files are parsed by the import adapter under TB-11's controls.

SecEng conditions (approved on security, all binding):

  1. Filename: Content-Disposition uses the RFC 6266 filename*=UTF-8'' form, with CR/LF and quotes stripped. The CSP is default-src 'none'; sandbox.
  2. Entity binding: attachment and entry_attachment both carry entity_id, with composite FKs, so a link can never cross entities. Viewers read; manager+ uploads.
  3. Purge: both tables get the poly_purge DELETE policy and the append-only trigger exception, and are included in the zero-rows-remain assertion (C-50).
  4. Quota: a per-entity storage quota and an upload rate limit protect the disk. The numbers are set in INFRA.
  5. Isolation: the bytes live in their own table (attachment_blob, 1:1 with attachment), so list and DTO queries never select bytea. Content is never parsed, and no AV scanning is an accepted consequence of that.

3.6 Custodial accounts and the chart by nature

Principal, 2026-11-06 (OQ-22, Option C): the ledger is organised by nature, with a custodian sub-account under each nature account.

  • Chart. Under Assets sit the four nature classes that are also Allocation's top level: Cash and cash equivalents, Fixed income securities, Marketable securities, Alternative investment assets. Each has a sub-account per custodian ("Marketable securities, Schwab brokerage"). The former Assets › Investments grouping is gone.
  • Sub-account naming (2026-11-07). A custodian sub-account is named institution + account type ("Schwab brokerage"). When one institution holds two custodials of the same type, the number mask is appended ("Schwab brokerage ··4821"); posting adds the mask to the existing sibling in the same transaction that creates the second, so neither name is ambiguous. The custodial_account keeps its own name, which the user may edit freely; the ledger name is derived once and is mutable after posting like any account name (§3.1).
  • Real estate and other no-custodian assets (Principal, 2026-11-07) sit under Assets beside the four nature classes, not inside them: an account with nature_class null and no custodial_account_id, one per property, like Prepaid tax but with no authority behind it. It has no lots, no provider link and no reconciliation, and is carried at the value the user books (an opening balance, then manual entries). It counts in the balance sheet, net worth and the roll-up's "other assets" line (§3.3a), and never in Allocation's classes, targets or percentages.
  • Mapping is one-to-many. A ledger account carries custodial_account_id; a custodial owns one ledger account per nature class it holds, enforced by a partial unique index on (custodial_account_id, nature_class). A checking account owns exactly one, and a credit card one liability account with a null nature class. There is no junction: a ledger sub-account never spans two custodials. posting creates a missing sub-account in the transaction that first needs it.
  • Tax authorities are custodial accounts with no provider link. Their prepaid-by-year and refund accounts (§4.5) have a null nature class, so the index does not limit them.
  • Lots reference the custodial and the security. The security's class picks which of the custodial's ledger accounts its basis posts to.
  • Reclassifying a held security moves its basis between nature accounts, so the mapping change posts that entry in the same transaction. The rulings leave this case open; this keeps §3.2.8 true.
  • Money-market funds in the Cash class are carried as cash with no lots, at their stable value. §3.2.8 therefore covers the three securities natures only, and the cash figure below stays one balance.
  • The money-market sub-category under Cash in Allocation therefore has no lot source. It reads the latest reported_position on that custodial of a security mapped to the sub-category, at the provider's reported value; the rest of the cash balance is plain cash. The class total is still the ledger cash balance, so the two always sum to it. A reported figure above the cash balance shows as a reconciliation gap, never as negative cash, and a custodial with no reported positions (a file or manual source) shows its whole balance as cash.

Roll-up per custodial:

  • Book = the sum of its ledger account balances.
  • Cash = its cash account balance.
  • Market = cash + the sum of lot quantity × latest price over lots held there.
  • Unrealized = market − book.

Reconciliation compares each ledger account against the reported balances and positions of the mapped provider account. Allocation reads the nature accounts across custodials (book) or lots by the security's class (market), and each ties to its own total by construction. Sub-categories come from security_allocation on lots (and, for money-market, on reported positions), never from the ledger. Accounts with no nature class are outside Allocation altogether.

No sequence diagram. tax.estimate(entity, jurisdiction, asOf) is a pure function over (a) year-to-date income by tax-treatment tag from the ledger, (b) the tax table row for that jurisdiction and filing year, (c) prior-year filed tax, typed per entity, per jurisdiction, per year, with the ledger's settled-filing figure shown beside it as a check once it exists (Principal, 2026-11-06), and (d) the balance of the custodial prepaid-tax sub-account for that jurisdiction and filing year, written P below. It returns:

  • Pending liability = annualized tax to date − P.
  • Both safe-harbor values and the required payment to date (the lesser of the two cumulative safe-harbor amounts).
  • Gap = required payment to date − P, which is what is still owed by the next due date.

(Principal ruling, 2026-09-30.) A job unit calls freeze() the day after each period cutoff and appends a tax_period_freeze row. The estimate is recomputed on read and never stored, except the frozen period figures. These freezes follow the authority's installment cutoffs and post nothing; the reporting-period closes below are separate.

The app never pays tax. v1 initiates no payment. The user pays the tax authority at their bank, and the payment arrives as an ordinary imported transaction with no counterparty leg. Nothing is accrued between closes: the pending liability is a computed figure, and the tax liability account is touched only at a period close and at filing.

Accounts, seeded per entity for each jurisdiction J:

  • Prepaid tax — J: an asset, held at the authority's custodial_account. It has one sub-account per filing year Y.
  • Income tax payable — J: a liability.
  • Tax refund receivable — J: an asset, held at the same custodial account.
  • Income tax expense — J: an expense.

Grantor trusts and pass-throughs use the entity's existing Distributions / owner draws equity account in place of the expense account (PRD §5 tax-classification routing).

Who accrues (Principal, 2026-11-06): a taxpayer entity accrues its own tax at each close. That means an individual, a non-grantor trust, a C-corp, or a parent classified joint filers. A grantor trust, a pass-through business or a parent classified pass-through to members accrues nothing: its tagged income allocates to its holders by the cap table (§3.1a), and they accrue. A parent classified joint filers ignores its cap table for tax: it accrues its whole income itself. A filing group combining a Household and its Persons on one joint return is not in v1 (OQ-28).

Allocation by the cap table (Principal, 2026-11-07). Replaces tax_allocation_share.

  • The split in force on each entry's date. Each tagged income line of a pass-through entity E allocates to each holder by that holder's stake in E on the entry's posting date (latest rows with effective_from ≤ posting_date). A holder who joins in July takes nothing from June's income.
  • One level onward. A holder that is an entity B is treated by its own classification. A taxpayer B (C-corp, non-grantor trust) adds the allocation to its own estimate and accrues it. A pass-through or grantor B allocates it onward to its holders by their stakes in B on the same posting date. Those holders are Persons, because §3.1a refuses a deeper chain, so nothing is left unallocated except the outside owners' share.
  • Outside owners take their share off-system: it allocates to no tracked entity. With the old share table that was an error (shares had to total 100%); now it is the normal case of an untracked partner.
  • The read. tax.estimate for any taxpayer entity, the Person-estimate definer of OQ-28 included, adds allocated income through one allowlisted definer, app.allocated_income(taxpayer_entity_id, from, to): income-by-tag totals × stake, never rows, because a holder's owner may hold no membership on the entity. It is owned by poly_stake, guarded by a membership on the taxpayer entity, and its reads are confined by role-targeted policies to app.held_entities() (SECURITY C-27, A-18). It reads equity_holding and equity_total for the two entities in the chain and nothing more. Any date range is accepted, with no period guard (P2). A purged holder's share is outside owners from the purge date (§3.4b).
  • A cap-table change after a close is late data: closes are never reopened, and the next close's delta carries it, as for a back-dated import.

Why a sub-account per filing year: a January Q4 payment belongs to the prior year. When a payment draft is created, the rule proposes the filing year from the due-date table (the year whose next unpaid due date the payment falls on or before), and the user can change it before confirming.

Reporting-period close (Principal, 2026-11-06). The accrual is trued up at each close, monthly by default, per the entity's cadence. Tax is a real liability, so net assets should not show it as one lump a year; and tax is nonlinear, so accruing per entry would mean correcting earlier entries.

  • The close. At period end a job unit raises a notification; it never posts. The user confirms one entry per jurisdiction, dated the period end. tax.close() writes the entry and its tax_close row in one transaction.
  • The amount is A = the annualized tax to date from tax.estimate at the period end, before prepaid is subtracted, because Prepaid tax stays a separate asset on the balance sheet. Using the pending liability, which already nets out P, would count prepaid twice.
  • The delta is A − the last accrued_to_date for that filing year, so the first close of a year posts the full figure and later ones the change. It is taken from tax_close, not the payable balance, because in the months before filing that one account also holds the prior year's accrual.
  • Late data. A back-dated import after a close is picked up by the next close's delta. Closes are never reopened. A skipped period needs no catch-up, and a cadence change applies from the next period end.
  • A wrong close is fixed by closing that period again: a new revision posts the difference. "Correct entry" is not offered, so the record and the ledger cannot part.
  • Between closes, the balance sheet and NAV reports add one computed line, "estimated tax since last close": tax.sinceClose(), the estimate at the report date minus the last accrued_to_date on or before it, across unfiled years. Net assets are right on any day with no posting on read. The line is labelled as an estimate, is not a ledger balance, and stays out of the trial balance.
  • Year end is simply the last close of the year. The line and the status "last closed through date" arrive with tax in POLY-1.0; the POLY-M5 statements render without them until then.

What the build carries (POLY-83, POLY-86, POLY-100):

  • Ownership. The migrate client logs in as poly_migrator and runs SET ROLE poly_owner, so audit keeps the login. A custom file that creates an object for another definer owner switches with SET ROLE and ends on SET ROLE poly_owner. A file check enforces that, and also refuses SET SESSION AUTHORIZATION, RESET ROLE and a SET ROLE to anything but poly_owner or a definer-owner role (the C-10 set). Drizzle's migrate() commits inside itself and offers no hook before the commit (read), so the end-of-file role is checked by privilege instead. Only poly_owner may insert into the tracking table, and no other role holds INSERT, UPDATE, DELETE or TRUNCATE on it, so a file that ends on another role fails its tracking insert and the whole run rolls back. That holds only if poly_migrator cannot use poly_owner's privileges without switching, so its membership is granted WITH INHERIT FALSE, SET TRUE and without ADMIN OPTION (Postgres 16 and later; unmeasured, the spike used INHERIT). The same holds for its membership in the definer-owner roles. The runner also asserts current_user = 'poly_owner' when migrate() returns, as a second check. The runner uses one client, never a pool, and closes it in finally. poly_owner is NOLOGIN NOBYPASSRLS, and poly_migrator is its only member. poly_migrator owns no object, which a catalog test checks over pg_class, pg_proc, pg_namespace and pg_type (SECURITY C-85, T-91, A-40). Custom migrations are created with generate --custom.
  • Tracking. drizzle.__drizzle_migrations, created by poly_owner. poly_migrator needs no database CREATE of its own (to be measured on POLY-83). poly_app and poly_worker get USAGE on the schema and SELECT on the table, for the start-up check that the schema is not behind the image.
  • What Drizzle's runner does not do (read from drizzle-orm 0.45.4, not run). It applies every pending migration in one transaction, so a failing file changes nothing. It takes no lock. It counts a migration as pending only if its journal timestamp is later than the last applied one, and it never compares hashes. A migration merged with an older timestamp would therefore be skipped silently, and an edited applied file would go unnoticed. So our runner takes an advisory lock first, and refuses to run unless the tracking rows match the journal's start hash for hash. CI refuses a journal whose timestamps do not strictly increase. One transaction means no CREATE INDEX CONCURRENTLY.
  • BetterAuth's tables are edited from the CLI output, not frozen. Every timestamp is withTimezone (timestamptz, unmeasured with BetterAuth, measured on POLY-86), and the grants follow §3.1c's column list exactly.
  • Versions. drizzle-orm and drizzle-kit are pinned exactly to the stable line measured. The 1.0 line (release candidate at the spike) is a separate upgrade, gated on the §3.3 battery and a clean second generate. ARCH fixes the Postgres major at 17; the image and minor are INFRA's.

7.2 Backup & Disaster Recovery

Resolves OQ-9.

  • Staging co-location: staging stays on the prod VPS (confirms §10's trade-off). Staging holds no real books, so its compromise has no ledger-confidentiality blast radius; splitting to a second box roughly doubles the fixed monthly cost for a single-household deployment with no compliance driver forcing separation. Revisit only if the app is offered to other self-hosters at meaningfully larger scale, or staging starts touching anything beyond fake data.
  • Backup store (INFRA D-3, §6.1; Principal, 2026-11-08): a Backblaze B2 bucket in B2's EU region with Object Lock in compliance mode and a 35-day default retention, one bucket per instance, written through B2's S3-compatible endpoint over HTTPS 443 by rclone in the upload step, which holds no database credential (below). The box holds a put-only key (write on this bucket only; no delete, no retention changes, no governance bypass); a separate read key lives on the operator's laptop for drills and restores; the account master key is never on a box. The store, not the box, enforces that nothing is deleted or overwritten for 35 days, which is also the bound on how long purged data can survive in backups (SECURITY R-5). One mechanism on every target, because 443 is the only outbound port the home box allows (C-76). A Hetzner Storage Box is a documented fallback on the Hetzner target only, once the C-73 cannot-delete test passes against it; Hetzner Object Storage is an alternative pending verification of its lock. The key capabilities are (unmeasured) until the first drill (INFRA OQ-INFRA-4).
  • Mechanism, revised per SECURITY §6.6 (asymmetric recipient, not restic's symmetric repository password): a nightly set of three artifacts — a pg_basebackup -F tar -X none of the cluster piped to stdout (the physical base WAL replays onto; a pg_dump cannot be one; tar to stdout cannot stream WAL, so the segments the base needs come from archive_command like every other, INFRA R-10, unmeasured, OQ-INFRA-11 checks it), a pg_dump --format=custom of the database (the portable fallback, restorable onto the same or a newer major), and pg_dumpall --globals-only --no-role-passwords (the roles RLS depends on, which a per-database dump omits) — and continuously-shipped WAL segments (archive_command, archive_timeout = 300) are each encrypted with age (X25519, the same primitive family as the credential keyring's HPKE scheme) to a recipient public key, then uploaded. The box holds only the age public key — sufficient to encrypt, useless to decrypt. archive_command runs inside the postgres container and encrypts each segment with age before it lands in the spool, so our Postgres image is the pinned upstream major plus age, and the spool never holds plaintext WAL (INFRA R-11). This is a deliberate change from an earlier restic-based draft: restic's repository password is symmetric, so a box holding it to write backups could also read them, which fails SECURITY §6.6's "box holds only the public half" requirement outright. Dedup/incremental snapshotting is given up for this; at single-household data volumes the cost is negligible.
  • Postgres major pinned (INFRA §6.1, §9.3): a physical restore needs the same major, so the major lives in one committed file, infra/postgres-major (one line, e.g. 17), is 17, the major the POLY-76 spike measured (§6.2). It is read by the backup object names (<instance>/<pgmajor>/…) and the Neon project setup. The minor and digest are INFRA's and are written in one place: the FROM postgres:17.<minor>@sha256:… line of the Postgres derivative image. Compose, CI's Postgres service and the backup container all take their image from that line, never retyped (INFRA v1.3 §6.1a). The two must agree: a CI check fails when that line's major differs from infra/postgres-major. A minor bump changes only that line, while a major upgrade changes both, as a planned step that takes a fresh base backup straight after.
  • The backup job's database role (SECURITY v1.3 C-79, A-36, T-89; confirmed with conditions): poly_backup (§3.3) is the one login with BYPASSRLS. It needs REPLICATION for pg_basebackup, and BYPASSRLS with pg_read_all_data for pg_dump, which refuses to dump a FORCE-RLS table it cannot read whole. BYPASSRLS grants no read the role does not already have, since a physical base backup copies every row of the cluster. What is controlled is where the credential can be used and where its output can go:
    • Attributes: LOGIN REPLICATION BYPASSRLS NOSUPERUSER NOCREATEDB NOCREATEROLE CONNECTION LIMIT 3; a member of pg_read_all_data and nothing else; no other grant; owns nothing; ALTER ROLE poly_backup SET default_transaction_read_only = on.
    • Where it connects from: the backup container sits on its own compose network, shared with postgres only, internal: true (no internet route) with a fixed subnet. Compose addresses are not stable, so pg_hba.conf matches the subnet, not a container address. Its first lines allow poly_backup for replication and the polycarpic database from that subnet (scram-sha-256), then reject poly_backup from anywhere else and any replication connection from anywhere else. db_password_backup is mounted into backup alone.
    • The credential and the internet never share a process: backup holds db_password_backup and the age public key. It pipes each dump and base backup through age as it is taken, so the spool holds only .age files. The upload is a separate step (a host script or an uploader container) that holds only the put-only key and the spool and is not on the backup network. This replaces a single backup service holding both (INFRA §2.2 to be re-folded).
    • Output: pg_dumpall --globals-only --no-role-passwords keeps password hashes out of the globals file; restored logins get new passwords from the password manager. The data dump does carry BetterAuth's tables, which is why the age private key is on no box.
    • Slots and WAL: max_replication_slots = 2, max_wal_senders = 3, max_slot_wal_keep_size 2 GB to start ((unmeasured), tuned with OQ-INFRA-5), so a slot cannot fill the disk. If pg_replication_slots shows any non-temporary slot, the 5-minute health ping is skipped and an alert is raised (pg_basebackup -X none opens none; WAL comes from archive_command).
    • Detection and one path: log_connections = on, and polycarpic-ops status flags any poly_backup connection in the last 24 hours that no backup or pre-migration run accounts for. The pre-migration backup (§8.1) and the nightly set both run through this container; no other dump path, and no superuser dump, exists in the scripts.
    • Tests (C-79): pgTAP on the attributes and membership, and an INSERT, UPDATE or DDL as poly_backup fails. provision-check: a poly_backup login (SQL and replication) is rejected from web and from the uploader and succeeds from backup; backup cannot reach the internet; the uploader has no db_password_backup; the spool holds only .age files; the slot and WAL settings are in place. A compose-policy lint checks that only backup and postgres are on the backup network, that it is internal, and that only backup mounts the password. The restore drill counts a FORCE-RLS table's rows in the dump against the base-backup restore.
  • Key custody: in plain terms, backups are locked with a key that never lives on the server, so stealing the server does not open them, and losing both offline copies of that key means the backups can never be opened. The age keypair is generated once at bootstrap, off the box. The public half is placed on the VPS (non-secret — it can only encrypt). The private half lives in the operator's password manager and a printed offline recovery copy per the runbook; it is never on the VPS, and is a wholly separate key from the credential keyring (§6.1/§6.4) — the two are never stored together, so a single compromised secret can't unwrap both live credentials and backup history. Rotation (new keypair) is a manual runbook step on suspected compromise; old backups stay readable under the old private key, which the runbook says to retain until its last covered backup expires.
  • RPO: ≤ 15 minutes via continuous, individually-encrypted WAL segment shipping; the nightly full dump is the tested fallback restore point (RPO 24h) if WAL replay is unavailable.
  • RTO: ≤ 4 hours for total loss of the VPS — provision a replacement box from the committed provisioning scripts (hcloud CLI and cloud-init, INFRA D-7), decrypt the latest base backup and WAL with the offline private key, restore, replay, redeploy the last tagged release image. ≤ 60 minutes for a bad-migration rollback that doesn't need a box rebuild, from the pre-migration backup (§8.1). That backup is encrypted to the offline key, so the restore runs from the operator's laptop, never on the box, and no plaintext dump is kept there (INFRA R-9; Principal, 2026-11-08). Per-target figures, including the home box's 1 day and the Vercel target's, are in INFRA §6.4.
  • Restore drills: monthly (SECURITY C-73, tightened from this section's earlier quarterly draft), scripted, and run off the prod VPS — the operator's own machine, or a throwaway scratch VPS spun up and destroyed for the drill — never a scratch compose project on the box itself: that would put the age private key on the VPS for the drill, which this section's own key-custody rule (§7.2 above) forbids outright, drill or not. Checked against a fixture query (trial balance sums to zero); logged as a runbook checklist item, not assumed to work from the backup job succeeding alone. The drill script also asserts the store credential cannot delete an existing object (C-73's second test, and the measurement the store bullet above is waiting on), and that the restored cluster carries the RLS roles from the globals artifact. The drill is a GA gate (INFRA §6.7).

7.3 Sizing

A 4 vCPU / 8 GB RAM shared-x86 plan rather than 2 vCPU / 4 GB, named by specification because Hetzner renames its plans (INFRA §2.1 records the plan name at order time): Postgres (prod + staging) + web + worker + Caddy fit comfortably inside 8 GB idle, and the extra headroom absorbs backup/WAL-shipping runs, migration bursts, and the staging Playwright smoke without contending with prod. Unmeasured — confirmed against real resource metrics after POLY-M1 lands; downgrading to 2 vCPU / 4 GB is a one-line change in the provisioning file if it proves oversized. Data lives on a separate 20 GB Hetzner Cloud Volume, LUKS2-encrypted and mounted at /srv/polycarpic (SECURITY C-72), so the root disk is replaceable. Swap is off on both Compose targets, so a memory spike hits a container cap, not a page of decrypted data on disk; per-container memory caps are INFRA §2.2.

7.4 Observability & Operations

  • Logs: web / worker emit structured JSON to stdout (one schema — ts, level, req_id, entity_id?, event, …; exact fields agreed with backend-lead before POLY-M1 ships anything that logs). Docker's json-file driver with max-size / max-file rotation captures them; docker compose logs / journalctl is the query surface at this scale. No log-aggregation service until a second box or third-party hosting is in play.
  • Health, split in two (INFRA R-6, D-10): public /api/v1/health answers ok or not and nothing else, so a stranger learns nothing about schema version or backup cadence. The detail goes on a status listener inside the web process, bound to 127.0.0.1 within the container, never given a ports: mapping and never routed by Caddy (TB-13): GET /status returns DB connectivity, the applied schema version against the image's expected one, and the time of the last successful job runs. The host scripts read it with docker compose exec web. Backup age is not app state: the backup job writes its last success to a host state file that polycarpic-ops status and the alerting read. The full Admin view (OQ-15, POLY-81) may move this listener into its own admin service; the seam (loopback only, read-only, no tenant data) stays.
  • Two alert paths, independent (INFRA §6.5): path A is app and host-script email through Resend; path B is a dead-man's switch at Healthchecks.io (free tier; Principal, 2026-11-08) that each box pings after a passing self-check, a backup upload and a deploy poll, and that emails the operator when a ping stops. It holds no data and never probes the box, so it works for the outbound-only home box as well. One failure (a dead box, a dead mail relay) never silences both.
  • Metrics: container resource metrics via docker stats on demand; no Prometheus/Grafana until scale or a second operator justifies the extra service.
  • Alerts (all by email — no on-call rotation for a household of one): backup job failure or a backup older than 26h; a missed heartbeat (path B); a failed or rolled-back deploy; a ledger hash-chain break, SEV1, from the weekly per-entity verifier (§3.2.9), which also emails the entity's owners; a verifier run that has not completed in 8 days alerts as well, so a stopped verifier is not silence.
  • Dashboard: the Healthchecks.io check list (green or red per box) plus polycarpic-ops status (running digest, last deploy, last backup, certificate days left, disk) is the v1 dashboard — the thing the team-lead can point to at launch. A Grafana-class dashboard is a documented future initiative once observability volume justifies the extra container.

7.5 Secrets Delivery & Postgres Config

DevOps's INFRA-level implementation of SECURITY §6.2 and §12.3's remaining asks.

  • Secrets as files, not env vars (SECURITY §6.2, C-74): every operator secret lives under /etc/polycarpic/secrets/ on the host (root:root, files 0400, directory 0700), mounted into containers as Docker Compose secrets: at /run/secrets/<name>. Apps read them through a *_FILE convention (e.g. DATABASE_PASSWORD_FILE=/run/secrets/db_password), never a bare env var — docker inspect, /proc/<pid>/environ and an error reporter dumping process.env all leak plain env vars, never a file only the right container can read. Per-container scoping: web never gets the credential private keyring or the backup private key; only worker mounts the keyring secret. Staging gets its own distinct secret values and its own keyring, which seals sandbox tokens only; it never holds a real provider credential. No secret is ever baked into an image or passed as a build arg; the app refuses to start outside development if a required secret file is missing.
  • The auth secret signs session cookies and also encrypts TOTP seeds, backup codes and OAuth access and refresh tokens (measured, 1.7.18). It is a secret file like the rest, mounted into web and worker only. Rotation goes through BetterAuth's versioned secrets option: the new version encrypts, older versions still decrypt until each row is rewritten (code-read; SECURITY §6). Replacing the secret outright ends every session and makes every enrolled factor undecryptable, so it is the incident path only.
  • Postgres logging (SECURITY C-75): log_parameter_max_length = 0 and log_parameter_max_length_on_error = 0 (bound parameter VALUES never reach the log, even on error — a sealed credential's ciphertext is one thing, but a query parameter carrying a raw token before it's sealed is exactly what this guards), log_statement = 'ddl' (schema changes only, never row data). Set in the Postgres compose service's config, asserted by a config-check in the DB battery (§8's DB battery row).
  • Connection pooling per target (INFRA D-6): the Compose targets run no pooler in v1; the app's own node-postgres pool holds the connections, and set_config(…, true) (§3.3) is transaction-local, so reuse is safe. A pooler service added to compose later is refused by the compose-policy lint unless it declares transaction mode. On Neon the runtime uses the pooled endpoint (PgBouncer, transaction mode) and migrations use the direct endpoint. A CI test connects through each target's endpoint (a local PgBouncer in transaction mode stands in for Neon on every run, a real Neon branch on the scheduled run), sets the setting inside a transaction, commits, and asserts that a later transaction on the same backend sees it empty — the pool-reuse property the pgTAP battery checks at the RLS layer, asserted here at the endpoint.

7.6 Vercel Tertiary Target: Two-Project Split (OQ-13)

Resolves OQ-13; SECURITY C-61/R-3 @ 3c66ce1 (phase/plan-security). DevOps builds the CI check; the split itself is a SecEng ruling.

  • Topology: the Vercel target is two Vercel projects deployed from the same repo, not one. web exposes only user-facing routes, holds only public keys and the poly_app DB credentials. jobs exposes only cron routes (each checking CRON_SECRET with timingSafeEqual), holds the credential keyring and the poly_worker credentials. This is the same TB-4 (web seals / worker opens) split the VPS target already has via separate compose services — Vercel just can't isolate them inside one deployment, so it takes two deployments instead.
  • CI check, three legs (SECURITY C-61's own "build tests"):
    • Route manifest vs. allowlist. Each project's build output (SvelteKit's route manifest under .vercel/output/functions/) is diffed against a checked-in allowlist per project — an exact-set match, not a subset check, so a route silently added to the wrong project's allowlist is caught too, not just one silently missing. jobs's allowlist is exactly the cron routes; web's is everything else.
    • No keyring reference in the web build. A bundle-scan (grep the built output for the keyring module's resolved import path, same mechanism the existing packages/secrets import-boundary lint uses source-side) asserts open() and the keyring module never got bundled into web's build artifact — catches a route misclassified into web's allowlist that would otherwise pass the manifest check by having the right PATH but the wrong CODE behind it.
    • Node build 404s job routes. The VPS's adapter-node build (one image, web/worker/migrate entrypoints, §8.1) is hit on its web entrypoint at each cron route path and must 404 — job routes exist only behind the worker entrypoint there, and this is the cross-check that the VPS and Vercel targets enforce the identical TB-4 boundary by two different mechanisms (separate compose service vs. separate Vercel project) without drifting apart.
  • Deploy (INFRA D-11, §4.7): the operator runs infra/vercel/deploy.sh from the laptop on a signature-verified tag; Vercel's own Git deployment points at a branch nobody pushes to. No Vercel deployment credential lives in GitHub, consistent with C-83: nothing GitHub holds can move a deployment. A failed migration step fails the build and Vercel keeps serving the previous deployment.
  • Backups (OQ-26, INFRA §6.6): a cron function cannot run pg_dump or ship WAL, so the target relies on Neon's point-in-time restore for the plan in use, plus a weekly polycarpic-ops neon-export run from the operator's laptop through a read-only role, encrypted to the same age recipient and put into the same bucket. RPO is up to 7 days beyond Neon's window. No database credential is held in GitHub (Principal, 2026-11-08); revisited with SecEng only if real data lands on this target.
  • Env check in CI (C-61): a Vercel API call, made with a read-scoped Vercel token held as a secret of a GitHub environment with required reviewers, lists each project's configured env var names (never values) and asserts the keyring variable name is present in jobs and absent from web — catches an operator (or a future IaC change) setting it on the wrong project directly in the Vercel dashboard, which the build-time checks above can't see.
  • Cron frequency — measured: Vercel's Hobby plan caps cron jobs at once per day, with timing guaranteed only within the hour (Pro lifts this to per-minute). Since Hobby is already the ceiling this self-hoster fallback target targets, daily is not a choice DevOps is making for cost reasons — it is the only cadence Hobby allows at all. Import polling, EOD prices and period-end jobs on the Vercel target therefore run once daily, a real (accepted) data-freshness gap against the VPS target's more frequent worker loop; SecEng's framing ("daily polling is acceptable for this fallback target") holds given Vercel is the tertiary target, the last resort of the hosting order.
  • Cost: two Hobby-tier Vercel projects, same as one — Hobby is free per project, so the split costs nothing beyond the CI check's own build time (one extra adapter-vercel build, ~same cost as the existing one). If POLY-77 ever needs Pro-tier cron frequency, that's a per-project upgrade, not a re-architecture.

7.7 Sync Rate Floors

The INFRA minimum interval SECURITY §4.2.1 and §3.1 defer to, for "Sync now" and the per-entity import schedule. Rejected below the floor (SECURITY §4.2.1).

  • Aggregators (SimpleFIN, Plaid) — floor 2 hours, default 6 hours. Measured (provider docs, 2026-09-28): SimpleFIN Bridge caps a connection at 24 requests/day, with warnings then access-token disablement beyond that — the binding constraint, since it has no per-call cost at all. Plaid's own /transactions/sync limit (50 req/min/Item in production) is far looser, and Transactions is billed per active Item monthly, not per call, so Plaid imposes no comparable floor of its own. One shared floor governs both providers rather than branching per-provider in the schedule UI: 2 hours (≤ 12 scheduled requests/day) leaves ≥ 12/day of SimpleFIN's budget as headroom for manual "Sync now" clicks and backoff retries without risking disablement, even if every connection runs at the floor. The out-of-the-box default is looser than the floor, 6 hours (4 syncs/day) — ample freshness for a personal dashboard that isn't real-time trading, and it leaves most of the SimpleFIN budget unused for the common case.
  • Broker APIs (Schwab, IBKR) — floor 1 hour, default 24 hours (EOD), both provisional (unmeasured against a registered app). Schwab's Trader API publishes generous, per-app-configurable limits (on the order of 120 req/min for market data) with no stated per-call cost; IBKR's are comparably loose for read-only position/lot queries. Neither is the binding constraint for a buy-and-hold personal-investor persona — product reasoning is: lots and positions settle end-of-day, so there is little value polling a brokerage intraday the way a checking account's pending transactions reward polling. Floor is set looser than the aggregator floor (1 hour) because the provider headroom is real, not because the data changes faster; default matches the existing EOD price-provider cadence (§4.4) at once daily. Reopen when POLY-67/69 registers a real developer app and its actual configured limits are known — "provisional" here means the number, not the reasoning, may move.
  • Enforcement: both floors are a single config value each (SYNC_FLOOR_AGGREGATOR_SECONDS, SYNC_FLOOR_BROKER_SECONDS), read by the same validation SECURITY §4.2.1 already specifies for "Sync now" and the per-entity schedule UPDATE policy — one seam, not a per-provider branch in application code. A provider added later slots into whichever floor its own rate limit and pricing most resembles; a provider that doesn't fit either (a hard per-call cost, for instance) gets its own floor then, not before.

8.1 Deploy mechanism

  • Decision, revised per SECURITY C-83: pull-based, not push-over-SSH. An earlier draft of this section chose GitHub Actions → SSH push; SecEng's explicit preference is pull-based specifically because it means no GitHub-held credential can ever reach prod — the box, not a GitHub Actions runner, decides when and what to deploy. A systemd timer on the box (every 5 minutes) runs a small poll script: query the GitHub Releases API for the newest v* tag (prod) or the registry for the newest main-branch image digest (staging); if it differs from what's running, pull the image by digest (never a mutable tag), then verify. A failed check at either verification step aborts the poll cycle and alerts (§7.4) — the box never runs an unverified image.
  • Attestation verification, pinned per SecEng's delta (SECURITY C-73/C-83 @ 61b4d2a): gh attestation verify <digest> --repo richmosko/polycarpic --signer-workflow .github/workflows/build.yml (the workflow that builds and attests; release.yml only looks the digest up and never rebuilds, INFRA §4.4) — pinning the repo and the exact signer workflow, not just "an attestation exists" (an unpinned check would accept a provenance attestation from any workflow in any repo the same GitHub identity can sign for). Prod adds a second, independent check: the v* tag itself must carry an SSH signature verifiable against /etc/polycarpic/allowed_signers, installed on the box at bootstrap from the operator's own machine and changed only by an operator step — never fetched from the repository, where anyone who can push could forge it (INFRA D-5) — and the tag's commit must be the one the digest was built from, read from an image label the attestation covers (the same signing /merge-pr already does before cutting a release tag, SECURITY §8 "Signing") — so a compromised registry or attestation service alone still can't move prod without also forging a tag signature staging never checks.
  • The box's GitHub credential: a fine-grained PAT, scoped to this one repo only, contents:read + packages:read, with an expiry (rotated per the runbook, same cadence discipline as §6.4's other operator secrets) — never a classic PAT, never org-wide. If the GHCR package and the repo are ever made public, the PAT is dropped entirely: an unauthenticated gh api / registry pull needs no credential on the box at all, which is strictly less attack surface than a scoped-but-present one.
  • Build once, promote: CI builds a single adapter-node image per commit, pushes it to GHCR tagged with the git sha, with an SBOM (CycloneDX) and a provenance attestation attached (SECURITY §8); that same image digest is promoted from staging to prod on tag, never rebuilt. This rules out a staging/prod code-drift class of bug. adapter-vercel builds separately in CI as the tertiary-target check (§7) but is not deployed by this pipeline. The one image serves three compose services through different entrypoints: web, worker and migrate. Each gets only its own secrets; the credential keyring is mounted into worker alone (TB-4), and the layer map keeps open() out of the web bundle (§2.1).
  • Deploy script (idempotent, same for staging/prod, under flock, invoked by the poll timer once it has a verified digest; INFRA §4.4–§4.5): extract the ops bundle (compose files, Caddyfile, scripts) from the verified image into /opt/polycarpic/releases/<digest>/, so the compose definitions carry the same attestation as the code → migrate check-config → migrate --plan → if anything is pending, a pre-migration backup (an encrypted pg_dump, uploaded and kept in the local spool for 7 days) → migrate under an advisory lock → docker compose up -d → poll the health check for up to 120 seconds. Healthy: record the new current digest and ping the monitor. The deploy script and the timer never change themselves during a deploy; polycarpic-ops self-update replaces them through the same verification, by an operator step.
  • The two migrate subcommands the script relies on (backend-lead implements; same image, migrate entrypoint, poly_migrator password only): migrate check-config reads the mounted secret files and host.env without connecting anywhere and exits non-zero, naming what is wrong, if a required secret file is missing or empty, TLS_MODE fails the §7.8 cross-check, or PLAID_ENV is not sandbox on staging. migrate --plan connects read-only, lists the pending migration files in order and exits 0 if none are pending, 3 if some are, and any other code on error; it never takes the advisory lock and never writes. web and worker refuse to start when the applied schema is behind the image, and start when it is ahead, which is what lets the previous release run on the new schema.
  • Interruption during a deploy (INFRA §4.6, R-4): up -d recreates web, so for a few seconds Caddy has no healthy upstream; Caddy retries for 10 seconds (lb_try_duration), which hides it for most requests. There is no blue-green swap on one box; v1 accepts those seconds (§10).
  • Automatic rollback: if health does not pass within 120 seconds of up -d, the script points the desired digest back at the current one, restarts that release's containers from its own ops bundle, writes the failure to the deploy log and alerts. The failed digest goes into /opt/polycarpic/quarantine and the poll skips it until a newer one appears. A failed migration file rolls back in its own transaction, so the old containers keep running on the old digest.
  • Manual rollback (one command): polycarpic-ops rollback points the poll script's "desired digest" file at the previous release's digest and re-runs the deploy script directly (no need to wait for the next timer tick, and no dependency on GitHub's Releases API being reachable at rollback time — the operator already knows the prior digest from the deploy log), and quarantines the newer release so the poll does not re-deploy it. Migrations are additive / backward-compatible by convention (expand-contract — no destructive migration ships in the same release as the code that depends on the drop), so a code rollback never needs a schema rollback. A schema-level rollback is rare and falls back to the DR restore path (§7.2), starting from the pre-migration backup.
  • Operator secrets on the box live as files under /etc/polycarpic/secrets/, mounted at /run/secrets/ into each container that needs it (§7.5) — placed once during VPS bootstrap and never touched by CI or the poll script, which only ever reads a public digest and a public attestation. Neither transmits a secret value onto, or reads one off, the box.

10. Trade-offs & Alternatives

  • Home-grown GL over pgledger (decided 2026-11-09, POLY-124). We own correctness, and in exchange we get a model that fits (multi-leg, tenancy, multi-currency-ready lines). Forking pgledger, a TS library such as Medici, and the external services of kickoff §2.5 were the alternatives. §6.1.
  • Drizzle over dbmate. One TS schema for queries and migrations, plus BetterAuth in the same chain, at the cost of hand-written files for triggers, functions and FORCE RLS, and a runner whose lock and ordering checks we add. Confirmed by the POLY-76 spike (2026-11-09); the policy differ was measured clean. §6.2.
  • BetterAuth inside our transaction (routing pool) over its own pool. The enrolment guards can read the session, and a refusal rolls back BetterAuth's earlier writes in the same request, so the first TOTP verify cannot be half-applied (measured). The cost is a ~30-line shim that depends on BetterAuth's internal pool use, hence an exact version pin and a CI test, and using BetterAuth's Kysely path rather than its Drizzle adapter. Keeping its own pool was rejected: the guard could only match "one live grant per user", and a refusal at the last write left twoFactorEnabled true with TOTP unverified (SECURITY A-31, A-32).
  • Transaction-local RLS context over per-user DB roles or session SET. Per-user roles don't scale with memberships and complicate pooling; session SET leaks across pooled connections. set_config(…, true) is pool-safe on both targets.
  • Import split into raw (L2) and posting (L4). This honours "import is the lowest layer" for raw data while keeping dependencies strictly downward. It costs one extra package.
  • One entry per entity for cross-entity transfers. Each entity's books balance on their own; there are no cross-entity entries. The cost is that matching must pair across entities and post twice (§4.3).
  • Signed single amount per line over debit/credit columns. The balance check becomes a single SUM = 0; presentation derives Dr/Cr from sign and the account's normal side.
  • Balances computed, not stored. No running-balance column until a measured need. That removes a whole class of lock contention and drift bugs, at the cost of a query that grows with history (indexed).
  • pg-boss (Postgres) over Redis for jobs. No extra service. The cost is job throughput we will never need.
  • Web pages call packages directly, not through /api/v1. This skips a serialization hop and keeps SSR fast. The two paths share DTO types, so they can't drift; the cost is that the web UI doesn't dogfood the HTTP API (the Playwright smoke and the native client will).
  • Staging on the prod VPS. Saves a second box. Staging holds no real books, so a staging compromise exposes none, but the two share a kernel. INFRA may split them later.
  • A recreate with a Caddy retry over blue-green on one box. A deploy costs a few seconds without a healthy upstream, mostly hidden by Caddy's 10-second retry, in exchange for one copy of each service and no swap logic to get wrong. INFRA §4.6.
  • An Object-Lock bucket over a Hetzner Storage Box for backups. The store enforces that nothing is deleted for 35 days and one mechanism works on every target over 443, at the cost of a second vendor account. The Storage Box has no measured immutable mode and its SFTP port is closed on the home box (C-76). INFRA D-3.
  • No connection pooler on the Compose targets. One process pool per container is enough for a household and leaves one fewer service, at the cost of a pooler-mode difference between the Compose and Neon targets that a CI test watches. INFRA D-6.
  • Committed hcloud scripts over OpenTofu. One server, one firewall and one volume need no planner and no state file for a novice operator to lose. Revisit with a second server. INFRA D-7.
  • Pull-based deploy over push-over-SSH (SECURITY C-83). No credential GitHub holds can ever reach prod directly, at the cost of a systemd timer on the box and up to a five-minute delay between a tag landing and the box noticing it (acceptable for a single-operator deployment with no SLA).
  • Age-recipient backup encryption over restic's symmetric password (SECURITY §6.6). A compromised box can encrypt new backups but never decrypt any backup, past or future — the cost is giving up restic's deduplication, negligible at this data volume.
  • Period closes over per-entry or year-end accrual. Liabilities stay current without correcting earlier entries, at the cost of a user step each period and one computed line between closes. §4.5.
  • Chart by nature with custodian sub-accounts (Option C). Allocation's top level and the ledger agree by construction, and a custodial keeps its own view. The cost is more accounts, plus an invariant tying lots to the ledger that every securities write must keep. §3.6.
  • An effective-dated, append-only cap table over a mutable share table. Any past allocation or economic figure is reproducible, and a mid-year change splits the year correctly, at the cost of a "latest row per holder on a date" query on every allocation read. Equity sits apart from access, so a co-owner needs no purge or export rights to hold units. §3.1a.
  • Refusing entity chains deeper than one link over composing them or treating them as outside. Tax never silently drops income and the composition stays one join, at the cost of not modelling a holding company inside a trust in v1. §3.1a.
  • A sibling economic function over a weighted mode inside app.rollup_totals. The gross function's shape and tests stay untouched and the economic one is reviewed on its own, at the cost of two definers with one guard to keep in step. §3.3c.
  • Recursive CTE over a closure table for nesting. One copy of the structure and no path counting on delete, at the cost of walking the graph on each roll-up read. §3.3b.
  • Locked counter row over a sequence for the Journal ID. Gapless numbers, as accountants expect, at the cost of serializing postings per entity. §3.2.7.
  • Collect deletion choices, then apply. Abort stays a true abort, at the cost of one more screen and a run that can stop midway on a failed revocation. §3.4a.
  • Reports as data (declarative) over code. Users can clone and edit, and upgrades don't clobber clones. The cost is building a small formula grammar. Scripting stays deferred (PRD §3).
