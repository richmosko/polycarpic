1. System Context

The system and the actors around it. C4 context level.

Polycarpic is a single self-hosted web application backed by one PostgreSQL database. Users (the Principal, household members holding a membership grant, later native iOS/macOS clients and a user-scoped MCP server) reach it over HTTPS. Inside, a genuine double-entry general ledger lives in Postgres under row-level security keyed on the membership join. Outbound, the system pulls transactions from bank/brokerage aggregators through a provider-agnostic adapter interface (a deterministic fake first, then SimpleFIN, Plaid, and direct broker APIs), end-of-day prices and the CPI-U series as reference data, and sends transactional email through Resend. Identity is local (BetterAuth in our own Postgres) with Google / Apple / GitHub as OAuth identity providers. Nothing about a user's books leaves the box except through a provider call the user initiated or an owner-initiated export.

2. Components & Layer Model

Layers depend only downward. Each layer is one or more workspace packages with its own tests; the boundary is enforced by lint, not convention.

2.1 Layer model

Kickoff §3 asks for layers defined before details, depending only downward, with narrow interfaces. The model below is the contract. Rule: a package may import only packages in a strictly lower layer or in its own layer's shared contracts; packages/* never import SvelteKit; only packages/db opens connections, and only through withTenant() / withSystem() (see §3.3). Enforced by eslint-plugin-boundaries (or dependency-cruiser) in CI.

block-beta
  columns 4
  L6["L6 Delivery"] web["Web + API"] wrk["Worker"] ui["UI kit"]
  L5["L5 Insight"] rep["Reports"] tax["Tax"] pf["Portfolio"]
  L4["L4 Posting"] post["Drafts, rules, matching, reconciliation"]:3
  L3["L3 Books"] led["Ledger"] sec["Securities"]:2
  L2["L2 Sources"] imp["Import + adapters"] ref["Reference data"]:2
  L1["L1 Identity"] auth["Auth"] ten["Tenancy"] secr["Secrets"]
  L0["L0 Platform"] dbp["DB access, migrations, PostgreSQL"]:3

Why import sits below the books. Kickoff §2.6 calls import "the lowest non-infrastructure layer". That holds for the raw side — adapters, the raw-transaction store and de-dup depend on nothing domain-level, so they sit at L2. Confirmation, rules and transfer matching need both raw rows and the ledger, so they are split into posting (L4). This keeps "raw data arrives first" true while dependencies stay strictly downward. The ledger never imports the importer: a journal entry carries an opaque source_ref; the two-way link and the posted-status flip happen inside one database transaction owned by posting.

2.3 Interface contracts worth pinning now

  • ImportAdapter — id; capabilities (transactions, balances, holdings, trades); connect(input) → sealedCredential; listAccounts(cred); fetchTransactions(cred, account, range) → RawTxn[]; fetchBalances(cred, account) → ReportedBalance[]; revoke(cred) (provider-side revocation, PRD §5). The fake source implements exactly this and is registered as fake; switching an instance to SimpleFIN is configuration. A CSV/OFX file adapter implements the same interface with no stored credential (SecEng's preferred credential-free path).
  • RawTxn — provider id, provider account id, posted date, amount (decimal string), currency, payee/memo, provider transaction id (nullable), provider payload (JSON). Before storing the payload, the adapter redacts full account numbers, PANs and any credential fields (SECURITY A-9). The de-dup hash is computed by import, never by the adapter: sha256(provider, provider_account_id, provider_txn_id ?? (date, amount, normalized payee, per-day ordinal)), enforced by a unique index.
  • PriceProvider / SeriesProvider — fetch(symbolOrSeries, range) → Observation[] with a source and a priority; CPI-U reuses the price-series pattern (PRD §5). Fake EOD provider: seeded random walk per ticker.
  • Job unit — run(ctx, params): Promise<Result>; must be idempotent, short (< 60 s per invocation, chunked otherwise), and triggerable by either scheduler (§7).
  • Screen DTOs — each page's server load returns a DTO type exported by the owning package. The same types back /api/v1, so the web UI and native clients share one contract. The list of screens comes from DESIGN (ux-designer); DTOs get pinned per screen in each package's design file (kickoff §2.13).

3.2 Invariants the database enforces (not the app)

  1. Balanced entries. A DEFERRABLE INITIALLY DEFERRED constraint trigger on journal_line checks Σ base_amount = 0 per entry at commit, and at least two lines. The app computes balance too, for good error messages; the trigger is the backstop.
  2. Append-only posted rows. BEFORE UPDATE OR DELETE triggers on journal_entry, journal_line, lot, lot_match, tax_period_freeze and on raw_transaction where status = 'posted' raise, and so do BEFORE TRUNCATE statement triggers on the same tables. No login role holds TRUNCATE. The one exception is DELETE by current_user = 'poly_purge' for the entity named in app.purge_entity (§3.4). Corrections go through reverseEntry(): a mirror entry referencing the original, plus a new entry.
  3. Two-way link. Confirming a draft inserts the entry and flips the raw row to posted with the entry id in one transaction. A check ensures a posted raw row always has an entry id and that the entry's source_ref points back.
  4. Single posting date. One date column per entry; a posting_date_allowed(entity, date) function hook (always true in v1) is the seam where period locking plugs in later without a schema change.
  5. Same-entity legs. Every line's account belongs to the entry's entity (composite FK (entity_id, account_id)). Cross-entity transfers are two entries, one per entity's books (see OQ-6).
  6. Actor recorded. actor_kind + actor_id are NOT NULL on entries and drafts, and are forced by a BEFORE INSERT trigger from the transaction's context rather than merely defaulted. actor_kind = 'user' requires actor_id = app.current_user_id(), so a caller cannot attribute an entry to someone else (SECURITY A-5).

3.3 RLS mechanism and connection-pooling safety

Confirmed by SecEng in SECURITY §4.3 / §12 (OQ-2), with the four additions listed last. The permission matrix is SECURITY §4.2.1: roles are uniform across entity types.

  • Roles. poly_owner (NOLOGIN; owns every object); poly_migrator (LOGIN; used only by the migrate step; runs migrations as set role poly_owner … reset role, which mosko-fintech measured as the working shape); poly_app (LOGIN; DML grants only; NOBYPASSRLS; not the table owner, so RLS applies); poly_worker (LOGIN; NOBYPASSRLS; reference-data writes plus tenant DML limited to the import path, SECURITY §4.4); poly_authz (NOLOGIN; owns the authorization functions and nothing else); poly_purge (NOLOGIN; NOBYPASSRLS; owns the purge function; DELETE on purgeable tables only). Role hygiene follows SECURITY §4.3(k). The operator's superuser bypasses RLS by definition — documented as an accepted risk (PRD §6).
  • Context per transaction, never per session. withTenant(userId, fn) opens a transaction and runs select set_config('app.user_id', $1, true) (is_local = true) before any query. The setting dies at COMMIT/ROLLBACK, so a pooled connection cannot carry a previous request's identity. This works with the in-process node-postgres pool on the VPS and with Neon's transaction-mode pooler. Session-level SET is banned by lint.
  • Default deny. Policies read context only through app.current_user_id() = nullif(current_setting('app.user_id', true), '')::uuid. The nullif matters: once a backend has set the GUC and the transaction has ended, current_setting returns '', not NULL. Without nullif, a reused backend would compare against an empty string instead of denying cleanly (SECURITY A-3). Every tenant table has RLS ENABLEd and FORCEd, including drafts, raw rows, lots and staging tables.
  • Policy shape. using (entity_id = any (app.visible_entities())) for reads; writes add app.has_role(entity_id, 'manager') or 'owner' per the permission matrix. Both functions are STABLE SECURITY DEFINER, owned by poly_authz (not poly_owner, because under FORCE RLS the owner is itself subject to policies). They read membership through a role-targeted SELECT … TO poly_authz policy, with search_path = ''. Every definer function is on a CI-checked allowlist (SECURITY A-1, §4.3(h)). Parent/child structure is never consulted — structure grants nothing.
  • System jobs. withSystem(job, target, fn) sets app.user_id to the target's principal and app.actor = system:<job>. It never runs context-free; if no principal resolves, the job errors. Targets come from one allowlisted definer function, app.job_targets(job), which returns (entity_id, principal_user_id, connection_id) and is executable only by poly_worker. Entity-bound jobs with no connection (the tax-period freeze) run as the entity's earliest owner membership. Reference-data policies are role-targeted (TO poly_worker), and poly_app gets SELECT only. Cash-in-Transit aging is computed on read by the exceptions report, not stored by a job (SECURITY A-12). Tenant writes by a job (import polling) run under the linking user's membership (provider_connection.linked_by_user_id) with actor = system:<job>, so authority and attribution stay separate. There is no system bypass clause in tenant policies (SECURITY §4.4, OQ-3).
  • SecEng additions (OQ-2). (a) The RLS coverage probe is derived from pg_catalog, never from a hand-maintained list. (b) poly_app also loses CREATE on public. (c) Policies are per-command with an explicit WITH CHECK on every write; FOR ALL is banned. (d) The inversion canary stays in the battery. The review added (e) to (l) (SECURITY §4.3):
    • (e) Authorization functions are owned by poly_authz.
    • (f) Context is read in the nullif form.
    • (g) TRUNCATE triggers.
    • (h) search_path = '', plus a definer allowlist.
    • (i) Tenancy columns are not updatable.
    • (j) Views are security_invoker = true, and there are no materialized views over tenant data (a matview has no RLS). A report needing a cache materializes into a tenant table under RLS.
    • (k) Role hygiene.
    • (l) UUID keys.
  • Proof. Every migration run in CI executes an RLS battery: an inversion self-test (an unprotected canary table must leak, proving the probe has teeth — borrowed from mosko-fintech), a per-table cross-tenant probe generated from the catalog (a table with RLS disabled fails the build), and a pool-reuse test. That test must run on a backend that has already served a request: tenant A's transaction, then tenant B on the same physical connection sees zero A rows, and a context-free query on that dirty backend sees zero rows. The full battery list is SECURITY §12.3 (qa-engineer).

3.4 The privileged purge path

A sole owner's whole-entity purge (PRD §5) runs through one SECURITY DEFINER function, app.purge_entity(entity_id, export_id, reauth_at). The function is owned by the dedicated NOLOGIN, NOBYPASSRLS role poly_purge, with search_path = '', and EXECUTE is granted to poly_app (SECURITY §4.5, OQ-4).

Why not poly_owner: under FORCE RLS the owner is itself subject to policies. Append-only tables have no DELETE policy, so an owner-run purge would delete zero rows and still report success (T-51).

How the deletes are allowed: each purgeable table carries CREATE POLICY purge … FOR DELETE TO poly_purge USING (entity_id = nullif(current_setting('app.purge_entity', true), '')::uuid). The append-only triggers allow DELETE only when current_user = 'poly_purge' and the row's entity matches. poly_app can set the GUC but can never become poly_purge.

The guards run in this order, in one transaction:

  1. Re-authentication within 5 minutes. The route checks it, and the function requires the timestamp as an argument.
  2. Sole-owner check against app.current_user_id().
  3. An export.completed audit event for this entity, by this user, within 24 hours, carrying a SHA-256.
  4. No tenant write to the entity since the export's snapshot marker. The entity row is locked FOR UPDATE.
  5. An entity.purged audit_event is written before the first delete. audit_event has no FK to entity and no purge policy.
  6. Every connection has been revoked at the provider by the worker revoke job. A failed revocation blocks the purge.
  7. Set app.purge_entity transaction-locally and delete in dependency order, attachments included.
  8. Assert zero rows remain for the entity in every purgeable table before commit (fail loud).

Not permitted: purge by a job; purge through the API without typed confirmation of the entity name; purge of a partial range; purge while a second owner exists. Rejected: DISABLE TRIGGER (DDL, affects every tenant), tombstoning (breaks PRD §5), BYPASSRLS (broader than needed). An optional cancellable 24-hour delay is pending the Principal (SECURITY §12.3 Q2).

3.5 Attachments

PRD §5 includes attachments (statements, receipts, closing documents) in export and purge, but v1 had no storage design (SECURITY A-14). The design:

  • Location: Postgres bytea in an entity-scoped attachment table. It is RLS-covered like every other tenant table, and it automatically falls inside backup, export and purge. It works unchanged on the secondary Vercel + Neon target.
    • Rejected for v1: a filesystem or S3-compatible object store. That would be a second access-control system to keep in lockstep with RLS, and a second thing to back up, export and purge.
    • Cost: database size. At household scale, a few hundred MB per year is expected (unmeasured).
    • Revisit if the attachment table exceeds a size set in INFRA.
  • Limits: 10 MB per file. Type allowlist: PDF, PNG, JPEG, and CSV/OFX (kept as import evidence). The type is sniffed server-side, and the client-declared type is never trusted. A SHA-256 is stored for de-dup and for the export manifest.
  • Serving: only through an app route inside withTenant, with Content-Disposition: attachment, X-Content-Type-Options: nosniff, the sniffed Content-Type, and a restrictive CSP. Nothing is rendered inline.
  • Linking: entry_attachment links an attachment to a journal entry, draft or account. A link doesn't change the entry, so attaching to a posted entry is allowed. Unlinking is manager+ and writes an audit_event. Attachment bytes themselves are insert-only.
  • Boundary: uploads cross TB-11 (untrusted file ↔ parser). Attachments are stored, never parsed. CSV/OFX import files are parsed by the import adapter under TB-11's controls.

SecEng conditions (approved on security, all binding):

  1. Filename: Content-Disposition uses the RFC 6266 filename*=UTF-8'' form, with CR/LF and quotes stripped. The CSP is default-src 'none'; sandbox.
  2. Entity binding: attachment and entry_attachment both carry entity_id, with composite FKs, so a link can never cross entities. Viewers read; manager+ uploads.
  3. Purge: both tables get the poly_purge DELETE policy and the append-only trigger exception, and are included in the zero-rows-remain assertion (C-50).
  4. Quota: a per-entity storage quota and an upload rate limit protect the disk. The numbers are set in INFRA.
  5. Isolation: the bytes live in their own table (attachment_blob, 1:1 with attachment), so list and DTO queries never select bytea. Content is never parsed, and no AV scanning is an accepted consequence of that.

4.5 Estimated-tax accrual (PRD Story 4)

No sequence diagram. tax.estimate(entity, jurisdiction, asOf) is a pure function over (a) year-to-date income by tax-treatment tag from the ledger, (b) the tax table row for that jurisdiction and filing year, (c) prior-year filed tax (an entity attribute per year), and (d) the prepaid-tax account balance. It returns pending liability, both safe-harbor values, the required payment and the gap. A job unit calls freeze() the day after each period cutoff and appends a tax_period_freeze row. The estimate is recomputed on read, never stored, except the frozen period figures.

7.2 Backup & Disaster Recovery

Resolves OQ-9.

  • Staging co-location: staging stays on the prod VPS (confirms §10's trade-off). Staging holds fake data only, so its compromise has no ledger-confidentiality blast radius; splitting to a second box roughly doubles the fixed monthly cost for a single-household deployment with no compliance driver forcing separation. Revisit only if the app is offered to other self-hosters at meaningfully larger scale, or staging starts touching anything beyond fake data.
  • Backup store: Hetzner Storage Box (same account, cheap) as the default, configured for append-only access (a restricted SSH/SFTP subaccount with no delete/overwrite permission on existing objects — Hetzner Storage Box's "no substitution" / read-append mode (unmeasured) until the C-73 cannot-delete test in the restore drill below actually passes against it); an S3-compatible bucket with Object Lock in compliance mode is the documented drop-in alternative for self-hosters outside Hetzner. Either way the store credential itself cannot delete or overwrite history (SECURITY C-73's own test: "a test that the store credential cannot delete").
  • Mechanism, revised per SECURITY §6.6 (asymmetric recipient, not restic's symmetric repository password): a nightly pg_dump --format=custom logical backup and continuously-shipped WAL segments are each encrypted with age (X25519, the same primitive family as the credential keyring's HPKE scheme) to a recipient public key, then uploaded. The box holds only the age public key — sufficient to encrypt, useless to decrypt. This is a deliberate change from an earlier restic-based draft: restic's repository password is symmetric, so a box holding it to write backups could also read them, which fails SECURITY §6.6's "box holds only the public half" requirement outright. Dedup/incremental snapshotting is given up for this; at single-household data volumes the cost is negligible.
  • Key custody: the age keypair is generated once at bootstrap, off the box. The public half is placed on the VPS (non-secret — it can only encrypt). The private half lives in the operator's password manager and a printed offline recovery copy per the runbook; it is never on the VPS, and is a wholly separate key from the credential keyring (§6.1/§6.4) — the two are never stored together, so a single compromised secret can't unwrap both live credentials and backup history. Rotation (new keypair) is a manual runbook step on suspected compromise; old backups stay readable under the old private key, which the runbook says to retain until its last covered backup expires.
  • RPO: ≤ 15 minutes via continuous, individually-encrypted WAL segment shipping; the nightly full dump is the tested fallback restore point (RPO 24h) if WAL replay is unavailable.
  • RTO: ≤ 4 hours for total loss of the VPS — provision a replacement box from the same IaC, decrypt the latest dump and WAL with the offline private key, restore, replay, redeploy the last tagged release image. ≤ 30 minutes for a bad-migration rollback that doesn't need a box rebuild (§8.1).
  • Restore drills: monthly (SECURITY C-73, tightened from this section's earlier quarterly draft), scripted, and run off the prod VPS — the operator's own machine, or a throwaway scratch VPS spun up and destroyed for the drill — never a scratch compose project on the box itself: that would put the age private key on the VPS for the drill, which this section's own key-custody rule (§7.2 above) forbids outright, drill or not. Checked against a fixture query (trial balance sums to zero); logged as a runbook checklist item, not assumed to work from the backup job succeeding alone. The drill script also asserts the store credential cannot delete an existing object (C-73's second test, and the measurement the append-only bullet above is waiting on).

7.3 Sizing

CX32-class (4 vCPU / 8 GB RAM) rather than CX22 (2 vCPU / 4 GB): Postgres (prod + staging) + web + worker + Caddy fit comfortably inside 8 GB idle, and the extra headroom absorbs backup/WAL-shipping runs, migration bursts, and the staging Playwright smoke without contending with prod. Unmeasured — confirmed against real resource metrics after POLY-M1 lands; downgrading to CX22 is a one-line IaC change if it proves oversized.

7.4 Observability & Operations

  • Logs: web / worker emit structured JSON to stdout (one schema — ts, level, req_id, entity_id?, event, …; exact fields agreed with backend-lead before POLY-M1 ships anything that logs). Docker's json-file driver with max-size / max-file rotation captures them; docker compose logs / journalctl is the query surface at this scale. No log-aggregation service until a second box or third-party hosting is in play.
  • Metrics: a /api/v1/health route reports DB connectivity, last successful migration, and last successful backup timestamp. Polled by a free external uptime monitor. Container resource metrics via docker stats on demand; no Prometheus/Grafana until scale or a second operator justifies the extra service.
  • Alerts (all by email — no on-call rotation for a household of one): backup job failure or a backup older than 26h; /health failing for >5 minutes; CI deploy-to-prod failure.
  • Dashboard: /health plus docker compose ps is the v1 dashboard — the thing the team-lead can point to at launch. A Grafana-class dashboard is a documented future initiative once observability volume justifies the extra container.

7.5 Secrets Delivery & Postgres Config

DevOps's INFRA-level implementation of SECURITY §6.2 and §12.3's remaining asks.

  • Secrets as files, not env vars (SECURITY §6.2, C-74): every operator secret lives under /etc/polycarpic/secrets/ on the host (root:root, files 0400, directory 0700), mounted into containers as Docker Compose secrets: at /run/secrets/<name>. Apps read them through a *_FILE convention (e.g. DATABASE_PASSWORD_FILE=/run/secrets/db_password), never a bare env var — docker inspect, /proc/<pid>/environ and an error reporter dumping process.env all leak plain env vars, never a file only the right container can read. Per-container scoping: web never gets the credential private keyring or the backup private key; only worker mounts the keyring secret. Staging gets its own distinct secret values and no keyring at all, since it only ever runs the fake provider. No secret is ever baked into an image or passed as a build arg; the app refuses to start outside development if a required secret file is missing.
  • Postgres logging (SECURITY C-75): log_parameter_max_length = 0 and log_parameter_max_length_on_error = 0 (bound parameter VALUES never reach the log, even on error — a sealed credential's ciphertext is one thing, but a query parameter carrying a raw token before it's sealed is exactly what this guards), log_statement = 'ddl' (schema changes only, never row data). Set in the Postgres compose service's config, asserted by a config-check in the DB battery (§8's DB battery row).
  • Connection-pooler mode, asserted on both targets: the VPS's Postgres and Neon (the secondary target) must both run in a pooler mode where set_config(..., true) (the transaction-local RLS GUC, ARCH §3.3) is safe under connection reuse — transaction-mode pooling, not session-mode, on any pooler in front of either target (PgBouncer on the VPS if one is added later; Neon's own built-in pooler). A CI assertion connects through each target's pooler and confirms the GUC resets between transactions on a reused connection (the same pool-reuse property qa-engineer's pgTAP battery checks at the RLS layer, asserted here at the pooler-config layer instead).

7.6 Vercel Secondary Target: Two-Project Split (OQ-13)

Resolves OQ-13; SECURITY C-61/R-3 @ 3c66ce1 (phase/plan-security). DevOps builds the CI check; the split itself is a SecEng ruling.

  • Topology: the Vercel target is two Vercel projects deployed from the same repo, not one. web exposes only user-facing routes, holds only public keys and the poly_app DB credentials. jobs exposes only cron routes (each checking CRON_SECRET with timingSafeEqual), holds the credential keyring and the poly_worker credentials. This is the same TB-4 (web seals / worker opens) split the VPS target already has via separate compose services — Vercel just can't isolate them inside one deployment, so it takes two deployments instead.
  • CI check, three legs (SECURITY C-61's own "build tests"):
    • Route manifest vs. allowlist. Each project's build output (SvelteKit's route manifest under .vercel/output/functions/) is diffed against a checked-in allowlist per project — an exact-set match, not a subset check, so a route silently added to the wrong project's allowlist is caught too, not just one silently missing. jobs's allowlist is exactly the cron routes; web's is everything else.
    • No keyring reference in the web build. A bundle-scan (grep the built output for the keyring module's resolved import path, same mechanism the existing packages/secrets import-boundary lint uses source-side) asserts open() and the keyring module never got bundled into web's build artifact — catches a route misclassified into web's allowlist that would otherwise pass the manifest check by having the right PATH but the wrong CODE behind it.
    • Node build 404s job routes. The VPS's adapter-node build (one image, web/worker/migrate entrypoints, §8.1) is hit on its web entrypoint at each cron route path and must 404 — job routes exist only behind the worker entrypoint there, and this is the cross-check that the VPS and Vercel targets enforce the identical TB-4 boundary by two different mechanisms (separate compose service vs. separate Vercel project) without drifting apart.
  • Env check in CI (C-61): a Vercel API call lists each project's configured env var names (never values) and asserts the keyring variable name is present in jobs and absent from web — catches an operator (or a future IaC change) setting it on the wrong project directly in the Vercel dashboard, which the build-time checks above can't see.
  • Cron frequency — measured: Vercel's Hobby plan caps cron jobs at once per day, with timing guaranteed only within the hour (Pro lifts this to per-minute). Since Hobby is already the ceiling this self-hoster fallback target targets, daily is not a choice DevOps is making for cost reasons — it is the only cadence Hobby allows at all. Import polling, EOD prices and period-end jobs on the Vercel target therefore run once daily, a real (accepted) data-freshness gap against the VPS target's more frequent worker loop; SecEng's framing ("daily polling is acceptable for this fallback target") holds given Vercel is explicitly the secondary, not the primary, deploy target (kickoff §2.8).
  • Cost: two Hobby-tier Vercel projects, same as one — Hobby is free per project, so the split costs nothing beyond the CI check's own build time (one extra adapter-vercel build, ~same cost as the existing one). If POLY-77 ever needs Pro-tier cron frequency, that's a per-project upgrade, not a re-architecture.

8.1 Deploy mechanism

  • Decision, revised per SECURITY C-83: pull-based, not push-over-SSH. An earlier draft of this section chose GitHub Actions → SSH push; SecEng's explicit preference is pull-based specifically because it means no GitHub-held credential can ever reach prod — the box, not a GitHub Actions runner, decides when and what to deploy. A systemd timer on the box (every 5 minutes) runs a small poll script: query the GitHub Releases API for the newest v* tag (prod) or the registry for the newest main-branch image digest (staging); if it differs from what's running, pull the image by digest (never a mutable tag), then verify. A failed check at either verification step aborts the poll cycle and alerts (§7.4) — the box never runs an unverified image.
  • Attestation verification, pinned per SecEng's delta (SECURITY C-73/C-83 @ 61b4d2a): gh attestation verify <digest> --repo richmosko/polycarpic --signer-workflow <path-to-the-release-workflow> — pinning the repo and the exact signer workflow, not just "an attestation exists" (an unpinned check would accept a provenance attestation from any workflow in any repo the same GitHub identity can sign for). Prod adds a second, independent check: the v* tag itself must carry an SSH signature verifiable against a checked-in allowed_signers file (the same signing /merge-pr already does before cutting a release tag, SECURITY §8 "Signing") — so a compromised registry or attestation service alone still can't move prod without also forging a tag signature staging never checks.
  • The box's GitHub credential: a fine-grained PAT, scoped to this one repo only, contents:read + packages:read, with an expiry (rotated per the runbook, same cadence discipline as §6.4's other operator secrets) — never a classic PAT, never org-wide. If the GHCR package and the repo are ever made public, the PAT is dropped entirely: an unauthenticated gh api / registry pull needs no credential on the box at all, which is strictly less attack surface than a scoped-but-present one.
  • Build once, promote: CI builds a single adapter-node image per commit, pushes it to GHCR tagged with the git sha, with an SBOM (CycloneDX) and a provenance attestation attached (SECURITY §8); that same image digest is promoted from staging to prod on tag, never rebuilt. This rules out a staging/prod code-drift class of bug. adapter-vercel builds separately in CI as the secondary-target check (§7) but is not deployed by this pipeline. The one image serves three compose services through different entrypoints: web, worker and migrate. Each gets only its own secrets; the credential keyring is mounted into worker alone (TB-4), and lint keeps open() out of the web bundle.
  • Deploy script (idempotent, same for staging/prod, invoked by the poll timer once it has a verified digest to move to): docker compose pull (by digest) → one-off migrate → docker compose up -d → poll /health with retry → non-zero exit on failure without swapping traffic (Caddy keeps routing to the last healthy containers until the new ones pass health).
  • Rollback (one button): a runbook command points the poll script's "desired digest" file at the previous release's digest and re-runs the deploy script directly (no need to wait for the next timer tick, and no dependency on GitHub's Releases API being reachable at rollback time — the operator already knows the prior digest from the deploy log). Migrations are additive / backward-compatible by convention (expand-contract — no destructive migration ships in the same release as the code that depends on the drop), so a code rollback never needs a schema rollback. A schema-level rollback is rare and falls back to the DR restore path (§7.2).
  • Operator secrets on the box live as files under /run/secrets/, one per container that needs it (§7.5) — placed once during VPS bootstrap and never touched by CI or the poll script, which only ever reads a public digest and a public attestation. Neither transmits a secret value onto, or reads one off, the box.

10. Trade-offs & Alternatives

  • Home-grown GL over pgledger. We own correctness, and in exchange we get a model that fits (multi-leg, tenancy, multi-currency-ready lines). §6.1.
  • Drizzle over dbmate. One TS schema for queries and migrations, plus BetterAuth in the same chain, at the cost of hand-written files for triggers and functions and an unproven policy differ. The spike gates the choice. §6.2.
  • Transaction-local RLS context over per-user DB roles or session SET. Per-user roles don't scale with memberships and complicate pooling; session SET leaks across pooled connections. set_config(…, true) is pool-safe on both targets.
  • Import split into raw (L2) and posting (L4). This honours "import is the lowest layer" for raw data while keeping dependencies strictly downward. It costs one extra package.
  • One entry per entity for cross-entity transfers. Each entity's books balance on their own; there are no cross-entity entries. The cost is that matching must pair across entities and post twice (OQ-6).
  • Signed single amount per line over debit/credit columns. The balance check becomes a single SUM = 0; presentation derives Dr/Cr from sign and the account's normal side.
  • Balances computed, not stored. No running-balance column until a measured need. That removes a whole class of lock contention and drift bugs, at the cost of a query that grows with history (indexed).
  • pg-boss (Postgres) over Redis for jobs. No extra service. The cost is job throughput we will never need.
  • Web pages call packages directly, not through /api/v1. This skips a serialization hop and keeps SSR fast. The two paths share DTO types, so they can't drift; the cost is that the web UI doesn't dogfood the HTTP API (the Playwright smoke and the native client will).
  • Staging on the prod VPS. Saves a second box. Staging holds fake data only, so a staging compromise exposes no real books, but the two share a kernel. INFRA may split them later.
  • Pull-based deploy over push-over-SSH (SECURITY C-83). No credential GitHub holds can ever reach prod directly, at the cost of a systemd timer on the box and up to a five-minute delay between a tag landing and the box noticing it (acceptable for a single-operator deployment with no SLA).
  • Age-recipient backup encryption over restic's symmetric password (SECURITY §6.6). A compromised box can encrypt new backups but never decrypt any backup, past or future — the cost is giving up restic's deduplication, negligible at this data volume.
  • Reports as data (declarative) over code. Users can clone and edit, and upgrades don't clobber clones. The cost is building a small formula grammar. Scripting stays deferred (PRD §3).
