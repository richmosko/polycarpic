1. Overview & Design Principles

What this product should feel like to use, and the principles that resolve design disputes.

  • Mobile-first when in doubt. The primary v1 target is a self-hosted web dashboard used on desktop for deep review (statements, lot tables) and on mobile for quick checks (dashboard glance, confirming a draft transaction) — design the dense screens up from a mobile layout, not down from desktop.
  • Accessible by default (WCAG AA). Non-negotiable per PRD §6. Financial gain/loss and status signals never rely on color alone — see Financial semantics.
  • No decorative loading states. Skeletons match the real layout; spinners are a last resort (see Component inventory).
  • Every number earns trust. This is a general ledger, not a budgeting toy — a balance, a delta, or a pending-liability figure must always be traceable to its source (the journal entry, the lot, the reconciliation). The UI never shows a number it can't explain if clicked.
  • Immutability is visible, not just enforced. A posted transaction reads as posted (badge, disabled edit affordance); a correction reads as a reversal + new entry, never as a silent edit (PRD §5).
  • Diverge from polycarpic's own tooling, deliberately. The cairn tracker (our internal tool) and the product are not the same thing and shouldn't look like it — this system's identity is derived from measured screenshots and live style reads off Monarch Money and Origin (`useorigin.com`), not memory (Principal direction, 2026-09-28) — see Inspiration: Monarch & Origin.
  • One brand hue, used honestly. The Principal's neon-green brand color (#2CFF05, 2026-09-30 — "the project name relates to fruiting plants") measures 1.36:1 against white, far below AA — kept as the literal --brand value everywhere it clears AA (dark surfaces), with a darkened same-hue green for light-mode --primary, stated plainly rather than silently swapped for a different hue — see Foundations.

5.1 Dashboard glance

Story (PRD §4.1): per-entity financial health at a glance. Source: flows/dashboard-glance-flow.md.

flowchart TD
  start([User logs in]) --> membership{Holds membership\non 1+ entity?}
  membership -- no --> empty[Membership-setup page:\nno entities yet, create or accept invite]
  membership -- yes --> default[Land on default entity\nlast-viewed or first by role]
  default --> render[Render dashboard:\nbalances, cash flow, recent activity,\npending tax liability, allocation snapshot]
  render --> loading{Data cached?}
  loading -- no --> skeleton[Skeleton matches real layout\nno spinner]
  skeleton --> render
  render --> switch{Switch entity?}
  switch -- yes --> picker[Entity switcher\nPerson / Trust / Business / Household]
  picker --> filtered[Re-render scoped to\nuser's membership on that entity]
  filtered --> render
  switch -- no --> drill{Drill into a number?}
  drill -- yes --> source[Navigate to source:\nledger line, lot, or liability detail]
  drill -- no --> idle([Glance complete])
  • Every number on this screen must be clickable through to its source (Overview principle: "every number earns trust").
  • Filtered strictly by membership (owner/manager/viewer) — no transitive access via parent entity (PRD §5 permission model).
  • No-membership state (pass 6): see wireframes/membership-setup.html — the Principal confirmed the dashboard's empty state can simply be the membership-setup page itself, not a separate illustrated empty-state screen.
  • "Skeleton matches real layout, no spinner" (pass 6): while dashboard data is loading, the screen shows placeholder blocks already shaped like the real cards (same card chrome, same approximate text-line widths) instead of a spinner — so nothing visually jumps or re-flows once the real numbers arrive, they just fade in where the placeholders already were.

5.2 Transactions — review, match & correct

Story (PRD §4.2): staged for review → matched/split/grouped → posted → correctable. Source: flows/import-confirm-flow.md. Pass 7 full rewrite: this screen is now Transactions ("Ledger"/"Import" renamed/retired) — the review mechanics below are the Principal's own Plaid bank-feed workflow spec.

flowchart TD
  poll([Plaid adapter polls\nor fake source generates batch]) --> stage[Raw transaction lands\nin the Pending card]
  stage --> transfer{Two legs match\nwithin date window?}
  transfer -- same posting date --> autoEntry[Locked debit leg +\nsuggested offset leg\ntwo-line preview]
  transfer -- different dates --> citEntry[Two entries via\nCash in Transit clearing account]
  transfer -- unmatched --> openItem[Remains a single-leg\nPending row]
  openItem --> aging{Older than\nexceptions threshold\ndefault 3 business days?}
  aging -- yes --> exceptions[Surface on\nExceptions card]
  aging -- no --> stage
  citEntry --> autoEntry
  autoEntry --> expand[User expands the row:\nAuto-Suggest Match view]
  expand --> action{User action}
  action -- edit offset --> editLeg[Inline search dropdown:\noverride the suggested account]
  editLeg --> action
  action -- split --> splitGrid[Split grid:\nadd offsetting rows]
  splitGrid --> liveCheck{Split sum equals\nthe Plaid total?}
  liveCheck -- no --> splitGrid
  liveCheck -- yes --> post
  action -- group --> bulkSelect[Checkbox-select rows,\nbulk action bar appears]
  bulkSelect --> groupModal[Group and Summarize modal:\npre-filled entry, one aggregate\nline + balancing distributions]
  groupModal --> post
  action -- approve --> post[User hits Approve and Post]
  post --> gate{Posting gate:\nbalanced, accounting equation,\ndate match, one entry per draft}
  gate -- fail --> stage
  gate -- pass --> commit[Row fades out of Pending;\nbalanced entry commits to the GL]
  commit --> toast[Toast: entry posted]
  commit --> posted([Appears on Posted,\npaged])
  exceptions --> resolve{Resolved manually?}
  resolve -- yes --> post
  resolve -- no --> exceptions
  posted --> correctQ{User clicks\nCorrect entry?}
  correctQ -- yes --> doCorrect[System posts the reversal\n+ the new corrected entry\nuser never sees reverse as the verb]
  doCorrect --> correctedBadge[Row now shows\nCorrected badge]
  correctedBadge --> clickThrough[Click-through: original lines\nshaded/struck + reversal + new entry]
  correctQ -- no --> complete([Flow complete])
  clickThrough --> complete
  • The locked leg is always the custodial cash side (verified bank reality) — never editable, in the preview, Split grid, or Group modal. The suggested offset leg is pre-filled from historical rules + Plaid category, overridden in place via an inline search dropdown.
  • Split is one draft → one multi-leg entry, live-validated to the Plaid total before it's submittable. Group is many drafts → one entry (the one many-to-one case, ARCH §3) via the shared journal-entry modal, pre-filled with an aggregate line + balancing distributions.
  • Posting gate: Σ debits = Σ credits; accounting equation per entity; entry date matches bank date (or the CIT rule); every posted draft linked to exactly one entry — any failure keeps the item in Pending.
  • Reframed pass 6, unchanged: a posted row's user-facing action is "Correct entry", never "edit"/"reverse" — reversal-only underneath (PRD §5). See design-system-spec.md § Correcting a posted entry.
  • A corrected row carries the Corrected badge (--outline + --brand-2-tinted dot, pencil icon); click-through reveals the full double-entry trail — original lines shaded/struck, the reversal, and the new entry. An auto-posted row carries the same badge/action plus a posted by rule — <name> line (addendum, pass 6).
  • Actor attribution (user / auto-post rule / system job) is shown on every draft and posted row, never inferred (PRD §5).

5.3 Tax liability & safe-harbor

Story (PRD §4.4): pending liability, required payment, gap, pay. Source: flows/tax-liability-flow.md.

flowchart TD
  view([Open Tax Liability view\nfor entity + jurisdiction]) --> accrual[Running accrual annualizes\nincome to date by tax treatment]
  accrual --> pending[Pending liability =\nannualized tax to date minus\ncustodial prepaid balance]
  accrual --> safeharbor[Two safe-harbor bases computed:\nprior-year and current-year]
  safeharbor --> required[Required payment to date =\nlesser of the two safe-harbor bases]
  required --> gap[Gap = required payments to date\nminus custodial balance,\nare you current with the authority]
  pending --> display[Display gauge + figures]
  gap --> tier{Gap status}
  tier -- "gap <= 0" --> onTrack[Tier: Normal / on track\npositive token]
  tier -- "gap > 0, due date > 14d out" --> caution[Tier: Caution\nwarning token]
  tier -- "gap > 0, due date passed" --> danger[Tier: Danger / overdue\ndestructive token]
  onTrack --> display
  caution --> display
  danger --> display
  display --> extPay[User pays the tax authority\nat their own bank, the app\nnever initiates a payment]
  extPay --> imported[Payment appears as an imported\nbank transaction, no counterparty]
  imported --> postEntry[User posts the GL entry:\ndebit the tax-authority custodial\naccount, pending liability itself\ndoes not change, not filed yet]
  postEntry --> accrual
  display --> waitNode([Wait for next period cutoff])
  waitNode --> freeze[Period cutoff freezes\nannualized figure for due date]
  freeze --> accrual
  • The three-tier status (normal/caution/danger) reuses the product-wide status vocabulary — see design-system-spec.md § Financial semantics.
  • Jurisdiction due dates, multipliers, and cumulative percentages are data-driven, so this view must render correctly for an arbitrary number of jurisdictions (PRD §5).
  • Redrawn pass 6: v1 never moves money — there is no "User initiates payment?" button. The user pays at their own bank; it lands as an imported transaction with no counterparty; the user posts the GL entry, debiting the custodial tax-authority account. Dashboard/tax-panel copy says "post your payment," never "pay" or "transfer."
  • Addendum, pass 6: two figures, both measured against the custodial account's balance but not against each other — Pending liability = annualized tax to date − custodial prepaid balance (what you'd owe net of prepayments, if filed today); Gap = required payments to date (safe-harbor) − custodial balance ("are you current with the authority"). Gap is never required − pending.

5.4 Custodial reconciliation, lots & allocation

Stories (PRD §4.5–4.7): GL vs. custodial reconciliation, allocation vs. target. Source: flows/securities-lots-flow.md. Pass 7: "Securities" is gone as a nav item — lots are now a Custodial Accounts sub-card, GL vs. custodial is two nav items not a toggle, Allocation is its own page.

flowchart TD
  view([Open Custodial Accounts\nfor entity]) --> accounts[Per-account cards:\nreported balance, link-health badge]
  accounts --> lotsCard[Lots sub-card per security:\npull-down shows lots,\nshort/long/total gain per lot + summed]
  lotsCard --> priceFeed[Daily EOD price feed\nupdates market value]
  priceFeed --> lotsCard
  accounts --> reconcile[Reconcile GL balance\nagainst custodian-reported balance]
  reconcile --> match{Balances match\nwithin tolerance?}
  match -- yes --> clean[Reconciliation: clean\npositive tier]
  match -- no --> break[Reconciliation: break\ndanger tier, flagged]
  clean --> glLink[General Ledger account register\nshows the same balance, GL side]
  break --> glLink
  glLink --> allocLink([Allocation: actual vs. target,\nits own nav item])
  allocLink --> adjust{User adjusts target?}
  adjust -- yes --> saveTarget[Save new target allocation]
  saveTarget --> allocLink
  adjust -- no --> done([View complete])
  • No toggle (pass 7): General Ledger and Custodial Accounts are two separate nav items, not one screen behind a Tabs switch.
  • Book-vs-market is implicit on the lots sub-card's own gain/loss figures, not a separate chart.
  • A reconciliation break uses the danger tier (--destructive) and must surface on the Dashboard glance too.

5.5 Entity switch & membership access

Story (PRD §4.8): owner/manager/viewer boundary. Source: flows/entity-membership-flow.md.

flowchart TD
  login([User logs in]) --> memberships[Load user's memberships:\nentity, role]
  memberships --> list{More than one\nentity?}
  list -- no --> single[Land directly on the\none entity, no switcher shown]
  list -- yes --> switcher[Entity switcher in header:\nlist entities by membership]
  switcher --> select[User selects an entity]
  select --> roleCheck{Role on\nselected entity}
  roleCheck -- owner --> ownerView[Full read/write:\npost, edit memberships, purge]
  roleCheck -- manager --> managerView[Read/write ledger,\nno membership/purge rights]
  roleCheck -- viewer --> viewerView[Read-only:\nbalances, activity, statements]
  ownerView --> guard{Parent-entity\nstructure implies access?}
  managerView --> guard
  viewerView --> guard
  guard -- "no (always)" --> explicit[Only explicit membership\ngrants access, never inherited]
  explicit --> render([Render scoped dashboard])
  • A Household's membership never transitively grants access to a member Person entity, or vice versa (PRD §5, hard requirement).
  • A viewer never sees a write affordance rendered-then-disabled — write controls are omitted entirely, not shown-and-greyed.
