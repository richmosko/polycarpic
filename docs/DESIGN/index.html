1. Overview & Design Principles

What this product should feel like to use, and the principles that resolve design disputes.

  • Mobile-first when in doubt. The primary v1 target is a self-hosted web dashboard used on desktop for deep review (statements, lot tables) and on mobile for quick checks (dashboard glance, confirming a draft transaction) — design the dense screens up from a mobile layout, not down from desktop.
  • Accessible by default (WCAG AA). Non-negotiable per PRD §6. Financial gain/loss and status signals never rely on color alone — see Financial semantics.
  • No decorative loading states. Skeletons match the real layout; spinners are a last resort (see Component inventory).
  • Every number earns trust. This is a general ledger, not a budgeting toy — a balance, a delta, or a pending-liability figure must always be traceable to its source (the journal entry, the lot, the reconciliation). The UI never shows a number it can't explain if clicked.
  • Immutability is visible, not just enforced. A posted transaction reads as posted (badge, disabled edit affordance); a correction reads as a reversal + new entry, never as a silent edit (PRD §5).
  • Diverge from polycarpic's own tooling, deliberately. The cairn tracker (our internal tool) and the product are not the same thing and shouldn't look like it — this system's inspiration is derived from measured screenshots and live style reads off Monarch Money and Origin — see Inspiration: Monarch & Origin.
  • One brand hue, used honestly. The neon-green brand color (#2CFF05, "the project name relates to fruiting plants") measures 1.36:1 against white, far below AA — kept as the literal --brand value everywhere it clears AA (dark surfaces), with a darkened same-hue green for light-mode --primary, stated plainly rather than silently swapped for a different hue — see Foundations.

5. User Flows

How users move through the product to accomplish the highest-traffic stories (PRD §4). Each flow is embedded inline below, because a browser serves flows/*.md as raw Markdown and its fenced mermaid blocks would never reach the page's Mermaid loader. The .md files stay as the diffable source of truth in flows/.

5.1 Home entry: Sign in, Get started, Sign up

Story (PRD §4.1): a visitor's first move from Home, on a product with no public sign-up. Source: flows/home-entry-flow.md.

flowchart TD
  home([Visitor on Home]) -- Sign in --> login[Login]
  home -- Get started --> gs{Get started:\ninvited to\nthis instance?}
  invite([Invite link from\nan entity owner]) --> signup
  login -- "Have an invite?\nCreate your account" --> signup[Sign up:\ninvite code, then account\nGoogle or email + password]
  login -- "No invite?\nSet up your own instance" --> gs
  login -- enter login credentials --> landed([Dashboard])
  gs -- "yes: I have an invite" --> signup
  gs -- "no: my own instance" --> walk[Walkthrough, same page:\nrequirements, deploy,\noperator sign-in, invite]
  signup -- valid invite --> invited([Dashboard of the\ninvited entity])
  • No public sign-up. Every instance is self-hosted and accounts on it come by invitation from an entity owner. The bar's action is therefore "Get started", never "Sign up".
  • Get started is one page, not a modal. The fork sits on top as two cards ("I have an invite" → Sign up; "I'm setting up my own instance" → the walkthrough directly below), so a self-hosting visitor never leaves the page and the walkthrough has room to grow. Alternative: a modal from Home's Get started button holding just the two cards; lighter on Home, but the walkthrough then needs its own page anyway.
  • Login shows the same branch. Its account line reads "Have an invite? Create your account" (to Sign up) and "No invite? Set up your own instance" (to Get started).
  • Every sign-in lands on a dashboard. Account creation also creates the user's own Person entity, so there is no signed-in state without an entity (design-system-spec.md § Entities & membership). Login lands on the last-viewed entity, else that Person entity; the operator's first sign-in after setup lands on the operator's own Person entity.
  • Sign up is invite-gated. The code arrives pre-filled and validated from an invite link, or is typed. A valid invite names the inviter and the entity. The invite is common to both account paths (Google, or email + password), and creating the account lands on the dashboard of the invited entity.
  • An invalid or used code keeps the visitor on Sign up with an inline error under the field; it never sends them to a dead end.

5.2 Dashboard glance

Story (PRD §4.2): per-entity financial health at a glance. Source: flows/dashboard-glance-flow.md.

flowchart TD
  start([User logs in]) --> default[Land on default entity:\nlast-viewed, else the user's\nown Person entity]
  default --> render[Render dashboard:\nbalances, cash flow, recent activity,\npending tax liability, allocation snapshot]
  render --> loading{Data cached?}
  loading -- no --> skeleton[Skeleton matches real layout\nno spinner]
  skeleton --> render
  render --> switch{Switch entity?}
  switch -- yes --> picker[Entity switcher\nPerson / Trust / Business / Household]
  picker --> filtered[Re-render scoped to\nuser's membership on that entity]
  filtered --> render
  switch -- no --> drill{Drill into a number?}
  drill -- yes --> source[Navigate to source:\nledger line, lot, or liability detail]
  drill -- no --> idle([Glance complete])
  • Every number on this screen is clickable through to its source (Overview principle: "every number earns trust").
  • Filtered strictly by membership (owner / manager / viewer) — no transitive access via a parent entity (PRD §5 permission model).
  • Viewer-role household members see the household's shared accounts and their own entity, never another member's entity (PRD §4.9).
  • "Skeleton matches real layout, no spinner": while dashboard data is loading, the screen shows placeholder blocks already shaped like the real cards (same card chrome, same approximate text-line widths) instead of a spinner, so nothing jumps or re-flows when the real numbers arrive; they fade in where the placeholders were. A spinner says "wait"; a layout-shaped skeleton also says what is coming. See design-system-spec.md § Component inventory → Skeleton.

5.3 Transactions — review, match & correct

Story (PRD §4.3): staged for review → matched / split / grouped → posted → correctable. The review mechanics follow a Plaid bank-feed workflow: every imported transaction is reviewed, matched, split or grouped, then posted. Source: flows/import-confirm-flow.md.

flowchart TD
  nav([Open Transactions\nfrom the sidebar]) --> filter[Account filter:\nAll Transactions by default,\nor one custodial account]
  filter -. scopes .-> tabs[Tabs with count badges:\nExceptions, Pending, Posted;\nopens on Pending]
  tabs --> stage
  tabs --> exceptions
  tabs --> posted
  poll([Plaid adapter polls\nor fake source generates batch]) --> stage[Raw transaction lands\nin the Pending tab]
  stage --> transfer{Two legs match\nwithin date window?}
  transfer -- same posting date --> autoEntry[Locked debit leg +\nsuggested offset leg\ntwo-line preview]
  transfer -- different dates --> citEntry[Two entries via\nCash in Transit clearing account]
  transfer -- unmatched --> openItem[Remains a single-leg\nPending row]
  openItem -- counterpart arrives --> transfer
  openItem -- user approves into CIT --> citOne[One-sided in-flight item:\ncash leg vs. Cash in Transit,\ncounterpart still to come]
  citOne --> post
  openItem --> aging{Older than\nexceptions threshold\ndefault 3 business days?}
  aging -- yes --> exceptions[Surface on\nExceptions tab]
  aging -- no --> openItem
  citEntry --> autoEntry
  autoEntry --> expand[User expands the row:\nAuto-Suggest Match view]
  expand --> action{User action}
  action -- edit offset --> editLeg[Inline search dropdown:\noverride the suggested account]
  editLeg --> action
  action -- split --> splitGrid[Split grid:\nadd offsetting rows]
  splitGrid --> liveCheck{Split sum equals\nthe Plaid total?}
  liveCheck -- no --> splitGrid
  liveCheck -- yes --> post
  action -- group --> bulkSelect[Checkbox-select rows,\nbulk action bar appears]
  bulkSelect --> groupModal[Group and Summarize modal:\npre-filled entry, one aggregate\nline + balancing distributions]
  groupModal --> post
  action -- approve --> post[User hits Approve and Post]
  post --> gate{Posting gate:\nbalanced, accounting equation,\ndate match, one entry per draft}
  gate -- fail --> stage
  gate -- pass --> commit[Row fades out of Pending;\nbalanced entry commits to the GL]
  commit --> toast[Toast: entry posted]
  commit --> posted([Appears on Posted,\npaged])
  exceptions --> resolve{Resolved manually?}
  resolve -- yes --> post
  resolve -- no --> exceptions
  posted --> correctQ{User clicks\nCorrect entry?}
  correctQ -- yes --> doCorrect[System posts the reversal\n+ the new corrected entry\nuser never sees reverse as the verb]
  doCorrect --> correctedBadge[Row now shows\nCorrected badge]
  correctedBadge --> clickThrough[Click-through: original lines\nshaded/struck + reversal + new entry]
  correctQ -- no --> complete([Flow complete])
  clickThrough --> complete
  • Account filter. A top-level selector in the row above the tabs scopes Exceptions, Pending and Posted together, count badges included. Opening Transactions from the sidebar always lands on All Transactions (every custodial account in the entity); the popover lists each custodial account by the name Custodial Accounts uses, with its provider and open-item counts. The Known delta badge on a Custodial Accounts card deep-links here with the filter preset to that account.
  • Tabs with count badges. Exceptions, Pending and Posted are one Tabs row under the account filter, one visible at a time, in urgency order. Each tab carries its count, so every stage's load stays visible while another is open: secondary, destructive-soft on Exceptions when non-zero. Transactions opens on Pending, the review inbox; a non-zero Exceptions count does not take the default, its badge is red instead. The counts follow the account filter, changing the filter keeps the current tab, and the URL hash carries the tab.
  • Every row names its source. Each Exceptions, Pending and Posted row carries one muted line under the payee: landmark icon + <account> · <institution> via <provider> (e.g. "Primary Checking · Bank Y via Plaid"). With the filter on one account, the line is omitted — the trigger already names it.
  • The locked leg is always the custodial cash side — verified bank reality (the Plaid transaction itself), never editable, in the two-line preview, the Split grid, or the Group modal. The suggested offset leg is pre-filled from historical rules + the Plaid category and overridden in place via an inline search dropdown, never a blank field.
  • Split is one draft → one multi-leg entry, live-validated: submission stays disabled until the rows sum exactly to the raw transaction's absolute total. Group is many drafts → one entry (the one many-to-one case, ARCH §3) via the shared journal-entry modal, pre-filled with one aggregate line + balancing distributions.
  • An unmatched transfer leg stays a staged draft in Pending until its counterpart arrives (then it matches like any transfer), or until the user explicitly approves it into Cash in Transit as a one-sided in-flight item — a balanced entry, cash leg against the CIT clearing account, cleared when the counterpart posts. A draft still unmatched past the exceptions threshold moves to Exceptions.
  • Posting gate: Σ debits = Σ credits; the accounting equation holds per entity; the entry date matches the bank date (or the Cash-in-Transit rule); every posted draft links to exactly one entry. Any failure keeps the item in Pending — no partial or silent post.
  • A posted row's user-facing action is "Correct entry", never "edit" or "reverse" — reversal-only underneath (PRD §5). Click-through shows the full trail: original lines shaded/struck, the reversal, and the new entry. See design-system-spec.md § Correcting a posted entry.
  • Badges: Draft (staged) (--secondary, clock), Posted (--outline, check), Corrected (--outline + --brand-2-tinted dot, pencil). An auto-posted row carries Posted plus a posted by rule — <name> line and the same Correct entry action.
  • Actor attribution (user / auto-post rule / system job) is shown on every draft and posted row, never inferred (PRD §5).
  • Import stats and link status (provider sync time, link health) show as a banner at the top of Transactions, not as a separate nav item.

5.4 Tax liability & safe-harbor

Story (PRD §4.5): pending liability, required payment, gap, post your payment. Tax is a sidebar item. Source: flows/tax-liability-flow.md.

flowchart TD
  nav([Sidebar: Tax]) --> view[Tax view for the entity:\njurisdiction tab selected]
  card([Dashboard: Pending tax\nliability card]) --> view
  view --> accrual[Running accrual annualizes\nincome to date by tax treatment]
  accrual --> pending[Pending liability =\nannualized tax to date minus\ncustodial prepaid balance]
  accrual --> safeharbor[Two safe-harbor bases computed:\nprior-year and current-year]
  safeharbor --> required[Required payment to date =\nlesser of the two safe-harbor bases]
  required --> gap[Gap = required payments to date\nminus custodial balance,\nare you current with the authority]
  pending --> display[Display gauge + figures]
  gap --> tier{Gap status}
  tier -- "gap < 0" --> onTrack[Tier: Normal / on track\nprepaid ahead of safe harbor\npositive token]
  tier -- "gap ≥ 0, due more than 14 days out" --> caution[Tier: Caution\nwarning token]
  tier -- "gap ≥ 0, due within 14 days or passed" --> danger[Tier: Danger\ndestructive token]
  onTrack --> display
  caution --> display
  danger --> display
  display --> extPay[User pays the tax authority\nat their own bank, the app\nnever initiates a payment]
  extPay --> imported[Payment appears as an imported\nbank transaction, no counterparty]
  imported --> postEntry[User posts the GL entry:\ndebit the tax-authority custodial\naccount, pending liability itself\ndoes not change, not filed yet]
  postEntry --> accrual
  display --> waitNode([Wait for next period cutoff])
  waitNode --> freeze[Period cutoff freezes\nannualized figure for due date]
  freeze --> accrual
  • Reached from the sidebar or the Dashboard card; both land on the same per-entity view with a jurisdiction selector.
  • Tiers: on track when gap < 0 (prepaid ahead of the safe-harbor requirement); caution when gap ≥ 0 and the due date is more than 14 days out; danger when gap ≥ 0 and the due date is within 14 days or has passed. They reuse the product-wide status vocabulary — design-system-spec.md § Status tiers.
  • Gap = 0 is not on track. It means exactly at the safe-harbor line, with nothing in hand beyond the requirement, so it takes the caution or danger tier by due date.
  • Two figures, both measured against the custodial account's balance but not against each other: Pending liability = annualized tax to date − custodial prepaid balance (what you would owe net of prepayments, if filed today); Gap = required payments to date (safe harbor) − custodial balance ("are you current with the authority"). Gap is never required − pending.
  • v1 never moves money. There is no pay button: the user pays the tax authority at their own bank; the payment lands as an imported transaction with no counterparty; the user posts the GL entry, debiting the custodial tax-authority account (a prepaid-tax asset). Copy says "post your payment" or "record your payment", never "pay" or "transfer".
  • Jurisdiction due dates, multipliers and cumulative percentages are data-driven (a lookup table), so the view renders for any number of jurisdictions per entity, not just federal (PRD §5).
  • At filing, the frozen per-period figures export for Schedule AI / Form 2210 and the state equivalent; the flow's freeze step is the source of that export.

5.5 Custodial reconciliation & lots

Stories (PRD §4.6–4.7): three figures per account, lots, and GL vs. custodial reconciliation. General Ledger and Custodial Accounts are two nav items, not a toggle. Source: flows/securities-lots-flow.md.

flowchart TD
  view([Open Custodial Accounts\nfor entity]) --> totals[Totals card:\nmarket value, book value, cash,\nUnrealized, summed]
  view --> accounts[Per-account cards:\nlink-health badge]
  accounts --> figs[Three figures, left to right:\nmarket value at EOD prices,\nbook value = GL cost basis, cash balance,\nand Unrealized]
  priceFeed[Daily EOD price feed] --> figs
  figs --> totals
  accounts --> lotsCard[Lots sub-card per security:\npull-down shows lots,\nshort/long/total gain per lot + summed]
  priceFeed --> lotsCard
  accounts --> reconcile[Reconcile GL balance\nagainst custodian-reported balance]
  reconcile --> match{Balances match\nwithin tolerance?}
  match -- yes --> clean[Reconciliation: clean\npositive tier]
  match -- "no: difference = staged drafts" --> unposted[Known unposted delta:\nthe unapproved drafts listed,\nnot a break]
  unposted --> glLink
  match -- "no: unexplained" --> brk[Reconciliation: break\ndanger tier, flagged\nalso on the Dashboard]
  clean --> glLink[General Ledger account register\nshows the same balance, GL side]
  brk --> glLink
  glLink --> done([View complete])
  • Three figures on every account, left to right: market value (cash plus every position at the last EOD price); book value (the GL's cost basis, cash included — the GL's own balance for the mirrored account); cash balance; and Unrealized = market − book, signed and coloured per § Delta coloring. A cash-only account shows the same row with equal figures and a $0.00 delta, so cards scan as columns. A totals card sums the four figures across accounts, with the price date. Cash sits last so the row reads as "market and book include cash" — the two totals first, the cash already inside them after.
  • An account's Unrealized figure equals its lots sub-card's total unrealized gain; the two must agree.
  • No toggle: General Ledger and Custodial Accounts are two separate nav items, not one screen behind a Tabs switch. Both read the same lot and journal data; the split is presentation, not a data fork.
  • Unapproved drafts are a known unposted delta, not a break. When the GL and custodian balances differ by exactly the account's staged drafts (e.g. an unmatched transfer leg not yet approved into Cash in Transit), the card shows the delta and lists those drafts, linking to Pending on Transactions; no danger tier. Only a difference the drafts do not explain is a break.
  • A reconciliation break uses the danger tier (--destructive) and surfaces on the Dashboard glance too, not only here.
  • Allocation (actual vs. target by asset class) is its own flow, 5.6.

5.6 Allocation vs. target

Story (PRD §4.8): actual vs. target by asset class and sub-category, drift, two-level target editor. Source: flows/allocation-flow.md.

flowchart TD
  open([Open Allocation\nfor entity]) --> actual[Actual by asset class:\nmarket value from lots,\nacross every custodial account]
  actual --> target[Overlay the target\nper class]
  target --> drift[Drift per class:\nactual minus target, in points]
  drift --> act{User action}
  act -- expand a class --> subs[Sub-category rows:\nactual vs. target and drift\nper sub-category]
  subs -- drill a sub-category --> lots
  act -- drill a class --> lots([Custodial Accounts lots,\nfiltered to that class])
  act -- adjust target --> edit[Target editor, two levels:\npercent per class, then\nper sub-category behind a pull-down]
  edit --> sum{Classes total 100%\nand each class equals\nthe sum of its sub-targets?}
  sum -- no --> edit
  sum -- yes --> save[Save target]
  save --> drift
  act -- none --> done([View complete])
  • Same data, different aggregation: actual allocation is the lots' market value summed by asset class across every custodial account for the entity — not a new data source.
  • Drift is information, not a warning. Over or under target shows as a neutral outline badge ("+2 pt over", "−2 pt under"); on target shows the positive soft badge. No caution or danger hue.
  • Drill: each asset-class or sub-category name opens Custodial Accounts' lots, filtered to it, so every percentage traces to the lots behind it.
  • Sub-categories behind a pull-down. Every class row, in the chart and in the target editor, has a chevron that reveals its sub-categories (the lots sub-card's disclosure pattern). Seeded defaults: US Equity → Large cap, Mid/Small cap; Intl Equity → Developed, Emerging; Fixed Income → Treasuries, Corporate, Municipal; Cash → Cash, Money market. In the chart, each sub-row shows its own actual / target and drift badge.
  • Target editor, two levels: sub-targets are whole-portfolio percent and must sum to their class target; the class row stays editable and carries a reconcile badge (positive soft "Sub-targets sum to N%", or neutral outline "N pt unassigned"). Save is enabled only when the classes total 100% and every class reconciles. Viewers see the chart but no editor and no Save (write controls are omitted, not greyed).
  • No nominal / inflation-adjusted toggle here. Allocation is a contemporaneous snapshot of today's holdings, so a CPI-U restatement adds no information; the toggle (PRD §4.10) belongs to the time-series views (Dashboard net-worth chart, Reports).

5.7 Entity switch, roll-up & membership access

Story (PRD §4.9): parents roll up whole base entities; owner / manager / viewer per entity; the drill-through boundary. Source: flows/entity-membership-flow.md.

flowchart TD
  login([User logs in]) --> memberships[Load memberships:\nbase and parent entities,\nrole on each]
  memberships --> land[Land on last-viewed entity,\nelse the user's own Person entity]
  land --> switcher[Entity switcher, always present:\nevery entity with membership,\nparents with their included\nbase entities nested]
  switcher --> select[User selects an entity]
  select --> roleCheck{Role on\nselected entity}
  roleCheck -- owner --> ownerView[Full read/write:\npost, edit memberships, purge]
  roleCheck -- manager --> managerView[Read/write ledger,\nno membership/purge rights]
  roleCheck -- viewer --> viewerView[Read-only:\nbalances, activity, statements]
  ownerView --> guard{Parent-entity\nstructure implies access?}
  managerView --> guard
  viewerView --> guard
  guard -- "no (always)" --> explicit[Only explicit membership\ngrants access, never inherited]
  explicit --> kind{Selected entity\nis a parent?}
  kind -- no --> baseView([Render the base entity's\nown ledger and accounts])
  kind -- yes --> consolidated[Render consolidated figures\nacross the whole included\nbase entities]
  consolidated --> drill[User clicks a figure\nfrom an included entity]
  drill --> boundary{Membership on\nthat base entity?}
  boundary -- yes --> into([Drill into that entity's\nregister or lots])
  boundary -- no --> stop([Boundary panel:\nIncluded from the named entity,\nno access to its ledger])
  • Base and parent entities. Accounts (custodial and GL) live only in base entities: Person, Trust, Business. A parent (Household; Holding) rolls up whole base entities, never individual accounts. A base entity may belong to more than one parent.
  • The switcher is always present, because every user owns at least their own Person entity. It lists every entity the user holds membership on, base and parent, with each parent's included base entities nested under it; a base entity in two parents is listed under both.
  • Access is explicit membership only (PRD §5, hard requirement): a parent's membership never grants access to an included base entity, or vice versa.
  • The drill-through boundary. A parent viewer sees the parent's consolidated figures. Every figure stays clickable; a drill into an included base entity the user has no membership on opens a boundary panel — "Included from <entity>. You don't have access to that entity's ledger." — instead of the register, never a disabled number or a silent dead end.
  • Role badges (Owner / Manager / Viewer) use decreasing visual weight — default / secondary / outline (design-system-spec.md § Entity, account, and category badges).
  • A viewer never sees a write affordance rendered-then-disabled: write controls are omitted entirely for a role that cannot use them.
  • Roll-up map: Entities opens with a Pack of every entity the user holds membership on — parents as circles holding their base entities, each circle stroked in its entity type's categorical slot, a shared base entity drawn once in each parent with an "also in" marker; each circle switches entity. The membership list below it is the accessible fallback. See design-system-spec.md § Entities & membership.

5.8 General Ledger: tree, register, entry

Story (PRD §4.7): three tabs; chart-of-accounts tree → account register → journal entry, with a custodial cross-reference. Source: flows/general-ledger-flow.md.

flowchart TD
  open([Open General Ledger\nfor entity]) --> tabs{Tab}
  tabs -- default --> tree[Chart of accounts tab:\ncategory → account → sub-account,\nGL balances]
  tabs --> map[Balance sheet map tab, prototype:\nAssets vs. Liabilities + Equity]
  tabs --> journal[Journal entries tab:\nby date, page size,\ndate range, sort]
  tree --> act{User action}
  act -- expand or collapse --> tree
  act -- open an account --> register[Account register:\nevery line that hit it,\ndate order, running balance]
  map -- click a tile --> register
  act -- custodial badge --> custodial([Custodial Accounts:\nthe mirrored physical account])
  register -- line chevron --> entry([Journal entry, expanded in place:\nevery leg, actor,\nCorrect entry action])
  register -- breadcrumb --> tree
  journal -- chevron --> entry
  register -- Journal ID link --> journal
  posted([Transactions: Posted tab]) -- Journal ID link --> journal
  search([Search by Journal ID]) -.-> journal
  • Three tabs, one section at a time: Chart of accounts (the default), Balance sheet map and Journal entries, in one Tabs row at the top of the content. Each keeps its card header. The URL hash carries the tab, so Back from a register returns to the tab it left; a Journal ID link selects Journal entries; the register's breadcrumb returns to the tree.
  • The tree is the GL's own view: every balance is the ledger's figure. The custodial badge (landmark icon + institution) is a cross-reference to Custodial Accounts, never a second data source; accounts with no physical counterpart (Owner's Equity, Cash in Transit) carry none.
  • The register is account-scoped and running-balance-shaped; Transactions is entry-scoped and time-ordered across every account. Different questions, deliberately two screens.
  • A register line expands to its full journal entry in the same block as the Journal entries card: every leg, not just the one that hit this account, plus the correction trail where one exists, with actor attribution and the Correct entry action (flow 5.3). Its Journal ID links to the GL card.
  • Balance sheet map (prototype): a nested treemap on its own tab, Assets | Liabilities + Equity as equal halves, each element in its fixed categorical slot; each tile opens its register. Recommendation and limits: design-system-spec.md § General Ledger → Treemap prototype.
  • Journal entries card: on its own tab, every posted entry header for the entity, newest first, with page size, date range (default This month, by ruling) and sort. A chevron opens the legs in the same block as Transactions' Posted tab. It lists a correction's three entries as three rows; the Posted tab rolls them into one.
  • Journal ID: a short per-entity display number, JE-000214, assigned at posting and distinct from the UUID key: gapless, serialized per entity, never reused. It leads the Journal entries card, the Posted tab and the register, copied on hover, so any entry can be cited exactly.
  • Journal ID links: on the register and the Posted tab the ID links to the entry's row on the Journal entries card (general-ledger.html#je-000212), which selects the tab, highlights the row and opens its legs, widening the date range if needed. An exact ID in search resolves to the same row within the active entity; no search surface is drawn yet (design-system-spec.md § Header).
  • Reversed entries stay listed, muted: no filter hides them. A Reversed original and its reversal render in muted ink, the original's description struck through; the Journal ID keeps full ink because it is the reference.

5.10 Sidebar & app shell

Story: the shell itself: eight flat items, icon-rail collapse, entity selector, avatar popover, keyboard. Source: flows/sidebar-flow.md.

flowchart TD
  load([Any app screen loads]) --> state{Remembered\nsidebar state}
  state -- expanded --> full[Expanded, ~240px:\nmark + wordmark, collapse button,\n8 labelled items, avatar + name]
  state -- collapsed --> rail[Icon rail, ~64px:\nmark, 8 icons, avatar]
  full -- collapse button --> rail
  rail -- click the mark --> full
  full --> nav[Pick a nav item:\nDashboard, Transactions, General Ledger,\nCustodial Accounts, Allocation,\nTax, Reports, Entities]

  switcher --> rescope([Current screen re-renders\nfor the chosen entity])
  • Eight flat items, no nesting (design-system-spec.md § Sidebar information architecture). Flat is what makes the icon rail work.
  • Collapse to an icon rail. The cue sits in the brand row: expanded shows a panel-left-close button right of the wordmark; collapsed shows the mark alone, which is itself the expand button and swaps to panel-left-open on hover or keyboard focus.
  • Remembered state: the expanded or collapsed choice persists per user across screens and reloads (shadcn Sidebar's stored open state).
  • Header entity selector: the current entity's name and its member avatar cluster (max 3 + "+N"); it opens the entity switcher, and the current screen re-renders for the chosen entity (flow 5.7).
  • Avatar popover opens to the right of the trigger, in both widths. Settings and Notifications are proposed entry points (.proposed-tag); Log out is last, --destructive-styled.
  • Keyboard: Tab order is brand-row button → nav items → avatar trigger; the header follows in the main region. Enter or Space activates; Esc closes the popover and returns focus to its trigger. Every control shows the --sidebar-ring focus outline.
