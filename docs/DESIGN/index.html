1. Overview & Design Principles

What this product should feel like to use, and the principles that resolve design disputes.

  • Mobile-first when in doubt. The primary v1 target is a self-hosted web dashboard used on desktop for deep review (statements, lot tables) and on mobile for quick checks (dashboard glance, confirming a draft transaction) — design the dense screens up from a mobile layout, not down from desktop.
  • Accessible by default (WCAG AA). Non-negotiable per PRD §6. Financial gain/loss and status signals never rely on color alone — see Financial semantics.
  • No decorative loading states. Skeletons match the real layout; spinners are a last resort (see Component inventory).
  • Every number earns trust. This is a general ledger, not a budgeting toy — a balance, a delta, or a pending-liability figure must always be traceable to its source (the journal entry, the lot, the reconciliation). The UI never shows a number it can't explain if clicked.
  • Immutability is visible, not just enforced. A posted transaction reads as posted (badge, disabled edit affordance); a correction reads as a reversal + new entry, never as a silent edit (PRD §5).
  • Diverge from polycarpic's own tooling, deliberately. The cairn tracker (our internal tool) and the product are not the same thing and shouldn't look like it — this system's inspiration is derived from measured screenshots and live style reads off Monarch Money and Origin — see Inspiration: Monarch & Origin.
  • One brand hue, used honestly. The neon-green brand color (#2CFF05, "the project name relates to fruiting plants") measures 1.36:1 against white, far below AA — kept as the literal --brand value everywhere it clears AA (dark surfaces), with a darkened same-hue green for light-mode --primary, stated plainly rather than silently swapped for a different hue — see Foundations.

5. User Flows

How users move through the product to accomplish the highest-traffic stories (PRD §4). Each flow is embedded inline below, because a browser serves flows/*.md as raw Markdown and its fenced mermaid blocks would never reach the page's Mermaid loader. The .md files stay as the diffable source of truth in flows/.

5.1 Home entry: Sign in, Get started, Sign up

Story (PRD §4.1): a visitor's first move from Home, on a product with no public sign-up. Source: flows/home-entry-flow.md.

flowchart TD
  home([Visitor on Home]) -- Sign in --> login[Login]
  home -- Get started --> gs{Get started:\ninvited to\nthis instance?}
  invite([Invite link from\nan entity owner]) --> signup
  login -- "Have an invite?\nCreate your account" --> signup[Sign up:\ninvite code, then account\nGoogle, Apple, GitHub\nor email + password]
  login -- "No invite?\nSet up your own instance" --> gs
  login -- enter login credentials --> known{Known device?}
  known -- yes --> landed([Dashboard])
  known -- "no: code\nor passkey" --> landed
  gs -- "yes: I have an invite" --> signup
  gs -- "no: my own instance" --> walk[Walkthrough, same page:\nrequirements, deploy,\noperator sign-in, invite]
  signup -- valid invite --> role{Joining as owner\nor manager?}
  role -- yes --> enrol[Set up a second step:\nauthenticator app or passkey,\nthen backup codes]
  role -- "viewer: offered,\nSkip for now" --> invited
  enrol --> invited([Dashboard of the\ninvited entity])
  • No public sign-up. Every instance is self-hosted and accounts on it come by invitation from an entity owner. The bar's action is therefore "Get started", never "Sign up".
  • Get started is one page, not a modal. The fork sits on top as two cards ("I have an invite" → Sign up; "I'm setting up my own instance" → the walkthrough directly below), so a self-hosting visitor never leaves the page and the walkthrough has room to grow. Alternative: a modal from Home's Get started button holding just the two cards; lighter on Home, but the walkthrough then needs its own page anyway.
  • Login shows the same branch. Its account line reads "Have an invite? Create your account" (to Sign up) and "No invite? Set up your own instance" (to Get started).
  • Every sign-in lands on a dashboard. Account creation also creates the user's own Person entity, so there is no signed-in state without an entity (design-system-spec.md § Entities & membership). Login lands on the last-viewed entity, else that Person entity; the operator's first sign-in after setup lands on the operator's own Person entity.
  • Sign up is invite-gated. The code arrives pre-filled and validated from an invite link, or is typed. A valid invite names the inviter and the entity. The invite is common to both account paths (Google, Apple or GitHub, or email + password), and creating the account lands on the dashboard of the invited entity.
  • An invalid or used code keeps the visitor on Sign up with an inline error under the field; it never sends them to a dead end.
  • A second step for owners and managers. An invitee joining as owner or manager sets up an authenticator app or a passkey on Sign up before landing, then receives backup codes; a viewer is offered the same step with Skip for now. Choosing Google, Apple or GitHub exempts no one. Sign in asks for the code or passkey only on a new device. Flow 5.11.
  • Home box on a .local name. Login and Sign up render no Google, Apple or GitHub button and no "or" divider; one line in their place reads "Google, Apple and GitHub sign-in are not available on this home box, because it runs on a local network name (polycarpic.local). Sign in with your email, password and second step." (login.html#local). On a home box with a real domain, the buttons show as usual.

5.2 Dashboard glance

Story (PRD §4.2): per-entity financial health at a glance. Source: flows/dashboard-glance-flow.md.

flowchart TD
  start([User logs in]) --> default[Land on default entity:\nlast-viewed, else the user's\nown Person entity]
  default --> render[Render dashboard:\nbalances, cash flow, recent activity,\npending tax liability, allocation snapshot]
  render --> loading{Data cached?}
  loading -- no --> skeleton[Skeleton matches real layout\nno spinner]
  skeleton --> render
  render --> switch{Switch entity?}
  switch -- yes --> picker[Entity switcher\nPerson / Trust / Business / Household]
  picker --> filtered[Re-render scoped to\nuser's membership on that entity]
  filtered --> render
  switch -- no --> drill{Drill into a number?}
  drill -- yes --> source[Navigate to source:\nledger line, lot, or liability detail]
  drill -- no --> idle([Glance complete])
  • Every number on this screen is clickable through to its source (Overview principle: "every number earns trust").
  • Filtered strictly by membership (owner / manager / viewer) — no transitive access via a parent entity (PRD §5 permission model).
  • Viewer-role household members see the household's shared accounts and their own entity, never another member's entity (PRD §4.9).
  • "Skeleton matches real layout, no spinner": while dashboard data is loading, the screen shows placeholder blocks already shaped like the real cards (same card chrome, same approximate text-line widths) instead of a spinner, so nothing jumps or re-flows when the real numbers arrive; they fade in where the placeholders were. A spinner says "wait"; a layout-shaped skeleton also says what is coming. See design-system-spec.md § Component inventory → Skeleton.

5.3 Transactions — review, match & correct

Story (PRD §4.3): staged for review → matched / split / grouped → posted → correctable. The review mechanics follow a Plaid bank-feed workflow: every imported transaction is reviewed, matched, split or grouped, then posted. Source: flows/import-confirm-flow.md.

flowchart TD
  nav([Open Transactions\nfrom the sidebar]) --> filter[Account filter:\nAll Transactions by default,\nor one custodial account]
  filter -. scopes .-> tabs[Tabs with count badges:\nExceptions, Pending, Posted;\nopens on Pending]
  tabs --> stage
  tabs --> exceptions
  tabs --> posted
  poll([Plaid adapter polls\nor fake source generates batch]) --> stage[Raw transaction lands\nin the Pending tab]
  stage --> entryMatch{Matches a posted\nmanual entry?}
  entryMatch -- no --> transfer{Two legs match\nwithin date window?}
  entryMatch -- yes --> rowWarn[Pending row shows a caution line\nnaming the entry; review panel\noffers Match to that entry]
  rowWarn -- match to that entry --> entryLinked[Entry gains the import link;\nrow leaves Pending]
  entryLinked --> posted
  rowWarn -- review as usual --> transfer
  transfer -- same posting date --> autoEntry[Locked custodial leg +\nsuggested offset leg\ntwo-line preview]
  transfer -- different dates --> citEntry[Two entries via\nCash in Transit clearing account]
  transfer -- between two entities --> treatment{Treatment on the draft:\ncontribution / distribution preselected,\nor due-to / due-from}
  treatment --> perEntity[One entry per entity]
  transfer -- unmatched --> openItem[Remains a single-leg\nPending row]
  openItem -- counterpart arrives --> transfer
  openItem -- user approves into CIT --> citOne[One-sided in-flight item:\ncash leg vs. Cash in Transit,\ncounterpart still to come]
  citOne --> post
  openItem --> aging{Older than\nexceptions threshold\ndefault 3 business days?}
  aging -- yes --> exceptions[Surface on\nExceptions tab]
  aging -- no --> openItem
  citEntry --> autoEntry
  autoEntry --> expand[User expands the row:\nAuto-Suggest Match view]
  expand --> action{User action}
  action -- edit offset --> editLeg[Inline search dropdown:\noverride the suggested account]
  editLeg --> action
  action -- split --> splitGrid[Split grid:\nadd offsetting rows]
  splitGrid --> liveCheck{Split sum equals\nthe Plaid total?}
  liveCheck -- no --> splitGrid
  liveCheck -- yes --> post
  action -- group --> bulkSelect[Checkbox-select rows,\nbulk action bar appears]
  bulkSelect --> groupModal[Group and Summarize modal:\npre-filled entry, one aggregate\nline + balancing distributions]
  groupModal --> post
  action -- approve --> post[User hits Approve and Post]
  post --> gate{Posting gate:\nbalanced, accounting equation,\ndate match, one entry per draft}
  gate -- fail --> stage
  gate -- pass --> commit[Row fades out of Pending;\nbalanced entry commits to the GL]
  commit --> toast[Toast: entry posted]
  commit --> posted([Each transaction appears on\nPosted with the Journal ID,\npaged])
  exceptions --> resolve{Resolved manually?}
  resolve -- yes --> post
  resolve -- no --> exceptions
  manual([New entry modal:\nDate is the transaction date;\nPost enabled once balanced]) --> dup{Duplicate candidate?\nA leg matches an imported\nPending or Posted transaction}
  dup -- no --> posted
  dup -- yes --> dupWarn[Caution warning above Post\nnames the matched transaction]
  dupWarn -- match to that transaction --> expand
  dupWarn -- match is already Posted --> jePopover
  dupWarn -- post anyway --> dupRow[Posted row carries a muted\npossible duplicate badge]
  dupRow --> posted
  posted -- click Journal ID --> jePopover[Journal entry popover:\nlegs, correction trail,\nactor, logged time]
  jePopover -- Open in General Ledger --> glRow([Entry's row on the\nJournal entries card])
  jePopover -- dismiss --> posted
  jePopover -- dismiss possible duplicate --> posted
  posted --> correctQ{User clicks\nCorrect entry?}
  correctQ -- yes --> doCorrect[System posts the reversal\n+ the new corrected entry\nuser never sees reverse as the verb]
  doCorrect --> correctedBadge[The entry's rows now show\nCorrected badge]
  correctedBadge --> clickThrough[Click-through: original lines\nshaded/struck + reversal + new entry]
  correctQ -- no --> complete([Flow complete])
  clickThrough --> complete
  • Account filter. A selector at the right end of the tab row scopes Exceptions, Pending and Posted together, count badges included. Opening Transactions from the sidebar always lands on All Transactions (every custodial account in the entity); the popover lists each custodial account by the name Custodial Accounts uses, with its provider and open-item counts. The Known delta badge on a Custodial Accounts card deep-links here with the filter preset to that account. On Posted the rule is leg-level and the same for every row: with one account selected, only the rows whose own leg posts a debit or credit to that account show, so the counterpart row of a transfer does not appear. A manual entry with a leg on that account shows as one row for that leg. All Transactions shows everything, including a manual entry with no custodial leg, such as an accrual, which no single account's view lists.
  • Tabs with count badges. Exceptions, Pending and Posted are one Tabs row, left of the account filter, one visible at a time, in urgency order. Each tab carries its count, so every stage's load stays visible while another is open: secondary, destructive-soft on Exceptions when non-zero. Transactions opens on Pending, the review inbox; a non-zero Exceptions count does not take the default, its badge is red instead. The counts follow the account filter, changing the filter keeps the current tab, and the URL hash carries the tab.
  • Every row names its source. Each Exceptions, Pending and Posted row carries one muted line under the payee: landmark icon + <account> · <institution> via <provider> (e.g. "Primary Checking · Bank Y via Plaid"). A manual entry has no bank source, so its line reads pen-line icon + "Manual entry". With the filter on one account, a line that only repeats the trigger is omitted; a Manual entry line stays.
  • The locked leg is always the custodial cash side, debit on inflows, credit on outflows — verified bank reality (the Plaid transaction itself), never editable, in the two-line preview, the Split grid, or the Group modal. The suggested offset leg is pre-filled from historical rules + the Plaid category and overridden in place via an inline search dropdown, never a blank field.
  • A leg always names its account by full path, root to leaf, in the Pending preview, the Split grid, the New entry modal, and the Posted expansion and popover: Expenses › Office Expense. Account controls show and list paths.
  • Split is one draft → one multi-leg entry, live-validated: submission stays disabled until the rows sum exactly to the raw transaction's absolute total. Group is many drafts → one entry (ARCH §3), the same many-to-one shape as a same-date matched transfer, via the shared journal-entry modal, pre-filled with one aggregate line + balancing distributions.
  • Posted is transaction-scoped. Every posted transaction is a row, mirroring Pending, and carries its entry's Journal ID. An entry built from several transactions appears as several rows with one ID: a group, or a same-date matched transfer (two legs, one entry). The rows sit together, because an entry has one date and same-date rows order by Journal ID. A split stays one row, however many legs its entry has. A transfer whose legs land on different dates posts as two entries through Cash in Transit, so its two rows carry two IDs. With the filter on one account, only that account's row of a transfer shows, whether the transfer is one entry or two; the Journal ID popover still lists both legs. The Posted badge counts rows, so it differs from the entry count on the GL Journal entries card, which is the entry-grained view.
  • A manual entry is a Posted row like any other. On All Transactions, an entry from the New entry modal is one row with its own Journal ID, however many legs it has, and its Amount is the entry's sum of debits, unsigned, because it has no bank sign. With one account selected it is one row for the leg on that account, signed like a bank row: a debit to a cash account reads +. It cannot exist outside a compliant journal entry, so the same rules apply: the account filter, Correct entry, the Journal ID popover.
  • Row Date is the transaction date. Date on Posted and on the GL Journal entries card is the date the user entered on the entry, never the time it was logged. The New entry modal's Date field is that date, so a backdated entry sorts by it on both lists, while its Journal ID still orders by posting. The audit trail (actor, logged-at) lives in the Journal ID popover and the GL entry view, not in the list.
  • Potential-duplicate warning. While a manual entry is open in the New entry modal, each custodial leg is compared with imported transactions that are Pending or Posted. A candidate has the same custodial account, the same amount and direction, and a date within the entity's Duplicate detection window of the entry's Date, either side (Settings, default ±1 day). A candidate shows a caution-tier warning above the actions naming it: "Looks like Sep 12 · Stripe Payout +$1,500.00 on Primary Checking, Pending". The nearest date is named, and a Pending candidate wins a tie. Match to that transaction instead discards the manual entry and opens the Pending row's review panel, pre-filled with the modal's offset leg; for a Posted candidate this action reads Open that entry and opens its Journal ID popover. Post anyway takes the Post button's place and posts the entry: its row carries a muted outline possible duplicate badge under its status until the user dismisses it from the popover or matches the import. Only New entry and imports check, because Correct entry, Split and Group start from a real transaction.
  • Mirror on Pending. The same rule and window run on Pending: an imported transaction that matches a posted manual entry, whichever arrived first, shows a caution line on its row: "Looks like manual entry JE-000215 · Sep 11 · +$1,500.00". The line shows collapsed or expanded, and the Journal ID opens that entry's popover. The nearest date is named, and an entry already linked to an import is no longer a candidate. The review panel adds Match to that entry as its default action, and Approve & Post steps down to an outline button beside it so Enter cannot slip past it. Match to that entry links the import to the existing entry and posts nothing: the row leaves Pending, the entry stays as it is, and the Posted count holds. The entry's row gains a matched import status line and loses any possible duplicate badge, and its popover lists the import. Approve & Post past the caution keeps both. Dismiss possible duplicate on the entry clears the caution on the row it names.
  • Journal ID popover. Clicking a Journal ID on Posted opens a Popover anchored to the ID, so an entry can be read without leaving the list. Header line: Journal ID with copy, transaction date, actor, "logged <timestamp>", status badge. Body: every leg, then the correction trail if any (the original and its reversal, since the entry's own legs are already above). Footer: Open in General Ledger, to the entry's row on the Journal entries card, plus Dismiss possible duplicate on a row that carries that badge. It is non-modal: an outside click or Esc dismisses it and focus returns to the ID. The View correction chevron on a Corrected row is a separate control: it expands the trail in place. The account register's Journal ID stays a link to the GL.
  • A cross-entity transfer carries one treatment choice on the draft: contribution / distribution preselected, or due-to / due-from. Each option says in plain language what it does to both balance sheets, and due-to / due-from says repayment is expected. One entry posts per entity, and both need Manager.
  • A brokerage draft splits by nature, one line per security under its nature account, with the cash leg locked. A trade in an unmapped security stays in Pending with an inline Map security form; mapping clears every waiting trade in it and Allocation's gap.
  • An unmatched transfer leg stays a staged draft in Pending until its counterpart arrives (then it matches like any transfer), or until the user explicitly approves it into Cash in Transit as a one-sided in-flight item — a balanced entry, cash leg against the CIT clearing account, cleared when the counterpart posts. A draft still unmatched past the exceptions threshold moves to Exceptions.
  • Posting gate: Σ debits = Σ credits; the accounting equation holds per entity; the entry date matches the bank date (or the Cash-in-Transit rule); every posted draft links to exactly one entry, and several drafts may share it (a group, a same-date matched transfer). Any failure keeps the item in Pending — no partial or silent post.
  • A posted row's user-facing action is "Correct entry", never "edit" or "reverse" — reversal-only underneath (PRD §5). Click-through shows the full trail: original lines shaded/struck, the reversal, and the new entry. Correct entry on any row of a multi-row entry corrects that one entry, and every row of it then carries the corrected entry's ID and the Corrected badge. See design-system-spec.md § Correcting a posted entry.
  • Badges: Draft (staged) (--secondary, clock), Posted (--outline, check), Corrected (--outline + --brand-2-tinted dot, pencil). An auto-posted row carries Posted plus a posted by rule — <name> line and the same Correct entry action. possible duplicate (--outline, muted ink) sits under the status of a manual row posted past the duplicate warning; matched import is the status line of a manual row linked to its import.
  • Actor attribution (user / auto-post rule / system job) is shown on every draft and posted row, never inferred (PRD §5).
  • Import stats and link status (provider sync time, link health) show as a banner at the top of Transactions, not as a separate nav item.

5.4 Tax liability & safe-harbor

Story (PRD §4.5): pending liability, required payment, gap, post your payment. Tax is a sidebar item. Source: flows/tax-liability-flow.md.

flowchart TD
  nav([Sidebar: Tax]) --> view[Tax view for the entity:\njurisdiction tab selected]
  card([Dashboard: Pending tax\nliability card]) --> view
  view --> accrual[Running accrual annualizes\nincome to date by tax treatment]
  accrual --> pending[Pending liability =\nannualized tax to date minus\ncustodial prepaid balance]
  accrual --> safeharbor[Two safe-harbor bases computed:\nprior-year and current-year]
  safeharbor --> required[Required payment to date =\nlesser of the two safe-harbor bases]
  required --> gap[Gap = required payments to date\nminus custodial balance,\nare you current with the authority]
  pending --> display[Display gauge + figures]
  gap --> tier{Gap status}
  tier -- "gap < 0" --> onTrack[Tier: Normal / on track\nprepaid ahead of safe harbor\npositive token]
  tier -- "gap ≥ 0, due more than 14 days out" --> caution[Tier: Caution\nwarning token]
  tier -- "gap ≥ 0, due within 14 days or passed" --> danger[Tier: Danger\ndestructive token]
  onTrack --> display
  caution --> display
  danger --> display
  display --> extPay[User pays the tax authority\nat their own bank, the app\nnever initiates a payment]
  extPay --> imported[Payment appears as an imported\nbank transaction, no counterparty]
  imported --> postEntry[User posts the GL entry:\ndebit the tax-authority custodial\nprepaid account, which lowers\nthe pending liability]
  postEntry --> accrual
  display --> waitNode([Wait for next period cutoff])
  waitNode --> freeze[Period cutoff freezes\nannualized figure for due date]
  freeze --> accrual
  display --> closeDue{Period ended and\nentity a taxpayer?}
  closeDue -- yes --> closePrompt[Close-due prompt, per jurisdiction:\ntrue-up since last close]
  closePrompt --> closeConfirm[User confirms: expense against\nincome tax payable, one entry]
  closeConfirm --> closed([Last closed through updates])
  closeDue -- "no, pass-through" --> allocated[Income allocates to holders\nby the cap table on each\nentry's date; each Person accrues]
  • Reached from the sidebar or the Dashboard card; both land on the same per-entity view with a jurisdiction selector.
  • Reporting-period close. A taxpayer entity trues up its accrual at each close, monthly by default or quarterly (Settings). A close-due prompt shows per jurisdiction; the user confirms one entry of expense against income tax payable, computed before prepaid. "Last closed through <date>" shows the status. A wrong close is fixed by closing again.
  • Pass-through income. A pass-through or grantor entity accrues nothing; a Person sees income allocated from such entities by the cap table on each entry's date, totals only.
  • Tiers: on track when gap < 0 (prepaid ahead of the safe-harbor requirement); caution when gap ≥ 0 and the due date is more than 14 days out; danger when gap ≥ 0 and the due date is within 14 days or has passed. They reuse the product-wide status vocabulary — design-system-spec.md § Status tiers.
  • Gap = 0 is not on track. It means exactly at the safe-harbor line, with nothing in hand beyond the requirement, so it takes the caution or danger tier by due date.
  • Two figures, both measured against the custodial account's balance but not against each other: Pending liability = annualized tax to date − custodial prepaid balance (what you would owe net of prepayments, if filed today); Gap = required payments to date (safe harbor) − custodial balance ("are you current with the authority"). Gap is never required − pending.
  • v1 never moves money. There is no pay button: the user pays the tax authority at their own bank; the payment lands as an imported transaction with no counterparty; the user posts the GL entry, debiting the custodial tax-authority account (a prepaid-tax asset). Copy says "post your payment" or "record your payment", never "pay" or "transfer".
  • Jurisdiction due dates, multipliers and cumulative percentages are data-driven (a lookup table), so the view renders for any number of jurisdictions per entity, not just federal (PRD §5).
  • At filing, the frozen per-period figures export for Schedule AI / Form 2210 and the state equivalent; the flow's freeze step is the source of that export.

Stories (PRD §4.6–4.7): three figures per account, lots, and GL vs. custodial reconciliation. General Ledger and Custodial Accounts are two nav items, not a toggle. Source: flows/securities-lots-flow.md.

  view --> groupBy[Group-by toggle:\nInstitution or Account type]
  groupBy --> groups[Group headers: count,\nsummed market, book and cash]
  groups --> accounts[Per-account cards:\nlink-health badge]
  accounts --> figs[Three figures, left to right:\nmarket value at EOD prices,\nbook value = GL cost basis, cash balance,\nand Unrealized]
  priceFeed[Daily EOD price feed] --> figs
  figs --> totals
  accounts --> lotsCard[Lots sub-card per security:\npull-down shows lots,\nshort/long/total gain per lot + summed]
  priceFeed --> lotsCard
  accounts --> reconcile[Reconcile GL balance\nagainst custodian-reported balance]
  reconcile --> match{Balances match\nwithin tolerance?}
  match -- yes --> clean[Reconciliation: clean\npositive tier]
  match -- "no: difference = staged drafts" --> unposted[Known unposted delta:\nthe unapproved drafts listed,\nnot a break]
  unposted --> glLink
  match -- "no: unexplained" --> brk[Reconciliation: break\ndanger tier, flagged\nalso on the Dashboard]
  clean --> glLink[General Ledger account register\nshows the same balance, GL side]

  • Three figures on every account, left to right: market value (cash plus every position at the last EOD price); book value (the GL's cost basis, cash included — the GL's own balance for the mirrored account); cash balance; and Unrealized = market − book, signed and coloured per § Delta coloring. A cash-only account shows the same row with equal figures and a $0.00 delta, so cards scan as columns. A totals card sums the four figures across accounts, with the price date. Cash sits last so the row reads as "market and book include cash" — the two totals first, the cash already inside them after.
  • Group by Institution or Account type. A Tabs toggle under the totals card groups the account cards; Institution is the default, and the choice persists per user. A group header carries the account count and the summed market value, book value and cash. The totals card sums asset accounts whichever grouping is on.
  • A credit card is a liability. Market value and book value both show what is owed, as a negative; cash and Unrealized show a dash. The negative nets into its group, and the totals card states it beside the asset total.
  • The card rests collapsed. The header carries two badges in a fixed order, link health then reconciliation, because a reconciliation is only as current as the link behind it. A chevron left of the title opens the card's details: the custodian's figure against the GL and the link to any staged drafts, then, on an account that holds securities, the lots sub-card with its pull-down per security. Allocation's holdings popover links here and arrives with the cards of the accounts it lists open.
  • An account's Unrealized figure equals its lots sub-card's total unrealized gain; the two must agree.
  • Two nav items: General Ledger and Custodial Accounts are two separate nav items, not one screen behind a Tabs switch. Both read the same lot and journal data; the split is presentation, not a data fork.
  • Unapproved drafts are a known unposted delta, not a break. When the GL and custodian balances differ by exactly the account's staged drafts (e.g. an unmatched transfer leg not yet approved into Cash in Transit), the card shows the delta and lists those drafts, linking to Pending on Transactions; no danger tier. Only a difference the drafts do not explain is a break.
  • A reconciliation break uses the danger tier (--destructive) and surfaces on the Dashboard glance too, not only here.
  • Allocation (actual vs. target by asset class) is its own flow, 5.6.

Story (PRD §4.8): the current allocation as a treemap, then actual vs. target by asset class and sub-category with drift; a two-level target editor behind a gear. Source: flows/allocation-flow.md.

flowchart TD

  actual --> map[Current allocation treemap:\ntier columns, one tile per class,\nsub-categories nested, area is\nshare of market value]
  map --> target[Actual vs. target card:\noverlay the target per class]
  target --> drift[Drift per class:\nactual minus target, in points]
  drift --> act{User action}
  act -- expand a class --> subs[Sub-category rows:\nactual vs. target and drift\nper sub-category]
  subs -- open a sub-category --> holdings
  act -- open a tile or class --> holdings[Holdings popover, in place:\nholdings grouped by custodial account,\nlots behind each security, total]
  holdings -- close --> drift
  holdings -- Open Custodial Accounts --> lots([Custodial Accounts,\nthose accounts' cards open])
  act -- click the gear --> edit[Target editor popover, two levels:\npercent per class, then\nper sub-category behind a pull-down]
  edit -- cancel --> drift
  edit --> sum{Classes total 100%\nand each class equals\nthe sum of its sub-targets?}
  sum -- no --> edit

  save --> drift
  act -- open the unmapped gap row --> gap([Pending on Transactions:\nthe staged trade, map the security])

  • Same data, different aggregation: the four classes are the ledger's nature classes. The market reading (lots by class, plus cash) ties to Custodial Accounts' market value; the book reading (the nature accounts) ties to its book value and the General Ledger tree.
  • Classes fixed, sub-categories yours. The target editor cannot add or remove a class, because the ledger is organised by them. Sub-categories are a per-security mapping outside the ledger and stay editable.
  • Unmapped holdings are a visible gap, never silently excluded: a position the custodian reports with no class mapping shows as a gap row with its dollars and a route to the staged trade in Pending, outside the total until mapped.
  • Drift is information, not a warning. Over or under target shows as a neutral outline badge ("+2 pt over", "−2 pt under"); on target shows the positive soft badge. No caution or danger hue.
  • Tier, class, sub-category. Asset classes sit under two tiers: Current (Cash and cash equivalents) and Non-Current (Fixed income securities, Marketable securities, Alternative investment assets). A tier is a label with its share, never a colour: captions over the treemap's two columns, group headers in the bars and the target editor.
  • Treemap first, table second. The page opens on the current allocation as a nested treemap: one tile per asset class in its fixed categorical slot, its sub-categories inside it in the same slot. The Actual vs. target card below is its table view and carries every percent.
  • Drill opens in place. Each treemap tile and each asset-class or sub-category name opens a read-only holdings popover on Allocation, because a class spans accounts and no single Custodial card can show it. Header: name, tier path, actual percent and dollars, target, drift badge. Body: the holdings behind that figure, grouped by custodial account with the account's share, each security with the Custodial card's lots pull-down; a cash sub-category lists cash balances per account. Footer: the aggregate total and one link, Open Custodial Accounts, which arrives with those accounts' cards open. Esc or a click outside closes it.
  • Sub-categories behind a pull-down. Every class row, in the Actual vs. target card and in the target editor, has a chevron that reveals its sub-categories (the lots sub-card's disclosure pattern). Seeded defaults: Cash and cash equivalents → Cash, Money market; Fixed income securities → Treasuries, Corporate, Municipal; Marketable securities → US Large cap, US Mid/Small cap, Intl Developed, Intl Emerging; Alternative investment assets → Digital Assets. Money market reads the provider's reported position; the rest of the cash is Cash; a manual or file custodial account shows all its cash as Cash. In the Actual vs. target card, each sub-row shows its own actual / target and drift badge.
  • The gear opens the target editor. A gear icon button at the top right of the Actual vs. target card opens the editor in a popover anchored to it, non-modal so the bars stay readable while targets change. Cancel or Esc closes it and discards the edits; a click outside closes it only when nothing has been edited. Focus moves to the first input on open and returns to the gear on close.
  • Target editor, two levels: sub-targets are whole-portfolio percent and must sum to their class target; the class row stays editable and carries a reconcile badge (positive soft "Sub-targets sum to N%", or neutral outline "N pt unassigned"). Save is enabled only when the classes total 100% and every class reconciles. Viewers see the treemap and the bars but no gear (write controls are omitted, not greyed).
  • No nominal / inflation-adjusted toggle here. Allocation is a contemporaneous snapshot of today's holdings, so a CPI-U restatement adds no information; the toggle (PRD §4.10) belongs to the time-series views (Dashboard net-worth chart, Reports).

5.7 Entity switch, roll-up & membership access

Story (PRD §4.9): parents hold accounts and roll up whole entities to any depth; owner / manager / viewer per entity; the drill-through boundary. Source: flows/entity-membership-flow.md.

flowchart TD
  login([User logs in]) --> memberships[Load memberships:\nbase and parent entities,\nrole on each]
  memberships --> land[Land on last-viewed entity,\nelse the user's own Person entity]
  land --> switcher[Entity switcher, always present:\nevery entity with membership,\nparents with their included\nentities nested]
  switcher --> select[User selects an entity]
  select --> roleCheck{Role on\nselected entity}
  roleCheck -- owner --> ownerView[Full read/write:\npost, edit memberships, purge]
  roleCheck -- manager --> managerView[Read/write ledger,\nno membership/purge rights]
  roleCheck -- viewer --> viewerView[Read-only:\nbalances, activity, statements]
  ownerView --> guard{Parent-entity\nstructure implies access?}
  managerView --> guard
  viewerView --> guard
  guard -- "no (always)" --> explicit[Only explicit membership\ngrants access, never inherited]
  explicit --> kind{Selected entity\nis a parent?}
  kind -- no --> baseView([Render the base entity's\nown ledger and accounts])
  kind -- yes --> consolidated[Render consolidated figures:\nits own accounts plus the whole\nincluded entities, each once]
  consolidated -. "Economic, POLY-1.1" .-> econ([Same rows weighted by\nthe viewer's stake,\neconomic net worth])
  consolidated --> drill[User clicks a figure\nfrom an included entity]
  drill --> boundary{Membership on\nthat entity?}
  boundary -- yes --> into([Drill into that entity's\nregister or lots])
  boundary -- no --> stop([Boundary panel:\nIncluded from the named entity,\nno access to its ledger])
  • Base and parent entities. Any entity may hold accounts: a base entity (Person, Trust, Business) has no children, and a parent (Household; Holding) may own accounts directly, such as joint checking. A parent rolls up its own accounts and whole entities to any depth, never individual accounts, each entity counted once. An entity may belong to more than one parent.
  • The switcher is always present, because every user owns at least their own Person entity. It lists every entity the user holds membership on, base and parent, with each parent's included entities nested under it; an entity in two parents is listed under both.
  • Access is explicit membership only (PRD §5, hard requirement): a parent's membership never grants access to an included base entity, or vice versa.
  • Adding to a parent is a consent, and says what it grants. Add to a parent on an entity's Included under list opens a confirmation, "Include <entity> in <parent>?", whose body is the fixed consent text: "Members of <parent>, and of any parent above it, see class and category totals for this entity for any period. For a small entity, that effectively reveals individual amounts and their dates. Nothing else is shown: no payee, memo, account or counterparty." A second line says a later parent above sees the same and the owner is told, and that the link can be removed from Included under. The text is a security requirement: it is never reworded per screen and changing it needs a security review. Any date range stays selectable on parent views; no picker snaps to months.
  • Placement is notify-and-pull-out. Agreeing to a parent accepts its later placement: every owner beneath is notified with the same consent text, the notification routes to the entity's Included under list, which names the parents above it with direct links marked, and an owner can remove a direct link. Either the entity's owner or the parent's owner may remove it.
  • A new member on a parent above is a notice too. When an invite to a parent is sent (any role), every owner of every entity beneath it gets one notice: "<person> was invited to <parent> as a <role>. <parent> includes your entities <entity>, through <path>, …", then the consent text and See included under. A later role raise sends none; nothing waits on the recipients.
  • Tax classification. A settable field on every entity. A parent is Joint filers or Pass-through to members, the default for a new Household. A pass-through entity allocates tagged income by its cap table on each entry's date; a Joint filers parent ignores its cap table for tax.
  • Cap table beside the membership list. One list per entity card, two columns, Access (Owner / Manager / Viewer / None) and Units: owner-access members first, then other members, then holders with no access, then the computed Outside owners row and the total. Equity and access never derive from each other. Owners edit, with an effective date on every save and a dated History; every member reads. A no-access Person holder is offered Invite as viewer. The creation form presets 100 units, all the creator's. Refusals: units over the total on a date, an entity becoming its own holder, a chain deeper than one entity.
  • Several owners govern together. On an entity with more than one owner, invites, role raises, co-owner removals and cap-table edits show Pending approval until every other owner approves; the founding owner carries a Founder badge and breaks a removal deadlock. Flow 5.12.
  • A purged holder stays on the cap table as "Former holder (purged <date>)", its units counted in Outside owners from that date, with an optional label the owners type themselves (Edit label, a cap-table edit, so it waits for approval on a multi-owner entity). Nothing of the purged entity is shown, not even its name, unless an owner typed it.
  • Gross / Economic (POLY-1.1). A parent view toggles to Economic: every figure weighted by the viewer's stake, closing on economic net worth, over exactly the entities the gross view shows. A 0% entity stays listed.
  • The drill-through boundary. A parent viewer sees the parent's consolidated figures. Every figure stays clickable; a drill into an included entity the user has no membership on opens a boundary panel — "Included from <entity>. You don't have access to that entity's ledger." — instead of the register, never a disabled number or a silent dead end.
  • Role badges (Owner / Manager / Viewer) use decreasing visual weight — default / secondary / outline (design-system-spec.md § Entity, account, and category badges).
  • A viewer never sees a write affordance rendered-then-disabled: write controls are omitted entirely for a role that cannot use them.
  • Roll-up map: Entities opens with a Pack of every entity the user holds membership on — parents as circles nested to any depth, stating any accounts of their own, each circle stroked in its entity type's categorical slot, a shared base entity drawn once in each parent with an "also in" marker; each circle switches entity. The membership list below it is the accessible fallback. See design-system-spec.md § Entities & membership.

The URL hash carries the tab, so Back from a register returns to the tab it left; a Journal ID link selects Journal entries; the register's breadcrumb returns to the tree.
  • The tree is the GL's own view: every balance is the ledger's figure. A chevron opens the legs in the same block as Transactions' Posted tab. It lists a correction's three entries as three rows; the Posted tab rolls them into one.
  • Journal ID: a short per-entity display number, JE-000214, assigned at posting and distinct from the UUID key: gapless, serialized per entity, never reused. It leads the Journal entries card, the Posted tab and the register, copied on hover, so any entry can be cited exactly.
  • Journal ID links: on the register the ID links to the entry's row on the Journal entries card (general-ledger.html#je-000212), and on the Posted tab the ID opens a popover whose Open in General Ledger link goes to the same row (flow 5.3). Arriving selects the tab, highlights the row and opens its legs, widening the date range if needed. An exact ID in search resolves to the same row within the active entity; no search surface is drawn yet (design-system-spec.md § Header).
  • Reversed entries stay listed, muted: no filter hides them. A Reversed original and its reversal render in muted ink, the original's description struck through; the Journal ID keeps full ink because it is the reference.

5.11 Second step & step-up

Story (PRD §5, access): Owners and managers confirm sign-ins with a second factor; risky actions ask again. Source: flows/second-step-flow.md.

flowchart TD
  invite([Invite as owner or\nmanager accepted]) --> enrol
  raise([Viewer raised to manager\nor owner, approvals done]) --> held[Role waits:\nviewer access kept,\nnotice to set up a second step]
  held --> enrol[Set up a second step:\nauthenticator app or passkey,\nthen ten backup codes]
  enrol --> active([New role in force])
  signin([Sign in on a new device]) --> ask[Password, or Google /\nApple / GitHub,\nthen code or passkey]
  ask --> known([Signed in; the device asks\nnothing more until the session ends])
  risky([Export, purge, grant access,\nlink a bank, answer a request]) --> fresh{Checked in the\nlast 5 minutes?}
  fresh -- yes --> go([Action runs])
  fresh -- no --> stepup[Confirm it's you:\npassword and code, or a passkey]
  stepup --> go
  first([No second step yet:\ncreate an entity, share\nthe own Person, or a step-up action]) --> gate[Set up a second step first:\npassword, then app or passkey,\nthen ten backup codes]
  gate -- cancel --> none([Nothing changes])
  gate -- "create or share" --> go
  gate -- "step-up action" --> stepup
  lost([Every method lost]) --> reset[The operator resets\nthe second step on the box]
  reset --> enrol
  • Required for owners and managers, offered to viewers. The owner role on a user's own Person is exempt while that Person has no other member. Anyone joining as owner or manager sets up an authenticator app or a passkey on Sign up, before landing (sign-up.html#second-step). A viewer sees the same step with Skip for now, which defers it to the first action that needs it. Signing up or in with Google, Apple or GitHub exempts no one, because the app cannot see the provider's own second factor.
  • Two methods, then backup codes. The choice is two radio cards, Authenticator app (a QR code, the key typed out, and a 6-digit check) or Passkey. Ten single-use backup codes follow, shown once.
  • A role raise waits for the second step. When a viewer without one is raised to manager or owner (after any co-owner approval), the new role does not take effect until they set one up; they keep viewer access meanwhile, and the notice "You are now a manager of <entity>. Set up a second sign-in step to start; until then you keep viewer access." links to Settings → Sign-in and second step. The members list shows their new role with an outline Waiting for second step badge.
  • Set up a second step first. A user with no second step whose only role is owner of their own unshared Person signs in and views freely. Creating a Trust, Business, Household or Holding, the first invite to their own Person, and any step-up action (export, purge, granting access, linking a bank, deleting the account) open one interstitial instead: "Set up a second step first", a subtitle naming the action, the password, then the Sign-up enrolment block (the two method cards, QR code and 6-digit check), Turn on and continue, the backup codes, and the action continues: a step-up action meets Confirm it's you next, with the method just set up. Cancel changes nothing. Shown on entities.html (Create entity, reference).
  • Asked on a new device, not every time. After the password (or an OAuth provider), a new device asks for the code, with Use a passkey instead and Use a backup code below (login.html#second-step). A known device asks nothing until its session ends.
  • Step-up before risky actions. Export, purge, granting access or changing a role, linking or unlinking a bank, answering a co-owner request, forcing a removal, transferring the founder role, deleting the account, and removing a second-step method each open Confirm it's you for a user with a second step, unless the user was checked in the last 5 minutes: password and code, or a passkey. A user without a password (Google, Apple or GitHub only) is sent to that provider to sign in again, then asked for the code. The dialog names the action ("Exporting Mosko (Person) needs a fresh check") and says it won't ask again for 5 minutes.
  • Settings → Sign-in and second step lists each method with the date it was added and Remove, Add passkey, the backup codes left with Make new codes, and Change password. While the user is an owner or manager on any entity other than their own unshared Person, the last method has no Remove, and the panel says why.
  • Lockout. "Lost every method? The person who runs this instance can reset your second step." There is no in-app recovery: the operator's audited reset on the box is the path.

5.12 Co-owner approval & the founding owner

Story (PRD §5, access): On a multi-owner entity, access, owner and cap-table changes wait for every other owner. Source: flows/co-owner-approval-flow.md.

flowchart TD
  ask([Owner of a multi-owner entity:\ninvite, role raise, remove or demote\na co-owner, cap-table edit]) --> req[Confirm it's you, then the\nchange shows Pending approval]
  req --> notify[Every other owner notified,\nwith Approve and Decline]
  notify --> wait{Answers}
  wait -- every other owner approves --> valid{Still valid?}
  valid -- yes --> applied([Applied; an invite email\ngoes out only now])
  valid -- "no, stale" --> stale([Declined as stale,\nnothing applies])
  wait -- one owner declines --> declined([Declined])
  wait -- "day 7, unanswered" --> remind[Reminder to owners\nwho have not answered]
  remind --> wait
  wait -- "day 14, unanswered" --> expired([Expired, counts\nas declined])
  wait -- requester withdraws --> withdrawn([Withdrawn])
  wait -- "an approver stops being an\nowner; the rest approved" --> confirm[Requester confirms,\nwith step-up]
  confirm --> valid
  declined --> force{Removal or demotion of\na co-owner, and you\nare the founder?}
  expired --> force
  force -- yes --> forced([Force removal: step-up,\nevery owner told, audited])
  force -- no --> again([Ask again later;\nonce per 7 days after\nan expiry])
  • What waits. On an entity with more than one owner: inviting a member or raising a role; removing or demoting a co-owner; any cap-table edit, including a former holder's label. Removing a viewer or manager, and lowering or giving up one's own role, act at once. A sole owner acts alone, including adding the first co-owner.
  • The invite screen says so. On a multi-owner entity the invite dialog's subtitle reads "The Moskos has two owners, so the invite is sent after Sam Mosko approves.", its button reads Request invite, and it states the 14-day window. On a sole-owner entity the subtitle is gone and the button reads Send invite. The invitee hears nothing until the request applies.
  • Pending is visible where the change will land. A requested invite is a row in the members list (email, role, outline Pending approval badge with a clock, "Invite requested by you · awaiting Sam Mosko · expires Nov 21"). A requested cap-table change is a dashed line under the table with the proposed split, who it waits on, the expiry and Withdraw for the requester; while it is open, Edit cap table is omitted, since one request per kind is open at a time. The card's heading carries the count ("2 pending"). Only owners see pending rows, an invitee's email included.
  • Approval requests in Notifications. "Sam Mosko asks to invite jo@example.com to The Moskos as a manager. The invite is sent once every other owner approves." with Approve and Decline, and the meta line "requested Nov 7 · expires Nov 21 unless every owner approves". At day 7 owners who have not answered get "Reminder: 7 days left to answer … A request nobody answers expires as declined on Nov 21." Every owner is told the outcome.
  • The target votes. In a request to remove or demote a co-owner, that co-owner is one of the approvers, so the others cannot remove them alone.
  • The founder breaks the deadlock. The entity's creator carries an outline Founder badge beside Owner. On a declined or expired removal or demotion of a co-owner, and only then, the founder's notice offers Force removal (or Force demotion). Its confirmation names the person and who declined, says they lose access at once and that every owner, them included, is told and the change is audited, and confirms with the second step; the button is destructive. The founder has no other extra power.
  • Transfer founder. The entity card offers Transfer founder to the founder alone, with a kv line "Founding owner: you". Its confirmation picks among the current owners, says the founder stays an owner, and notifies every owner. Stepping down is this action.
  • An approver leaves mid-request. Their approval stops counting and they stop being required. If the rest have approved, the requester gets "Every remaining owner has approved … Confirm to send the invite." with Confirm and send and Withdraw; nothing applies on its own.

5.13 Account deletion

Story (PRD §5): Every entity gets a choice, a founder names a successor, and nothing applies until the end. Source: flows/account-deletion-flow.md.

flowchart TD
  start([Settings: Delete account]) --> check[Confirm it's you]
  check --> list[Your entities, in three groups]
  list --> succ[Founded, with other owners:\nname a successor founder]
  list --> sole[Only you own it:\ntransfer to a member,\nor purge after an export]
  list --> leave[Other owners remain:\nyou leave, they are told]
  succ --> final{Every entity has\na choice; confirm?}
  sole --> final
  leave --> final
  final -- cancel --> nothing([Nothing changes])
  final -- confirm --> run[Successors and transfers,\nthen purges, then the account]
  run -- a bank revoke fails --> stopped([Stops at that entity;\naccount kept; retry])
  run --> done([Account deleted;\nconfirmation email])
  • Choices first, effects last. One dialog collects every choice; nothing applies until Delete my account, which stays unavailable until every entity has a choice and asks for the second step. Cancel at any point changes nothing. Transfer is never preselected.
  • 1. Name a successor founder. For each entity the user founded that has other owners: a select among those owners, with one line on why ("The founder breaks a deadlock over removing a co-owner, so someone must hold it."). An entity the user co-owns but did not found needs no step.
  • 2. Entities only you own. Each takes Transfer to a member… (that member becomes owner and founder) or Purge, after an export. The transfer select lists the entity's members; one without a second step is listed disabled, "needs a second step", because the new owner must hold owner in force. With no member eligible, only Purge is offered. A purge choice shows its export once ready, with the ledger fingerprint line, or "none, no entries are posted yet" for an entity with no posted entries.
  • 3. Entities you leave. Listed by name, with the note that their other owners are notified.
  • A failed bank revoke stops the run at that entity: entities already purged stay purged, the rest are untouched, the account is kept, and the user sees which entity stopped it.
  • The plan belongs to this sign-in. Another session, or signing in again, starts from the list; if the 5-minute check lapses mid-run, Confirm it's you appears again.
